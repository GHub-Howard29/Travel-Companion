## 3. 程式流程檢查

主要檔案：`src/hooks/useAppUpdate.ts`、`src/components/UpdatePrompt.tsx`、`vite.config.ts`。

- 更新流程在讀取版本政策及執行 `registration.update()` 後，等待 waiting／active replacement 狀態。
- 更新流程先執行 `registration.update()`，再由 `waitForUpdateWorkerReady()` 等待新版 worker 可接管。
- 原本 `hasActivatedReplacement()` 只檢查 active 是否已替代舊 controller 且狀態為 `activated`，未要求 `registration.waiting`／`registration.installing` 都清空。此條件可能讓 ready helper 在 active 已變更、但仍有另一個 installing worker 且沒有 waiting worker 時提前回報 ready。
- 後續程式原本以 `registration.waiting ?? registration.installing` 作為 `expectedWorker`，並呼叫 `updateServiceWorker(false)`。Prompt 模式的 `SKIP_WAITING` 需要實際存在的 waiting worker；若拿到的只是 installing worker，可能沒有 worker 接收該訊息，handoff 就會持續等待並在 12 秒後回報逾時。此為從程式分支推得的高可信競態，手機端當時的 worker 物件狀態仍未直接取得。
- 使用者手動關閉／重新啟動後能進入 V3.10.10，與「更新過程沒有成功送出／完成 SKIP_WAITING；舊 client 關閉後 waiting worker 才有機會啟用」的推論相符，但仍需 Android 實機證據確認。
- 原流程另外在呼叫 `window.location.reload()` 前就寫入「已更新版本」儲存值，沒有在新 document 啟動後確認 `APP_VERSION`；即使 reload 未完成，也可能先記錄成功。
- 現行 `vite.config.ts` 使用 `registerType: 'prompt'`、`clientsClaim: true`，此設定本身不能證明 reload 一定成功。

## 6. V3.10.11 修正實作

### 版本設定

- `src/config/appVersion.ts`、`package.json`、`package-lock.json` 與 `public/app-version.json` 已統一為 `3.10.11`。
- `PREVIOUS_RELEASE_VERSION` 設為 `3.10.10`；`src/config/versionHistory.ts` 已補入 V3.10.10 作為上一個已發布版本。
- minimum supported version 維持 `3.9.27`，force update 維持 false；本版不改成必要更新。
- Release note：修正 Android App 更新後無法自動重新載入新版的問題。

### Service Worker ready／handoff 修正

- 新增 `src/utils/serviceWorkerUpdatePolicy.ts` 的 `hasStableActivatedReplacement()`，統一定義穩定 active replacement：active 必須與舊 controller 不同且為 `activated`，同時 `waiting` 與 `installing` 都必須為 null。
- `waitForUpdateWorkerReady()` 不再只因 active 已改變就提前回報 ready；若仍有 installing／waiting 狀態，繼續等候狀態收斂。
- 真正進入 `SKIP_WAITING` 流程前，只接受 `registration.waiting` 作為 `expectedWorker`；不再把 `registration.installing` 當成可接收 `SKIP_WAITING` 的 worker。若狀態在檢查時已消失，顯示「新版尚未進入可接管狀態」，保留舊版並允許稍後再試。
- 保留既有 12 秒 handoff 窗口、單次 `updateServiceWorker(false)`、唯一 `reloadOnce()` owner；不以延長 timeout 或第二次 SKIP_WAITING 掩蓋競態。

### 新頁面版本確認

- waiting-worker 分支在送出單次 `SKIP_WAITING` 前先寫入 `travel_companion_pending_update_version`，不提前寫入已更新版本；activated replacement 分支則在直接 reload 前寫入同一 marker。
- 即使舊頁面沒有在 handoff 時限內觀察到 controllerchange，但 worker 隨後已啟用並由使用者重新啟動，新 document 仍可讀取 pending marker。
- 新 document 啟動時由獨立 `useEffect` 執行確認，不依賴 standalone／release notice UI 是否顯示；只有當 pending version 與新 bundle 的 `APP_VERSION` 相同，才寫入已更新版本並清除 pending marker。不同版本 bundle 保留 pending marker。
- 若 reload 後仍是舊 bundle，pending marker 保留，且一般版本政策仍可顯示更新提示；不會誤報成功，也不會讓使用者失去重試入口。
- 已儲存的 Trip、清單、帳本與附件資料不清除，不變更 Offline First 資料策略。

### 自動化測試

- 新增 `scripts/verify-v31011-pwa-reload-confirmation.mjs`，直接測試穩定 active replacement 的多種狀態組合，包含 active + installing、active + waiting 不可當成穩定 replacement；並驗證新 document 透過啟動 effect 確認 pending version，且不同版本 bundle 不清除 marker。
- 新測試已加入 `npm run build` 必要驗證群組。
- 更新 `verify:v3924-update-handoff` 與 `verify:v3913-update-race`，保留原有 handoff／資料 preflight 契約，並改為驗證 pending version 與 waiting-only handoff。

## 10. 結論

PWA reload 問題與帳本紀錄者顯示問題是兩個不同議題。本次帳本問題已確認正式資料正確，前端因空 metadata map 遮蔽授權載入的 detail map 而顯示錯誤；本機程式修正與 targeted regression、TypeScript、ESLint 通過。仍待正式 App／Android 載入新版後實機確認 Howard 顯示正確。不得把本機通過宣稱為已部署或已完成手機驗收。

原 PWA 更新結論：本次除了修正 reload 前過早記錄更新成功，也找到一條更可能直接造成原始 12 秒逾時的程式競態：ready helper 可能在仍有 installing worker 時提前回報 ready，接著卻沒有 waiting worker 可送出 SKIP_WAITING。V3.10.11 已收斂 stable active replacement 與 waiting-only handoff，並以新 document 啟動確認版本更新成功。Android 真實跨版本實機驗收尚未執行，不得宣稱已正式排除。
