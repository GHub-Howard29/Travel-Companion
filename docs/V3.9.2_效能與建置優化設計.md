# V3.9.2 效能與建置優化設計

> 本文件記錄 V3.9.2 規劃中關於「測試腳本瘦身」與「離線冷啟動優化」的設計規劃。

## 1. 測試腳本 (`verify:*`) 瘦身規劃

### 1.1 盤點分析
目前 `package.json` 包含超過 35 個 `verify` 指令，其中多數為舊版專項驗證，導致 `npm run build` 前置驗證時間過長。

### 1.2 瘦身策略
- **分級歸檔**：
    - **核心驗證 (保留)**：`update-policy`, `release-history`, `browser-security`, `itinerary-*`。
    - **歸檔驗證 (移出 build 流程)**：`v362-trip-lock`, `v363-front-end`, `v364-*`, `v365-performance` 及 V3.9.1 之前的專項測試。這些驗證改為在需要進行深度回歸時手動執行，而非強綁在 `npm run build`。
- **流程優化**：建立綜合驗證指令 `npm run verify:core`，將核心測試集中管理，簡化 CI/CD 建置邏輯。

---

## 2. 離線冷啟動與載入效能優化

### 2.1 觀測指標 (Baseline)
在進行任何優化前，將於開發環境記錄以下冷啟動時間：
- **T0 (Service Worker Ready)**：SW 激活完成時間。
- **T1 (First Contentful Paint)**：側邊欄與頁首渲染完成時間。
- **T2 (Interactive)**：行程列表資料載入與 IndexedDB 初始化完成時間。

### 2.2 優化方向
- **資料分流**：評估在離線冷啟動時，是否應採用「分頁載入」或「只載入當前 Day」的方式，減少一次性讀取大量歷史行程資料對 IndexedDB 的壓力。
- **快取機制**：檢視 Service Worker 策略，確保關鍵資產在冷啟動時優先獲取。

---

## 3. 實作步驟
1. 盤點所有 `verify` 腳本的依賴，確認歸檔後對系統穩定性的影響。
2. 在 `src/main.tsx` 埋入 `performance.mark` 追蹤點。
3. 根據觀測結果，輸出優化方案並經 Product Owner 確認。
