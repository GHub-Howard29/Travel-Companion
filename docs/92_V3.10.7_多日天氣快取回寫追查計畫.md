以上資料證明後續日期確實進入了快取資料列並留下刷新失敗記錄；不能用「沒有選中目標」或單純舊快取缺欄位解釋。旗津的資料結果與使用者先前回報的畫面不完全一致，應以同一次測試的 trace／卡片 ID 再對齊，不可把它當成已完全重現或已修復。

1. Edge Function 取得／讀取座標快取。
2. `tc_weather_claim_lease(place_id, forecast_date)` 為每個地點日期取得獨立 token。
3. 呼叫 Open-Meteo，建立含座標、日期、來源網址、時區及天氣欄位的結果。
4. `tc_weather_release_lease(..., p_success=true)` 寫入預報；RPC error 或回傳非 `true` 都會被收斂成 `WEATHER_CACHE_WRITE_FAILED`。
5. 失敗處理再嘗試以同一 token 釋放 lease 並寫入失敗碼。

優先假設（尚未確診）：

- **A. 成功回寫 UPDATE 未命中**：本機 migration 的成功分支除了 token／日期條件，還要求座標快取列為 valid、未過期，且緯經度與 payload 完全相同。UPDATE 未命中會回傳 false；目前呼叫端把 false 與 SQL/RPC error 合併成同一錯誤碼。
- **B. lease/token 競態或逾時**：不同日期各有 lease，但同一地點跨日並行取得座標與回寫；需核對各 trace 的 claim／release 時序及正式函式定義。
- **C. migration history 漂移**：原始失敗發生時 `weather-forecast` 為 ACTIVE version 8；安全診斷版目前為 ACTIVE version 9。正式 DB 已有 `source_url` 欄位、約束與對應函式內容，但 `supabase_migrations.schema_migrations` 沒有 `20261018100000`。函式內容比對與本機核心邏輯一致，因此這是獨立的發布追蹤風險，不能直接視為本次失敗根因。
- **D. 其他資料庫約束／型別錯誤**：需取得 RPC 的安全錯誤碼與資料庫 SQLSTATE；不可從 `WEATHER_CACHE_WRITE_FAILED` 單一訊息推斷。

## 5. 2026-10-18 前後端回應對卡片對應追查

- 已唯讀檢查 `src/services/weatherForecastService.ts`、`src/components/ItineraryPage.tsx` 與 `supabase/functions/weather-forecast/index.ts` 的相關程式鏈，沒有修改程式。
- 前端送出的每個項目含 `card_id`、`place_id`、`day_number`、`forecast_date`；Edge Function 以卡片 ID 建立 `request_id`，依 `place_id + forecast_date` 去重取得一次結果，再把結果的 `request_id` 對回每張卡片；前端再驗證 `request_id`、`place_id` 與 `forecast_date`，並以卡片 ID 存入狀態。這段欄位契約目前看起來一致，**尚未找到可直接判定為根因的前後端映射錯誤**。
