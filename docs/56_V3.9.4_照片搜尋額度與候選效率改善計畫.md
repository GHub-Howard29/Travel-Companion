# V3.9.4 照片搜尋額度與候選效率改善計畫

> 狀態：規格已定案；Commons 改善已完成本機實作與靜態驗證，Pexels 隔離 metadata 矩陣已完成，自行上傳與新版裁切尚未實作，尚未發布
>
> 本文件核准本機程式與文件實作；Pexels 外部矩陣已依 2026-09-18 單次授權執行。第三方 key、production 變更、部署或發布仍未獲核准。
>
> **來源使用定案：** 正式入口只保留 Wikimedia Commons 與「自行上傳」。Pexels 隔離矩陣只保留為研究紀錄，不接入 App；Pixabay 永久取消，不保留 UI、API、設定或未來啟用入口。

## 1. 問題定義

V3.9.4 聚焦兩個可觀測問題：

1. 搜尋工作容易消耗現行 Commons 專案級用量預算，使用者可嘗試的次數不足。
2. 一次搜尋完成後，可顯示的相關照片經常少於 6 張，換一批後仍可能沒有足夠的新候選；上游請求數與實際可採用候選數不成比例。

本版不以「直接提高額度」作為預設答案。必須先分辨消耗來自實體解析、分類展開、metadata 查詢、重複候選、硬篩淘汰、空結果或換批，再決定調整預算或演算法。

## 2. 先建立的基線

使用既有 `commons_precision_usage_daily` 彙總與隔離矩陣，補齊以下指標；不得保存搜尋詞、QID、Trip、卡片或使用者操作明細：

- 每次搜尋的上游請求總數與各階段占比。
- 第一批 `hit@6`、至少 3 張命中率、零候選率及 `no-suitable-image` 比例。
- 原始候選數、硬篩淘汰數、重複淘汰數、最後可見候選數。
- 每張可見候選平均耗用的上游請求數。
- 首批及換一批的平均／p95 延遲、快取命中率、配額拒絕率。
- 相同 page ID／檔名跨證據來源重複率，以及換批新增候選率。

只在取得新的 External-mode 單次授權後才能執行 Wikimedia 真實矩陣；未授權時只用離線 fixture、純函式與本機 synthetic Edge 回應。

## 3. 改善方案候選

### 3.1 先降低無效請求

- 將 QID、P18、P373、Commons category 與直接搜尋得到的 page ID 先正規化並全域去重，再查 metadata。
- 同一搜尋工作共用實體解析與分類結果，避免換批重跑前段步驟。
- 對已證明無候選的實體／分類建立短效 negative cache；不得把 quota、timeout 或上游錯誤誤存成空結果。
- 每一階段設定請求預算；已取得 6 張強候選時提早停止，不為填滿內部候選池繼續請求。
- 先批次取得必要 metadata，再依證據強度排序；避免對已重複或明顯不合格項目逐張查詢。

### 3.2 提高相關候選產出

- 維持實體證據優先順序，先擴充同一已選 QID 的 P18、P373 與直接相關分類，不自動切換到其他同名實體。
- 在不降低硬篩安全線的前提下，檢查目前過早淘汰的規則，分開「證據不足」與「已知不相關」。
- 續頁 token 保存去重集合與階段游標，使換一批只取新候選，不重跑已消耗的頁面。
- UI 明確顯示「本批找到 N 張」及可否換批；額度耗盡、上游失敗與確實無結果保持不同狀態。

### 3.3 額度治理

- 先以基線證明每次成功搜尋的合理請求成本，再提出每分鐘／每日硬停的新值。
- 若只是重複或無效請求造成不足，優先修正效率，不調高額度。
- 若改善後仍無法達到核准的候選命中目標，才提出小幅、可回復的額度調整，並保留 20% 以上安全緩衝。
- 所有新額度須同時評估 Wikimedia 使用禮節、Supabase Edge／Database 用量、快取容量與濫用風險；不得自動升級付費方案。

## 4. 分階段交付

1. **觀測契約**：補齊不含敏感內容的階段用量與候選產出統計，先用離線測試確認。
2. **純函式優化**：全域去重、階段預算、提前停止、續頁新候選率與 negative cache 分類。
3. **隔離本機整合**：本機 Supabase、synthetic Edge、快取／配額／鎖與桌面／390×844 狀態回歸。
4. **受控外部矩陣**：另行取得單次授權後，以既有代表性地點矩陣比較修改前後指標；不寫 production Trip、Storage 或快取。
5. **額度決策**：以數據決定維持或調整硬停；Product Owner 核准後才能修改額度。
6. **發布閘門**：完整 build、production preflight、費用與安全說明、發布授權分開處理。

## 5. 驗收門檻（待基線後定值）

- 不降低既有同名實體選擇、設施級安全停止、授權資訊與人工確認邊界。
- 換一批不得回傳已顯示過的 page ID；相同搜尋不得因重試繞過配額或單一上游鎖。
- quota、timeout、上游錯誤與真正無結果不可混為同一狀態。
- 需要數值門檻的 hit@6、零候選率、每張候選請求成本與 p95 延遲，須以核准的基線矩陣定案；本文件不先虛構改善百分比。
- 外部實測、production migration、Edge 部署、額度調整與第三方 key 均各自需要明確授權。

## 6. 定案行為

- 精確搜尋首批為零張且仍有續頁時，自動再查一批；第二批之後一律由管理者手動繼續。
- 每個加密搜尋 session 累積上限為 12 次上游請求、30 秒處理時間與 40 個已檢查檔案；續頁不得重設預算。專案級 20／分鐘、900／日維持不變。
- 精確候選最多保留 12 張。仍有精確續頁時不得取得延伸候選；精確層耗盡後才顯示「載入延伸候選」。
- 延伸候選只讀取直接 Commons 分類的一層子分類；完整名稱或該一層分類關係均可形成可稽核證據。每批最多 6 張，新批次取代延伸區舊圖，不影響精確候選區。
- 延伸候選可包含地點整體、景觀及可辨識內部場景；仍由管理者人工判斷，並保留作者、授權、來源頁與放大檢視。
- 搜尋範圍只顯示「已辨識搜尋範圍：{名稱}」及「修改上方搜尋詞可重新判定範圍」，不自動覆寫搜尋詞，也不提供冗餘的「變更關鍵字」按鈕。

## 7. 桃園機場驗收案例

本機離線案例使用「桃園國際機場」／`Taiwan Taoyuan International Airport`，驗證：

1. 精確續頁存在時不開放延伸候選。
2. 精確層耗盡後，可由管理者手動載入一層相關分類。
3. `Interior of Taiwan Taoyuan International Airport` 可形成 `related-category` 證據並產生最多 6 張延伸候選。
4. 再換一批時只替換延伸區，精確候選仍保留且總數不超過 12 張。
5. 所有候選仍保留作者、授權及 Commons 來源頁；此案例完全使用 synthetic payload，不連線 Wikimedia。

## 8. Pexels 隔離閘門

- V3.9.4 不正式啟用 Pexels；只準備隔離命中矩陣。Pexels key 必須由管理者手動設定在 server-side secret，不得出現在前端、文件或測試輸出。
- 真實矩陣需另取得單次外部測試授權，並事先列出查詢集合、請求上限、逾時、重試與寫入政策；不得寫 production Trip、Storage、快取或資料庫。
- Commons 的發布判斷不依賴 Pexels 矩陣。Pixabay 已永久取消，不再進行測試、實作或啟用評估。

### 8.1 隔離矩陣工具

- `node scripts/spikes/evaluate-v394-pexels-isolated.mjs --plan` 只列出案例與限制，不讀取 key、不連線外部服務。
- 真實執行前須由管理者在程序環境設定 `PEXELS_API_KEY`，並在取得當次單次授權後設定一次性確認值；工具不接受命令列 key，也不輸出 key。
- 固定 12 個地點、中文／日文與英文各一組，共 24 個依序請求；每次只取前 6 筆、10 秒逾時、無重試、無圖片下載，最多 24 次請求。
- 第一個案例固定為桃園國際機場。輸出只寫入 Git 忽略的 `supabase/.temp/v394-pexels-isolated-matrix.json`，候選先標記為待人工判讀，不自動宣稱 hit@3 或可用率。
- 2026-09-18 重查官方文件：API key 置於 `Authorization` header；預設限制仍為 200 requests/hour、20,000 requests/month，成功回應提供 `X-Ratelimit-Limit`、`X-Ratelimit-Remaining`、`X-Ratelimit-Reset`。工具只記錄這三個額度 header，不記錄 request header 或 key。
- 報告必須保留 Pexels 照片頁、攝影者與攝影者頁面，供人工命中判讀及後續 attribution 設計；隔離矩陣通過前不接入 App UI。

### 8.2 2026-09-18 隔離矩陣結果

- 已完成固定 24 次順序請求：12 個地點各以原生名稱與英文名稱查詢一次；無重試、無圖片下載、無 Supabase／production／Storage／快取寫入。
- 24 個查詢皆完成；23 組回傳 6 筆、1 組回傳 5 筆。單次 API 延遲為 361–736 ms，平均 547 ms，p95 為 730 ms。
- 桃園國際機場的中文查詢前 6 筆文字描述皆明確指向桃園機場；英文查詢前 3 筆內亦有明確命中，但同批混入松山機場與泛用機場照片，證明候選仍須逐張人工確認。
- 只依各查詢回傳的 `alt` 文字嚴格判讀，不跨語言補證時，24 組中有 11 組在前 3 筆出現可辨識的精確實體；這 11 組均屬桃園國際機場、熊本城、高千穗峽、首里城、沖繩美麗海水族館或萬座毛等知名地點。
- 以地點為單位，6 個知名地標／景點均至少有一組語言可辨識精確命中；OTS 臨空豐崎營業所、那霸日航城市飯店、福助玉子燒飯糰、琉球新麵通堂小祿本店、肉餐廳肉久名護店及 BANTA CAFE 等 6 個商業地點，均未從文字 metadata 找到精確實體證據。
- 本輪沒有載入候選圖片，因此上述結果是 **metadata 初判**，不能視為圖片內容、構圖或代表性已通過人工驗收；結果檔仍保留 24 組 `manualReview: pending`。
- 決策：Pexels 隔離矩陣不通過「通用照片來源」閘門，結果只保留為研究紀錄，不接入 production 或 App UI，也不再安排正式啟用。商業地點不得以泛用同類照片冒充精確實體。

## 9. 自行上傳與裁切定案

### 9.1 來源入口

- 照片來源只顯示「Wikimedia Commons」與「自行上傳」；移除目前停用的 Pexels、Pixabay 選項。
- 「自行上傳」提供「拍照」與「從裝置或圖庫選擇」兩個入口。後者使用瀏覽器／作業系統原生檔案選擇器，可使用裝置已整合的相簿、iCloud、Google Drive、OneDrive 等來源；App 不另接雲端硬碟 OAuth 或 API。
- 不提供貼上任意圖片網址，也不由 Edge Function 或其他伺服器代抓任意網址。
- 上傳介面須以紅色醒目文字顯示：**「請勿上傳侵權圖片，亦不得任意下載、複製或重製他人照片。」** 不另增加授權審核表或強制勾選聲明。
- 自行上傳的封面來源標示為「自行上傳」，不偽造 Commons 作者、授權或來源頁欄位；只保存最終處理後的 WebP，不保存來源原檔或中間檔。

### 9.2 76×76 預覽與縮放

- 76×76 為每日行程卡片的正方形最終預覽框；實際保存仍輸出 640×640、最多 120 KiB 的 WebP，避免把檔案降成 76×76 後在高密度螢幕模糊。
- 縮放的 `100%` 定義為前景照片完整置入正方形框，整張來源照片皆可目視；最大放大比例為 `250%`。
- 非正方形照片在 `100%` 產生的上下或左右空間，以同一張來源照片的滿版模糊延伸背景補足；不得使用其他照片或生成式內容補圖。
- 前景照片可用滑桿、加減按鈕、滑鼠／觸控拖曳、手機雙指縮放及鍵盤控制，在 `100%`～`250%` 間調整大小與位置；背景維持滿版並隨最終結果一起輸出。
- 拍照與圖庫選擇完成後均進入同一裁切步驟；儲存前顯示 76×76 卡片效果，確認後才建立並上傳 640×640 WebP。

### 9.3 驗收案例

1. 相機與系統圖庫／檔案選擇器均可進入同一裁切流程；不支援相機的裝置須正常退回原生選檔行為。
2. 橫向與直向非正方形照片在 `100%` 都能完整顯示，空間由同圖模糊背景補足，不能出現透明、白色或黑色裸露區。
3. 縮放控制可到 `250%`，縮回下限時準確回到完整原圖；按鈕、滑桿、雙指與鍵盤結果一致。
4. 最終卡片以 76×76 顯示，但 Storage 只保存 640×640 WebP；重新載入及跨裝置後構圖一致。
5. 自行上傳流程全程顯示紅色侵權提醒；已保存卡片顯示來源為「自行上傳」，不出現虛構作者或授權連結。
