# V3.9.19 正式發布收尾與 V3.9.20 文件合併操作手冊

> 建立日期：2026-09-30
>
> 單次啟動關鍵詞：**執行3.9.19收尾**
>
> 適用情境：V3.9.19 已完成 RC，且 gh-pages 曾部署 3.9.19 候選版，但正式 source／main／tag 收尾尚未完成；另一台電腦可能仍保有未提交的 V3.9.19 source。
>
> 這份手冊的優先原則是：**先保住另一台電腦的 V3.9.19 source，再完成正式發布；最後才把 V3.9.20 文件規劃合併回 develop。**

## 已知基準

- V3.9.18 已正式發布。
- V3.9.19 RC 已完成。
- gh-pages 已存在 V3.9.19 候選部署 commit：`c0a42db`。
- 目前這台電腦先前看到的 `origin/develop` 尚未包含 V3.9.19 source commit。
- V3.9.19 內容已凍結，不再加入新功能。
- V3.9.20 已規劃為「其他資訊自訂子類別」，但尚未實作。
- V3.9.20 規劃文件已隔離在分支：`docs/v3920-category-planning`。

## 收尾時禁止事項

在確認另一台電腦的 V3.9.19 source 已安全保留之前：

- 不執行會覆蓋工作目錄的 hard reset。
- 不執行 checkout／switch 到會丟失未提交變更的分支。
- 不執行 clean 移除未知檔案。
- 不 rebase 未提交工作。
- 不直接把 V3.9.20 文件分支 merge 進 develop。
- 不新增 V3.9.20 程式碼。

## 第一階段：保護另一台電腦的 V3.9.19 source

收到「執行3.9.19收尾」後，先在另一台電腦目前的 Travel-Companion repository 執行唯讀檢查：

1. 確認目前目錄與分支。
2. 檢查 `git status --short`。
3. 檢查 `git log -10 --oneline --decorate`。
4. 檢查 `git reflog -30`。
5. 檢查 `git stash list`。
6. 檢查是否有其他 branch／worktree。
7. 確認 V3.9.19 相關 source 是否存在於工作目錄、未提交變更、local commit、stash、reflog 或其他 worktree。

只要找到未提交的 V3.9.19 source，**先不要 pull、reset 或切分支**。

## 第二階段：確認 V3.9.19 source 是否就是 RC 版本

找到 source 後：

- 確認 package／app version 預期為 3.9.19 或可明確辨識為 V3.9.19 RC source。
- 檢查 V3.9.19 專項變更是否存在。
- 執行對應的專項驗證、lint、build 與必要 regression。
- 將新 build 產物與既有 gh-pages V3.9.19 候選版進行合理比對。
- 若 source 與既有 RC 候選版不一致，先判斷差異來源，不直接發布。

## 第三階段：補齊 V3.9.19 Git 歷史

只有在 source 確認正確後才進行：

1. 將 V3.9.19 source 與對應文件整理成正式 commit。
2. push 至 `origin/develop`。
3. 確認遠端 develop 已包含完整 V3.9.19 source。
4. 依既有 release 流程合併到 `main`。
5. 建立 annotated tag：`v3.9.19`。
6. push main 與 tag。
7. 不回寫既有已發布版本；所有修正向前處理。

## 第四階段：完成 V3.9.19 正式發布驗證

正式發布完成前至少確認：

- 正式 source commit 可追溯。
- `origin/main` 指向正確 V3.9.19 發布內容。
- `v3.9.19` tag 指向正確發布 commit。
- GitHub Pages 正式部署成功。
- 公開 `app-version.json` 為 3.9.19。
- fresh-load UI 顯示版本正確。
- 首頁與核心資產可正常載入。
- 必要的 PWA／更新 smoke 通過。
- 發布紀錄、專案現況與版本歷史文件更新完成。

## 第五階段：合併本次 V3.9.20 文件規劃

V3.9.19 正式發布完全收尾後：

1. 回到 `develop`。
2. `git pull --ff-only` 取得最新 V3.9.19 develop。
3. fetch 遠端文件分支。
4. 合併 `docs/v3920-category-planning` 到 develop。
5. 若文件因 V3.9.19 收尾已有變更，逐項解 conflict，不覆蓋最新發布事實。
6. 執行 `npm run verify:docs-links`。
7. 確認 Git diff 只包含預期文件整合。
8. push 更新後的 develop。

合併完成後，V3.9.20 才正式進入可開發狀態。

## V3.9.20 接續開發基準

V3.9.20 名稱：**其他資訊自訂子類別**

已定案範圍：

- 沿用「其他資訊管理」入口。
- 可新增、改名、拖曳排序、顯示／隱藏子類別。
- 顯示使用眼睛，隱藏使用斜線眼睛。
- 切換時顯示約 1 秒「已顯示／已隱藏」toast。
- 自動排列每列最多 3 個。
- 換行後由少字元到多字元優先。
- 長名稱放不下直接換行，不壓縮字寬。
- 自動排列規則預設收合。
- 隱藏不得刪除既有資料。
- 原 V3.9.20 時間重算計畫後續再因 PWA 更新修復插版，目前順延為 V3.9.22。

完整規格見：
- `67_V3.9.20_其他資訊自訂子類別規格.md`
- `68_V3.9.22_排序後續時間重算評估紀錄.md`

## 單次指令語意

當 Product Owner 在另一台電腦輸入：

**執行3.9.19收尾**

代表授權依本手冊執行 V3.9.19 收尾工作，包含必要的檢查、source 保護、驗證、commit／push、main 合併、tag 與正式發布驗證；完成後再將 `docs/v3920-category-planning` 合併回 develop。

如果當下狀態與本手冊前提不一致（例如 source 找不到、內容與 RC 候選版不一致、存在不明未提交變更或發布驗證失敗），應先停在安全狀態並說明差異，不得強行發布。
