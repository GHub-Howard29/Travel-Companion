# 先前方案草案：原 V3.9.0 使用者使用紀錄與開發者二次驗證

- 原排程版本：V3.9.0；目前不排入實作
- 現行方向：見《37_V3.10.0_使用紀錄重新評估草案》
- 本文件只保留先前需求、介面與安全設計供追溯，不代表目前核准範圍；不得據此修改資料庫、正式 UI、版本 metadata 或部署

## 1. 目標與版本邊界

- 提供低風險的 App 使用紀錄，供日後排查登入／使用頻率，不建立跨站或裝置指紋追蹤。
- 本功能包含資料庫、獨立權限、TOTP 二次驗證與新管理介面，屬 Minor 功能，排入 V3.9.0，不使用 V3.7.5，也不併入 V3.8.0。
- 本階段只保存設計文件；不得新增 migration、修改正式 UI、調整 App 版號或部署。

## 2. 紀錄範圍與隱私原則

### 2.1 有效使用工作階段

- 已登入使用者在線上開啟 App，且 Supabase session 可成功驗證時，才嘗試建立使用紀錄。
- 同一隨機工作階段 ID 在 30 分鐘內因重新整理、重新連線、多分頁、重試或併發請求產生的事件，只計為一次。
- 超過 30 分鐘後再次開啟或使用，計為新的有效工作階段。
- 純離線開啟不記錄，也不在裝置暫存事件等待補送；恢復連線並成功驗證 session 後才可記錄。
- 紀錄採 best-effort；服務失敗不得阻擋登入、行程載入或既有離線功能。

### 2.2 保存資料

永久摘要保存：

- Supabase Auth user ID。
- 正規化後的 Email。
- 首次使用時間。
- 最近使用時間。
- 累計有效工作階段次數。

逐次明細保存：

- Supabase Auth user ID。
- 正規化後的 Email。
- 資料庫產生的使用時間。
- 隨機工作階段 ID，僅供冪等與 30 分鐘去重。

逐次明細只保留最近 180 天，由 Supabase Cron 每日清除逾期資料；首次、最近使用時間與累計次數持續保留。

### 2.3 明確不收集

- IP 位址。
- User-Agent、瀏覽器版本或作業系統版本。
- 裝置類型、裝置型號、裝置指紋或廣告識別碼。
- PWA 模式、位置、時區、語系或鍵盤資訊。
- 行程內容、頁面瀏覽路徑、按鈕操作或功能使用內容。
- Gmail、Google Drive、聯絡人或照片等 Google 帳號資料。

## 3. 系統開發者權限與入口

- 建立獨立 `system_developer` 授權，不納入 Guest、User、`trip_editor` 或 `super_admin` 角色繼承關係。
- 初始且目前唯一系統開發者為 `haw1971@gmail.com`。
- 授權資料同時綁定 Supabase Auth user ID 與正規化 Email；Email 或帳號不一致時採 fail closed，必須完成受控審查後才能更新。
- 未來新增系統開發者，只能透過明確且受控的 migration 或管理 SQL，不因取得 `super_admin` 自動授權。
- 側邊選單入口放在底部區域、版本資訊上方，名稱為「使用紀錄」，並標示「進入時驗證」。
- 只有後端確認為啟用中 `system_developer` 的帳號才顯示入口。其他一般使用者、`trip_editor` 與其他 `super_admin` 均不顯示。
- `haw1971@gmail.com` 登入後可顯示「超級管理員・系統開發者」；其他 `super_admin` 維持原角色顯示。

入口隱藏只負責介面體驗，不作為安全邊界。即使因前端 BUG 顯示按鈕、直接輸入網址或手動呼叫 API，後端仍必須重新驗證完整權限與 MFA 條件。

## 4. TOTP 二次驗證流程

- TOTP 只在 `haw1971@gmail.com` 點擊「使用紀錄」入口時觸發，不影響一般 Google OAuth 登入、App 啟動或其他功能。
- 首次進入時提供 Authenticator QR Code 與手動密鑰，完成註冊後輸入六位數動態碼驗證。
- 之後每次重新開啟使用紀錄頁都必須再次輸入六位數動態碼；不能沿用前一次開頁狀態。
- 查詢 RPC 同時要求 JWT 已達 `aal2`，且 JWT `amr` 中的 TOTP 驗證時間仍在最近 5 分鐘內。
- 關閉或離開使用紀錄頁時，必須清除查詢結果、輸入碼與頁面驗證狀態，不寫入 localStorage 或 sessionStorage。
- QR Code、手動密鑰及六位數動態碼不得寫入前端紀錄、錯誤追蹤或資料庫使用紀錄。
- Supabase TOTP 不提供復原碼；遺失 Authenticator 時須採受控管理流程復原，不建立繞過 MFA 的前端入口。

## 5. 資料庫與縱深防禦

- 授權、永久摘要與逐次明細放在非公開 schema，前端不得直接讀寫資料表。
- `anon`、`authenticated` 與 `PUBLIC` 不具有相關資料表的直接查詢或 DML 權限。
- 對前端僅提供必要 RPC；公開包裝函式採安全呼叫方式，私有權限函式固定安全的 `search_path`，並收斂函式執行權限。
- 「記錄本次使用」RPC 只接受工作階段識別所需資料；Auth user ID、Email 與時間均由資料庫依目前登入者及伺服器時間取得，前端不能指定或修改。
- 永久累計值由資料庫交易內更新，不接受客戶端傳入；工作階段 ID、30 分鐘窗口與唯一限制共同處理重試、多分頁及併發去重。
- 「查詢使用紀錄」RPC 必須全部通過下列條件：
  - `auth.uid()` 有效。
  - Auth user ID 與正規化 Email 同時符合啟用中的 `system_developer` 授權。
  - JWT 驗證層級為 `aal2`。
  - JWT `amr` 中的 TOTP 驗證時間在最近 5 分鐘內。
- 任一條件失敗時，不回傳紀錄，也不揭露資料是否存在。
- 其他 `super_admin` 即使自行設定 TOTP、知道頁面網址或直接呼叫 RPC，也不得讀取資料。

## 6. 先前曾確認的介面設計（目前未定案）

### 6.1 登入安全提示

- 清楚說明紀錄目的為服務維運與使用頻率排查。
- 顯示會保存 Email、使用時間與累計次數。
- 說明逐次明細保存 180 天，永久摘要保留首次、最近時間與累計次數。
- 清楚列出不收集 IP、裝置指紋、位置及行程內容等資訊。

### 6.2 TOTP 設定與驗證

- 首次畫面顯示 QR Code、手動密鑰與六位數驗證欄位。
- 後續開頁只顯示六位數動態碼驗證畫面，並提示每次開啟都須重新驗證。
- 驗證失敗不得載入任何摘要或明細資料。

### 6.3 使用紀錄頁

- 顯示使用者總數與永久累計有效工作階段數。
- 每位使用者顯示 Email、累計次數、首次使用時間及最近使用時間。
- 可查看最近 180 天的逐次使用時間明細。
- 時間以目前裝置所在地顯示；資料庫仍保存 `timestamptz` 絕對時間。
- 離開頁面後，畫面不得保留前次查詢資料。

### 6.4 側邊選單

- 系統開發者：在版本資訊上方顯示「使用紀錄／進入時驗證」。
- 其他使用者與其他 `super_admin`：完全不顯示入口，也不保留空白占位。

## 7. 先前方案的實作驗收條件（目前不執行）

- 驗證首次使用、30 分鐘內去重、超過 30 分鐘重新計數、重試、多分頁及併發情境。
- 驗證離線不記錄、恢復連線後可記錄，且紀錄服務失敗不影響 App。
- 驗證 Email、時間、Auth user ID 與累計值不能由客戶端偽造。
- 驗證一般使用者、`trip_editor` 與其他 `super_admin` 在 UI、RPC 及資料表層全部遭拒，包括已設定 TOTP 的其他 `super_admin`。
- 驗證 TOTP 首次設定、錯誤碼、過期碼、舊 `aal2`、正確驗證、5 分鐘短效窗口及每次重開強制再驗證。
- 驗證超過 180 天的明細會被排程刪除，但永久摘要不受影響。
- 驗證私有 schema、函式權限、固定 `search_path` 與 Supabase advisors。
- 執行 TypeScript、lint、完整 build，以及 Google OAuth、PWA 更新、離線行程與既有角色權限回歸。
- 正式實作前須依當時 Supabase Auth、MFA、Cron 與 Database 文件重新確認 API 與安全建議。
