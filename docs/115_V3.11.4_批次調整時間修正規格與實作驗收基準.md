## 1. 目標與問題範圍

修正每日行程卡片批次調整時間及相關編輯體驗的已確認缺口：

1. 批次路線所需地點資料不完整時，應在預覽前顯示可理解的提示，不把後端「路線查詢資料格式不正確」直接暴露給使用者。
2. 移除不需要的「卡片原地編輯」提示文字。
3. 編輯卡片時，地點搜尋輸入框在沒有有效地圖地點時，可暫時帶入活動標題；未經使用者確認的文字不得成為正式地點。
4. 手動輸入到達時間允許任意合法分鐘，不受系統半小時進位建議值限制。
5. 手動時間依交通可行性判斷，修正合理時間可輸入、改回合理時間卻被拒絕的問題。
6. 確保批次預覽、逐站接受、取消及正式儲存具備一致且可理解的資料生命週期。

## 2. 最小化設計原則

- 不新增逐卡片資料庫寫入；每日卡片仍隨同一筆 Trip content 一次保存。
- 不新增資料庫 schema、migration、Edge Function、Secrets 或正式 DB 操作。
- 只改動本次問題必要範圍；天氣功能既有未提交工作不得混入、覆蓋或還原。
- 批次作業期間固定參與卡片順序；不全面改寫索引結構。畫面 React key 優先使用現有穩定卡片 ID。

## 3. 原始資料與預覽結果

### 3.1 原始資料

- 開始批次調整時，複製一次當日原始卡片資料，供本次批次計算使用。
- 原始資料複本在本次批次期間保持不變。
- 每次手動調整及下游重算均以這份原始資料為基準，不得以之前的預覽結果冒充原始資料。
- 原始到達時間、原始離開時間及原始停留時間不得因重複調整產生累積誤差。
- 預覽結果只更新批次預覽狀態，不直接修改正式行程資料。

### 3.2 取消與結束

- 取消整批作業時，丟棄預覽及接受狀態，回到進入批次前的正式行程資料。
- 只有確認本機正式保存成功後，才結束批次及清除預覽狀態。
- 本機保存失敗或儲存流程丟出錯誤時，保留預覽及接受狀態，讓使用者可以重試或取消。
- 頁面離開／重新整理造成批次中斷時，不得將未確認的預覽寫入正式資料。

## 4. 交通估算沿用規則

- 預覽建立時取得的交通估算沿用現有 `TimeAdjustmentResult.segments` 保存，不另建第二份交通快照。
- 同一批次的手動時間調整與下游重算都使用該批次既有交通估算。
- 正式保存時不得再次靜默查詢並替換預覽使用的估算。
- 一般快取到期與本次預覽估算失效是不同概念；不得只因一般快取期限到期，就自動要求重新查詢或替換已用於本批次的估算。
- 若本次預覽估算因必要識別資料或結構已無法安全使用，阻止保存並提示重新建立預覽；不要在保存流程中暗中換成另一份估算。
- 不增加不必要的地圖服務請求或費用。

## 5. 手動時間及下游重算

### 5.1 手動輸入

- 手動時間允許任何有效分鐘，例如 14:10、14:11、14:30、14:31。
- 手動到達時間的可行性條件為：

  `新到達時間 >= 上一站離開時間 + 本區段移動時間`

- 不得以系統建議時間（例如半小時進位後的時間）作為手動輸入最低門檻。
- 自動建議仍可維持既有半小時進位規則。
- 保留既有跨午夜阻擋規則，不自動將行程移至隔日。

### 5.2 下游重算

- 上游時間變更後，所有下游尚未接受的受影響站點應即時重新計算。
- 每站停留時間使用原始資料複本計算：原始離開時間減原始到達時間。
- 已接受站點若因上游調整而改變時間，必須取消該站的接受狀態，要求使用者重新確認；不可靜默保留已接受狀態。
- 不納入交通計算的卡片依現有規則維持原時間。

## 6. 逐站接受

- 保留目前逐站「接受／調整到達時間」操作及接受狀態 Set，不另建卡片狀態機。
- 使用者按下整批套用前，檢查所有需要接受的變更站點都已接受。
- 尚未接受的必要站點不得進入正式保存。
- 上游改動造成已接受站點的預覽時間變更時，只需使受影響站點重新確認。
- 批次期間參與卡片順序固定，因此現有索引關聯可暫時沿用，不做全面 ID 重構。
- 預覽卡片 React key 改用現有穩定卡片 ID，避免索引或標題變化導致不必要重新掛載。

## 7. 儲存結果與離線行為

目前保存鏈路需區分本機保存與雲端同步結果，不可將雲端未同步誤認成本機保存失敗，也不可把本機保存成功誤報為雲端同步成功。

- 批次作業判斷是否結束，以「本機正式行程資料是否成功保存」為依據。
- 本機保存失敗：保留預覽，不結束批次，允許重試。
- 本機保存成功且雲端同步成功：結束批次。
- 本機保存成功但雲端暫時未同步：依既有離線同步機制結束批次，保留／呈現既有待同步狀態；不得宣稱雲端已同步。
- 修正 `ItineraryPage` → `App.tsx` → `useTripWorkspace.ts` 的結果傳遞，使批次呼叫端能辨識本機保存結果及必要的同步狀態。
- 不為本功能增加新的儲存服務或逐卡片 DB 寫入。
- 若保存前發現行程已被其他裝置或其他流程更新，應使用既有版本／編輯權保護停止本次套用，提示重新載入或確認；不得覆蓋外部更新。

## 8. 地點輸入框自動帶入

- 有有效 Place ID／地圖地點時，不自動覆蓋現有地點。
- 沒有有效地點時，編輯畫面的搜尋輸入框可暫時顯示活動標題。
- 自動帶入的標題只屬搜尋草稿，不是正式 `location` 欄位。
- 使用者選擇並確認有效搜尋結果後，才更新正式地點資料及相關識別資訊。
- 使用者未確認有效地點就儲存時，放棄本次自動帶入的草稿；不得把活動標題保存為正式地點。
- 下次再次進入編輯時，可重新以活動標題帶入搜尋框。
- 不新增持久化欄位來記錄「曾否放棄標題」。

## 9. UI 更新與提示

- 移除「卡片原地編輯」提示。
- 批次預覽以局部狀態更新為主，不重建整頁。
- 使用穩定卡片 ID 作為預覽卡片 React key。
- 不在每次輸入或重算後強制捲動。
- 先以既有焦點及局部更新機制完成，不新增 DOM 管理或焦點復原子系統。
- 瀏覽器驗收確認輸入焦點、游標、捲動位置及展開狀態不會因一般預覽更新而不必要重置。
- 路線查詢等待僅顯示必要局部狀態；較舊的非同步結果不得覆蓋使用者最新輸入所對應的預覽。

   - 其餘既有規則維持不變。此案例為需求基準，實作前仍須核對目前排程 helper 如何表達各段原始預留時間，避免把「交通估算時間」和「原始站間預留時間」混為一談。
4. **非標準時間格式警告待修正。** 使用者輸入不符合標準格式的時間時，畫面目前沒有出現警告；應參照一般卡片時間輸入規則及其既有提醒文案，讓批次調整欄位採用一致的格式檢查與錯誤提示。

**第 3、4 項：尚未驗證**

- 使用者回報第 3、4 項遇到未知問題，要求先更新第 1、2 項紀錄；目前不推定其結果，也不擴大調查。
