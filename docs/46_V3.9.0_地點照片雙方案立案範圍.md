# V3.9.0 地點照片雙方案立案範圍

- 決策日期：2026-09-12
- Product Owner 決策：V3.9.0 同時納入兩個方案
- 方案 A：地點搜尋候選使用 Google Place Photos 暫態索引照
- 方案 B：每日行程卡片由管理者從 Wikimedia Commons 候選中選擇照片
- 狀態：功能範圍、可見文案與桌面／390×844 UI 已核准；正式實作已完成本機驗證，Supabase migration／Edge Function 部署與發布尚待執行

## 1. 不共用來源的雙軌原則

兩個方案解決不同問題，不把 Google 照片保存成卡片封面，也不使用 Commons 圖片判斷 Google 地點候選：

| 軌道 | 目的 | 來源 | 保存 |
| --- | --- | --- | --- |
| Google 候選索引照 | 協助管理者確認候選 `placeId` 是否正確 | Google Place Details／Place Photos | 不保存；只存在當次搜尋記憶體 |
| Commons 卡片照片 | 讓每日行程卡片顯示管理者確認過的知名景點照片 | Wikimedia Commons | 選定後保存受控衍生檔與完整 attribution metadata |

## 2. Google 候選索引照

- 既有 `placeAutocomplete` 先回傳文字候選，候選可立即操作。
- 前端再以同一 Trip、最多 5 個唯一 `placeId` 查詢照片，避免慢圖阻擋文字結果。
- Edge Function 驗證登入者為該 Trip 管理者，截斷超過 5 個的輸入並限制欄位。
- 每個候選最多取第一張 320×180 索引照；無照片、逾時、403、404、429 時保持純文字候選。
- 回傳暫態 `photoUri`、Google Maps URI 與作者 attribution；不得寫入 Trip、Storage、IndexedDB、localStorage 或 Service Worker。
- 每月照片請求達內部軟門檻後停止照片查詢，Autocomplete 仍可使用。

## 3. Commons 管理者選圖

### 搜尋

- 只有可寫入該 Trip 的管理者能開啟選圖；歷史唯讀 Trip 不可新增、更換或移除封面。
- 搜尋詞預設使用卡片地點，但必須可以編輯；中文與英文的命中項目不同，不能只固定一種語言。
- 每次最多顯示 8 個圖片候選，必須由管理者人工確認，不自動採第一張。
- 搜尋只接受 Commons `File:`、`BITMAP` 與可顯示縮圖 MIME；排除分類頁、PDF、音訊、影片及其他文件。
- Action API 的 `extmetadata` 成本較高且實測曾回傳 429；正式 Edge Function 應先用 REST 搜尋，再批次查詢少量 imageinfo，加入 debounce、節流、`Retry-After` 與短期查詢快取。

### 授權白名單

- 接受：Public Domain、CC0、CC BY、CC BY-SA。
- 排除：授權不明、缺作者／來源、缺必要 license URL、GFDL-only、NC、ND、限制欄位非空或非 `BITMAP`。
- 儲存作者、credit、file title、Commons 來源頁、license short name、license URL、原始 MIME／尺寸、來源 revision／SHA-1、選擇時間與是否經縮放／壓縮。
- CC BY／CC BY-SA 顯示作者、來源及授權連結；若輸出經縮放、格式轉換或壓縮，attribution 明確標記已修改。CC BY-SA 衍生圖片沿用相容授權。
- Public Domain／CC0 仍顯示 Commons 來源，保留 provenance 與移除／申訴處理能力。

### 保存與公開讀取

- 不永久 hotlink Commons；官方允許但不建議，且來源刪除或網址變動會造成卡片破圖。
- 使用新的 public bucket，例如 `itinerary-covers`。目前 `public.trips` 對 `anon` 可讀，封面公開讀取與既有 Trip 可見性一致；若未來 Trip 改為私有，兩者必須一起遷移。
- Bucket 只允許最終採用的單一 MIME，候選為 WebP；單檔硬上限 120 KiB。7 張 640px Commons 原縮圖實測平均約 239.8 KiB、只有 1／7 低於 120 KiB，因此選定後必須在瀏覽器縮放／壓縮，再上傳自有 Storage。
- 物件路徑使用既有 UTF-8 hex scope 概念：Trip scope／item scope／隨機版本檔名；不採原始檔名、不覆寫舊物件。
- Storage INSERT／DELETE 僅允許 `tc_can_write_shared_trip(tripId)`；不因 bucket 公開而開放寫入。正式 policy 不使用 `user_metadata`，也不只用 `TO authenticated` 代替 Trip 授權。

## 4. 卡片資料契約候選

Trip item 僅在已選封面時加入 `coverPhoto`：

```ts
interface ItineraryCoverPhoto {
  source: "wikimedia-commons";
  storagePath: string;
  fileTitle: string;
  sourcePageUrl: string;
  creator: string;
  credit?: string;
  license: string;
  licenseUrl?: string;
  sourceSha1?: string;
  sourceRevisionAt?: string;
  selectedAt: string;
  modified: boolean;
  width: number;
  height: number;
  mime: "image/webp";
  size: number;
}
```

- 舊版忽略未知 `coverPhoto`，V3.9.0 讀取時嚴格驗證所有 URL、MIME、尺寸與容量。
- 選圖採「上傳新物件 → 更新 Trip payload → 成功後刪除舊物件」；Trip 更新失敗時回滾新物件。
- 移除封面、刪除卡片、縮短天數或刪除 Trip 時清理物件；清理失敗記錄為可重試 orphan，不讓 Trip 指向不存在物件。
- Product Owner 已核准：跨日複製沿用同一 `coverPhoto` 引用而不複製 Storage 物件；移除、刪除卡片或縮短天數時，只有 Trip 內已無其他卡片引用同一路徑才刪除物件。刪除 Trip 則先清理該 Trip 的照片目錄，再執行既有刪除交易。

## 5. 已確認 UI 與待定可見文案

下列 UI 與可見文案已由 Product Owner 依桌面與 390×844 模擬圖核准；若正式實作需要新增其他畫面或文案，須再次停止確認：

- Google 候選縮圖的位置、大小、載入骨架、無照片狀態，以及作者 attribution 如何從候選卡開啟。
- Commons 選圖入口、可編輯搜尋欄、8 張候選格、授權篩選結果、選取確認與失敗狀態。
- 每日卡片已核准沿用「選擇正確地點」候選的緊湊橫列：左側方形縮圖、中間時間與行程文字、右側管理操作；不使用大幅 16:9 封面。縮圖以 `object-fit: cover` 顯示，原始衍生檔維持比例，並保留圖片來源／作者／授權列、更換與移除入口。
- V3.8.2 跨日複製卡片時一併沿用照片引用；不新增複製提示，最後一個引用移除後由系統清理 Storage 物件。
- 120 KiB 壓縮失敗、授權資料不完整、429、離線與 Storage 同步失敗時的可見文案。
