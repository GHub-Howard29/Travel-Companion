## 已確認問題與下一個決策閘門

1. 已採用詞契約只接受與 Wikidata 正式名稱、別名或 match 完整相等的唯一實體；舊 V3.9.0 泛用 Commons 複合查詢詞不一定是 Wikidata 名稱，因此三個地標與 OTS 在第一層即停止。這不應以自動刪字、翻譯或猜 QID 繞過。
2. 已解析 QID 的四個精確地點與一個上位地點都有原始候選，但全部被硬篩。檢查發現程式把 `CC BY` 的選用 `credit` 誤當必填；核准規格實際要求作者、來源頁及有效 HTTPS 授權連結，`credit` 若存在才受 500 字上限。已依核准契約修正並新增離線回歸測試。
3. V3.9.0 已知 OTS 臨空豐崎營業所的 Commons／Openverse hit@3 為 0，但《50》6.1 的文字把兩個交通案例都列入零候選回歸條件。要變更 OTS 的預期、固定採用詞，或新增人工指定 QID 流程，都會修改已核准驗收契約，不能由實作者自行決定。
4. 本輪單次真實 spike 授權已使用。任何修正後的 Wikimedia 重跑，都必須先核准新的固定範圍與單次授權。

## 第三次前的離線修正

既有 V3.9.0 Commons 流程已將 `thumb.wikimedia.org` 的 HTTPS 縮圖 URL 正規化為 `upload.wikimedia.org`；第二次矩陣的彙總拒絕原因顯示此一致性缺口可能是主要原因之一。精準 pipeline 現已採相同但更窄的規則：只接受 HTTPS，且只把該單一 Commons 舊 CDN 別名改寫為既有白名單 host；其他 host 仍回傳 `invalid-thumbnail-url`，來源頁仍獨立檢查 `commons.wikimedia.org`。離線契約、精準候選契約、TypeScript、lint 均已通過。

此修正尚未重跑 Wikimedia，因此不宣稱已改善命中率；需先取得第三次固定 15 例、最多 135 次、順序且零寫入的單次授權。

完整 production build 亦已在此修正後通過。V3.9.0 的靜態回歸驗證已從舊的 `gsroffset` 呼叫更新為目前的精準 action／不透明 token 邊界；公開候選投影驗證則補齊既有資料契約中的縮圖 MIME、來源 SHA-1 與來源修訂時間欄位。
