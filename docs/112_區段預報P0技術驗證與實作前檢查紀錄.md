### 2.1 Open-Meteo 真實 API payload

本節合併記錄既有正式 Forecast API 與 Historical Forecast API 證據；兩者用途不同，不可混為同一項測試，也不因新增區段摘要功能而重複執行已完成的 API 驗證。

**正式 Forecast API（既有正式端點驗證，非本輪重測）：**先前已透過公司端 Chrome 直接取得 `https://api.open-meteo.com/v1/forecast` 真實回應，測試座標為東京（`35.6812, 139.7671`）、日期 `2026-11-20`，請求使用 `hourly=temperature_2m,precipitation_probability,weather_code`、`start_date=end_date=2026-11-20`、`timezone=auto`、`timeformat=unixtime`、攝氏、`models=best_match`、`cell_selection=land`。回應確認 `timezone=Asia/Tokyo`、`utc_offset_seconds=32400`、hourly 三欄均存在且各有 24 筆，`time` 為 Unix Epoch 秒數。這已證明 production `/v1/forecast` 可提供本功能所需的 hourly 欄位及時間資料格式；API 未變更，故不重新呼叫相同端點重測。

**Historical Forecast API（本輪 UTC／DST 方法驗證）：**透過公司端 Open Browser Use 直接請求 Historical Forecast API，取得東京 2026-11-20 真實 hourly response。PowerShell 直接對外請求因 TLS／連線重置失敗，故改由已登入 Chrome 的 Browser Use 取得；這是測試取數路徑差異，不代表 Open-Meteo API 本身不可用。此歷史端點用於驗證 UTC 時窗、DST 與真實 hourly payload 篩選，不取代上述正式 Forecast API 證據。

Historical Forecast 東京真實回應觀察：

- 回應座標 snap 至模型網格約 `35.7, 139.75`，IANA timezone 為 `Asia/Tokyo`。
- `hourly.time` 為 Unix 秒數，包含 24 個連續小時。
- 三組欄位為 `temperature_2m`、`precipitation_probability`、`weather_code`，陣列長度與 time 相符。
- 用 08:00–12:00 inclusive 五筆資料計算摘要：temperature max 13.1°C、min 10.8°C、precipitation probability max 0、weather code 0。
- `precipitation_probability` 表示每小時前一小時降水超過 0.1 mm 的機率；區段摘要取區段內各小時機率最大值，不應稱為整段累積降雨機率。

官方來源：Open-Meteo [Forecast API 文件](https://open-meteo.com/en/docs)（參數 `hourly`、`start_hour`、`end_hour`、`timezone`、`timeformat`）；官方文件說明 `timeformat=unixtime` 使用 Unix 秒數，回應 `utc_offset_seconds` 是該請求回應的固定 offset，不應當作跨 DST 的時間轉換權威。歷史回應實測 endpoint：`https://historical-forecast-api.open-meteo.com/v1/forecast`；實際日期、座標與請求參數見本文件 §2.2。

### 2.2 DST 與 UTC 時窗驗證

已排除兩種不可靠方案：

1. 單日 `start_date=end_date` 搭配目的地 timezone 的日期切片，無法保證洛杉磯 DST 日期包含所有真實當地小時。
2. 直接把目的地當地時間放進 `start_hour/end_hour`，API 仍以整個回應固定 offset 解析時間，DST 切換邊界會漏掉當地小時；單純擴張當地時間窗口也未解決。

**已驗證可行的 P0 請求方式：**

1. 使用景點 IANA timezone，計算 forecast date 當地 00:00 與下一個當地日期 00:00 對應的 UTC epoch。
2. 將兩個 epoch 格式化成 UTC ISO datetime，送入 `start_hour`、`end_hour`，明確指定 `timezone=UTC`、`timeformat=unixtime`。
3. Open-Meteo 的 hour window 回應包含右端點，因此服務端只接受半開區間 `[start_epoch, end_epoch)`。
4. 再以景點 IANA timezone 將每個 Unix timestamp 換算當地日期／小時，驗證目標日所有真實樣本；不得以固定 24 筆或單一 `utc_offset_seconds` 判斷完整性。

真實 Historical Forecast API 驗證案例：

| 地點／日期 | 目的地當地日 | UTC 起訖 | half-open 後目標樣本 |
|---|---:|---|---:|
| America/Los_Angeles 2026-03-08（春季跳時） | 23 小時 | 2026-03-08 08:00Z → 2026-03-09 07:00Z | 23 |
| America/Los_Angeles 2026-11-01（秋季回撥） | 25 小時 | 2026-11-01 07:00Z → 2026-11-02 08:00Z | 25 |
| Asia/Tokyo 2026-11-20 | 24 小時 | 2026-11-19 15:00Z → 2026-11-20 15:00Z | 24 |
| Asia/Kathmandu 2026-11-20（UTC+05:45） | 24 小時 | 2026-11-19 18:15Z → 2026-11-20 18:15Z | 24 |

秋季回撥日的兩筆 01:00 必須保留為兩個不同 Unix epoch；春季跳時日不存在的 02:00 不可自行補資料。

### 2.5 Hourly 新增請求成本估算（2026-11-15）

**計算單位與範圍**

- 只估算新增的 interval hourly provider request；既有 daily forecast request、Google Places 座標取得費用不納入本項。
- 一個更新目標是唯一的 `(place_id, forecast_date)`，不是一張卡片。同一地點／日期被多張卡片或多個 Trip 引用時共用一筆 hourly 快取及一次更新；APP 與 Cron 同時觸發時由共用 lease 去重。
- hourly 成功快取 24 小時內為 fresh；24–48 小時為 stale；48 小時失效。正常成功情境下，同一目標約每 24 小時新增一次 hourly API call。每次更新最多重試一次，因此單次更新最多兩次 provider calls。
- 既有每 6 小時 Cron 是每日 4 次 Edge Function 排程，不代表每個目標每日呼叫 4 次 Open-Meteo；只有 cache miss／stale、資格仍有效且成功取得 lease 的目標才發出 hourly request。

**Open-Meteo 新增 calls/day 情境**

令 `N` 為每日實際需要新增或刷新 hourly 資料的唯一 `(place_id, forecast_date)` 目標數：

| 情境 | 每目標每日更新次數 | 每目標 provider calls/day | 全體新增 calls/day | 30 日新增 calls |
|---|---:|---:|---:|---:|
| 正常成功 | 約 1 次／24h | 約 1 | `N` | `30 × N` |
| 持續失敗、只有 Cron 觸發 | 最多約 4 次（每 6h） | 最多 8 | `8 × N` | `240 × N` |
| 持續失敗、APP 也反覆觸發 | 受 1h failure cooldown 限制，理論最多約 24 次 | 最多 48 | `48 × N` | `1,440 × N` |

最後一列是保守壓力上限，不是預期用量：假設每個目標持續失敗、APP 每小時至少觸發一次，而且每次更新的原始請求與一次重試都失敗。現行設計沒有額外的每日硬性使用者限流，因此不能把「Cron 每日 4 次」誤當成全系統每個目標的絕對請求上限。

| 每日唯一目標數 N | 正常 calls/day（月） | Cron 失敗壓力 calls/day（月） | APP＋Cron 失敗壓力 calls/day（月） |
|---:|---:|---:|---:|
| 100 | 100（3,000） | 800（24,000） | 4,800（144,000） |
| 200 | 200（6,000） | 1,600（48,000） | 9,600（288,000） |
| 1,000 | 1,000（30,000） | 8,000（240,000） | 48,000（1,440,000） |

沿用既有文件記錄的 Open-Meteo Free API 限額 10,000 calls/day、300,000 calls/month 作容量比較：正常情境下每日 1,000 個唯一目標約使用日限額 10%、月限額 10%；但在 APP 與 Cron 持續失敗壓力模型下，約 208 個持續失敗目標便可能接近日／月限額。這是風險邊界，不表示目前已有這種流量。若未來實際目標數接近此壓力邊界，應先檢視失敗原因與重試日誌，再由產品決策是否調整 interval failure cooldown；本次不擅自改動既定 1 小時規則，也不新增複雜限流系統。

**Supabase／Edge Function 增量**

- 不新增 Edge Function、不新增 Cron。沿用既有 weather-forecast function 與每 6 小時 Cron；Cron 本身仍為每日 4 次、每月約 120 次 invocation。Hourly 工作若併入同一次 APP／Cron batch，不會因每個 hourly provider call 再增加一次 Edge Function invocation；APP 原有的觸發 invocation 數亦不因 hourly 欄位本身倍增。
- Edge Function 仍須額外執行 hourly HTTP、解析最多約 23／24／25 個目的地當地小時資料、篩選與摘要計算、寫入獨立 interval cache。每筆仍沿用單次 HTTP 8 秒、單筆總期限 20 秒、最多重試一次；批次最多 10 個目標、最多 5 個併發，既有估算最壞約兩輪 40 秒，低於 Free Edge Function 150 秒 wall-clock 限制。這是既有 timeout／batch 上限推算，不是新增流程的實測 CPU benchmark；Free 每次 invocation CPU 2 秒，實作後仍須以實際 Edge logs／測試量測 CPU。
- 因 hourly 原始資料只在後端使用，不回傳前端、不保存 LocalStorage，也不拆成每小時多筆資料；資料庫只新增每個唯一目標一列的 JSONB cache。

**DST 23／24／25 小時對處理成本的影響**

- DST 不會增加每個 `(place_id, forecast_date)` 的 HTTP 請求次數；春季跳時、一般日及秋季回撥日都仍是同一個 hourly request。23／24／25 小時只影響單次回應中實際需要保留及處理的 hourly 樣本數。
- 相較一般 24 小時日，春季跳時日少處理 1 筆，秋季回撥日多處理 1 筆。HTTP payload 傳輸、JSON 解析、區段篩選及摘要計算均只增減一筆資料，屬於極小的線性差異；不需要因 DST 增加額外 API request、額外排程或另一套計算流程。
- 若保存完整 hourly JSONB，23／25 小時日的資料量也只會相對 24 小時基準少／多一個 hourly sample；實際 bytes 會依欄位值與 JSONB 結構略有不同。現有 1,450 bytes／24 小時真實 payload 是估算基準，不應把每筆平均 bytes 當成精確固定值，也不需為 DST 預留固定額外欄位或資料列。
- 正確性要求高於這一筆資料的微小成本差異：以 IANA timezone 計算當地午夜對應的 UTC epoch，使用半開區間 [start_epoch, end_epoch) 篩選。秋季重複的當地 01:00 必須以不同 Unix epoch 保留兩筆；春季不存在的當地小時不得補造。不得假設固定 24 筆，也不得只用當地小時字串作唯一識別。
- **成本判斷：** DST 本身不構成額外架構或成本優化的理由；維持既有 IANA timezone＋UTC Epoch 設計即可。實作後仍需量測 Edge CPU 與正式 DB row／索引／TOAST，但不需要為 23／25 小時另做效能測試矩陣；只需把兩種 DST 日期納入時間完整性與摘要正確性測試。

**資料庫儲存量**

- 24 小時東京真實 payload 重建的必要 hourly object，PostgreSQL `pg_column_size(jsonb)` 為 **1,450 bytes／列**；這是目前可用的實測基準，不是正式 table row 的完整大小。
- 原始 hourly JSONB 下限估算：100 列約 145 KB（0.14 MiB）、1,000 列約 1.45 MB（1.38 MiB）、10,000 列約 14.5 MB（13.83 MiB）。計算式為「未過期的唯一 `(place_id, forecast_date)` 列數 × 1,450 bytes」。
- 實際 DB storage 還會包含欄位 metadata、row header、索引與可能的 TOAST；目前沒有正式資料表 insert／index／TOAST 實測，故不得把 1,450 bytes 當成完整 row size，也不虛構額外百分比。48 小時 TTL 與主鍵 upsert／purge 讓資料量受未過期的唯一地點／日期列數控制，不會按每次 API request 永久累加。

**成本結論**

- Open-Meteo 在既有非商業免費授權及限額內沒有按次費用；新增成本主要是 API calls quota 使用量、Edge CPU／HTTP wall time，以及 interval JSONB 儲存。
- 正常使用以每日每個唯一目標約 1 次新增 hourly call 作容量基線；100／200／1,000 個唯一目標分別約 100／200／1,000 calls/day。
- 最大的不確定風險不是正常成功流量，而是「連續失敗＋APP 每小時重觸發＋每次重試」；現行 1 小時 cooldown 使理論壓力上限達每目標 48 calls/day。保留此風險供實作觀測，不在本階段自行改寫已定案政策。
- 此估算不含 Open-Meteo API 授權重新稽核、不含 Google Places 費用，也不宣稱正式 DB storage／CPU 已完成實測。

## 3. 現有程式核對發現

以下均為唯讀觀察，尚未修改正式 source。

### 3.1 前端 departure_time 契約核對（本輪已完成唯讀盤點；正式 source 尚未修改）

**既有卡片資料模型與儲存語意：**

- `src/types/trip.ts` 的 `ItineraryItem` 已有 `time: string`（到達時間）及 `departureTime?: string`（離開時間），不是新增卡片欄位。
- `src/components/ItineraryPage.tsx` 儲存卡片時，`departureTime = requestedDepartureTime || arrivalTime`；`time = arrivalTime || requestedDepartureTime`。因此正常新儲存資料中：有到達、未輸入離開時，兩者會相同；兩者皆未輸入時，兩者皆空；僅輸入離開時，time 會以該值作為起始時間。舊資料仍可能缺少 `departureTime`，後端應以 `departureTime || time` 做相容 fallback。
- 依《79》§2.7，模式只能由已儲存欄位推導：兩者皆空為 `daily`；有效到達／離開時間皆有值且不同為 `interval`；只有到達時間或離開時間沿用到達時間時為單一到達小時區段。不可把空字串轉成 `00:00`，也不可新增模式欄位。

**目前前端 request／fingerprint：**

- `requestTripWeatherOnce()` 目前送出 `card_id`、`place_id`、`day_number`、`forecast_date`、`arrival_time: card.time`，沒有 `departure_time`。
- 同一 `(place_id, forecast_date)` 的 client target grouping 不應改變；每張卡片仍需保留自己的 `card_id`／時間，以便後續逐卡回傳摘要。
- `requestTripWeather()` fingerprint 目前包含 `card.time`，但未包含 `card.departureTime`；使用者只改離開時間時，in-flight request key 可能仍相同，無法明確區分不同區段。應納入到達時間、正規化離開時間及由兩者推導的模式；不需另傳 `forecast_type` 作權威。
- `WeatherForecastItem` 目前只有 `arrival_time` 作為停止更新結果的本機快取比對 metadata，尚無 `departure_time`、`forecast_type` 或 interval 起訖小時 metadata。這些回應欄位應在 interval pipeline 接通時增加，daily 舊回應欄位維持相容。

**目前 Edge Function 信任邊界：**

- `makeCandidate()` 目前只從已儲存卡片 `card.time` 建立 `arrivalTime`；`Candidate` 型別也只有 `arrivalTime`，沒有 `departureTime`。
- 使用者 request handler 目前讀取 client 的 `card_id`、`place_id`、`day_number`、`forecast_date` 作為候選定位，再透過 RLS scoped Trip 重新讀取已儲存卡片；`getStoredCandidate()` 重新呼叫 `makeCandidate()` 並核對 Place ID／日期。client 的 `arrival_time` 並未被當作權威使用。
- 因此正確的最小契約是：client payload 增加 `departure_time` 作為候選快照／對應資訊，但 Edge 必須完全依 `getStoredCandidate()` 從已儲存 `card.departureTime`（缺值時 fallback 到 `card.time`）建立權威候選；client 的 arrival/departure time、forecast type、區段起訖都不得覆蓋已儲存資料。若 client 時間快照與已儲存資料不一致，應拒絕該卡片或回傳同步等待狀態，不可用 client 時間執行摘要。
- `forecast_date` 亦需由已授權 Trip 的 `departure_date + day_number` 重算並核對，不能僅接受 request 傳入日期；現行 `getStoredCandidate()` 已有這項核對。

**下一個最小實作切片（尚未執行）：**

1. 前端 request item 增加 `departure_time: card.departureTime ?? card.time ?? ""`；保留既有 `arrival_time` 相容欄位，或在獨立契約版本確認後再移除，避免同時做無必要的 breaking change。
2. 前端 fingerprint 加入到達時間、正規化離開時間及推導模式；相同時間內容必須得到穩定 fingerprint。
3. Edge `Candidate` 增加 `departureTime`；`makeCandidate()` 只讀儲存卡片，使用 `card.departureTime`，舊資料缺欄位時 fallback `card.time`；`getStoredCandidate()` 比對時同樣只依儲存內容。
4. Edge request handler 可將 client `departure_time` 與儲存值作一致性檢查，但不可用它取代儲存值；考慮行程同步延遲時，採既有 `WEATHER_CARD_NOT_FOUND`／waiting 重試語意，不洩漏卡片資料。
5. 加入前端 payload／fingerprint 與 Edge stored-candidate regression，覆蓋兩時間皆空、到達單時、到達＋離開區段、舊資料缺少 `departureTime`、只改離開時間、偽造 client departure time，以及每日模式相容性。

本輪只完成唯讀盤點與契約定義；未修改 `weatherForecastService.ts`、`weather-forecast/index.ts`、資料庫、Migration、RLS、Cron、Secrets 或部署。

### 3.2 共享引用資格 OR 與 Cron 代表候選

`supabase/functions/weather-forecast/target-selection.ts` 的 `preferSharedTargetCandidate` 會優先選無到達時間卡片，否則挑最晚到達時間卡片。

`supabase/functions/weather-forecast/index.ts` Cron 路徑按 `(place_id, forecast_date)` 去重後，只重新讀取代表候選所屬 Trip、再驗證代表卡片；目前不是重新收集所有 Trip 的同地點／同日期有效引用卡片。

區段路徑必須重新收集所有有效且已啟用天氣的引用卡片，逐卡套用既定目的地資格規則，任何一張仍有資格即可更新。既有 daily 路徑不可因這次需求被順手改寫；應將區段的候選集合／OR 判斷隔離並獨立回歸。

### 3.3 Daily／Interval 必須隔離

每日表 `weather_daily_forecasts`、每日欄位／回應和每日 lease/RPC 維持原樣。區段另建 `weather_interval_forecasts` 與獨立 lease/RPC；座標變更時須於同一資料庫交易同步清除 interval cache，並防止舊座標請求回寫。

### 3.4 下一階段最小實作順序（2026-11-15 更新）

目前 P0 時區 helper、WMO 優先級 helper 與 fixture 已建立，但尚未接入正式 hourly pipeline。建議依下列順序逐段完成，每段先驗證再進下一段；不要一次把 schema、排程、UI 與部署全部攤開。

**第一段：前後端卡片時間契約（下一個可執行切片）**

1. 前端只調整既有 `requestTripWeatherOnce()` payload 與 request fingerprint：保留 `arrival_time`，新增 `departure_time` snapshot；departure fallback 使用 `card.departureTime ?? card.time ?? ""`，並將到達時間、正規化離開時間及推導模式納入 fingerprint。相同時間資料須產生穩定 key；只改離開時間必須產生新 key。
2. Edge `Candidate` 增加 `departureTime`；`makeCandidate()` 僅從 RLS 已授權重新讀取的已儲存卡片建立時間，舊資料缺少 `departureTime` 時 fallback 至 `card.time`。不得以 client 傳入時間或 `forecast_type` 覆蓋 server stored data。
3. 若 client snapshot 與 server stored time 不一致，採既有卡片不存在／同步等待語意處理，不回傳其他 Trip 或卡片內容；不得把 client snapshot 當成授權或資料權威。
4. 這一段只建立時間契約與測試，不開始 hourly HTTP、摘要演算法、DB schema／migration、RLS／RPC、Cron 或部署。
5. Regression 至少涵蓋：兩時間皆空（daily）、單一到達時間、到達＋離開區段、舊卡片缺 departureTime、只改離開時間、偽造 client departure_time、client/server snapshot 不一致，以及 daily 舊回應相容。

**第二段：同 Place/date 跨 Trip 引用資格 OR**

1. 在獨立區段候選路徑中，對同一 `(place_id, forecast_date)` 收集所有可合法存取、已啟用天氣且有效的引用卡片；逐卡套用既定目的地資格規則，任一引用仍有資格即允許該共用目標更新。
2. APP 使用者請求與 Cron 必須採相同的 OR 語意；不能只依 `preferSharedTargetCandidate` 選出的單一代表卡片決定整個共用快取是否停止更新。
3. 明確限制跨 Trip 授權範圍、分頁與批次上限；不得為了查找其他 Trip 而擴大一般使用者的讀取權限。若現有授權模型無法安全取得完整引用集合，先提出最小 RPC／資料庫設計再實作。
4. Daily 路徑保持原樣，並以多 Trip／多卡片測試驗證 OR 結果。

**第三段：再進入 schema／migration 與完整 pipeline 設計**

只有前兩段契約與資格語意通過回歸後，才定稿 interval table、獨立 lease/RPC、RLS、座標變更同交易失效、purge 與 Cron batch。此階段仍須另行核對 migration 與遠端操作授權；本文件不授權正式 DB 寫入或部署。

**全程不變的範圍界線：**每日預報 table／RPC／response／UI／更新資格不得因區段功能被改寫；不新增卡片時間欄位或 mode 欄位；不保存或回傳 hourly raw list；不為 DST 增加額外 request／排程；不擅自改變已定案的 WMO 優先級、1 小時失敗冷卻與既有更新政策。
