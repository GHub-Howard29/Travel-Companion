## 問題與原因

- 每日行程的地點搜尋請求在到達 Google Places API 前失敗，使用者只能保留原文字。
- 直接原因：V3.6.4 起前端會附加 `x-travel-companion-client-id`，但 Edge Function 的 CORS 白名單未包含此標頭，導致瀏覽器只完成 OPTIONS，隨即阻擋實際 POST。
- 錯誤遮蔽：前端假設函式錯誤內容一定是 `Response` 並呼叫 `clone()`，因此畫面顯示 `clone is not a function`，掩蓋原始網路錯誤。
- 驗證相容問題：正式 Supabase 專案已使用 ES256 非對稱使用者 JWT，但 `travel-route` Edge Function 仍啟用舊式平台 `verify_jwt`；CORS 修正後仍可能在函式執行前遭到 401 拒絕。
- 金鑰設定問題：函式原本使用不存在的單數新版環境變數名稱，無法正確銜接 Supabase 新版金鑰設定。

## 修正內容

- 正式部署 `travel-route` 時固定使用 `verify_jwt=false`，由函式內的 `auth.getUser()` 驗證使用者 JWT。
- CORS 白名單加入 `x-travel-companion-client-id`，讓正式前端能送出實際 POST。
- 函式仍以 `admin_users` 判定 `super_admin` 或該 Trip 的 `trip_editor`，未登入或未授權請求不得呼叫 Google 地圖服務。
- 優先解析 `SUPABASE_PUBLISHABLE_KEYS` 與 `SUPABASE_SECRET_KEYS` 的 `default` 金鑰；新版變數不存在時才回退舊版 `SUPABASE_ANON_KEY` 與 `SUPABASE_SERVICE_ROLE_KEY`。
- 新版金鑰 JSON 損壞、缺少 `default` 或值為空時安全失敗，不回退舊金鑰掩蓋錯誤。
- 地點搜尋與路線估算的前端介面及回應格式不變。
- 前端只在錯誤內容確實是 `Response` 時解析 JSON，避免網路錯誤被 `clone is not a function` 覆蓋。
