# 一、版本目標

在每日行程中，於兩張直接相鄰且都有已確認地點的卡片之間，顯示由地圖路線服務取得的預估移動時間與距離。

每一段交通可獨立選擇開車、步行或大眾運輸。一般使用者只查看管理者已儲存的結果，不在瀏覽行程時重複呼叫外部服務。

---

# 二、顯示方式

交通資訊直接顯示在兩張行程卡片中間，不另設第二層明細卡：

```text
🚗 約 21 分鐘 · 8.4 公里
🚶 約 48 分鐘 · 3.2 公里
🚇 約 26 分鐘 · 6.1 公里
```

- 顯示交通方式圖示、預估時間與公里數。
- 所有結果均以「約」表示，不視為保證抵達時間。
- 預設交通方式為開車。
- 每個交通區段可獨立設定交通方式。
- 不提供手動輸入或覆寫移動時間。
- 不自動調整後續行程卡片時間。

---

# 三、交通區段建立規則

## 3.1 相鄰規則

只有兩張直接相鄰且都有有效地點的卡片才建立交通區段。

```text
有地點 A → 有地點 B
結果：顯示 A 至 B 的交通資訊。

有地點 A → 無地點 → 有地點 B
結果：無地點卡片中斷關聯，兩側均不顯示交通資訊，不跨卡計算。
```

## 3.2 航班排除

- 不建立機場到機場的航班交通區段。
- 不從航班資料產生飛行時間或飛行距離。
- 起飛時間與抵達時間由旅程卡片本身呈現，不納入本功能。
- 機場與一般地點之間的地面交通仍可計算，例如「那霸機場 → 飯店」。
- 實作時應以卡片類型或明確資料標記判斷航班區段，不以地點名稱是否包含「機場」作為唯一依據。

# 四、地點資料與確認流程

目前既有 `location` 為自由文字。V3.6.0 保留它作為使用者設定與卡片顯示文案，另保存可供路線服務穩定識別、且依 Google Maps 現行政策允許長期保存的 Place ID：

```ts
place: {
  placeId: string;
}
```

建議地點建立流程：

1. 管理者輸入地點名稱。
2. 顯示 Google Places 地點候選名稱與地址。
3. 管理者選擇候選並確認位置。
4. `location` 保留使用者原本設定的顯示文字，結構化資料只長期保存 Place ID；候選名稱與地址只在本次確認流程顯示，不長期寫入 Trip。
5. 未確認的既有文字地點仍可顯示及開啟導航，但不保證可建立交通區段。

地點確認功能應按需載入，不讓地圖或 Places 元件增加 App 首次開啟負擔。

> 2026-08-28 開發時重新核對 Google Maps 現行政策：Place ID 可長期保存，但 Places 內容不得無期限快取，因此以 Place ID 取代原規格的地址與經緯度永久保存方案。候選結果旁須顯示 `Google Maps` attribution。

## 4.1 已確認卡片顯示與文案

- 每日行程卡維持原設計，只顯示既有時間、類型、標題、說明及地點按鈕；不新增景點圖案或地址列。
- 原卡片「地圖導航」改為「在地圖中查看」，用於開啟地點頁面、評論、照片與其他資料，不表示查看兩地路線。
- 地點確認面板的次要按鈕使用「保留原設定地點」。

# 五、交通方式選擇

Trip Editor 或 Admin 點選交通資訊後，開啟輕量選擇面板：

```text
交通方式

[🚗 開車] [🚶 步行] [🚇 大眾運輸]

約 21 分鐘 · 8.4 公里

[儲存這個交通方式]
[使用 Google Maps 查看路線]
```

- 切換交通方式時先讀取快取；沒有快取才呼叫外部路線服務。
- 新結果先在面板預覽，按下儲存後才更新卡片中間的正式顯示。
- 查詢失敗時保留原本已儲存結果，不清空交通資訊。
- App 內不顯示完整互動路線地圖。
- 面板提供外部 Google Maps 按鈕，由 Google Maps App 或網頁負責完整路線檢視與導航。
- 交通結果在沒有嵌入 Google 地圖時，依現行 attribution 規範於結果附近標示 `Google Maps`。
- 交通方式偏好與區段永久保留；Google 的時間與距離過期後，卡面改顯示「路線資訊待更新」，不讓區段從頁面消失。
- Guest／User 點擊交通區段時直接開啟外部 Google Maps，不呼叫本專案的 Places／Routes API。
- Trip Editor／Super Admin 開啟交通面板時不自動查詢；只有明確選擇交通方式取得預估時才呼叫 Routes API。

## 5.1 大眾運輸範圍

- 第一版不讓管理者進一步指定公車、捷運或火車。
- 第一版不提供多條候選路線清單。
- 由 Google 選擇建議路線，並依主要搭乘工具顯示適合的交通圖示。
- 若管理者需要比較其他路線，使用「Google Maps 查看路線」。

# 六、大眾運輸時間基準

大眾運輸依賴班次資料，外部服務仍需合法的查詢日期時間，但 UI 不要求使用者選擇查詢日期。

採用以下規則：

1. 使用前一張卡片的「離開時間」作為預估出發時段。
2. 若舊資料沒有 `departureTime`，使用原有的到達時間 `time`，等同 V3.4.2 的自動補值規則。
3. 後端搭配最近一個可查詢的同星期日期送出查詢。
4. 若該時段沒有可用班次，改以同一天 12:00 查詢日間參考路線。
5. 使用日間備援結果時，在管理者選擇面板標示「此結果為日間班次估算」。
6. 卡面仍只顯示圖示、預估時間與距離，不顯示技術性錯誤。

此規則不追求即時班次準確度，目標是提供兩地之間可供排行程參考的既有移動時間，並避免晚間設定時因沒有班次而無法取得結果。

---

# 七、時間不足警告

V3.6.0 不自行推算停留時間，也不新增停留時間欄位；直接使用 V3.4.2 已設定的前一站離開時間與下一站到達時間。

若兩張直接相鄰卡片都有有效時間，使用下列規則：

```text
可用移動時間＝下一張卡片到達時間－目前卡片離開時間

可用移動時間 < 預估移動時間
```

符合時顯示：

```text
⚠️ 行程間隔可能不足 10 分鐘
```

- 不自行推算目前地點的停留時間；停留範圍已反映在卡片的到達／離開時間中。
- 不判定使用者一定會遲到。
- 不自動修改任何行程時間。
- 跨午夜、時間缺漏或格式無效時不顯示警告。

## 7.1 時間順序衝突

若前一張卡片的離開時間晚於下一張卡片的到達時間，例如：

```text
景點 A：離開 14:00
景點 B：到達 13:30
```

直接顯示：

```text
⚠️ 行程時間順序衝突：前一站離開時間晚於下一站到達時間
```

- 時間順序衝突警告優先於「行程間隔可能不足」警告。
- 不為了判斷衝突而呼叫 Google Routes API，因此不消耗額外查詢額度。
- 若已有交通結果，保留並繼續顯示原結果及衝突警告。
- 若尚無交通結果，Trip Editor / Admin 仍可手動開啟交通方式面板查詢；查詢成功後衝突警告仍保持顯示。
- 系統不自動修改任一卡片時間。

# 八、角色權限

| 角色 | 查看已儲存結果 | 切換交通方式 | 呼叫外部服務 | 儲存結果 |
|------|----------------|--------------|----------------|----------|
| Guest | 可以 | 不可以 | 不可以 | 不可以 |
| User | 可以 | 不可以 | 不可以 | 不可以 |
| Trip Editor | 可以 | 可以 | 可以 | 可以 |
| Admin / Super Admin | 可以 | 可以 | 可以 | 可以 |

Guest 與 User 完全不能切換交通方式，只能查看管理者最後儲存的快取結果。

# 九、服務架構與安全

建議使用：

- Google Places：選擇並確認地點。
- Google Routes API：取得開車、步行及大眾運輸的時間與距離。
- Supabase Edge Function：代理 Routes / Places Web Service 請求並保護私密 API 金鑰。

```text
Travel Companion 前端
        ↓
Supabase Edge Function
        ↓
Google Routes / Places
```

- 不在公開 PWA 前端放置可任意呼叫 Web Service 的私密金鑰。
- Edge Function 必須驗證登入身分與 Trip 編輯權限。
- Guest、User 不得透過直接呼叫 Edge Function 繞過前端限制。
- 外部服務失敗時應回傳可辨識錯誤，前端保留最後成功結果。

正式部署前置條件：

1. Google Cloud 啟用 Places API (New) 與 Routes API，並完成帳單、每日配額、預算和費用警示設定。
2. Supabase Edge Function 設定伺服器端 secret `GOOGLE_MAPS_API_KEY`；不得使用 `VITE_` 前綴或寫入 PWA 環境變數。
3. 先套用 V3.6.0 migration，再部署 `travel-route` Edge Function。
4. 以 `super_admin`、被指派的 `trip_editor`、一般登入者及未登入者分別做權限驗證。

# 十、快取與成本控制

Google Routes 與 Places 為需啟用帳單的按量計費服務。開發時採以下控制：

- 只有 Trip Editor、Admin / Super Admin 能產生新查詢。
- Guest、User 一律只讀已儲存結果。
- 每段只查詢目前選擇的交通方式，不一次預抓三種方式。
- 相同起點、終點、交通方式與時間基準優先使用快取。
- 距離與時間結果最多快取 30 天；到期後不再顯示數字，讀取／再次同步時移除，Edge Function 查詢時亦清除已過期伺服器快取。
- 最後選擇的交通方式不屬於過期 Google 結果，會持續保留；到期卡面以該圖示搭配「路線資訊待更新」維持頁面完整性。
- 起點、終點或交通方式沒有改變時，不因重新整理、切換 Day 或重新渲染而查詢。
- 地點變更時，只讓相鄰受影響區段失效。
- 前一張卡片的離開時間變更時，大眾運輸的時間基準已改變，應讓該交通方式的快取失效。
- 下一張卡片的到達時間只影響時間警告，不影響路線本身，因此只在前端重新計算警告，不呼叫 Routes API。
- 修改卡片標題或說明不影響交通快取。
- 不啟用 `TRAFFIC_AWARE` 或其他提高 SKU 等級的即時路況功能。
- Google Cloud 設定每日配額、帳務預算與費用警示。
- Routes API 每日查詢上限確認設為全專案合計 100 次，不是每位管理者各 100 次。
- 達到每日上限後，Guest / User 仍可查看快取結果，管理者暫時不能取得新的路線結果；既有交通資料不受影響，待隔日配額恢復後再繼續查詢。
- 後續只有在檢視實際用量、免費額度與費用風險後，才調整每日上限。

已於 2026-08-28 重新核對 Google Maps Platform 官方價格頁：現行方案採各 SKU 免費月用量與超量計費，實際免費量依 SKU／方案而異；不得再以舊版固定月度抵用金假設成本。正式啟用前仍須在 Google Cloud 設定每日配額、帳務預算與費用警示。

# 十一、V3.6.0 明確不做

- 不計算或顯示機場到機場的航班時間與距離。
- 不解析航班資料來建立交通區段。
- 不另外輸入或推算停留時間；沿用 V3.4.2 卡片的到達／離開時間。
- 不自動推算或修改後續卡片時間。
- 不提供手動交通時間。
- 不提供 App 內完整路線地圖或逐步導航。
- 不提供大眾運輸工具細分選擇。
- 不提供多條大眾運輸候選路線比較。
- 不提供即時交通路況。
- 不讓 Guest、User 切換交通方式或重新查詢。

# 十二、開發順序

1. V3.4.2 到達／離開時間與 PWA 啟動流程完成。
2. 確認動態載入與 PWA 離線行為穩定。
3. 啟動 V3.6.0 地點間預估移動資訊。
4. V3.6.0 的 Places／地點確認與交通選擇面板沿用 V3.4.0 建立的按需載入方式。

# 十三、V3.4.2 銜接修正計畫

V3.6.0 開發時依下列順序銜接既有行程時間資料：

1. 將 `ItineraryItem.time` 視為到達時間，維持目前依到達時間排序。
2. 將 `ItineraryItem.departureTime || ItineraryItem.time` 視為有效離開時間，確保舊資料相容。
3. 大眾運輸查詢以有效離開時間作為預估出發時段。
4. 時間不足警告改以「下一站到達時間－前一站有效離開時間」計算。
5. 先檢查時間順序衝突，再檢查移動時間是否不足。
6. 前一站離開時間變更時只失效受影響的大眾運輸快取；下一站到達時間變更時只重算警告。
7. 不因本次銜接新增停留時間欄位，也不修改 V3.4.2 的自動補值與排序規則。
