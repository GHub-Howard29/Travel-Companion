# 未帶產品版本號文件的歸類討論清單

> 建立日期：2026-10-21
> 原則：本次只搬遷檔名明確包含產品版本號、且版本已正式發布的歷史文件。下列檔案**全部保留原路徑，沒有搬遷**；本表是供 Product Owner 討論的建議，不代表已核准改分類。

## 建議分類原則

1. **核心文件／治理入口**：維持 docs 根目錄，作為目前規範與入口。
2. **架構與功能參考**：目前先留在根目錄；若日後要分類，可討論建立 reference 子目錄，但需同步修正引用。
3. **操作手冊／維運流程**：可考慮 operations 子目錄。
4. **草案／功能規格**：可考慮 specs 或 drafts 子目錄，先確認仍有效、是否已被新文件取代。
5. **診斷與驗收紀錄**：已結案者可考慮 diagnostics 或 diagnostics/archive；仍有追蹤事項者維持根目錄或 active tracking。
6. **外部服務評估**：可考慮 assessments/weather-links；不因評估已終止就自動搬遷，需保留目前決策入口。
7. **重複／舊名文件**：先核對內容與引用，再決定合併、保留相容入口或標記取代；本次不刪除、不改名。

### 開發規範權責初步對照

| 文件 | 主要責任（建議） | 不宜繼續重複承擔的內容 |
|---|---|---|
| 根目錄 `AGENTS.md` | AI／代理每次執行必須遵守的硬性操作規則：Git 與 Supabase 核對、特定 PWA／天氣驗證要求、診斷紀錄維護。 | 不再複製完整產品開發理念、通用 Coding Style 或完整文件維護 Checklist；需要時連結到 `08` 或工程標準。 |
| `docs/08_開發規範.md` | 專案工作流程、產品原則、文件治理與文件維護 Checklist；作為團隊／Product Owner 可閱讀的專案流程入口。 | 不應重複列出代理執行時的所有硬性命令，也不應與 `AGENTS.md` 各自維護一份不同版本的 Git／Supabase 強制步驟。 |
| `docs/000 Development Standard.md` | 若保留，定位為通用工程原則與 Coding Standards 的詳細參考；目前含程式碼風格、Git、Build、Release、AI 行為等多個主題。 | Git／Build／Release／文件維護／AI 回覆規則與 `08`、`AGENTS.md` 重疊的章節，應改成摘要與連結，或在確認無獨有內容後刪減；不要直接整份刪除或覆蓋。 |

**初步結論：**不建議把三份直接合併成一份。較安全的方案是保留三個角色、指定唯一規則主責，先建立引用關係，再逐章精簡 `000 Development Standard.md`。正式精簡前仍需比對 `000` 的 Coding Standards 與 Release Workflow 是否含有 `08`／`AGENTS.md` 尚未涵蓋的獨有規則。

### 第二階段建議處理順序

1. **先處理開發規範權責**：只建立對照表，不立即合併內容。
2. **整理外部天氣評估群**：確認 Weathernews 的授權／URL 追蹤是否已由 TODO 或其他權威文件承接，再決定整組搬至 `assessments/weather-links/`。
3. **釐清 79 與 90 的狀態**：修正可能被誤認為現行規格或仍在執行的舊提案；未結事項必須先移交至現行追蹤文件。
4. **最後才考慮 `reference/`、`operations/`、`drafts/`**：先核對內容有效性與入站／出站連結，再一次性搬遷。

本輪核對沒有搬遷、改名或刪除任何無產品版本號文件。
