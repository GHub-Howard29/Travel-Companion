# V3.9.26 行程公開權限與安全隔離定案規格

> 定案日期：2026-10-08。狀態：**產品規格完全定案，僅記錄，尚未實作、RC、migration 或部署**。
> 本次文件整理不代表授權實作或正式發布。

## 目標與背景

安全稽核確認正式 Supabase 資料庫 `public.trips` 具備匿名 SELECT 權限，且 SELECT RLS 政策為 `USING (true)`；目前 `trips.content` 包含 `participantEmailMap`，公開讀取整列可能暴露參與者電子郵件。另有共用清單、其他資訊及行程封面需要對齊公開範圍。本版新增「行程公開／不公開」設定，不犧牲免登入閱覽與原有協作權限。

## 已定案權限矩陣

| 角色／行為 | 公開行程閱覽 | 不公開行程閱覽 | 既有授權行程管理與同步 | 修改公開設定 |
| --- | --- | --- | --- | --- |
| `super_admin`（管理員） | 可 | 可 | 完全維持 | **唯一可設定** |
| 已受邀且獲授權於該行程的 `trip_editor` | 可 | **可** | **完全維持原有權限** | **不可** |
| 未獲該行程授權的 `trip_editor` | 可 | 不可 | 不得管理該行程 | 不可 |
| `user` | 可 | 不可 | 不因公開而新增編輯權 | 不可 |
| `guest`（未登入） | 可 | 不可 | 不因公開而新增編輯權 | 不可 |

- `is_public` **只控制一般閱覽／可見性**；不應變更現有 `super_admin` 與已授權 `trip_editor` 的清單、帳本、附件、其他資訊、離線及跨裝置同步能力。
- 不公開的行程不能由未授權角色透過列表、直接 Trip ID、REST API、Realtime、關聯資料表或檔案 URL 繞過限制。
- `trip_editor` 的授權以**該行程**為範圍，不是擁有此角色就能讀所有不公開行程。
- 公開的行程僅提供瀏覽權限，不授予寫入。

## 介面及預設值

- 行程新增／編輯介面的「公開行程／不公開行程」設定**僅 `super_admin` 可見與操作**；`trip_editor` 不可顯示或操作，伺服器也必須拒絕其直接變更欄位的請求。
- 新建行程預設 **不公開**。
- 已有行程遷移時 **維持公開**，避免升級當下中斷既有訪客使用；遷移後由 `super_admin` 個別調整。
- 公開狀態切換不可清空行程、清單、帳本或附件，也不可影響既有已授權編輯者的權限。

## 資料庫及個資隔離要求

1. 在 `trips` 增加 `is_public`（或等效狀態欄位），新建預設 `false`；既有資料以遷移顯式設為 `true`。 migration 必須考慮既有資料和 default 的執行順序。
2. 以 Supabase **RLS／資料庫層**落實公開／不公開 SELECT 政策；不能只在前端過濾。確保 `super_admin`、**該 Trip** 的 `trip_editor` 仍可存取私人行程。
3. `is_public` 的變更須由資料庫層明確僅授權 `super_admin`，即使 `trip_editor` 仍有 Trip 主資料 UPDATE 權限，也不能改此欄位。需評估觸發器、分欄權限或獨立管理 RPC 等方案，避免繞過。
4. **公開行程也不得公開 `participantEmailMap` 等個資。** 現在它位於 `trips.content`，不可只新增 `is_public` 就視為完成。需將個資移至獨立受保護資料結構或實作安全的公開資料投影，並調整前端／同步／資料復原流程。不得將含個資的整列留給匿名角色直接 SELECT。
5. 逐一核對 `checklists`、`checklist_items`、`other_info_items`、`trip_deletion_tombstones`、`trip_change_journal`、Storage Bucket、Realtime 與 RPC 的讀取邊界。共同清單於**公開**行程維持既有訪客可讀；在**不公開**行程需遵守行程可見性，但不得削弱授權編輯者的既有操作。
6. `itinerary-covers` 目前是 public Bucket：將公開行程改為不公開時，不能承諾既有公開 URL 立即失效。實作前應規劃公開封面與私人附件的分離、受保護 URL／遷移或清理策略。
7. Offline First：須評估撤權或公開→不公開時本機 LocalStorage、IndexedDB、Service Worker Cache、其他分頁及跨裝置資料殘留；同時不得破壞已授權 `trip_editor` 的離線及同步。
8. 不改變私人／共用帳本既有業務及所有權規則；權限修改僅按此版已定案公開可見性要求最小化。

## 實作前安全核對與回歸驗收

- 建立至少 `super_admin`、行程 A 授權 `trip_editor`、未授權 `trip_editor`、`user`、`guest` 的測試矩陣；公開、私人兩種行程都驗證列表、直接 ID、REST、RPC、Realtime、清單與其他資訊。
- `trip_editor` 編輯行程正常、無法以 UI 或 API 改 `is_public`；已授權私人行程仍可使用帳本、照片、清單、其他資訊及同步。
- 匿名查公開行程可見行程，但**無法讀取 email mapping**；查不公開行程及關聯內容不可得。
- 公開→私人、私人→公開、新建預設與既有遷移（包含多裝置、登出、離線快取、更新與撤權）均需測試。
- Migration 需具備可回復方案；先本機／測試資料庫驗證，再經獨立授權才執行正式 migration、RC 或部署。
- 上述測試不得以服務角色 BYPASSRLS 結果冒充匿名／一般登入者驗證；正式資料不以測試手段任意變更。

## 與既有安全盤點的關係

- 已確定的 `trips` 公開整列與 `participantEmailMap` 混放問題，列為本版 P1 核心目標。
- 套件 `brace-expansion`、`uuid`／`exceljs`、公開匯率服務速率限制、外洩密碼檢查及其他獨立安全議題，仍屬安全稽核追蹤；**非本版已授權擴充實作範圍**。
- 本文件優先於較早的討論草案；最終裁決：**僅 super_admin 能設定公開狀態，已授權 trip_editor 不因行程不公開而失去任何既有權限。**
