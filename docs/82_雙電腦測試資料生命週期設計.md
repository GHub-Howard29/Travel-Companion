# 雙電腦測試資料生命週期與自動同步規則

## 目標

任一台電腦產生的合成測試資料，都要能被另一台電腦取得、套用、驗證及追蹤；資料在回歸測試明確解除前不得清除。解除後，依測試資料的生命週期標記，選擇刪除或封存但不再載入。

## Push／Pull 的自動化界線

- `git push`／`git pull` 只傳輸已提交的版本控制檔案，不會讀取或傳輸本機資料庫中的資料列。
- 版本化測試資料必須先由本機資料庫匯出成 fixture／變更集，經過敏感資料檢查後納入 Git；另一台取得 Git 版本後，再由本機同步入口套用。
- 可將安全的資料套用與驗證掛接到安裝完成的 Git hooks，但 hooks 必須由專案設定明確安裝，且必須允許停用／診斷。不得假設 clone 後 hook 自動存在。
- `push` 前不能盲目自動提交整個本機資料庫；匯出若遇到真實資料、秘密、無法識別的表、衝突或未完成測試資料，必須停止並提示人工處理。
- `pull` 後只允許自動套用已審查、已版本化且標記為可載入的測試資料變更集；不得自動清除本機資料。

## 資料生命週期

每個測試資料集應有穩定的 `fixture_id`、版本、建立來源電腦、狀態與回歸測試紀錄。狀態依序為：

1. `active`：測試資料可使用，必須同步到兩台電腦。
2. `regression_pending`：資料內容已固定，等待指定回歸測試；仍須同步並保留。
3. `released`：回歸測試通過且已明確解除使用；不可再自動載入為活躍測試資料。
4. `archived` 或 `deleted`：解除後依決策封存或刪除。封存資料只作為歷史記錄，不得由日常同步入口重新匯入。

資料集只有在兩台電腦均確認收到同一版本及相同狀態後，才能完成解除／清除。任一台離線或未確認時，另一台不得先刪除唯一可用的測試資料來源。

## 同步安全要求

- 只同步明確標記為合成測試資料的資料集；不得把整個 Supabase dump 當成 fixture。
- 匯入需具冪等性，重複執行不重複新增資料；套用前先驗證 fixture schema、版本、識別碼及相依關係。
- 不可把 Auth session、密碼、token、API key、secret、真實參與者個資、Storage 檔案本體或本機環境設定放入 fixture。
- 跨電腦不得依賴各自不同的 `auth.users.id`。若測試資料需要使用者關聯，應以合成角色映射建立本機關聯，或在匯入時明確重映射；無法安全重映射時停止。
- 不可靜默採用 last-write-wins。相同識別碼但內容不同時，應標記衝突並保留兩邊資料，待人工選擇合併結果。
- 刪除也必須是版本化的明確狀態變更／tombstone，不可因來源電腦缺少某列就推斷另一台應刪除。
- 不建立額外備份，除非使用者另行要求。

## 驗收條件

1. 電腦 A 新增合成行程資料，匯出後可在 Git 中看到精確變更集。
2. 電腦 B 取得同一版本並套用後，核心行程資料及關聯資料與 A 一致。
3. 重複套用同一變更集不會重複新增資料，也不會清除其他本機資料。
4. A、B 各自新增資料後，匯出／合併能保留兩邊變更；衝突會明確中止，不會靜默覆蓋。
5. `active`／`regression_pending` 資料不能被清除；只有通過回歸測試且明確標記 `released` 後，才可封存或刪除。
6. `released`／`archived` 資料不會被一般同步入口重新啟用。
7. 兩台電腦都完成實際驗證前，不可宣稱雙電腦同步流程完成。

## 目前實作狀態

- `npm run db:sync:local` 已整合成本機標準同步入口：確認 `develop` 與 Supabase loopback、套用 pending migrations、匯入已驗證的版本化合成 fixture、準備標準回歸資料，再跑本機回歸驗證。不執行 reset、不清除本機資料，也不自動 pull／commit／push。
- `npm run testdata:export -- tc-test-<name>` 僅允許 `tc-test-` 命名且 `content.__testFixture=true` 的行程；只查詢本機 loopback Supabase，匯出限定表與欄位，排除使用者關聯／附件資料，拒絕非空的 `participants`，並檢查疑似 email、token 與敏感欄位。
- `npm run testdata:validate -- supabase/test-fixtures/tc-test-<name>` 會檢查 schema、狀態、表清單、識別碼、依賴關係、每表筆數、敏感資料與 checksum。
- `npm run testdata:import:all` 只匯入 `active`／`regression_pending` fixture；`released`／`archived`／`deleted` 不會由一般入口重新載入。匯入使用單一 PostgreSQL `DO` statement：先檢查既有主鍵／業務鍵是否內容一致，再補入缺少的列，最後再次檢查；相同資料可重複套用，有衝突就失敗，不採用 last-write-wins，也不刪除其他本機資料。
- `npm run testdata:handoff` 會掃描本機明確標記的 `tc-test-` 合成行程、比對資料、僅在變更時建立下一版 fixture 並驗證 checksum。透過被 `supabase/.gitignore` 忽略的本機狀態檔保存 fixture 檔案雜湊，避免覆寫人工編輯或未經本機確認的他台版本；只回報變更，不會自動 stage／commit／push。
- 已新增專用版本控制 fixture `supabase/test-fixtures/tc-test-sync-example/`，包含合成 Trip、shared checklist、checklist item 與 expense；本輪公司電腦以本機 Supabase 成功匯入，連續重複匯入成功，`handoff` 無變更檢查成功，將合成清單項目改為已勾選後，入口偵測差異並把版本由 1 升至 2；衝突測試恢復本機合成值時，因資料庫 `updated_at` 觸發器更新時間，接力入口再將 fixture 升至目前的第 3 版。第 3 版重新驗證並重複匯入成功。整合後 `npm run db:sync:local` 回報 `synchronized: true`，Migration、標準 fixture prepare 與本機回歸驗證通過。
