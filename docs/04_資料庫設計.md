# 資料庫設計

> Version：V3.4.1（現行架構；V3.4.7 Trip 存取設計待套用）
>
> 最後更新：2026-08-23

## V3.4.7 Trip 公開／私人存取（待套用 migration）

- `trips.is_public`：最終為 `boolean not null default false`；新建 Trip 一律從私人開始。
- Product Owner 已決定所有既有雲端與靜態 Trip 在 V3.4.7 的單一 migration 套用後全數轉為私人；不可先以公開狀態發布，再由後續版本改寫。
- `trips` 的 RLS 將分為匿名 Guest 的公開讀取，以及登入後由公開狀態、`super_admin`、指定 `trip_editor` 組成的讀取規則。
- `trip_editor` 只能編輯被指派 Trip 的既有內容；資料庫 trigger 會拒絕其直接變更 `is_public`，只有 `super_admin` 可切換公開狀態。
- `checklists`、`checklist_items`、`other_info_items` 的讀取 RLS 同樣以 Trip 讀取權限為前置，避免透過個別 REST endpoint 越過主 Trip 的私人限制。
- 前端不再讀取 `public/trips/` 靜態 seed；公開資料由匿名 RLS 查詢取得，私人資料必須在登入後由授權查詢取得。
- 本機 Trip cache 改為公開共用快取及每個 `userId` 私人快取兩部分。伺服器成功刷新後，以授權清單覆蓋目前帳號的私人快取；無權限／登出者不會讀取私人快取。
- migration 只可在 V3.4.7 候選版完成資料備份、隔離環境演練、RLS／REST／靜態網址驗收後，於同一維護窗口套用。現有未提交的候選 migration 不屬任何已發布版本，不得直接套用至正式 Supabase。

### 不可回溯與發布順序

- 已套用的正式 migration、已發布 App 版本與版本更新紀錄均視為不可回寫歷程。若驗收發現問題，僅能以新的向前修復 migration 或新版程式處理。
- 正式資料變更前必須保存 Trip 匯出、筆數與 ID 清單。這是災難復原依據，不作為一般發布失敗時的回退手段。
- GitHub Pages 前端與 Supabase migration 無法原子部署；V3.4.7 前端必須能偵測資料庫尚未完成升級並保持安全唯讀，避免在欄位／政策不存在時提供會失敗的公開設定操作。
- 維護窗口依序為：部署候選前端並確認靜態 Trip 已移除 → 套用同版 migration → 立即執行正式環境驗收 → 全數通過後才記錄為已發布。
- `is_public` 狀態、存取政策與快取隔離不可拆成不同發布版驗證；V3.4.6 僅含 PWA／版本資訊修正，絕不包含本設計的資料庫或前端功能。

## V3.4.1 共用帳本 ownership

- `expenses.client_item_id`：前端穩定記錄 ID，同一 Trip 內唯一，用於離線重試與 A+B 去重。
- `expenses.owner_user_id`：固定為建立記錄的 `auth.uid()`，不可由付款人選擇或後續轉移。
- `expenses.recorded_by_email`：顯示實際代為記帳的登入者；不作為 RLS 唯一依據。
- `expenses.payer`：付款人名稱，只用於分帳、統計及匯出。
- `trip_editor` 可讀取所屬 Trip 全部帳目，但只管理自己建立的帳目；`super_admin` 可管理全部。舊帳目沒有 owner 時保留相容管理規則。
- schema、RLS 與驗證腳本：`docs/sql/011_expense_ownership_and_merge_schema.sql`、`docs/sql/012_expense_ownership_and_merge_validation.sql`。
- 2026-08-11 已套用正式 Supabase `travel-companion-db` 並驗證：5 個欄位、4 個索引、4 項 RLS policy、2 個 trigger 與 table grants 皆存在；anon 無讀取權限，authenticated 由 RLS 控制 CRUD。
- 既有 2 筆帳目均已回填 `client_item_id`，`owner_user_id` 維持 `null`，由舊資料相容 policy 管理，不會錯誤歸屬給部署當下的帳號。

# 二、資料儲存架構

Travel Companion 採用 Offline First（離線優先）架構。

資料依用途儲存在不同位置。

```text
Travel Companion
        │
        ▼
     Storage Layer
        │
        ├── localStorage
        ├── IndexedDB
        └── Supabase
```

所有資料皆透過 Storage Layer 存取。

Travel Tool 不直接操作資料來源。

目前定案使用：

| 資料表 | 用途 |
|------|------|
| trips | 旅程基本資料與 Trip detail content |
| admin_users | `super_admin` / `trip_editor` 權限來源 |

`trips` 目前保存：

- `id`
- `title`
- `departure_date`
- `participants`
- `currency_config`
- `sidebar_config`
- `content`
- `is_public`（V3.4.7 migration 套用後）
- `created_by`
- `created_at`
- `updated_at`

V3.4.7 前端讀取旅程資料時改為兩條授權來源：

```text
Supabase trips（未登入：僅公開；登入：RLS 回傳有權限公開／私人）
localStorage（公開快取 + 目前 userId 的私人快取）
```

同步規則：

- `updatedAt` / `updated_at` 較新的版本勝出。
- App 內新增 / 編輯會先寫對應公開／私人 localStorage cache，再嘗試同步 Supabase。
- Supabase 同步成功後，會把資料庫回傳的 `updated_at` 回寫到本機 cache。

Trip RLS 原則：

- Guest 僅可讀 `is_public = true` 的 `trips`。
- `super_admin` 可新增 / 編輯 / 刪除旅程。
- `trip_editor` 可讀取並編輯被指派的私人旅程，但不可變更公開狀態。
- 新建旅程預設私人；只有 `super_admin` 可將既有旅程轉為公開。

`admin_users` 權限原則：

- `super_admin` 可管理 `trip_editor` 名單。
- `trip_editor` 可讀自己被指派旅程的 editor 名單，但不可修改。
- 一般使用者可讀自己的權限 row。

目前進度：

- 前端已完成 App 內新增 / 編輯旅程第一版。
- SQL schema 已透過 Supabase connector 執行。
- Validation SQL 已驗證。
- 已補充 `harden_trip_cloud_grants` migration，移除舊的寬鬆 `admin_users` read policy 並收斂 `trips` / `admin_users` grants。
- 已補充 `tune_trip_cloud_advisor_findings` migration，建立 `trips_created_by_idx` 並調整 `trips` write policies。
- 尚待 App 端實機測試 `super_admin` / `trip_editor` / Guest 流程。

# 八、Checklist 雲端資料表

V3-1 Checklist 雲端資料表 SQL：

```text
docs/sql/001_checklist_cloud_schema.sql
```

執行後可用以下只讀 SQL 驗證：

```text
docs/sql/002_checklist_cloud_validation.sql
```

目前定案使用：

| 資料表 | 用途 |
|------|------|
| checklists | 共同 / 私人確認清單主檔 |
| checklist_items | 確認清單項目 |

`checklists.scope`：

- `shared`：共同檢查清單
- `private`：私人確認清單

私人確認清單 ownership：

本機 localStorage：

```text
userEmail + tripId
```

雲端同步：

```text
owner_user_id = auth.uid()
trip_id = 目前旅程 id
```

權限來源：

```text
admin_users
```

目前程式與 SQL 皆依 Supabase `admin_users` 判斷：

- `super_admin`
- `trip_editor`
- `trip_id`

新增旅程或新增 `trip_editor` 時，只需維護 Supabase `admin_users` 資料，不需要修改程式。

私人確認清單 RLS 原則：

- 所有私人清單讀寫皆限制 `owner_user_id = auth.uid()`。
- `super_admin` 不可讀取其他使用者的私人確認清單。
- `trip_editor` 不可讀取其他使用者的私人確認清單。
- `user` 目前只使用本機私人確認清單，不同步雲端。
- `trip_editor` / `super_admin` 可同步自己的私人確認清單到雲端。
- 前端本機 item id 以 `checklist_items.client_item_id` 保存，避免用 label 猜測雲端 row。
- `checklist_items_one_client_item_per_checklist` 確保同一清單內 `client_item_id` 不重複。

共同檢查清單 RLS 原則：

- `guest` / `user` 可讀。
- `trip_editor` 依 `trip_id` 可更新。
- `super_admin` 可更新所有 Trip 的共同檢查清單。

目前進度：

- SQL schema 已執行並完成人工驗證。
- 私人確認清單最小雲端同步已接上。
- 共同檢查清單仍使用 Trip JSON seed + localStorage 勾選進度，下一步再接 shared checklist 雲端同步。

# 十二、設計原則

資料庫設計遵循以下原則：

- Trip（旅程）為資料核心。
- Storage Layer 統一管理資料存取。
- Travel Tool 不直接操作資料來源。
- 優先擴充，不修改既有架構。
- 保持低耦合、高可維護性。
