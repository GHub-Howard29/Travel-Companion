# 二、資料儲存架構

Travel Companion 採用 Offline First（離線優先）架構。

資料依用途儲存在不同位置。

```text
Travel Companion
        │
        ▼
     Storage Layer
        │
        ├── localStorage
        ├── IndexedDB
        └── Supabase
```

所有資料皆透過 Storage Layer 存取。

Travel Tool 不直接操作資料來源。

同步規則：

- `updatedAt` / `updated_at` 較新的版本勝出。
- App 內新增 / 編輯會先寫 localStorage cache，再嘗試同步 Supabase。
- Supabase 同步成功後，會把資料庫回傳的 `updated_at` 回寫到本機 cache。

Trip RLS 原則：

- Guest 維持現行 Trip 瀏覽權限，但 V3.5.0 不提供 Guest 離線行程內容。
- `super_admin` 可新增 / 編輯 / 刪除旅程。
- `trip_editor` 可瀏覽全部旅程，只能編輯被指派的旅程。
- `user` 可瀏覽全部旅程，不具 Trip 管理權限。

V3.6.2 已建立並於 2026-09-01 套用 migration，補強歷史行程共用資料的資料庫防線；回滾式角色驗證 9 項全數通過：

- 依 `departure_date` 與更新前 `content.days` 計算最後一天，並以 `Asia/Taipei` 的資料庫目前日期判斷；最後一天為 9 月 1 日時，自 9 月 2 日 `00:00` 起視為歷史行程共用資料已鎖定。
- 歷史行程的 `trip_editor` 不得更新 `trips`，也不得寫入該 Trip 的共同清單、共同帳本、其他資訊或其他共用資料；`super_admin` 保留既有管理權。
- `trips` 驗證必須使用更新前已儲存資料，避免同一請求修改日期而繞過歷史判斷；相關資料表以目標 `trip_id` 查詢 Trip 日期與天數。
- 非歷史行程沿用既有 RLS 與角色規則。歷史行程的整個 Trip 刪除仍只有 `super_admin` 可執行，並沿用既有流程。
- 前端縮短天數確認後，`content.days` 與 `content.daysData` 只保留新天數範圍；共同清單、帳本、其他資訊及其他資料表不因本操作刪除。
- migration：`20260901064451_v362_historical_trip_write_lock.sql`；驗證 SQL：`docs/sql/021_v362_historical_trip_lock_validation.sql`。私人清單同步 helper 未被改寫。

`admin_users` 權限原則：

- `super_admin` 可管理 `trip_editor` 名單。
- `trip_editor` 可讀自己被指派旅程的 editor 名單，但不可修改。
- 一般使用者可讀自己的權限 row。

# 八、Checklist 雲端資料表

V3-1 Checklist 雲端資料表 SQL：

```text
docs/sql/001_checklist_cloud_schema.sql
```

執行後可用以下只讀 SQL 驗證：

```text

```

目前定案使用：

| 資料表 | 用途 |
|------|------|
| checklists | 共同 / 私人確認清單主檔 |
| checklist_items | 確認清單項目 |

`checklists.scope`：

- `shared`：共同檢查清單
- `private`：私人確認清單

私人確認清單 ownership：

本機 localStorage：

```text
userEmail + tripId
```

雲端同步：

```text
owner_user_id = auth.uid()
trip_id = 目前旅程 id
```

權限來源：

```text
admin_users
```

目前程式與 SQL 皆依 Supabase `admin_users` 判斷：

- `super_admin`
- `trip_editor`
- `trip_id`

新增 `trip_editor` 權限時維護 `admin_users`；要讓帳號以固定名稱預帶入新旅程參與者時，另維護 `admin_profiles`。兩表職責分離，顯示名稱不得用於授權。

私人確認清單 RLS 原則：

- 所有私人清單讀寫皆限制 `owner_user_id = auth.uid()`。
- `super_admin` 不可讀取其他使用者的私人確認清單。
- `trip_editor` 不可讀取其他使用者的私人確認清單。
- `user` 目前只使用本機私人確認清單，不同步雲端。
- `trip_editor` / `super_admin` 可同步自己的私人確認清單到雲端。
- 前端本機 item id 以 `checklist_items.client_item_id` 保存，避免用 label 猜測雲端 row。
- `checklist_items_one_client_item_per_checklist` 確保同一清單內 `client_item_id` 不重複。

共同檢查清單 RLS 原則：

- `guest` / `user` 可讀。
- `trip_editor` 依 `trip_id` 可更新。
- `super_admin` 可更新所有 Trip 的共同檢查清單。

目前進度：

- SQL schema 已執行並完成人工驗證。
- 私人確認清單最小雲端同步已接上。
- 共同檢查清單仍使用 Trip JSON seed + localStorage 勾選進度，下一步再接 shared checklist 雲端同步。

# 十二、設計原則

資料庫設計遵循以下原則：

- Trip（旅程）為資料核心。
- Storage Layer 統一管理資料存取。
- Travel Tool 不直接操作資料來源。
- 優先擴充，不修改既有架構。
- 保持低耦合、高可維護性。
