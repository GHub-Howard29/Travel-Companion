# 資料庫設計

> Version：V3.4.11（現行架構；V3.5.0 Other Info 安全方案與 BUG024 同步修正已補全，待 migration／驗證）
>
> 最後更新：2026-08-25

## V3.5.0 Other Info 卡片可見範圍（已定案、程式已補全）

- V3.5.0 維持現行 Trip 與角色制度，不新增 `trips.is_public`，也不執行原規劃的 Trip 公開／私人 migration。
- `other_info_items.allowed_roles` 繼續作為第二層卡片的資料庫可見範圍來源，但不在一般資訊編輯畫面提供角色選項。
- 一般資訊儲存為 `allowed_roles is null`；敏感資料快捷入口儲存為 `['trip_editor', 'super_admin']`。
- RLS SELECT 必須依目前 Trip 的實際角色判斷；其他 Trip 的 `trip_editor` 對目標 Trip 應視為 `user`。
- INSERT、UPDATE、DELETE 仍只允許目前 Trip 的 `trip_editor` 與 `super_admin`，UPDATE 同時需要 `USING` 與 `WITH CHECK`。
- 未授權角色不得透過 Data API 取得受限制卡片；前端過濾只能作為顯示層防護，不能取代 RLS。
- 既有資料角色收斂 migration：`docs/sql/013_v350_other_info_security_scheme.sql`；驗證補充在 `docs/sql/006_other_info_cloud_validation.sql`。
- V3.5.0 同時納入 V3.4.11 BUG024 同步修正：以 `trip_id + client_item_id` 先 UPDATE、無資料才 INSERT，並由 `docs/sql/014_other_info_sync_deleted_rows.sql` 讓行程管理者可重新啟用軟刪除列；UPDATE 依賴 SELECT policy，正式環境必須先完成 013／014 migration。
- 卡片從所有人可看改為僅管理者可看後，Guest／User 下一次成功刷新時必須清除舊快取；管理者離線資料須依帳號隔離，登出後不得供下一帳號讀取。
- 既有未限制卡片維持 `allowed_roles is null`，避免升級後無預期隱藏；既有受限制卡片編輯時應維持敏感資料模式。
- V3.5.0 不新增敏感附件可見層級；固定帳號保護的雲端文件由外部雲端服務的帳號權限控管。既有附件功能的 Storage 安全維護另列於 V3.5.1，不與卡片可見範圍混用。
- 相關 UI 模擬圖已完成並取得 Product Owner 確認；程式依本方案補全，正式上線前仍需執行 migration 與角色驗證。
- 本版前端與 013／014 migration 必須同批驗證；候選發布採 `FORCE_UPDATE = true`，避免舊版在 RLS／同步規則不一致時繼續操作。

## V3.4.1 共用帳本 ownership

- `expenses.client_item_id`：前端穩定記錄 ID，同一 Trip 內唯一，用於離線重試與 A+B 去重。
- `expenses.owner_user_id`：固定為建立記錄的 `auth.uid()`，不可由付款人選擇或後續轉移。
- `expenses.recorded_by_email`：顯示實際代為記帳的登入者；不作為 RLS 唯一依據。
- `expenses.payer`：付款人名稱，只用於分帳、統計及匯出。
- `trip_editor` 可讀取所屬 Trip 全部帳目，但只管理自己建立的帳目；`super_admin` 可管理全部。舊帳目沒有 owner 時保留相容管理規則。
- schema、RLS 與驗證腳本：`docs/sql/011_expense_ownership_and_merge_schema.sql`、`docs/sql/012_expense_ownership_and_merge_validation.sql`。
- 2026-08-11 已套用正式 Supabase `travel-companion-db` 並驗證：5 個欄位、4 個索引、4 項 RLS policy、2 個 trigger 與 table grants 皆存在；anon 無讀取權限，authenticated 由 RLS 控制 CRUD。
- 既有 2 筆帳目均已回填 `client_item_id`，`owner_user_id` 維持 `null`，由舊資料相容 policy 管理，不會錯誤歸屬給部署當下的帳號。

---

# 二、資料儲存架構

Travel Companion 採用 Offline First（離線優先）架構。

資料依用途儲存在不同位置。

```text
Travel Companion
        │
        ▼
     Storage Layer
        │
        ├── localStorage
        ├── IndexedDB
        └── Supabase
```

所有資料皆透過 Storage Layer 存取。

Travel Tool 不直接操作資料來源。

---

目前定案使用：

| 資料表 | 用途 |
|------|------|
| trips | 旅程基本資料與 Trip detail content |
| admin_users | `super_admin` / `trip_editor` 權限來源 |

`trips` 目前保存：

- `id`
- `title`
- `departure_date`
- `participants`
- `currency_config`
- `sidebar_config`
- `content`
- `created_by`
- `created_at`
- `updated_at`

前端讀取旅程資料使用現行來源：

```text
Supabase trips（現行角色與 Trip 存取規則）
localStorage（現行 Trip 快取；V3.5.0 補強 Guest 與登入帳號的離線隔離）
```

同步規則：

- `updatedAt` / `updated_at` 較新的版本勝出。
- App 內新增 / 編輯會先寫 localStorage cache，再嘗試同步 Supabase。
- Supabase 同步成功後，會把資料庫回傳的 `updated_at` 回寫到本機 cache。

Trip RLS 原則：

- Guest 維持現行 Trip 瀏覽權限，但 V3.5.0 不提供 Guest 離線行程內容。
- `super_admin` 可新增 / 編輯 / 刪除旅程。
- `trip_editor` 可瀏覽全部旅程，只能編輯被指派的旅程。
- `user` 可瀏覽全部旅程，不具 Trip 管理權限。

`admin_users` 權限原則：

- `super_admin` 可管理 `trip_editor` 名單。
- `trip_editor` 可讀自己被指派旅程的 editor 名單，但不可修改。
- 一般使用者可讀自己的權限 row。

目前進度：

- 前端已完成 App 內新增 / 編輯旅程第一版。
- SQL schema 已透過 Supabase connector 執行。
- Validation SQL 已驗證。
- 已補充 `harden_trip_cloud_grants` migration，移除舊的寬鬆 `admin_users` read policy 並收斂 `trips` / `admin_users` grants。
- 已補充 `tune_trip_cloud_advisor_findings` migration，建立 `trips_created_by_idx` 並調整 `trips` write policies。
- 尚待 App 端實機測試 `super_admin` / `trip_editor` / Guest 流程。

# 八、Checklist 雲端資料表

V3-1 Checklist 雲端資料表 SQL：

```text
docs/sql/001_checklist_cloud_schema.sql
```

執行後可用以下只讀 SQL 驗證：

```text
docs/sql/002_checklist_cloud_validation.sql
```

目前定案使用：

| 資料表 | 用途 |
|------|------|
| checklists | 共同 / 私人確認清單主檔 |
| checklist_items | 確認清單項目 |

`checklists.scope`：

- `shared`：共同檢查清單
- `private`：私人確認清單

私人確認清單 ownership：

本機 localStorage：

```text
userEmail + tripId
```

雲端同步：

```text
owner_user_id = auth.uid()
trip_id = 目前旅程 id
```

權限來源：

```text
admin_users
```

目前程式與 SQL 皆依 Supabase `admin_users` 判斷：

- `super_admin`
- `trip_editor`
- `trip_id`

新增旅程或新增 `trip_editor` 時，只需維護 Supabase `admin_users` 資料，不需要修改程式。

私人確認清單 RLS 原則：

- 所有私人清單讀寫皆限制 `owner_user_id = auth.uid()`。
- `super_admin` 不可讀取其他使用者的私人確認清單。
- `trip_editor` 不可讀取其他使用者的私人確認清單。
- `user` 目前只使用本機私人確認清單，不同步雲端。
- `trip_editor` / `super_admin` 可同步自己的私人確認清單到雲端。
- 前端本機 item id 以 `checklist_items.client_item_id` 保存，避免用 label 猜測雲端 row。
- `checklist_items_one_client_item_per_checklist` 確保同一清單內 `client_item_id` 不重複。

共同檢查清單 RLS 原則：

- `guest` / `user` 可讀。
- `trip_editor` 依 `trip_id` 可更新。
- `super_admin` 可更新所有 Trip 的共同檢查清單。

目前進度：

- SQL schema 已執行並完成人工驗證。
- 私人確認清單最小雲端同步已接上。
- 共同檢查清單仍使用 Trip JSON seed + localStorage 勾選進度，下一步再接 shared checklist 雲端同步。

# 十二、設計原則

資料庫設計遵循以下原則：

- Trip（旅程）為資料核心。
- Storage Layer 統一管理資料存取。
- Travel Tool 不直接操作資料來源。
- 優先擴充，不修改既有架構。
- 保持低耦合、高可維護性。
