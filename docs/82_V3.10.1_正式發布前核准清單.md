## 2. 更新規則（現有程式行為與本次建議）

1. **同版本不顯示「發現新版本」**；首次開啟且沒有版本紀錄時只記錄目前版本，不應誤判成新版本。
2. 版本資訊由 `public/app-version.json` 提供；它不得被 PWA precache。版本不同時至少顯示一次更新內容。
3. 本次建議採**一般更新**：`IS_MANDATORY_RELEASE=false`、`FORCE_UPDATE=false`，`minimumSupportedVersion` 維持 `3.9.27`。此設定已於 2026-10-17 寫入正式版本 metadata，並由 production build 驗證。
4. **最低支援版本優先於 `forceUpdate`**：`src/utils/appVersionPolicy.ts` 在 metadata 有 `minimumSupportedVersion` 時，以目前版本是否低於最低支援版本決定是否強制更新；只把 `forceUpdate` 改成 `false` 並不會讓低於最低支援版本的客戶端變成可延後更新。
5. `IS_MANDATORY_RELEASE` 會影響版本資訊視窗的「必要更新／一般更新」標籤；它與 `minimumSupportedVersion` 的更新阻擋判斷是不同設定，三者須一致。
6. 選擇更新時，現有流程會先執行資料同步／行程工作區檢查，再重新檢查版本政策、下載新版 Service Worker、等待新版接管後才重新載入。離線、同步失敗、下載失敗或接管失敗時顯示錯誤並允許重試；不得清除使用者已儲存資料。
7. 一般更新可稍後更新；必要更新不可關閉提示。是否升高最低支援版本必須有舊版不相容、安全風險或可能造成資料遺失的具體證據，不能只因新增天氣功能就自動強制更新。
8. 天氣預報服務暫時無法取得資料時，卡片可依現有功能顯示無法取得天氣；不可將外部 API 暫時失敗誤報成整個 APP 更新失敗。

## 4. 原五筆待部署 migration 逐筆審查（部署前審查紀錄）

### 4.1 `20261015090000_v3101_weather_cache.sql`

**目的**：新增地點座標與每日天氣快取資料表、RLS、租約／快取清理函式及每小時清理 Cron。

**權限審查與已做調整**：

- `anon`、`authenticated` 對兩張快取表明確 `REVOKE ALL`，RLS 啟用。
- 已將 `service_role` 權限縮小為 `weather_place_coordinates` 的 `SELECT/INSERT/UPDATE`，以及 `weather_daily_forecasts` 的 `SELECT`，並先撤銷該角色對兩張表的既有權限，避免 GRANT 只是累加而未移除原本的 DELETE／TRUNCATE 權限。交易回滾測試確認：座標表 SELECT／INSERT／UPDATE 為 true、DELETE／TRUNCATE 為 false；天氣表只有 SELECT 為 true，INSERT／DELETE／TRUNCATE 均為 false。天氣預報寫入透過受限的 `SECURITY DEFINER` RPC；清理工作由資料庫 owner 排程執行，不再直接授予兩張表的廣泛 `ALL` 權限。
- `tc_weather_claim_lease`、`tc_weather_release_lease` 僅授權 `service_role`；`tc_weather_purge_expired_cache` 不授權 `service_role`，由資料庫 owner 的 Cron 執行。

**審查結論**：功能必要；縮小後的表權限符合 Edge Function 直接讀寫需求。正式套用前仍須檢查 Edge Function 呼叫的每個表操作及 RPC ACL，並確認部署帳號／資料庫角色行為一致。

### 4.2 `20261015120000_v3101_weather_coordinate_integrity.sql`

**目的**：在每日天氣快取保存實際座標快照；座標改變時清除對應的舊天氣快取，避免 Place ID 座標變更後仍顯示舊地點資料。

**權限審查**：`tc_weather_store_coordinates` 使用 `SECURITY DEFINER`、固定 `search_path`，撤銷 `public`、`anon`、`authenticated` 權限，只授予 `service_role` 執行；租約函式同樣受限。

**審查結論**：功能必要，變更限於天氣快取與座標一致性，不直接改寫旅程資料。

### 4.3 `20261016100000_v3101_production_schema_alignment.sql`

**目的**：讓從 migration 重建的乾淨本機 schema 對齊正式資料庫既有欄位、索引、約束、trigger、Storage policy 與 Realtime 狀態。

**已確認的正式環境事實**：`expenses.id` 已是 `bigint identity`；目標欄位契約、索引、trigger、檢查約束、Storage policy 與 Realtime membership 已存在。原始 migration 在正式環境會無條件重建 Storage policy／trigger、重做已相符的欄位 DDL，並掃描已有約束／索引保護的資料表；這些屬不必要的正式環境變更或工作量。

**已在尚未部署的 migration 檔案中修正**：

- 只有在 `expenses.id` 真的是 UUID、且安全檢查通過時，才暫時移除依賴該欄位的 Storage policies；正式環境已是 `bigint identity`，不會進入此分支。
- 欄位只有在型別、NULL／DEFAULT 狀態與目標不同時才執行 ALTER，避免正式環境不必要的 DDL lock。
- 只有對應的約束／唯一索引缺失時才掃描資料以檢查違規／重複值。
- 既有 Storage policies 與 trigger 保留；只有缺少時才建立。
- 身分保護 trigger 函式的條件與正式環境定義對齊，避免兩筆 migration 之間短暫改變 NULL 比較語意；並在第一筆 alignment migration 即撤銷公開執行權限、只授權 `postgres`／`service_role`。

**審查結論**：必要的是「缺少時補齊」的對齊能力；不應無條件重建正式環境已相符的政策、trigger 或欄位。修改後已在本機以交易回滾方式試跑五筆 migration，SQL 執行通過，變更全部 rollback；尚未對正式資料庫執行。

### 4.4 `20261016103000_v3101_production_schema_alignment_followup.sql`

**目的**：修正本機 UUID→bigint 對齊時可能產生的 identity sequence 名稱，並讓幾個身分保護 trigger 函式與正式環境一致。

**正式環境查核**：暫存 sequence `expenses_id__production_seq` 不存在；`admin_users_normalized_email_check`、`admin_users_role_check` 兩個約束也不存在，因此相應 rename／drop 分支不會改變正式 schema。函式最終定義與正式環境一致，ACL 限制為 `postgres`／`service_role`。

**審查結論**：保留作為 migration history 的向前修正；正式環境預期不會改變資料列或主鍵，也不應引入新的公開權限。

### 4.5 `20261016140000_v3101_weather_refresh_schedule.sql`

**目的**：安裝 `pg_net`、建立由資料庫 Cron 呼叫的 dispatch 函式，並每 6 小時於 UTC 01/07/13/19（台灣時間 09/15/21/03）觸發天氣 Edge Function。

**正式環境前置條件**：唯讀盤點確認正式環境目前沒有 `pg_net`、天氣 Cron job、`SUPABASE_URL` Vault secret、`WEATHER_CRON_SECRET` Vault secret，也沒有 `weather-forecast` Edge Function。排程 migration 若在 secret 尚未就緒時套用，未來排程執行會丟出 `WEATHER_CRON_VAULT_SECRETS_NOT_CONFIGURED`。

**審查結論**：功能必要，但必須放在正式發布順序後段；只有在 Edge Function 已部署並通過測試、Vault 中的兩個必要名稱已正確設定、Edge Function secret 與 Vault 中的 `WEATHER_CRON_SECRET` 值一致後，才可套用並啟用排程。不得把 secret 值寫入 repository 或文件。

### 4.6 `20261017100000_v3101_weather_scheduled_refresh_acl_fix.sql`（部署後權限修正）

**發現**：原 Edge Function 在排程路徑直接更新 `weather_daily_forecasts.last_scheduled_refresh_at`，但依最小權限設計，`service_role` 對該表只有 SELECT。該欄位更新會被拒絕，因此不可把原本 HTTP 200 空結果當作已驗證所有寫入路徑。

**修正**：新增 `SECURITY DEFINER` 函式 `tc_weather_mark_scheduled_refresh(text, date)`，固定 `search_path`，只授予 `service_role` 執行；Edge Function 改呼叫此 RPC。正式 catalog 驗證 `service_role` 可執行、`anon`／`authenticated` 不可執行，且 `service_role` 仍無 `weather_daily_forecasts UPDATE` 權限。已套用 migration 並重新部署 Edge Function；受控 dispatch 再次回傳 HTTP 200、`results=[]`、無 HTTP error。

## 5. Schema diff 與權限差異：禁止直接套用生成 SQL

`npx supabase db diff --from linked --to local --schema public,private,storage` 仍會輸出大量與 V3.10.1 無直接關係的角色權限差異，包括：

- 多個既有 helper function 的 `service_role` `REVOKE`。
- 既有表格的 `service_role` GRANT／REVOKE。
- `postgres` role 的 default privileges 差異。
- 本機 `tc_current_email()` 對 email 加 `lower()`，正式版本沒有此行為。
- 本機 `tc_touch_updated_at()` 使用 `clock_timestamp()`，正式版本使用 `now()`。

這些差異未全部證明為無害，且有些會改變既有權限或應用語意。**不可把整份 schema diff 當成正式部署 SQL，也不可為了讓 diff 清空而一併推送這些差異。** 本次只套用經核准的五筆原始 migration，另有一筆經部署後權限驗證發現的必要 ACL 修正 migration；上述既有 drift 應另立議題處理。

## 6. 實際正式發布順序與結果

1. 備份／復原方案、維護窗口與正式發布負責人確認；再次唯讀核對 migration history 與 schema preconditions。
2. 依組織的 Secret 管理流程建立正式 Vault `SUPABASE_URL`、`WEATHER_CRON_SECRET`，並為 Edge Function 設定同一個 `WEATHER_CRON_SECRET` 與必要的 Google Places API key；只確認名稱與存在狀態，不輸出 secret 值。
3. 依序套用前四筆 migration，核對資料表、RLS、最小權限、約束／索引、Storage policies、trigger、Realtime 與 migration history。
4. 部署 `weather-forecast` Edge Function，確認其使用正式 Supabase URL、service-role credential、Google Maps API key 及匹配的 Cron secret；先以受控測試驗證授權、單卡、跨行程與錯誤回應。
5. 只有在 Edge Function 及 Vault 都通過檢查後，才套用第五筆排程 migration；核對四個 UTC 排程、dispatch HTTP 回應與 `cron.job_run_details`。
6. 更新 `appVersion.ts`、`public/app-version.json`、`versionHistory.ts` 為 V3.10.1 正式設定，採一般更新、最低支援版本暫維持 `3.9.27`；完成 build、版本政策測試、PWA／瀏覽器回歸與使用者端更新提示驗收。
7. 最後部署前端產物，驗證正式 metadata、APP 更新提示、天氣卡片與離線／背景回前景行為。所有必要驗收通過後才記錄為正式發布完成。
