# V3.6.5 PWA 更新後介面顯示效能改善規格

> 狀態：Product Owner 已於 2026-09-03 核准兩項改善方向，尚未實作
>
> 建立日期：2026-09-03
>
> 版本類型：Patch

---

## 一、問題與版本邊界

V3.6.1 已修正「第一次點擊只檢查更新、必須第二次點擊才會實際更新」的 Service Worker 競態；V3.6.2 實測亦確認單次點擊可完成更新。本版不重新設計該流程，而是處理更新成功後，使用者仍需等待較久才重新看見 App 介面的問題。

V3.6.5 只納入以下兩項已核准改善：

1. App 資料狀態已就緒時，立即移除靜態啟動畫面，不再等待目前功能頁的 lazy chunk 完成。
2. App 初次載入期間共用同一份 Trip 雲端快照，避免旅程清單與旅程詳細資料依序重複讀取完整雲端 Trip。

不變更 Supabase schema、RLS、角色、同步資料格式、版本更新按鈕、`SKIP_WAITING`、`controllerchange` 或單次 reload 保護。

## 二、可移除效能量測

量測預設完全關閉；只有網址帶有 `?app-perf=1` 時才記錄，並以 `[App Performance]` JSON 寫入目前裝置的瀏覽器 Console。

量測範圍包含：

- Service Worker 註冊、更新 ready、按下更新、版本政策檢查、`registration.update()`、`SKIP_WAITING`、`controllerchange` 與 reload。
- reload 前資料以 `sessionStorage` 暫存一次，新頁讀取後立即移除，僅供串接同一次更新的前後時間軸。
- 新頁 navigation timing、React render、Session 還原、Trip metadata、Trip detail、資料 ready 與啟動畫面移除。
- 不上傳量測資料、不新增遠端 telemetry、不記錄 Trip 內容、帳目、Email 或權限資料。

量測程式集中於 `src/utils/appPerformance.ts`，其餘檔案只保留具名 mark；完成 V3.6.5 實機驗證後，發布候選版預設移除量測檔與所有呼叫點，除非 Product Owner 另行同意保留。

## 三、V3.6.2 基準量測與判定

2026-09-03 以 localhost production preview、桌面 Chrome、Guest、既有 Service Worker 更新至 V3.6.2 進行受控量測：

| 階段 | 更新後首次 reload | 一般 reload 對照 |
| --- | ---: | ---: |
| 按下更新至新版 Worker 接管 | 約 38 ms | 不適用 |
| 按下更新至要求 reload | 約 45 ms | 不適用 |
| navigation 至 Service Worker 開始處理 | 約 1,018 ms | 約 2 ms |
| navigation 至 App 資料 ready | 約 1,788 ms | 約 642 ms |
| navigation 至啟動畫面移除 | 約 2,099 ms | 約 951 ms |
| 資料 ready 後額外等待啟動畫面移除 | 約 311 ms | 約 309 ms |

判定如下：

1. 更新按鈕、Worker ready 與 `controllerchange` 並非本次主要慢點；不得為追求速度而移除既有單次更新安全保護。
2. 更新接管後第一次 navigation 約有 1 秒瀏覽器／Service Worker 啟用等待，一般 reload 未出現相同等待。此段由瀏覽器管理，本版不採繞過 reload、混用新舊 bundle 或提前 reload 等高風險作法。
3. App 初始化會先完成 Trip metadata，再讀取 Trip detail；兩者目前都會呼叫完整的 `getCloudTripRecords()`，形成可避免的同次啟動重複查詢。
4. App 資料已 ready 後，`AppLaunchReady` 位於功能頁 `Suspense` 內，仍需等待 lazy chunk 才移除靜態啟動畫面，基準差距約 0.31 秒。

以上數值只代表本機桌面樣本，不直接視為 Android／iOS 正式結果；改善前後必須在相同裝置、網路與登入狀態下比較。

## 四、改善一：資料 ready 後立即顯示 App

- 將靜態啟動畫面的移除條件固定為 `isSessionReady && !isLoading`。
- 啟動畫面移除不得再依賴 `ItineraryPage` 或其他目前功能頁 lazy chunk 是否完成。
- lazy chunk 尚未完成時，顯示既有「載入功能中...」fallback；不新增動畫、文案、圖示或版面設計。
- 維持設定缺失、必要更新提示與既有錯誤狀態，不得因提早移除啟動畫面而短暫顯示未授權內容。
- 目標是消除「資料 ready 至啟動畫面移除」的固定等待，不承諾消除瀏覽器控制的 Service Worker navigation 時間。

## 五、改善二：初次載入共用 Trip 雲端快照

- 初次載入只取得一次 Trip 雲端資料，供旅程清單合併及初始旅程詳細資料選取共用。
- 共用範圍只限同一次 App 初始化，不建立跨頁面、長時間或跨帳號的全域快取。
- 其他資訊仍依既有 RLS-safe query、pending queue 與 merge 規則載入；不得因共用 Trip 快照而跳過權限過濾或覆蓋較新的本機 pending 資料。
- 登入狀態改變、切換 Trip、回到前景、Realtime 通知、重新連線及使用者手動刷新，仍依各自流程取得新資料，不沿用啟動快照。
- 初次查詢失敗、離線或雲端無資料時，必須維持既有 seed／localStorage fallback 與錯誤處理。
- 不以固定秒數 TTL 快取取代本次啟動快照，避免跨裝置變更被延遲看見。

## 六、驗收條件

### 更新安全回歸

- 手機與桌面從舊 build 更新時，第一次點擊即可完成更新。
- 只在新版 Worker 已接管後 reload，且整個流程只 reload 一次。
- 更新後不得出現舊 App shell、新舊 bundle 混用、空白頁或重複更新提示。
- `app-version.json` 繼續使用 `cache: "no-store"` 且不得加入 PWA precache。

### 顯示與資料回歸

- `isSessionReady && !isLoading` 後立即移除靜態啟動畫面；lazy chunk 尚未完成時顯示既有 fallback。
- Guest、User、所屬／其他 Trip editor、super admin 的初始可見範圍與編輯權限不變。
- 登入、登出、切換 Trip、線上、離線、pending queue、跨裝置更新與重新連線後資料結果不變。
- 初次載入的完整 Trip 雲端讀取由兩次降為一次；後續需要新鮮資料的流程不得被合併或快取。

### 效能驗證

- 改善前後各至少量測 5 次，分開記錄更新後首次 reload 與一般 reload，不以單次最快值判定。
- 桌面 Chrome／PWA 與 Android Chrome／PWA 為必要矩陣；iOS Safari／standalone PWA 有設備時補驗。
- 應分開報告 Worker 接管、Service Worker navigation、Trip 初始化及啟動畫面移除，不以總時間掩蓋個別退化。
- 若改善造成權限、離線、同步或更新安全回歸，立即停止該項改善，不以效能收益接受資料風險。

## 七、非本版範圍與發布決策

- 不取消更新後 reload，也不繞過 Service Worker 接管等待。
- 不改為自動更新、不移除更新提示、不改變必要／一般更新政策。
- 不修改 PWA scope、start URL、precache 範圍或 Supabase schema／RLS。
- V3.6.5 是否採必要更新，待實作完成與風險驗證後由 Product Owner 決定。
