# V3.6.4 正式發布操作手冊

> 狀態：Git／CI／production backup／migration／結構核對已完成；待 Product Owner 手動執行兩階段 GitHub Pages 發布
>
> 建立日期：2026-09-07
>
> 固定順序：備份 → migration → V3.6.3 smoke → V3.6.4 assets → assets 驗證 → V3.6.4 metadata →正式 smoke

## 一、不可跳過的停止條件

- Git 工作目錄不乾淨、`develop` 尚未完整合併至 `main`、GitHub Actions 最終驗證未通過，立即停止。
- migration history 分歧，或 dry-run 不只列出 `20260904105703_v364_trip_data_revision.sql`，立即停止；不得執行 `migration repair`。
- logical backup 任一檔案為空、dump 失敗或無法取得 SHA-256，立即停止。
- migration 後出現新的 Security／Performance Advisor finding，或 V3.6.3 登入、讀取、Trip 寫入、Travel Tool 任一失敗，不發布 V3.6.4 assets。
- 第一階段正式資產未逐檔通過，或正式 `app-version.json` 不再是 V3.6.3，不發布 V3.6.4 metadata。
- 任何步驟失敗只保存錯誤並停止，不重複盲目執行、不改寫已套用 migration history。

## 二、發布前 Git 與 CI

1. 確認 `develop` 已推送且工作目錄乾淨。
2. 將 `develop` 合併至 `main` 並推送；正式候選必須以 `main` 的確切 commit 為準。
3. 從 GitHub Actions 手動執行 `V3.6.4 Supabase validation`，確認 migration、RLS、Realtime、V3.6.3 無 header 相容、advisor、回滾與重新套用全部通過。
4. 執行 `npm ci`、`npm run lint`、`npm run build` 與 `git diff --check`。
5. 建立並推送 annotated Git 版本標籤 `v3.6.4`；這只建立 Git 發布基準，不代表 App 已發布。

## 三、無額外費用的 production logical backup

Supabase platform preflight 顯示 `PITR=false` 且沒有可用 physical backup。正式 migration 前須啟動 Docker Desktop，將下列三個 dump 存到 repository 外、只有 Product Owner 可存取且具足夠空間的位置；不得放進 Git、雲端公開目錄或 `.release`。

```powershell
$backupDir = '<repository 外的私密絕對路徑>\Travel-Companion-v364-pre-migration-20260907'
New-Item -ItemType Directory -Path $backupDir
npx supabase db dump --linked -f "$backupDir\roles.sql" --role-only
npx supabase db dump --linked -f "$backupDir\schema.sql"
npx supabase db dump --linked -f "$backupDir\data.sql" --use-copy --data-only -x "storage.buckets_vectors" -x "storage.vector_indexes"
Get-ChildItem -LiteralPath $backupDir -File | Select-Object Name,Length
Get-ChildItem -LiteralPath $backupDir -File | Get-FileHash -Algorithm SHA256
```

三個檔案都必須存在且非空，並把檔名、大小與 SHA-256 記入《28_V3.6.4_實作與驗證紀錄》。dump 包含正式資料，不提交 repository；確認後關閉 Docker Desktop。

## 四、production migration 與 V3.6.3 相容窗口

先保留一個已完整載入、仍為 V3.6.3 的正式站分頁，再執行：

```powershell
npx supabase migration list --linked
npx supabase db push --linked --dry-run --skip-vault
npx supabase db push --linked --skip-vault
npx supabase migration list --linked
npx supabase db advisors --linked --type all --level warn --fail-on none
```

只允許套用 V3.6.4 migration。套用後以保留的 V3.6.3 分頁完成：

1. Google 登入與 Session 維持。
2. Trip 清單、目前 Trip 與每日行程讀取。
3. 不帶 `x-travel-companion-client-id` 的 Trip 主資料儲存。
4. 既有共同清單、其他資訊、記帳與換匯等 Travel Tool。
5. console 無新增 error；測試資料復原或清除。

## 五、手動兩階段 GitHub Pages 發布

截至 2026-09-07，前四節由 Codex 可完成的作業已執行並記錄於《28_V3.6.4_實作與驗證紀錄》。以下為 Product Owner 的手動發布入口；不得改用一般 `npm run deploy`。

現行一般 `npm run deploy` 會讓 assets 與必要更新 metadata 同批上線，本版禁止直接使用。V3.6.4 固定使用以下命令：

```powershell
npm run release:v364:prepare-assets
npm run release:v364:publish-assets
npm run release:v364:verify-assets
npm run release:v364:publish-metadata
npm run release:v364:verify-metadata
```

- `prepare-assets` 建立 production build，從正式站讀取 V3.6.3 metadata，另建被 Git 忽略的 `.release/v364-assets`。原始 `dist` 保留 V3.6.4 metadata，staging 則保留 V3.6.3 metadata。
- `publish-assets` 使用 `--add` 發布新資產並保留舊 hashed assets；執行前再次確認正式 metadata 未改變。
- `verify-assets` 逐檔比對正式站與候選 SHA-256，並確認 metadata 仍是 V3.6.3；未通過時，下一階段防呆會拒絕執行。
- `publish-metadata` 只在第一階段已驗證且候選未改變時，使用同一組資產公開 V3.6.4 必要更新 metadata。
- `verify-metadata` 再次逐檔比對並確認 `version=3.6.4`、`minimumSupportedVersion=3.6.4`、`forceUpdate=true`。
- 完成全部正式 smoke 與證據整理後，執行 `npm run release:v364:cleanup` 清除本機 staging；舊 hashed assets 暫時保留，避免更新中的舊客戶端載入失敗。

## 六、正式 smoke 與人工驗證

1. V3.6.3 取得不可略過的必要更新；更新後只發生一次 Service Worker 接管與 reload。
2. V3.6.4 同版不重複顯示更新提示，登入、Trip 與 Travel Tool 正常。
3. 兩個隔離 Session 驗證一般提醒、稍後只鎖 Trip、own-source 排除、版本衝突、撤權最後訊號、Trip 刪除與停止接收。
4. 測試只使用指定的臨時 Trip／角色，完成後清除並確認私人資料與其他 Trip 未受影響。
5. iOS 與兩台實體裝置完成指定流程後，才能把狀態改為「已發布」。Android 依 Product Owner 決定於發布後補驗。

## 七、失敗與回復

- migration 在 transaction 提交前失敗：停止，確認沒有新 migration history，不發布 assets。
- migration 已提交但 V3.6.3 smoke 失敗：停止前端發布；依已驗證的 `docs/sql/023_v364_trip_data_revision_rollback.sql` 評估緊急停用，但正式修正仍以新的 forward migration 為原則。
- assets 階段失敗：metadata 尚為 V3.6.3；保留證據並停止，不會觸發必要更新。
- metadata 階段失敗：確認正式 metadata 實際內容；必要時先從 `v3.6.3` 基準重新發布 V3.6.3 metadata，再處理 App assets。
- 不刪除或移動已發布的 Git 版本標籤，不回寫已套用 migration。
