# 卡片編輯故障根因與旅程級編輯契約調查紀錄

> 文件狀態：統一架構已定案（ADR-001 Accepted）；本文件負責根因證據、統一實作審查方案與驗收追蹤。尚未授權開始本次整合架構的程式實作。
> 建立日期：2026-11-19；統一架構定案／文件整理：2026-11-19
> 範圍：僅限 ADR-001 所定義的「每日詳細行程」：卡片新增／修改／刪除、旅程級單一編輯權、保存協調、更新提示簡化。其他功能的同步與驗證行為維持不變。

## 1. 工作目標與統一執行方式

本工作統一處理原 P0 卡片保存可靠性、P1 旅程級單一編輯權及 P3 提示簡化。三者必須依同一目標架構設計，不再把 P0 當成先獨立最佳化、P1 之後再另行重構的兩套工作。既有 P0 已完成的最小修正與測試證據保留，後續實作仍須核對其與統一鎖定／保存契約是否一致。

- **P0＋P1：統一編輯與保存協調。** 由 Trip Edit Lock 決定編輯權，Realtime 提供事件通知，Revision 提供必要更新／異常訊號，CAS／Version 防止舊版本覆寫，Local Pending Sync 負責本機持久化及離線恢復。每日詳細行程新增／修改／刪除與恢復同步使用同一協調入口，不增加平行卡片外部驗證機制。
- **P2：範圍隔離及回歸驗收。** 證明清單、帳本、旅程基本資料、設定及其他非每日詳細行程功能沒有被鎖定或改動同步行為。
- **P3：提示與背景工作簡化。** 取消每日詳細行程的變更預覽、變更分類／統計計數與專用摘要呈現；只保留編輯鎖提示及資料更新提示。更新事件只提示，不自動讀取完整 Trip／Journal；進入每日詳細行程管理時主動取得鎖及必要最新狀態，使用者主動要求更新時再讀取。正常瀏覽不持續輪詢鎖或完整 Trip。

工作順序採「先統一目標設計與詳細審查，再按相依性實作與驗收」，不再規定 P0 必須完全結案後才能開始 P1 設計。任何程式修改仍須通過本文件第 5 節審查及明確實作授權；本次僅完成架構定案與文件整理。

**問題現象（使用者實際回報）：**
- Preview 環境（`npm run preview`）儲存後反覆出現「正在確認其他裝置的卡片編輯狀態…」及「新增依到達時間排序；編輯時間不改卡片順序。」等訊息。
- 其他裝置收到變更通知，但開啟變更預覽時摘要內容或結果不正確。
- 正式網站刪除卡片後，卡片先消失，稍後又重新出現，並顯示「已偵測遠端變更」。
- 正式網站新增卡片也回報儲存後無法持續保存及顯示。
- 使用者質疑既有編輯鎖既已限制同一資源的編輯權，為何儲存仍頻繁遇到編輯／版本衝突；應優先排除重複、互相矛盾或不必要的程式碼邏輯，不應先增加更多同步或合併機制。

**既有 P0 工作與結果：**
- 曾以最小修正把全域 revision 通知刷新與保存授權分離：仍可更新 revision 通知，但全域 revision boolean 不再單獨拒絕合法卡片保存；真正的 `TripVersionConflictError` 仍拒絕覆寫。
- 既有 P0 單元／契約測試、原七項 revision／preview／version recovery／workspace recovery／merge／lease 測試、完整 build 及 local Supabase 雙 Auth/JWT/HTTP context 整合測試均有通過紀錄，詳見本文件第 7、9 節。
- 仍待兩個真實瀏覽器 profile 的 App UI 端到端操作，以及 offline pending→online recovery 的真實瀏覽器 lifecycle 驗收。既有證據不可被擴大宣稱為完成完整 UI 驗收。
- 上述最小修正保留為統一架構的既有基礎，不代表新的 P0＋P1＋P3 整合實作已完成或已驗收。**整合修改完成後，原 P0 所有既有 PASS 測試、build、資料庫整合測試及實際瀏覽器操作案例都必須重新驗證；舊結果只作基準，不可抵用整合後驗收。**

### P0＋P1 統一目標契約

- 「每日詳細行程管理」被視為明確的編輯意圖入口：進入該管理介面前向伺服器以 atomic claim 取得目前 Trip 的 Lock；claim 成功及取得必要最新資料後才開放管理／編輯。一般瀏覽及其他功能均不 claim 此鎖。
- 一般瀏覽及其他功能期間不查詢或持有每日詳細行程編輯鎖。
- 進入每日詳細行程管理是明確的編輯意圖入口；伺服器以單一 atomic claim 取得整趟 Trip 的編輯權，不採用分離的「先查詢、再寫入」。
- 成功取得後，該裝置才能進入該旅程編輯模式。
- 其他裝置按下編輯時，若已有其他有效持有者，必須拒絕進入編輯模式並顯示清楚狀態；使用者可稍後重試。
- 編輯期間僅保留維持有效租約必要的續期機制；租約失效時不得繼續以有效編輯者身分寫入。
- 正常退出編輯時釋放編輯權；異常中斷由租約到期回收。
- 編輯權以整趟旅程為單位，不是每張卡片各自取得鎖。
- 儲存應遵循編輯權所有權，不應再以重複或矛盾的本裝置 revision 檢查阻止合法持有者保存。
- 若 lock claim 成功但讀取最新 Trip／版本失敗或無法確認，不得先開放編輯；顯示無法確認狀態並維持原資料與 Pending 安全。

**統一實作工作：**
1. 檢查目前卡片級 lease 的 schema、RPC、取得／續期／釋放、Realtime 通知與有效期。
2. 提出最小可行的旅程級契約修改方案，並確認 DB 原子性與失效安全。
3. 盤點所有每日詳細行程寫入入口，定義唯一 lock／save 協調入口及伺服器端 enforcement。
4. 依 P3 移除預覽／計數與不必要背景讀取，保留輕量更新提示及操作時補查。
5. 完成統一方案審查及必要測試設計後，才進入整合實作。

### P2：範圍隔離與回歸驗收

P2 與統一架構實作同步設計、在整合實作後驗收，確認 ADR-001 外的功能維持原行為。

至少驗證：
- 清單、帳本、旅程基本資料、旅程設定、Other Info 及其他非每日詳細行程功能不受 Trip Edit Lock 阻擋。
- 上述功能既有 revision、Realtime、同步、提示、CAS／版本及驗證流程未被修改或繞過。
- Daily Itinerary 自身的 revision／Realtime 輕量通知、操作時最新狀態補查及資料更新提示運作正確；不再出現預覽與變更計數。
- 本機保存、雲端同步、pending retry、離線與重新連線恢復均維持資料安全。
- 一般瀏覽不查詢鎖；管理意圖原子取得 Trip Lock；第二裝置取得失敗；續期、失效、正常釋放及到期回收正確。
- 合法持有者新增、修改、刪除，保存及重新讀取後資料一致。

不得只以單元測試或假資料斷言「其他功能沒有改變」；應對既有機制設計可重現的回歸驗收。所有正式資料庫及正式旅程資料均不得用作破壞性測試。

## 2. 不可違反的限制

1. **統一設計：** P0＋P1＋P3 必須依 ADR-001 的同一架構設計與審查，不得先把 P0 做成獨立保存機制再另行重構。
2. **最小修改：** 僅修改根因或統一契約必要的程式；禁止藉機全面重構其他同步、資料模型或 UI。
3. **保留必要更新訊號：** P3 移除預覽及計數，不代表移除必要的 revision／Realtime 更新通知及事件遺失後補查。
4. **先查清責任：** 必須分辨 Realtime 訂閱、focus／visibility／online 補查、30 秒 connectivity probe、workspace reconciliation、pending 恢復及 Trip lock heartbeat；不可用「移除輪詢」一語概括全部工作。
5. **不增加重複保護機制：** 先驗證現有鎖與版本保護的責任是否重疊或互相衝突；不得未經證據就新增另一套鎖、版本或合併流程。
6. **編輯權與更新提示分離：** Trip Lock 負責授權；Realtime／Revision 提示只告知資料可能更新，均不得互相取代。
7. **正式環境保護：** 不操作正式 Supabase DB，不用正式使用者旅程做刪除／新增等破壞性驗證，不修改正式資料。
8. **外部操作限制：** 未經明確核准不得 commit、push、建立 RC、發布或部署。
9. **其他工作保護：** 不覆蓋、還原或混入同工作樹其他未提交工作；先檢查 Git 狀態與變更歸屬。
10. **證據優先：** 結論需標示「已確認證據」「合理假設」「尚待驗證」，不得將可能原因寫成已證實根因。
11. **回歸驗收：** 每一段都須留下測試範圍及結果；第三段需證明既有功能維持原行為。

## 3. 調查時必須分清楚的三個子系統

### A. 編輯權管理（誰有權修改）

回答：
- 誰可以進入編輯模式？
- 編輯權是否具備原子取得？
- 鎖定範圍是單張卡片還是整趟旅程？
- 租約何時續期、釋放、到期？
- 失去編輯權後是否仍可保存？
- 儲存端是否驗證目前持有者？

編輯權管理只負責授權與排他，不負責資料更新通知、預覽或變更筆數計算。

### B. 更新提示與最新狀態取得（何時通知、何時讀取）

回答：
- 如何用輕量 Realtime revision 事件產生資料更新提示？
- 進入每日詳細行程管理或使用者主動更新時，如何補查最新 Trip／版本？
- Realtime、focus／visibility／online 恢復各自負責什麼，哪些讀取可取消？
- 斷線、休眠、事件遺失後，如何確保進入管理與保存時不使用過期資料？
- 本裝置自己的寫入如何避免誤觸發對外更新提示？

更新提示只告知有資料更新，不計算預覽或統計筆數，也不得被拿來授予或拒絕編輯權。

### 子系統交界規則

- 編輯權取得成功不代表可省略進入管理時的最新資料讀取。
- Realtime 可作低成本資料更新提示，但不能作為資料最新性的最終證據。
- 明確操作時點為：進入每日詳細行程管理、使用者主動更新，以及保存／Pending 恢復前的必要驗證；在這些時點以權威讀取確認最新資料。
- 移除每日詳細行程背景預覽讀取後，進入管理、主動更新及保存時的必要讀取／CAS 必須涵蓋事件漏失。
- 舊 30 秒 connectivity probe、workspace recovery 與 lease heartbeat 各自獨立評估；不得把它們一併當成可移除輪詢。

## 5. 最小修改方案審查要求

提出方案時，必須逐項說明：
1. 根因與可重現路徑。
2. 根因證據的檔案／函式／資料流位置。
3. 最少需要修改的檔案清單，以及每個檔案的必要性。
4. 哪些現有檢查／輪詢／重試必須保留、調整或移除；逐項列出責任，不得只寫「簡化輪詢」。
5. preview／統計移除後 revision／Realtime 更新提示、操作時補查、source-client 排除及離線恢復的影響與回歸方式。
6. 旅程級鎖的資料庫原子性、租約到期、釋放、所有權校驗及失效安全。
7. 最小測試集合與通過條件。
8. 明確列出不修改的檔案／功能，以證明範圍受控。

方案審查未通過或根因尚不清楚時，不開始程式修改。

## 6. 根因調查結果與證據

### 6.1 已確認證據

**E1 — 卡片儲存前以全域 revision 通知作為拒絕條件（高可信度的直接程式缺陷）**
- `src/App.tsx` 的 `onSaveTripDetail` callback（目前約第 1592 行附近）在呼叫 `saveItineraryTripDetail(trip)` 前先執行 `await checkForRemoteTripChange()`；若回傳 `true`，直接 throw「偵測到其他裝置的資料變更，請重新載入後再試」並中止卡片儲存。
- `src/hooks/useTripDataRevision.ts` 的 `checkForRemoteTripChange()` 讀取的是 `app_data_revision` 全域 singleton，接著由 `acceptRevision()` 按 `shouldNotifyForRevision()` 判斷是否需要通知。
- `src/services/tripDataRevisionService.ts` 的 `shouldNotifyForRevision()` 條件為 revision 前進且（來源 client 不同 **或** revision 有缺口）。它不檢查本次待保存的旅程是否發生衝突，也不是編輯權確認。
- DB trigger `supabase/migrations/20260904105703_v364_trip_data_revision.sql` 在 `trips` 的 INSERT/符合欄位條件的 UPDATE/DELETE，以及 trip editor 權限變更時都會推進同一筆 `app_data_revision`。因此其他旅程的資料或管理者權限事件也可能影響目前旅程卡片儲存前的判斷。
- 實際資料寫入已另有旅程版本競態保護：`src/services/tripCloudService.ts` 的 `updateCloudTripRecord()` 使用 `.eq("id", tripId).eq("updated_at", expectedUpdatedAt)`；無資料回傳會丟出 `TripVersionConflictError`。`src/services/tripRepository.ts` 再經 `updateTripWithVersionRecovery()`，只有雲端 Trip 本體沒有差異時才允許修復舊 cloudUpdatedAt，真正資料差異仍保留衝突阻擋。

**判定：** 將全域通知判斷當作卡片保存的前置拒絕條件，是已由程式碼確認的錯誤責任耦合；它會在沒有證明目前旅程資料衝突時阻止儲存。這是 P0 最優先的根因候選／直接缺陷。正式環境「卡片先消失後復現」是否完全由此造成，仍須在隔離測試資料下重現；現有證據不足以將所有復現現象只歸因於此一處。

**E2 — 全域更新來源與歷史 preview 過濾機制（P3 後續需核對共用依賴）**
- `src/App.tsx` 建立 Supabase client 時已設置 `x-travel-companion-client-id: APP_SOURCE_CLIENT_ID` 全域 header。
- `private.tc_request_source_client_id()`（revision migration）從 `request.headers` 讀取該 header，若缺失或 UUID 解析錯誤則回傳 null；revision trigger 與 `trip_change_journal` writer 都使用此函式。
- `src/services/tripChangePreviewService.ts` 過濾 `source_client_id === APP_SOURCE_CLIENT_ID` 的 journal row，但保留 null source，並把它標為「遠端資料」。因此 client ID 缺失仍可能造成來源錯標；目前已確認程式有 header 設定，但尚未以實際 HTTP／本機 Supabase integration test 證實所有請求路徑都攜帶 header。
- 行程卡片預覽筆數不是直接累加 itinerary journal 的 added/deleted 次數；目前實作會以 snapshot baseline 和雲端目前 daysData 做淨差異比較，再以 journal 累計非 itinerary 類別。因此預覽錯誤應同時檢查 baseline 與 revision window，不宜只看 journal 計數。

**E3 — Revision 通知、操作時補查與 30 秒 connectivity probe 屬不同責任**
- `src/hooks/useTripDataRevision.ts` 目前同時處理初次 revision check、Realtime `revision_changed` broadcast，以及 focus、online、visibilitychange 時的補查；P3 應拆出每日詳細行程的輕量更新提示與操作時最新資料取得，不再為 preview window 維持背景完整讀取。
- `c95756a` 移除的是 `useTripWorkspace.ts` 中 30 秒 connectivity probe，以及每次 online/focus/visibility 的額外 workspace reconciliation effect。新的 `startTripWorkspaceRecoveryLifecycle()` 只有在 `recoveryPending`（例如 offline→online）時才嘗試 reconciliation。
- 因此不得把「30 秒 connectivity probe」和「revision/change count refresh」當成同一輪詢。現有 revision 監測本身未見 30 秒 interval。移除 c95756a 的固定探測後，變更偵測仍有上述 Realtime／focus／online／visibility 機制；但 workspace reconciliation 的觸發頻率確實改變。

**E4 — 目前編輯租約是卡片級，不是旅程級**
- `supabase/migrations/20261101103000_v31012_itinerary_card_edit_leases.sql` 的 primary key 為 `(trip_id, card_id)`；claim RPC 以此鍵執行原子 UPSERT，租約 45 秒，續期由 client 呼叫。
- `src/services/itineraryCardEditLeaseService.ts` 設定 heartbeat 15 秒。
- `src/components/ItineraryPage.tsx` 在 `canUseEditLeases` 時就初始化 lease 清單查詢與 Realtime listener，不是只有按下編輯時才查詢；按下編輯時另以 claim RPC 原子取得該張卡片租約。
- 因此目前 lock 的原子單卡 claim 並非沒有競爭保護；但其範圍及生命週期不符合使用者已同意的整趟旅程單一編輯契約。這屬 P1，不是目前 P0 儲存錯誤的充分解釋。

**E5 — pending 自動同步與重試風險**
- `src/hooks/useTripWorkspace.ts` 的 `saveItineraryTripDetail()` 會先本機保存 pending，再讀雲端、執行 pending reconciliation，最後條件式雲端寫入；同旅程 Promise Map 只序列化重疊中的呼叫。
- 另有 pending auto-sync effect：只要目前旅程同步狀態為 pending 且 session/online/permission 條件成立，就再次呼叫 `saveItineraryTripDetail()`。
- `startTripWorkspaceRecoveryLifecycle()` 只補做連線恢復時 workspace reconciliation；不直接刷新行程卡片 revision。
- **尚未證實：** 一次雲端失敗是否一定會讓 effect 自動再次啟動。需要以純本機 mock／測試確認 currentTrip 更新、sync state 更新和 effect dependency 的實際觸發序列，不可僅憑存在此 effect 就斷言已形成無限迴圈。

### 6.2 尚待驗證的根因項目

1. 以兩個隔離瀏覽器 context 與本機 Supabase 測試資料，重現「只有其他旅程 revision 增加」時，當前行程的卡片保存是否會被 `checkForRemoteTripChange()` 擋下。
2. 測試 client header 在 trips update、RPC 與 journal trigger 路徑實際落到 source_client_id 的結果（同 client ID、其他 client ID、null 三種）。
3. 對 pending auto-sync effect 建立 mock 測試，量測失敗後是否重複 GET／重試，以及會否以舊 `currentTrip` 再次提交。
4. 使用隔離資料重現新增／刪除後雲端回讀與本機 cache 的時間序列，確認是否還有 baseline、pending reconcile 或 workspace reload 將舊資料覆回的第二個原因。
5. 變更預覽在 journal window、snapshot updatedAt 與 revision interval 的交集條件下，核對用戶所見錯誤摘要的具體情境。

- 提交明確的程式／migration／測試檔案白名單，逐檔說明必要性；禁止順便改其他功能。
- 先完成單元／契約測試，再使用 local Supabase、兩獨立 Auth context 驗證資料庫原子 claim、server-side enforcement、CAS 與 pending；最後以兩個真正瀏覽器 profile 驗證 UI。

2. 同旅程真正的遠端版本變更仍受 `updated_at` compare-and-set、pending reconciliation 或既有真實衝突保護；不得改成無條件覆寫。
3. 新增、修改、刪除每一操作均需保存後重新讀取，確認雲端／本機狀態一致且不會由舊快照覆回。
4. 本裝置自己的 revision/journal 事件不誤當遠端衝突；來源 client header 的正常、異常／null 情境均需覆蓋。
5. 保留必要 Revision／Realtime 更新提示、source-client 歸屬、操作時最新狀態補查、Pending、離線與重新連線恢復責任；每日詳細行程預覽及變更統計依 ADR-001 取消，不要求保留僅供預覽的讀取與計算。
6. 不以正式 DB 或正式使用者旅程執行破壞性測試。

**既有 P0 測試證據與統一架構待驗矩陣：**
- A. 單一裝置、同旅程無遠端變更：新增／修改／刪除成功，刷新或重新讀取結果不回復舊值。
- B. 目前旅程未變、另一旅程推進全域 revision：合法保存仍成功；Realtime 只顯示輕量更新提示，不自動完整讀取 Trip／Journal 或計數。
- C. 另一裝置修改同一旅程：不得靜默覆蓋對方資料，應依既有 conflict／merge 規則明確保護。
- D. 本裝置寫入帶相同 client ID：不得觸發錯誤的遠端更新提示；null source 行為需有明確且可驗證的預期。
- E. offline pending→online recovery：不丟失本機變更、不重複提交舊快照，恢復後重新讀取一致。
- F. recovery lifecycle：原有 30 秒探測取消後的事件觸發與 `061046d` in-flight/completed 條件需維持；若未證實其缺陷，不恢復 30 秒 probe 或一般 focus reconciliation。
- G. 更新提示回歸：遠端 revision 事件只產生輕量提示；使用者進入每日詳細行程管理、主動更新或保存時能讀取可信最新資料；不顯示預覽或變更計數。
- H. Trip Lock／其他功能邊界：鎖定期間同 Trip 的清單、帳本、基本資料或設定仍可依既有流程更新，不得被每日詳細行程 Lock 無差別阻擋。

**測試分層：** 先以純本機 unit/mock 驗證 revision gate 與 recovery lifecycle 的狀態轉移；再用兩個隔離 context 與本機測試 Supabase 驗證真正的條件式更新、journal source 和讀回一致性；最後才在非正式的 Preview／測試環境做 UI 驗收。不能用靜態程式碼斷言取代跨 context 整合測試。

- 天氣結果若判定卡片不符合請求資格，且沒有可用的 cached weather，現行 effect 可能把卡片 `showWeather` 設為 false，並呼叫 `onSaveTripDetailRef.current()`。這會形成天氣結果回寫卡片、再次進入保存流程的反向回饋路徑，需一併驗證是否可能造成重入。
- effect cleanup 的 `cancelled = true` 只阻止後續 UI state 更新；目前這段 cleanup 本身沒有取消已送出的網路請求。若需中止請求，必須另有 AbortSignal／服務層支援。
- `src/services/tripRepository.ts` 的一般 `saveTripRecordWithCloudSync()` 仍走整筆 Trip record 的既有 cloud upsert/update + `updated_at` optimistic lock；這不是 ADR-001 已定案的專用 daysData Save RPC。此項是架構落差，仍待依 ADR-001 審查及實作，不可在本次紀錄中宣稱已完成。

**根因判斷（結構性風險，尚非執行量歸因）：**
1. **雲端確認／回讀重入（待量測）：** §10.2 的使用者實測已指出一次新增後約 2～3 次 DB 確認／回讀及畫面跳動；程式側 `saveItineraryTripDetail()` 含雲端讀取、pending reconciliation 與多個 `setCurrentTrip()` 更新點。這些狀態轉換可能重新觸發相關 effect／同步路徑，但目前尚未取得同一操作的 Network log，不能判定 2～3 次觀察分別對應哪幾個 SELECT／UPDATE，也不能宣稱每次保存一定重複執行。
2. **天氣請求重入（結構性風險）：** 保存／雲端核對／reconciliation 更新 daysData state（尤其產生新 daysData 參照）→ 天氣 effect 因依賴變動重新執行 → 快取雖可供畫面顯示，但 online 分支仍發 request → 若前一次 Promise 已結束，in-flight 去重已清除，同一 fingerprint 可能再次呼叫天氣 Edge Function。此為程式碼可達成的風險路徑，尚未證明每次卡片保存都會觸發，也未量化對既有天氣 POST 總量的貢獻。
3. **可能的反向回饋：** 天氣資格不符時回寫 `showWeather=false` 並呼叫保存 callback，可能再改變 daysData 並重入 effect；須驗證欄位已 false 時是否仍重複保存／請求。

**證據限制：**
- §10.2 的「約 2～3 次」是使用者實機畫面觀察，不是本次 Agent 已取得的 CDP Network 請求計數。
- 本節天氣部分是依程式碼資料流確認可達風險，尚未以本機隔離環境 Network log／request counter 實測一次保存實際觸發幾次天氣請求；不能將既有 Supabase 天氣 POST 總量直接歸因於卡片保存。
- 其他雲端 GET／UPDATE 的必要性及重複次數也尚未完成同一次操作的網路追蹤，須與天氣請求分開計數。

**V3.11.4 審查／修正驗收清單：**
1. 對單次卡片新增、修改、刪除及衝突／recovery 分別追蹤 save callback、local Pending、cloud preflight/readback、reconciliation、`setCurrentTrip`、daysData 參照及天氣 effect 執行次數；逐筆區分必要權威讀取與重複回讀。

**程式碼路徑證據（高度可信的 re-entry 缺陷候選）：**
1. `useTripWorkspace.ts` pending auto-sync effect（約 1268–1298）在 pending + online/session/permission ready 時呼叫 `saveItineraryTripDetail(pendingTrip)`；effect dependency 包含整個 `currentTrip`。
2. `saveItineraryTripDetail()`（約 919–954）每次被呼叫都以 `createPendingItinerarySyncState()` 建立新的 pending revision UUID，即使輸入的 pendingDaysData 內容未改變；接著保存 pending state 並呼叫 `setCurrentTrip()`（約 984–987）。
3. 這次 currentTrip 更新使 effect 重新評估。若前一保存仍在進行，同旅程 Promise Map 會讓下一次 save await 前一個 Promise，但等待中的呼叫並未被取消或以 pending revision 去重；前一 save 完成後，等待呼叫仍可能以 effect 捕獲的 currentTrip snapshot 再建立新的 pending revision。因而「Promise 序列化」不等於「同一待同步資料只處理一次」，可能形成 sequential re-entry / pending 循環，造成 UI loading／lease確認等狀態反覆更新。
4. `createPendingItinerarySyncState()`（`src/services/itinerarySync.ts` 約 440–456）每次必定 `crypto.randomUUID()`，沒有相同內容 revision reuse/once-only guard。既有 `verify-v31012-itinerary-sync.mjs` 只驗證 pending baseline 保持，不驗證相同 snapshot 的 idempotency。

**判定限制：** 上述來源形成完整且具因果性的重入路徑，與現場 pending/跳動一致；但目前尚無 browser network trace／runtime effect counter，因此記為高度可信的程式碼根因候選，未宣稱已完整證實 UI 無限迴圈或已修復。

## 11. ADR-001 審查紀錄：daysData enforcement 與版本隔離（2026-11-20）

### 已定案
- **DB Trigger 精準限制：** `daysData` 改變時由 DB enforcement 驗證有效 Trip Edit Lock；驗證租約持有者、必要 client identity 與租約期限，無效／過期租約拒絕寫入。非 `daysData` 更新不得因 itinerary lock 被阻擋，禁止 blanket row lock enforcement。
- **Edit Lock／CAS 分離：** Edit Lock 授權每日詳細行程編輯；獨立 itinerary CAS／Version 確認 `daysData` 保存基準。其他 Trip 功能造成的全列 `updated_at` 變更不得直接等同 itinerary conflict。
- **已定案：Trip-level Lease：** 將現有 card-level lease 改為每 Trip 單一 lease；每日詳細行程管理意圖進入時取得、正常退出釋放，異常中斷由 expiry 回收。Lease 身分以 `auth.uid()` 為權威，client ID 僅區分同一使用者的編輯 session。
- **已定案：原子保存契約：** Save RPC 交易內鎖定 Lease row，驗證 user/client/expiry 與 expected itinerary version，僅更新 `daysData` 並原子增加專屬版本。Claim/Renew/Release/Save 必須遵循一致序列化規則，以避免競爭接管造成授權失效。
- **已定案：直接寫入封鎖：** 專用 RPC 為唯一合法 `daysData` 寫入通道；Trigger 拒絕任何未經受控通道的直接變更，包含舊路徑。不得以單純前端旗標授權；必須證明一般 authenticated 無法偽造受控標記。其他 `content` 資料更新不受阻擋。
- **已定案：Pending 版本改造：** 保留三方 merge engine／本機 snapshot；baseline/conflict 使用 itinerary version。舊 timestamp state 不直接轉換；Recovery 先讀可信 Cloud data/version，保留 Pending，安全重建 baseline。無法安全重建則保留資料、停止自動覆寫。
- **實作安全驗證：** Trigger、RPC、權限及直接 UPDATE bypass 必須經資料庫整合測試證實，尚未實作或測試之前不得宣稱已封閉漏洞。以上決策未授權程式實作。

### 審查證據與不足
- `src/services/tripCloudService.ts` 的 `updateCloudTripRecord()` 現行整列更新與 `updated_at` CAS；`src/services/tripRepository.ts` 的 `saveTripRecordWithCloudSync()` 透過 version recovery。
- `trips_touch_updated_at` trigger 使整列更新都更新 `updated_at`，因此目前全列版本基準會被其他功能更新影響。
- DB enforcement 必須保證所有寫入 `daysData` 的途徑均受 trigger 限制，不只 UI/service 路徑；仍需審查 DB JSON comparison、NULL／缺欄位／型別與 dayCount/schema normalization、權限與 client identity 來源可信度、lease expiry/renew/release 競爭、以及版本 CAS 原子性。
- **下一步只繼續本項審查：** 盤點完整 `daysData` 寫入入口與 DB Trigger／RPC、現行 CAS recovery/Pending lifecycle、其他功能同列更新及資料內容交界；比較最小版本設計方案，提出實際方案與測試條件。項目完成定案前不得進入下一項或實作。

**執行邊界**
- 僅允許本機 loopback Supabase／隔離 DB、臨時 fixtures、短生命週期 Auth users/JWT、交易 rollback 與精確 finally cleanup；不得連線或寫入 linked／正式 Supabase，不使用正式使用者旅程資料。
- Auth 驗收必須建立兩個真正獨立的 Supabase Auth session，使用不同 user、不同有效 JWT，分開 HTTP/API request context；不得以單一 psql session 內反覆 set_config／切換 uid 冒充雙 Auth context。需以實際 Supabase Auth API 登入／簽發流程取得 session，並以 authenticated role/RLS/Trigger 實際驗證。postgres／service role 測試不能代替 authenticated 驗收。
- 競爭測試須由獨立程序／連線並行執行，記錄兩邊結果、最終 Lease owner、itinerary version、daysData 及 history；同時檢查 deadlock、rollback 和失敗時清理。
- 僅新增測試 runner、測試案例及本節所需紀錄；沿用現有 local-only Auth/JWT 測試及 Pending/merge 工具，不新增平行產品邏輯，不調整 ADR 架構。禁止 commit、push、RC、deploy、production DB 操作。

**測試自動化分層**
1. DB/Auth integration：本機 Supabase Auth API + 兩個獨立 JWT/session + authenticated REST/RPC + RLS/Trigger；涵蓋 SR-01～SR-11。
2. Concurrency integration：多程序／多連線同時呼叫 Claim、Renew、Release、Save；涵蓋 SR-04、SR-05、SR-11，並驗證 lock order、CAS、無死鎖及原子回滾。
3. App recovery regression：沿用 src/hooks/useTripWorkspace.ts、src/services/itinerarySync.ts 及現有 pending state/reconcile 函式與 Node 測試入口；涵蓋 SR-12 的成功恢復、三方合併、版本衝突、損壞 snapshot／baseline 無法重建時保留 Pending、不自動覆蓋。DB 測試不可代替此層。
4. 單一 orchestrator 彙整輸出每項 PASS／FAIL／BLOCKED、case ID、環境、兩個 context 的非敏感識別、請求結果、資料前後狀態摘要、錯誤與清理結果；不得輸出 JWT、密碼、secret 或完整旅程內容。未執行／缺少證據一律 BLOCKED，不可默認 PASS。
