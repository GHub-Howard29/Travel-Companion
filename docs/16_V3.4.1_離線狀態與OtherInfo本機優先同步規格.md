# V3.4.1 離線狀態與 Other Info 本機優先同步規格

> 建立日期：2026-08-06
>
> 狀態：程式與 Supabase SQL 已完成，待 Android／iOS 實機回歸
>
> 範圍：PWA 離線載入、領隊／導遊聯絡資訊、其他資訊、特殊資訊、側欄連線／登入狀態提示、App 版本提示及共用帳本多人疊加

---

## 一、問題背景

V3.4.0 部署後驗證發現五項需要在 V3.4.1 修正的問題：

1. 側欄目前可能把「尚未取得 Supabase session」誤判為離線，沒有明確區分網路、登入與快取權限。
2. Other Info 共用元件在新增、修改、刪除卡片時，會等待 Supabase 同步與 Trip 儲存流程完成後才更新畫面；離線、弱網路或 Supabase 無法連線時，使用者會長時間看到「儲存中」，刪除也會延遲才反映。
3. `travel_companion_seen_app_version` 只代表「已閱讀更新說明版本」，卻被沿用為新版提示條件，造成 App 已執行 V3.4.0 時仍顯示「目前版本 3.4.0／最新版 3.4.0／發現新版本」。
4. Android Chrome／PWA 的更新對話框可能延伸至系統導覽列下方，導致底部操作按鈕被遮擋。
5. PWA 斷網後重新開啟可由快取載入本機旅程，已載入的旅行工具也可切換；但在離線狀態下刷新 App 會出現瀏覽器「無法顯示頁面」等錯誤，表示離線導覽刷新仍有失敗情境。

目前慢速流程：

```text
使用者操作
  → 等待 other_info_items 雲端同步
  → 等待 Trip content 雲端同步
  → 重新取得 Trip 清單
  → 更新 React 畫面
```

問題不是裝置運算效能，而是畫面操作被雲端請求阻塞。

## 二、已確認的設計決策

採用「本機優先＋單一最新狀態背景同步」，不建立逐筆操作 Queue。

```text
使用者操作
  → 立即更新畫面
  → 立即寫入本機 Trip
  → 標記此 Trip 的 Other Info 待同步
  → 背景同步最新完整狀態
```

選擇理由：

- 效率：新增、修改、刪除與排序不等待網路。
- 風險：本機先保存，即使頁面關閉或雲端逾時也不遺失操作。
- 簡單：只同步某 Trip 的最新 `otherInfoItems` 快照，不重播「新增 A、修改 A、刪除 B」等逐筆命令。
- 相容：沿用既有 `client_item_id`、`isDeleted`、`updatedAt` 與最後更新者為準的行為。

### 2.1 版本提示模式

- `update`：只有 Service Worker 確認存在不同版本 bundle 時使用，顯示「目前版本／可更新至」、馬上更新與稍後更新。
- `releaseNotice`：目前 bundle 已是最新版、但使用者尚未閱讀本次說明時使用，顯示「已更新至 Vx.y.z」及單一「我知道了」按鈕。
- `travel_companion_seen_app_version` 只保存已閱讀更新說明版本，不再代表目前執行版本。
- `releaseNotice` 確認後寫入目前 `APP_VERSION`；真正的更新提示選擇稍後時不寫入，重新開啟仍需提醒。
- 手機對話框以 `100svh`、可捲動內容區及 `safe-area-inset-bottom` 保留底部操作空間。

## 三、明確不採用的方案

- 不只移除 `await`：會讓失敗靜默發生，且無法判斷資料是否已同步。
- 不建立完整 Pending Queue：逐筆操作順序、去重與重播判斷過於複雜，不符合目前規模。
- 不在同步失敗時回滾畫面：回滾會讓使用者誤以為資料消失，也可能覆蓋後續操作。
- 不加入固定秒數輪詢：避免背景持續產生不必要的 Supabase 請求。
- 不在 V3.4.1 開發多人衝突合併 UI：維持目前最後更新者為準，衝突合併另行立案。
- 不擴及 Checklist、Expense 或 Exchange Rate：V3.4.1 先限縮 Other Info 共用元件，驗證穩定後再評估共用化。

## 四、資料與狀態模型

### 4.1 本機資料

操作後立即把最新 `otherInfoItems` 寫入既有本機 Trip record。本機 Trip 是操作當下的主要來源。

### 4.2 待同步標記

每個 Trip 只保存一筆同步狀態，不保存操作清單。建議新增專用 storage：

```text
src/storage/otherInfoSyncStorage.ts
```

建議資料：

```ts
type OtherInfoSyncState = {
  tripId: string;
  revision: string;
  status: "pending" | "failed";
  updatedAt: string;
  lastError?: string;
};
```

規則：

- 每次本機修改產生新的 `revision`，使用 `crypto.randomUUID()`，避免同一毫秒連續修改碰撞。
- `syncing` 只存在 React／協調器記憶體，不寫入 storage；App 被關閉後一律由 `pending` 重新開始。
- 雲端兩個資料來源均成功後才能清除 pending。
- 同步完成時若本機 revision 已改變，不得清除新版 pending，必須再同步最新快照。

### 4.3 刪除標記

- 卡片在畫面上立即消失。
- 本機資料保留 `isDeleted: true` 與新的 `updatedAt`。
- 雲端確認軟刪除成功前，不得從待同步快照移除 tombstone（刪除標記）。
- 這項規則用來避免離線刪除後，舊雲端卡片重新出現。

## 五、背景同步協調器

每個 Trip 同時間只能有一個 Other Info 同步工作。

建議流程：

```text
收到同步要求
  → 若正在同步，只記錄已有較新的 revision
  → 若未同步且目前可連線／有權限，讀取本機最新快照
  → 同步 other_info_items
  → 同步 Trip content.otherInfoItems
  → 兩者都成功且 revision 未改變：清除 pending
  → revision 已改變：立刻再同步一次最新快照
  → 失敗：保留 pending，顯示待同步或同步失敗
```

重要限制：

- 背景工作必須每次讀取本機最新快照，不得沿用事件發生時的舊陣列。
- `syncCloudOtherInfoItems` 應回傳成功／失敗結果，不能只寫 console warning。
- Trip content 與 `other_info_items` 任一同步失敗，都保留 pending。
- 不允許平行同步同一 Trip，避免舊請求較晚完成而覆蓋新狀態。

## 六、同步觸發時機

僅使用以下明確事件：

- Other Info 新增、修改、刪除或排序後。
- 瀏覽器觸發 `online`。
- App 由背景回到前景。
- 進入 Other Info／特殊資訊頁時發現該 Trip 有 pending。

同步前必須同時確認：

- `navigator.onLine === true`。
- Supabase session 已恢復。
- 使用者仍有目前 Trip 的同步權限。

網路恢復時先重新確認 session 與旅程權限，再啟動 pending 同步。

---

## 七、雲端讀取與覆蓋保護

現有 Trip 載入流程在取得雲端資料後可能替換本機 record。V3.4.1 必須加入以下保護：

- 若某 Trip 存在 Other Info pending，不得用較舊雲端 `otherInfoItems` 覆蓋本機快照。
- 同一 item 以 `updatedAt` 較新者為準，刪除標記也參與比較。
- pending 完成前，本機 Other Info 為該 Trip 的顯示來源。
- 其他非 Other Info 的 Trip 欄位仍沿用既有合併規則，避免擴大變更範圍。

這是防止「離線刪除復活」與「重新連線後本機新增消失」的必要條件。

## 八、UI 行為

### 新增／修改

- 點擊儲存後立即更新卡片、關閉表單並保存本機。
- 不因雲端同步延遲持續鎖住「儲存中」。

### 刪除

- 點擊刪除後立即從畫面移除並保存本機 tombstone。
- 背景同步失敗不讓卡片回復。

### 同步提示

Other Info 頁面只使用簡單狀態：

- `同步中`
- `已儲存於本機，待連線同步`
- `同步失敗，將自動重試`

同步成功後可隱藏提示或顯示短暫完成狀態。錯誤訊息不得阻塞新增、修改、刪除與排序。

## 九、側欄連線與登入狀態

- 以 `navigator.onLine` 及 `online`／`offline` 事件維護明確連線狀態。
- 不再用 `!userEmail && hasEditPermission` 推定離線。
- 分別處理：線上未登入、線上 session 恢復中、線上已登入、離線無快取權限、離線有快取權限。
- 恢復連線後重新取得 Supabase session 與目前 Trip 權限，再決定是否執行 pending 同步。

## 十一、驗收條件

### 操作速度

- Online、Offline、弱網路三種情境下，新增／修改儲存後卡片立即更新且表單立即關閉。
- 刪除後卡片立即消失，不等待 Supabase timeout。
- 快速連續新增、修改、刪除與排序後，畫面維持最後一次操作結果。

### 本機持久化

- 離線操作後立即重新整理，資料仍存在。
- 關閉並重開 App，pending 狀態仍存在。
- 不同 Trip 的 pending 與資料完全隔離。

### 恢復同步

- 恢復網路後先恢復 session／權限，再自動同步。
- 同一 Trip 不會同時產生多個平行同步工作。
- 同步期間再次修改時，舊 revision 完成不會誤清除新 pending。
- 新增不重複、刪除不復活、排序不回退。
- `other_info_items` 與 Trip `content.otherInfoItems` 最終一致。

### 權限與錯誤

- 無同步權限時資料保留本機，畫面不宣稱已同步。
- Supabase timeout、RLS 拒絕與 session 過期均不會清除本機資料。
- 線上／離線／session 恢復中提示正確，不互相誤判。

### 既有功能回歸

- 領隊／導遊聯絡資訊、其他資訊與特殊資訊資料不互相污染。
- 瀏覽模式、管理模式、退出管理與卡片排序正常。
- `npm run lint` 與 `npm run build` 通過。
- V3.4.0 動態載入、PWA precache 與工具切換維持正常。

### PWA 離線導覽

- 線上完整載入並由 Service Worker 控制後，關閉 App、斷網再重新開啟可載入本機旅程。
- 離線狀態下刷新 App 仍由快取的 App Shell／`index.html` 回應，不得顯示瀏覽器「無法顯示頁面」。
- 已載入過的旅行工具在離線重開與離線刷新後均可正常切換。
- 共用清單離線載入與操作時不得先發出 Supabase 請求；恢復連線後才執行雲端同步。
- 具私人清單同步權限的使用者登入後，應立即背景預載目前旅程的私人清單至 Email 隔離快取；未先開啟該頁面即離線時仍可讀取已完成預載的資料。
- 共用與私人清單的離線排序須保存帳號隔離的 pending revision；恢復連線時 pending 必須優先於首次雲端讀取，且只有相同 revision 同步成功後才能清除。
- 共用清單離線勾選採相同 pending 規則，重連、重新登入及跨裝置確認後不得被舊雲端狀態覆蓋。
- 私人清單同一旅程與帳號的雲端快照寫入必須依序完成，不得讓較早啟動的上傳晚於刪除快照完成而復原項目。
- 私人清單雲端讀取完成後、套用結果前必須重新檢查本機 pending revision 與內容版本；讀取期間若本機已變更，須上傳最新本機快照並捨棄該次舊雲端結果。
- 更新流程清除舊快取時，不得在新 precache 尚未完成前留下無法離線刷新的空窗。

### 版本提示與手機版面

- App 已載入最新版、僅尚未閱讀更新說明時，顯示「已更新至 Vx.y.z」，不顯示「發現新版本」。
- Service Worker 確認存在不同版本時，才顯示目前版本、可更新版本與更新操作。
- 「我知道了」只標記更新說明已讀；「稍後更新」不標記已讀且重新開啟仍提醒。
- Android Chrome／PWA 與 iOS PWA 的標題、內容及所有按鈕均位於可視範圍，底部不受系統導覽列遮擋。
- 「馬上更新」可清除 App 快取並重新載入新 bundle，且不清除旅程、清單、記帳與附件資料。

### 12.1 共用帳本 A+B 疊加與代記帳（已確認）

- 共用帳本顯示 A、B 等旅程成員建立資料的聯集，不以最後登入帳號的快取整份覆蓋。
- 帳目以 `trip_id + client_item_id` 去重；同一筆才依 `updated_at` 判斷較新資料。
- `owner_user_id` 固定為實際登入者 `auth.uid()`，用於 RLS、離線佇列、修改及刪除權限。

- 離線待同步帳目依 `tripId + owner_user_id` 隔離；B 登入時不會上傳或覆蓋 A 尚未同步的資料。

## 十三、待討論事項（未定案）

> 本節只記錄問題、討論過程與候選方案，不代表 Product Owner 已確認需求。開始實作前必須逐項確認。

### 13.1 本機快取先顯示後，雲端更新造成卡片跳變

問題來源：

- 為縮短離線重新載入約 30 秒的等待，曾建議 App 啟動時先顯示本機快取，再於背景取得雲端資料。
- Product Owner 提出正常在線時的畫面一致性疑慮：例如本機只有 3 張卡片、雲端已有 10 張卡片，若先顯示本機再整份套用雲端，畫面會由 3 張突然變成 10 張。
- 這種結果在資料上可能正確，但可能讓使用者誤以為資料曾經遺失、重複、載入失敗，也可能改變捲動位置或打斷閱讀。

目前尚未定案：

- 正常在線且已有本機快取時，是否立即顯示快取，或允許短暫等待雲端後再首次顯示。
- 可接受的線上等待門檻是 1 秒、2 秒或其他時間。
- 雲端資料與目前畫面不同時，應自動更新、顯示提示後自動更新，或讓使用者點擊套用。
- 卡片數量或內容大幅改變時，是否需要顯示「已更新 N 筆雲端資料」。
- 使用者正在編輯、管理、排序或捲動畫面時，遠端更新應立即套用或延後至操作結束。

建議的混合方案：

1. 離線時立即顯示本機資料，不等待 Supabase。
2. 在線但沒有本機快取時，顯示載入狀態並等待雲端。
3. 在線且有本機快取時，先給雲端約 1～2 秒的短等待；若雲端在門檻內完成，首次畫面直接顯示最新資料，避免跳變。
4. 雲端超過門檻仍未完成時，顯示本機資料及「正在確認最新資料」，不要讓使用者面對空白畫面。
5. 雲端資料稍後回來時只更新一次，並保留目前分類、捲動位置與展開狀態；必要時短暫提示更新筆數。
6. App 啟動後可背景預抓非首屏 Other Info；使用者稍後進入工具時，多數情況已取得最新資料。
7. 本機存在 pending 時，本機資料維持主要來源，依 item id、`updatedAt` 與 tombstone 逐筆合併，不得整份以雲端覆蓋。
8. 使用者正在編輯、刪除、排序或管理時，不即時替換目前畫面；操作完成後再合併最新遠端結果。

方案取捨：

- 完全本機先顯示：離線與弱網路最快，但在線時最容易看到 3 張跳成 10 張。
- 完全等待雲端：在線畫面最一致，但弱網路可能再次出現長時間等待。
- 短等待加本機備援：兼顧速度與穩定，狀態控制較複雜，目前為優先建議，但尚未由 Product Owner 定案。

定案前應回答：

1. 在線時最多可接受等待幾秒才首次顯示卡片？
2. 雲端晚到且資料不同時，是否接受自動更新一次？
3. 是否需要顯示「已更新 N 筆雲端資料」？
4. 使用者正在操作時，是否一律延後遠端畫面更新？

### 13.2 討論觸發規則

- Product Owner 只要說「待討論事項」，Codex 應先讀取本節與其他文件中標記為未定案的內容。
- Codex 應立即逐項提出問題背景、候選方案、風險、建議與需要 Product Owner 決定的問題。
- 未經 Product Owner 明確確認，不得把本節建議改寫成「已確認設計決策」，也不得依建議直接實作。
