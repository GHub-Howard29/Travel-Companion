## 版本編號規則

採 `MAJOR.MINOR.PATCH`：

- `X`（Major）：產品世代、核心架構或資料模型發生大規模且不相容的改變。
- `Y`（Minor）：新增一項明確、可被使用者感知的主要功能，或進入新的產品功能階段。
- `Z`（Patch）：Bug 修正、小型 UI／體驗改善、效能調整、安全維護或既有功能補強。
- `FORCE_UPDATE` 與版本層級分開判斷；只有資料不相容、安全、RLS／schema、同步或舊快取有重大風險時才建議強制更新。

版本發布後不可回寫版號、migration 或版本歷史；若發現問題，使用新的向前修復版本。

## 核定 Roadmap

### V3.5.0 iOS PWA 與敏感資訊可見範圍強化

本版維持現行角色與 Trip 瀏覽制度，不新增 Trip 公開／私人設定，也不建立 `trips.is_public` migration。主要範圍如下：

- 修正 iOS PWA 在管理／編輯欄位聚焦後保留放大倍率、退出後可左右移動的問題；表單實際字級不得低於 16px，退出管理時解除焦點並限制水平溢出。
- iOS standalone PWA 的 HTML 載入階段顯示專案圖示；Android 仍維持 V3.4.11 的單次原生 Splash 圖示流程，不得出現第二張圖示。
- 自駕／租車、領隊／導遊及一般其他資訊維持原有第二層卡片結構；進入管理編輯時預設為「一般資訊」，不新增可見範圍選項。
- 編輯者可按「新增敏感資料」快捷入口建立或編輯敏感卡片；此模式自動套用「僅行程管理者可查看」，不新增敏感資料夾或第三層分類。
- 「僅行程管理者可查看」只允許目前 Trip 被指派的 `trip_editor` 與 `super_admin` 讀取；Guest、User 與其他 Trip 的編輯者不得取得資料。
- 沿用 `other_info_items.allowed_roles` 並由 Supabase RLS 落實卡片讀取限制；不能只在前端隱藏。未授權角色不得保存敏感卡片快取，卡片改為限制後須在下次成功刷新時清除舊快取。
- 儲存敏感資料時才顯示二次提醒：訂房編號、訂位代碼、租車確認碼、私人電話、個資或受限文件連結，應使用敏感資料模式；一般公開網路連結可維持一般資訊，固定帳號保護的雲端文件仍屬敏感內容。這段文案不直接放在編輯畫面。
- Guest 不提供離線行程內容；登入且仍具權限的帳號才可使用依帳號隔離的離線資料。
- 本版不建立額外的「敏感附件」可見層級；固定帳號保護的雲端文件由外部雲端服務的帳號權限控管，卡片本身則依本版資訊可見範圍限制。
- 納入 V3.4.11 發現的 BUG024：其他資訊同步失敗修正、失敗提示手動重試、`trip_editor` 權限收斂，以及 `docs/sql/014_other_info_sync_deleted_rows.sql`；前端、013／014 migration 與驗證同屬 V3.5.0 發布範圍。013／014 已套用正式 Supabase 專案，發布前同步、權限與離線佇列驗證已通過；Android／Chrome PWA 與 iOS 列為發布後補驗證。
- 本版所有新增或調整畫面必須先製作模擬圖，經 Product Owner 確認後才可修改程式。
- V3.5.0 已發布並採 `FORCE_UPDATE = true`：本版同時包含敏感資訊 RLS、權限快取隔離與同步流程修正；舊版 PWA 升級及 Android／Chrome PWA 啟動／版面已通過，iOS 因目前無設備而保留未驗證並暫時跳過；發布後驗證已於 2026-08-26 確認結案。

### V3.5.1 Supabase Storage 附件安全維護、跨裝置即時刷新與 App 分享（不新增敏感附件可見層級）

- 將 `expense-attachments` bucket 與 `storage.objects` 政策納入可版本控制的 migration。
- 確認 bucket 為 private，並依 Trip 權限限制 INSERT、SELECT、UPDATE、DELETE。
- 驗證附件路徑中的 Trip ID，並評估簽名網址有效期限。
- 納入已確認的 App 分享功能：頁首於既有關閉按鈕左側新增小型分享圖示，點擊後開啟浮動視窗；既有 App 文案與小圖示不得變動。
- 浮動視窗依已確認模擬圖顯示本專案圖示、「我的旅行小幫手首頁」超連結（開啟預設瀏覽器）、「分享連結」文字，以及每行四個可上下滑動的原生分享 App 圖示。
- 點擊原生 App 圖示後使用系統分享機制，由使用者選擇通訊軟體頻道或其他分享目標；不新增「更多」按鈕、不建立單一 Trip 分享網址。
- 保留原本關閉按鈕，點擊後直接返回當下 App 主畫面；新增功能僅能變動本次確認的分享部分，不能改動既有文案與小圖示。
- 修正其他資訊、領隊／導遊資料及共同準備清單的跨裝置即時刷新缺失：同一 Trip 的另一台裝置收到新增、修改、勾選或軟刪除事件後自動重新載入。
- 以 Supabase Realtime 監聽 `other_info_items`（限定 `trip_id`），收到事件後透過 RLS-safe query refetch；軟刪除以 UPDATE 事件處理，不直接顯示未驗證的事件 payload。
- 共同準備清單同步監聽 `checklists`（限定 `trip_id`、`scope = shared`）及其 `checklist_items`（限定 shared checklist ID），涵蓋新增、修改、勾選、刪除／軟刪除與排序變更。
- 補上不同帳號同時修改同一共同清單項目的競態驗收：同一欄位採最後成功雲端寫入結果；離線／結構修改沿用三方合併，pending 不得被遠端事件清除或覆蓋。
- 保留 focus／visibility／reconnect fallback；重新載入不得覆蓋尚未送出的本機同步佇列，並補上 Realtime publication／migration 與雙裝置驗證。
- 屬既有功能的安全補強，使用 Patch；是否強制更新依舊版相容與暴露風險決定。
- 已於 2026-08-26 完成發布並結案：正式 Supabase migration、Storage 四角色 RLS、宜蘭附件、跨裝置即時刷新與共同清單競態回歸均已通過。

### V3.5.4 管理者帳號名稱映射與新增旅程預帶入（已定案）

- 新增 `admin_profiles` 作為管理者帳號設定來源，與既有僅管理角色／Trip 指派的 `admin_users` 分離。
- `admin_profiles` 保存 Supabase Auth 使用者識別、目前 Email、固定顯示名稱、是否預設帶入新增旅程及排序；Email／名稱調整後由 App 讀取最新設定。
- 新增旅程時，App 依 `include_in_new_trip` 與 `sort_order` 預帶入「名稱=Email」參與者；可編輯者 Email 欄位維持空白，只顯示範例。
- `admin_users` 維持權限來源，不以顯示名稱作授權判斷；profile table 需具最小 RLS，只有 `super_admin` 可維護設定。
- 此項包含 schema、RLS、既有管理者資料初始化與表單行為回歸，獨立為 V3.5.4，不插入已進入驗證階段的 V3.5.1。
- V3.5.4 起新建 Trip 的 ID 依建立當下的型態與出發日固定產生：自由行為 `free-travel-YYYY-MM-DD`，跟團為 `group-tour-YYYY-MM-DD`；月、日皆補零為兩碼。
- 同一型態與同一出發日只允許一個 Trip；建立前必須同時檢查本機與 Supabase 既有 ID，重複時阻擋建立並提示使用者調整出發日或型態。
- 既有 Trip ID 一律不搬移、不重命名；新建後的 ID 亦不因後續編輯名稱、型態或出發日而改寫，避免破壞帳目、清單、Storage、RLS 與離線快取關聯。
