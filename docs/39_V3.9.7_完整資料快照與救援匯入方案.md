# V3.9.7 完整資料快照與救援匯入方案

> 狀態：已確認方案，尚未實作。本文不代表 migration 已套用、工具已發布，或正式資料已復原。

## 一、事故結論與範圍

本次事故不只影響每日行程。已觀察到舊資料覆蓋下列內容：

- `trips`：每日行程、地圖定位、交通時間與方式、照片引用、Trip 設定、參與者與 Email 綁定。
- `other_info_items`：導遊／領隊卡片與其他資訊子分類內容；部分較新的項目仍存在。
- 行程內帳號／權限相關設定：至少包含 `participantEmailMap`；若 `admin_users` 的 Trip editor 也被變更，須另行鑑識其寫入來源。

既有事故路徑可解釋「部分覆蓋」：舊的其他資訊待同步會先依 `client_item_id` 更新已存在的 `other_info_items`，但不會自動刪除舊快取中不存在且沒有刪除標記的新項目；之後舊程式會把本機快取的完整 Trip 無條件 upsert 至 `trips`，因此將整個 `content` 一併覆寫。

`admin_users` 不會被該背景其他資訊同步路徑直接修改；若 Trip editor 清單確實被覆寫，必須檢查是否曾以舊資料執行旅程管理儲存或存在其他寫入來源。

## 二、目前已完成的 V3.9.7 內容

已提交於 commit `5d5e645`（`實作 V3.9.7 行程防覆寫與離線救援工具`），但尚未部署或套用正式資料庫 migration。

### 2.1 防止舊快取覆寫

- 移除其他資訊待同步後對完整 `trips` 的無條件 upsert。
- 其他資訊同步僅寫入獨立的 `other_info_items`。
- 此修正保留；它是防止同型事故再次發生的必要 hotfix。

### 2.2 PWA 外部連結返回

- 外部連結開啟前保存一次性 Trip／Day 上下文，有效期 30 分鐘。
- 返回後優先恢復原 Trip 與原 Day。
- 上下文過期、Trip 已不存在或 Day 無效時，維持既有預設 Trip／Day 規則。

### 2.3 行程卡片其他資訊子分類捷徑

- `ItineraryItem.otherInfoFolderId` 可選欄位。
- 管理表單可設定其他資訊子分類。
- 卡片顯示目標子分類按鈕；地圖按鈕文案為「查看地圖」。
- 未設定、分類不存在、分類內容對目前角色均不可見時不顯示。

### 2.4 初版每日行程歷程與工具

- 已有私有 `private.itinerary_day_history` migration：同 Trip／Day 每小時首次變更前快照，最多 30 筆。
- 已有本機維運工具，可列出與還原單一 Day，並要求 `updated_at` 樂觀鎖與二次確認。
- 已有 Windows x64 離線救援匯出 ZIP，可唯讀解析 Chrome／Edge Local Storage LevelDB，輸出目標 Trip 的 `daysData`。

### 2.5 已知限制

- 上述 Day 歷程只涵蓋 `daysData`，不涵蓋本次實際受影響的完整資料域。
- 每小時只保存第一份快照，無法可靠保留同一小時內事故前的最後正確版本。
- 離線救援工具目前只匯出 `daysData`，沒有匯入能力。
- 初版歷程與救援工具不得視為本方案完成；應在後續實作中以新 migration／新工具向前替換，不改寫已發布 migration 歷史。

## 三、已確認的完整快照策略

### 3.1 目標與邊界

採「每日完整應用資料一致性快照，保留最近 7 份成功快照」。目標是防範 App 邏輯、同步或人工操作造成的資料誤覆寫，RPO 約為 24 小時。

這不是 Supabase 平台、Auth 或 Storage 的完整災難備份；它不處理帳號系統毀損、整個資料庫遺失或被刪除的情況。

### 3.2 每日快照資料域

同一份快照必須在一致性讀取範圍內包含：

- `trips`
- `other_info_items`，包含軟刪除列
- `admin_users`
- `admin_profiles`
- `checklists` 與 `checklist_items`
- `exchange_purchases`
- `expenses`
- `trip_deletion_tombstones`
- 行程照片與帳本附件的 Storage 引用清單

不納入：

- Supabase Auth 使用者、session、JWT、refresh token
- `app_data_revision`
- 路線、Commons 等可再建立的快取、配額、鎖與使用統計
- 系統使用紀錄等維運資料

### 3.3 建立、驗證與保留

- 以台灣時間低使用量時段執行，預設 03:00。
- 快照以單一一致性資料讀取建立，保存格式版本、建立時間、各資料域列數、payload 與 SHA-256。
- 新快照必須通過格式、列數與 checksum 驗證，才視為成功。
- 成功後才刪除最舊快照，永遠保留最近 7 份「成功」快照；排程失敗不能先刪除舊快照。
- 快照放在非暴露的 `private` schema，瀏覽器角色不得讀寫；使用最小權限的受控維運入口讀取。
- 快照資料與排程不得暴露 service key 或資料庫連線字串至 PWA。

### 3.4 匯入前安全快照

任何受控匯入、完整還原或大量同步前，先建立一份 `pre_restore` 即時快照：

- 不計入每日 7 份的名額。
- 先驗證成功才允許進行還原。
- 使錯誤還原仍可回到還原前的雲端狀態。

## 四、Storage 檔案保護

資料庫快照只保存照片／附件路徑與中繼資料，不包含二進位檔案。因此：

- 解除照片或附件引用後不可立即永久刪除。
- 最近 7 份每日快照或任一 `pre_restore` 快照仍引用的檔案不得刪除。
- 解除引用後至少延遲 8 天清理，提供一日緩衝。
- 清理前應再次檢查目前資料與保留快照的引用；未引用才可刪除。
- 若未來需要涵蓋 Storage 災難，另行設計外部檔案備份；不把它誤稱為本方案已提供的能力。

## 五、離線救援匯出工具的擴充範圍

離線工具持續保持「唯讀、無網路、無 Supabase 密鑰」的性質。它不應直接匯入正式資料庫。

### 5.1 輸出內容

工具需改為輸出目標 Trip 的完整本機救援包，採 allowlist，至少包括：

- 完整 `StoredTripRecord`：Trip 主資料、`daysData`、地點、交通、照片引用、`participantEmailMap`、本機 `editorEmails`、側邊欄設定。
- 其他資訊項目與資料夾結構。
- 共同／私人清單中屬於目標 Trip 的本機資料。
- 目標 Trip 的帳本快取、離線帳本佇列與匯率資料。
- 待同步狀態、快取版本與來源 profile 資訊，僅供鑑識，不得直接匯入。
- 每個資料域的 schema 版本、筆數、摘要、來源時間與 SHA-256。

不得輸出 Supabase session、refresh token、JWT 或不屬於目標 Trip 的資料。匯出檔可能含參與者 Email、帳本與私人清單，使用 USB／Dropbox 傳輸時須以受信任且受保護的位置保存。

### 5.2 執行規則

1. 將工具完整複製至目標電腦並確認可離線使用。
2. 中斷網路。
3. 完全關閉 PWA、Chrome 與 Edge。
4. 工具複製 Local Storage LevelDB 到系統暫存區，確認來源指紋複製前後一致。
5. 輸出救援包與人類可讀摘要；不修改原始瀏覽器資料。
6. 直到完成雲端差異比對與受控還原前，不重新開啟舊 PWA。

## 六、受控匯入／還原工具

匯入工具與離線匯出工具分離，僅能在受控維運環境執行。

### 6.1 唯讀預覽

- 驗證救援包或每日快照格式、schema 版本與 SHA-256。
- 讀取目前雲端資料，但不寫入。
- 依資料域顯示新增、修改、刪除、筆數、標題與時間差異。
- 不允許「不看差異的一鍵全部覆蓋」。

### 6.2 還原流程

1. 選擇快照或救援包，以及明確資料域。
2. 再次讀取目前雲端版本，確認樂觀鎖條件仍成立。
3. 建立並驗證 `pre_restore` 快照。
4. 顯示最後差異並要求精確二次確認字串。
5. 在短交易中依外鍵順序還原選定資料域。
6. 觸發既有 revision 通知。
7. 重新讀取並比對快照／救援包 checksum、列數與摘要。
8. 驗證成功後才允許重新開啟新版 PWA 與恢復一般同步。

### 6.3 實作邊界

- 不在 PWA 前端保存 service key 或資料庫密碼。
- 不把匯入能力放入離線救援工具。
- 由本機受控維運 CLI 使用當次明確提供的連線資訊，或由受限的私有後端操作。
- 任何正式寫入、排程部署、migration 套用、Storage 清理與權限還原均需另一次明確授權。
