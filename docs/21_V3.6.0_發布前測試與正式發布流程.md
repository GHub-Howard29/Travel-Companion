## 一、用途與恢復規則

本文件是 V3.6.0 後續測試、正式資料庫變更與發布順序的操作依據。

Product Owner 指出「3.6.0下一階段」後，Codex 必須：

1. 先讀取本文件、《15_V3.6.0_地點間預估移動資訊規格》與《09_待辦事項_TODO》。
2. 檢查 Git 工作目錄、目前分支、已發布版本、Supabase CLI／專案連結及尚未完成項目。
3. 從本文件第一個未完成階段開始，不重做已完成且有證據的項目。
4. 一次只引導一個安全階段，完成檢查並回報結果後再進下一階段。
5. 正式 migration、正式 Edge Function 部署、正式前端發布、Git tag 等外部變更，均須在執行前指出目標與影響並取得 Product Owner 當次明確同意。
6. 不使用 `db reset --linked`、不在正式環境加入 seed，也不直接以 Dashboard 改寫正式 schema 或 migration history。

## 四、階段 B：開發／staging 整合測試

### 4.1 資料庫與 Edge Function

- [ ] 先執行 migration list，確認 staging migration history 沒有分歧。
- [ ] 執行 migration dry-run，只允許預期的 V3.6.0 migration。
- [ ] 對 staging 套用 migration，不包含 seed。
- [ ] 執行 `docs/sql/020_v360_route_estimate_security_validation.sql`。
- [ ] 執行 Database Security Advisor 與 Performance Advisor；不得留下與本版新增物件有關的高風險項目。
- [ ] 設定 staging `GOOGLE_MAPS_API_KEY` secret，部署 `travel-route` Edge Function。
- [ ] 確認 Function 保持 JWT 驗證，不使用 `--no-verify-jwt` 部署正式設定。

### 4.2 角色與費用邊界

| 測試身分 | Places 搜尋 | Routes 查詢 | 查看已存結果 | 點擊外部 Google Maps |
|---|---:|---:|---:|---:|
| Guest | 必須拒絕 | 必須拒絕 | 可以 | 可以，且不呼叫專案 API |
| User | 必須拒絕 | 必須拒絕 | 可以 | 可以，且不呼叫專案 API |
| 其他 Trip 的 trip_editor | 必須拒絕 | 必須拒絕 | 可以 | 可以，且不呼叫專案 API |
| 所屬 Trip 的 trip_editor | 可以 | 可以 | 可以 | 可以 |
| super_admin | 可以 | 可以 | 可以 | 可以 |

- [ ] 未登入請求由 Supabase gateway 拒絕，不能到達付費 Google API。
- [ ] 一般 User 與其他 Trip editor 由 Function 角色檢查拒絕。
- [ ] 只有所屬 Trip editor 與 super_admin 能產生 Places／Routes 查詢。
- [ ] API key、service role／secret key 不出現在瀏覽器 Network response 或 bundle。

### 4.3 地點與卡片 UI

- [ ] 原卡片維持既有資訊結構，不新增景點圖案或地址列。
- [ ] 地點按鈕顯示「在地圖中查看」，開啟地點頁而非誤稱導航。
- [ ] 地點候選只在確認面板暫時顯示，Trip 長期只保存 Place ID 與原 `location` 文案。
- [ ] 次要按鈕顯示「保留原設定地點」。
- [ ] 修改地點文字會解除舊 Place ID 與舊估算，但保留最後交通方式偏好。
- [ ] Google Maps attribution 顯示符合當下官方規範。

### 4.4 交通區段與時間規則

- [ ] 兩張直接相鄰且 Place ID 不同的卡片才建立交通區段。
- [ ] 中間有無地點卡片時不得跨卡計算。
- [ ] 相同 Place ID 不建立區段。
- [ ] 明確標記的機場到機場航班不建立地面交通區段。
- [ ] 開車、步行、大眾運輸均可查詢、預覽與儲存。
- [ ] 管理者只開啟交通面板時不查詢；明確點選交通方式才呼叫 Routes API。
- [ ] Guest／User 點擊已存或待更新區段只開啟 Google Maps，不呼叫專案 Routes API。
- [ ] 大眾運輸使用前一站有效離開時間；無班次時日間備援文案正確。
- [ ] 起終點、交通方式或大眾運輸離開時間改變時，舊估算正確失效。
- [ ] 只修改標題／說明不讓估算失效；下一站到達時間只重算警告。
- [ ] 時間衝突優先於時間不足，兩者皆不自動修改行程時間。

### 4.5 快取、過期與配額

- [ ] 相同快取鍵重複查詢時使用 cache，不增加 Google Routes 外部查詢。
- [ ] cache miss 才宣告每日配額並呼叫 Google Routes。
- [ ] 過期估算不再顯示時間／距離，但保留交通方式及「路線資訊待更新」。
- [ ] 雲端讀寫與純離線本機讀取都會清除過期估算值。
- [ ] 每日 100 次上限以 staging 測試資料或受控方式驗證，不為測試實際送出 100 次付費 Google 請求。
- [ ] 達上限後既有結果仍可讀取，新 cache miss 回傳可辨識錯誤。

### 4.6 PWA 與裝置回歸

- [ ] 桌面瀏覽器、Android PWA 與可取得的 iOS 裝置檢查卡片間距、面板與外部開圖。
- [ ] 線上儲存後重新整理、切換 Day、切換 Trip 不會自行查詢 Routes。
- [ ] 離線仍可讀取有效的已存結果；過期結果顯示待更新，不嘗試背景查詢。
- [ ] 重新連線不覆蓋尚未同步的行程變更。

通過條件：上述必要項目全部通過；若設備無法取得，必須記錄為已知未驗證，不得寫成通過。

## 六、階段 D：正式環境發布順序

本階段每一項外部變更都要先回報目標正式專案並取得 Product Owner 當次同意。

### 6.1 正式 migration 前

1. [ ] 確認正式 Supabase project ref，不依賴先前連結狀態。
2. [ ] 確認備份／PITR 狀態及低流量發布時段。
3. [ ] 執行正式 migration list，確認 local／remote history 一致。
4. [ ] 執行 `db push --dry-run`，畫面只應包含預期 migration。
5. [ ] 若出現 history 分歧，停止；未釐清前不得直接執行 `migration repair`。

### 6.2 正式發布

1. [ ] 套用正式 migration，不包含 seed。
2. [ ] 立即執行 `020` 驗證 SQL、Security Advisor 與 Performance Advisor。
3. [ ] 任一權限、RLS、函式或索引驗證失敗即停止，不部署 Edge Function／前端。
4. [ ] 確認正式 `GOOGLE_MAPS_API_KEY` secret 已存在且權限限制正確。
5. [ ] 部署 `travel-route` Edge Function。
6. [ ] 以所屬 trip_editor／super_admin 各做最少量成功 smoke test；以 Guest／User／其他 Trip editor 驗證拒絕與不產生付費查詢。
7. [ ] 確認資料庫與 Function 正常後，最後發布 V3.6.0 前端。
8. [ ] 驗證 PWA 更新、版本顯示、主要行程及既有 V3.5.6 功能回歸。

正式順序固定為：

```text
正式 migration
→ SQL／Advisors 驗證
→ Edge Function
→ 正式 smoke test
→ V3.6.0 前端
→ 發布後驗證與文件
```

## 七、停止與回復原則

- migration 或驗證失敗：停止後續部署，保存完整錯誤；不得反覆重跑或直接 repair history。
- migration 已成功、Edge Function 尚未成功：不發布前端；修正 Function 後再部署。
- Edge Function 已成功、前端尚未發布：舊版 v3.5.6 不會呼叫新 Function，可安全停在此階段排查。
- 前端發布後發現問題：優先回退／停用前端新入口；本次 additive schema 不因一般發布回退而刪除。
- 已套用正式 migration 視為不可回寫；需要資料庫修正時建立新的向前修復 migration。
- 不使用正式備份作為一般版本回退工具；備份只供災難復原。
