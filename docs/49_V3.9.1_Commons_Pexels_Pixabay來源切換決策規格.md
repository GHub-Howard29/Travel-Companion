## 2. 決策摘要

1. **預設來源維持 Wikimedia Commons。** 每次重新開啟選圖流程都回到 Commons；不把上次選擇寫入 Trip、瀏覽器儲存或帳號偏好。
2. **Pexels 與 Pixabay 為使用者明確切換的補充來源。** 不同時查三個來源、不背景預抓、不因零結果或錯誤自動改查另一來源。
3. **來源切換只改變後續搜尋來源。** 保留目前輸入的搜尋詞，但清除候選、選取、頁碼／游標與已看過集合；切換本身不送出請求，必須再由使用者明確搜尋。
4. **「換一批」每次只向目前來源取下一頁，每批最多 6 張。** 不用補抓多頁湊滿 6 張，也不在一個操作內跨來源補足。
5. **三來源都只能由可寫入 Trip 的管理者人工選圖。** 不自動採第一張，不依標題推定為同一地點。
6. **選定後一律轉成既有受控 WebP 並保存至專案 Storage。** 卡片不永久 hotlink 第三方；沿用單檔 120 KiB 上限、Trip／item scope、隨機版本路徑、引用計數式清理與文字卡片降級。
7. **共同候選契約、來源別保存契約。** 前端只依共同欄位呈現候選；Trip 內以 discriminated union 保存各來源不可互換的識別與授權證據，不把 Commons 欄位勉強套到 Pexels／Pixabay。
8. **Pexels／Pixabay 沒有 key 或尚未通過同一命中率矩陣時，不得進入實作／發布。** 本次不申請 key；正式 API 實測是後續開發閘門，不是本研究的假資料。

## 3. 為何預設 Commons

- V3.9.0 已有 Commons 的正式搜尋、授權白名單、壓縮保存、Storage、資料相容與清理契約；切換功能不應改變已發布卡片的讀取行為。
- Commons 不需要專案 API key，且可逐檔取得作者、來源頁、授權、revision 與 SHA-1，最適合做可稽核的預設來源。
- Pexels／Pixabay 都需要 API key；本次依停止條件不申請，也沒有真實 API 命中率可支持把任一來源升為預設。
- Pexels／Pixabay 的圖庫品質可能較適合廣義旅遊意象，但仍是關鍵字搜尋，沒有 Google `placeId` 對應，不能宣稱比 Commons 更能辨識特定餐廳、分店或小型景點。
- Pixabay 明文要求 API 回應快取 24 小時；Pexels 也會將回應快取 24 小時且重複請求仍計入額度。兩者若成為預設，會先引入 key、持久快取與額度治理依賴。

## 5. 來源切換與搜尋狀態機

### 5.1 開啟、切換與重新搜尋

- 開啟某張卡片的選圖流程：`source=wikimedia-commons`、`page=first`、`seenKeys=empty`、`candidateSelection=null`。
- 預設來源不因卡片現有照片來源而改變；開啟與切換來源都不送出來源 API 請求。
- 搜尋欄只可使用原始輸入或管理者已採用的一個 Gemini 單語候選詞；A 已於 2026-09-15 定案停用自動英文擴充，C 亦已停用。在 V3.9.1 不得自動翻譯、多語搜尋、增加 Google Place Details 請求或使用 Google Places 衍生內容。
- 來源切換：保留目前搜尋詞，重置該流程中的候選、選取、分頁、下一頁資訊、錯誤與 `seenKeys`；不立刻呼叫新來源。
- 搜尋詞實質改變後重新送出：對目前來源建立全新搜尋 session，頁碼與 `seenKeys` 歸零。
- 關閉再開：不延續來源、頁碼或 `seenKeys`。現有已保存封面不受影響，直到新照片完整保存成功才替換。
- 不保存「上次來源」偏好，避免未預期地消耗有 key 的來源額度，也避免來源 attribution 在不同裝置產生不一致。

### 5.1.1 文字式 UI 行為：來源選擇（已核准）

Product Owner 於 2026-09-14 已核准下列行為：

1. 只有可寫入 Trip 的管理者可開啟選圖；歷史唯讀者只可讀取既有照片與來源資訊。
2. 來源名稱必須以文字清楚呈現 `Commons`、`Pexels`、`Pixabay`，三者互斥，不只使用圖示。
3. 切換來源保留當前搜尋欄文字，清空候選與已選候選，重設分頁、錯誤與去重紀錄；切換本身不送請求。
4. 來源因 key 未設定、額度停線、離線或供應商故障而不可用時，名稱仍應可辨識但不可選取，並告知不可用原因；不得靜默退回 Commons。
5. 已有卡片照片時，開啟更換流程不得影響原照片；只有新照片完整保存成功後才替換。
6. 搜尋與換一批期間只鎖定該來源的重複操作；關閉或取消流程不得刪除既有照片、不得重送請求。

2026-09-15 Product Owner 已核准：開啟選圖時只預填該行程已保存的 `location` 原始文字；若沒有 `location` 則留白，不得以行程標題、`placeId` 或 Google／其他衍生資料補值。預填後不自動搜尋，管理者可改寫。

### 5.1.2 與子方案 A／C 相依的搜尋起點（均已停用）

下列為 2026-09-14 的歷史討論紀錄；2026-09-15 的停用決策優先，僅保留仍與 Gemini 人工採用候選詞相容的原則。

> 2026-09-15 已由《48》定案：A 的自動翻譯／多語擴充，以及本節所有涉及 C／Google Place Details 的方向（第 3、4、7、8、9、10 點），均由「V3.9.1 停用 A／C」取代，不得實作或據此增加外部呼叫。B 只可使用原始輸入或管理者已採用的一個 Gemini 單語候選詞。

1. 管理者原始輸入永遠保留，不被自動改寫。
2. A、C 只能產生可採用的搜尋建議，不能直接送出 Commons／Pexels／Pixabay 搜尋。
3. C 僅在管理者明確要求使用已確認 MAP 地點時，才可執行 Place Details；回傳資料只留在當次記憶體，不寫入 Trip。
4. C 不把完整地址或座標傳給 Pexels／Pixabay；是否傳給 Commons 的鄰近搜尋，留待 C 的隱私與命中率決策。
5. 管理者明確採用一個建議後，B 才收到單一最終搜尋詞並執行一次來源搜尋；不改動 B 已核准額度。
6. 搜尋建議的語言不固定為英文：優先產生目的地的在地語言候選，英文只作全球通用的備援候選。每次只能由管理者採用其中一種語言的一個最終搜尋詞，B 不得自動以多語言平行或連續搜尋。
7. C 的在地語言只能來自管理者當次明確指定的目的地語言脈絡（例如日本為日文 `ja`、臺灣為繁體中文 `zh-TW`），只存在當次記憶體、不寫入 Trip；不得由既有 `placeId`、原始輸入或推測國別自行判定。
8. C 只以該語言執行一次 Place Details 並產生該語言的建議。英文備援不是自動行為；只有管理者明確要求改用英文時，才可另開一個新的 C 查詢並獨立計入 Places 額度。未明確指定目的地語言時，C 不呼叫 Place Details、不產生在地語言建議，仍保留原始輸入供 A 或後續 B 使用。
9. 目的地語言以繁體中文名稱供管理者指定（例如「日文」、「英文」、「繁體中文〔臺灣〕」），系統只在當次記憶體正規化為 BCP 47 代碼（`ja`、`en`、`zh-TW`）供 C 使用；不要求或顯示技術代碼作為必填輸入。
10. 不接受含糊的「中文」或任意自由文字作為語言值；繁體中文（臺灣）、繁體中文（香港）與簡體中文必須分別指定。可選語言僅限事先定義、Google 支援的清單；中文名稱與代碼均不得寫入 Trip。
11. 可另以 AI 形成 A 的「搜尋詞建議器」：只接收管理者原始輸入，不接收 Google 回傳內容、`placeId`、帳號／Trip 識別、完整行程、地址或座標；不得以 AI 規避 C 的 Google Maps Content 合規停止條件。
12. AI 每次最多產生 3 個可採用的短搜尋詞，每個候選只有一種語言與對應來源 locale；不直接呼叫圖庫。管理者採用一個候選後，B 才以該單一詞、單一語言、單一來源執行一次搜尋。
13. AI 不得捏造正式店名、別名或地址；無法可靠轉換時必須保留原文或不提供建議。複合敘述應整理為適合作封面照片的單一主題詞，不宣稱可搜尋到多個地點同框的照片。
14. AI 的模型、供應商、資料保留條款、每次 token 成本、速率與額度停止條件仍待獨立定案；在此之前不得申請 AI key、串接服務或實作。
15. V3.9.1 的 AI 定義為 Gemini 免費層的測試磨合期，不作 production 依賴。專案自訂硬停為每個 Gemini 專案每天最多 100 次 AI 建議請求；實際可用次數固定取 `min(100, Google 當時對該模型／專案授予的 RPM、TPM、RPD)`，不因「免費」而假設 100 次必然可用。
16. 測試期禁止自動重試、平行請求、跨模型／跨供應商自動降級與 Google Search／Google Maps grounding；任何 429、逾時、離線、模型不可用或本專案 100 次硬停，都直接降級為原始輸入，不送出 B 的照片來源請求。Gemini 免費層輸入／輸出可能用於 Google 產品改進一事，Product Owner 已基於本項只傳公開可檢視地點文字而接受；仍不得傳送先前禁止的識別、Trip、Google Places、地址或座標資料。
17. OpenAI 保留為日後付費備選：API 與 ChatGPT 訂閱分開計費；若啟用，採預付額度、關閉自動儲值並設專案硬停，不以訂閱制取代 token 用量計費。啟用前仍須依既有 key 流程向 Product Owner 說明費用、付款、稅費／外幣、資料保留與安全風險並取得明確核准。

## 6. 快取、額度與請求治理

### 6.1 共用搜尋快取

- 快取位於伺服器側，key 為 `source + SHA-256(normalizedQuery + locale + pageToken + filters + contractVersion)`；不得以明文搜尋詞作資料列 key、log 或 metrics label。
- value 只保留正規化候選、下一頁資訊、來源回應時間、到期時間與必要額度 header；不保留使用者、Trip 或卡片識別。
- Commons 成功與空結果 TTL 10 分鐘。
- Pexels 成功與空結果 TTL 24 小時，以避免對官方已快取的相同請求重複扣額度。
- Pixabay 成功與空結果 TTL 24 小時；若無法保證這個共用快取，Pixabay 必須保持停用。
- 429、401／403、5xx、逾時或格式錯誤不可快取成「零結果」。429 只保存來源 cooldown；其他錯誤可短暫熔斷，但不得污染搜尋結果快取。
- 快取到期採下一次明確搜尋時 lazy refresh；禁止背景預熱或批次抓取。

### 6.2 額度與節流

- 所有第三方搜尋集中由 Edge Function 執行，先驗證登入者可寫入指定 Trip；瀏覽器不得直呼帶 key 的 API。
- 全來源同一使用者同一 Trip 同一時間只允許一個搜尋；來源端總並行限制最多 3，Commons 必須使用含公開聯絡網址或信箱的合規 User-Agent。
- Pexels 保存成功回應的 `X-Ratelimit-Limit`、`Remaining`、`Reset`；當 remaining 為 0 或收到 429，停止至 reset。每小時 200 次限制若沒有可依賴的 header，收到 429 後依 `Retry-After` 或保守 cooldown 處理。
- Pixabay依 60 秒視窗 header 節流；remaining 為 0 或 429 時停止至 reset。
- Wikimedia 429／503 遵守 `Retry-After`；缺 header 時至少等待 5 秒並採指數退避。單一使用者操作不自動重試超過一次，避免一按造成多筆來源請求。
- quota／cooldown 屬來源不可用，不是無結果；不得用空陣列掩蓋，也不得自動消耗另一來源額度。

### 6.3 Pexels／Pixabay 免費額度限制規則（已核准）

本節只計入會打到 Pexels／Pixabay API 的上游 HTTP 呼叫：搜尋與必要的單筆 metadata 核對各算 1 次。回傳一批 6 張候選、顯示候選縮圖、Cache hit、或從已核對候選下載一張供管理者選定的圖片，都**不是**額度計數的 6 次 API 搜尋；不過圖片下載另受第 6.3.4 節防大量下載限制。

#### 6.3.1 官方額度與可計算結論

| 來源 | 官方預設硬限制 | 可直接計算的安全可用上限 | 不可假設的部分 |
| --- | --- | --- | --- |
| Pexels | 200 req/hour、20,000 req/month | 保留 20% 供 header 誤差、重試與人工救援後，內部硬停在 160 req/hour、16,000 req/month；14,000 req/month 進入預警 | Pexels 沒有承諾本專案可以使用 unlimited；不得以免費名義預先申請提高額度 |

#### 6.3.2 單次流程與個人濫用保護

| 範圍 | Pexels | Pixabay | 規則目的 |
| --- | ---: | ---: | --- |
| 同一來源、同一正規化搜尋詞、同一次選圖 session | 最多 5 個 page token／cache miss | 最多 5 個 page token／cache miss | 首頁加最多 4 次「換一批」，不論 cache hit／miss 都最多檢視 30 張候選；防止任意翻頁 |

- 「臺北日」採 `Asia/Taipei` 00:00～23:59:59，只用於本專案的公平使用限制；Pexels 月重置一律以官方 header timestamp 為準。

- 只有成功送到來源端的 cache miss 扣來源與個人額度；驗證失敗、取消於送出前、或本地 cache hit 不扣。429、5xx、timeout 仍記入風險計數，避免用失敗重試繞過節流。
- 任何一層達上限時，該來源在該層作用範圍內回報 `rate-limited`，不得改查另一來源、縮短 cache TTL 或重設 session 來規避。

#### 6.3.3 全專案保護預算與月內配速

| 來源 | 預警 | 硬停 | 月內配速公式 |
| --- | ---: | ---: | --- |
| Pexels | `min(14,000, floor(X-Ratelimit-Limit × 0.70))` | `min(16,000, floor(X-Ratelimit-Limit × 0.80))` | `floor((內部硬停 - 本月已用 cache miss) / max(1, ceil((X-Ratelimit-Reset - now) / 86,400 秒)))` |
| Pixabay | 8,000 個 cache miss／月（專案自訂） | 10,000 個 cache miss／月（專案自訂） | `floor((10,000 - 本月已用 cache miss) / 當月剩餘臺北日數)` |

- 月內配速是「今天最多可再使用的 fresh API calls」；若已超過配速，來源進入當日保留狀態，次日再依剩餘預算重算。這避免月初少數大量搜尋耗盡 Pexels 20,000 的免費上限。
- Pexels 在官方月額度、內部月硬停、官方每小時 200、內部每小時 160、個人限制之間，以**最小可用值**為準。
- Pixabay 在官方每 60 秒 100、內部每 60 秒 60、個人限制、24 小時 cache、及 10,000 自訂月預算之間，以**最小可用值**為準。10,000 是為遵守「real human requests」與控制本專案間接成本而設，並非 Pixabay 收費門檻；實測一個完整月後才可另案調整。
- Pixabay 的 8,000／10,000 自訂月預算採 `Asia/Taipei` 曆月，在下個臺北曆月 00:00 重置；它不取代來源端每 60 秒 header 的即時判定。
- 預警只記錄與通知維護者，不改變既有已保存卡片；硬停只停新的來源 API 呼叫，Commons、其他來源、既有自有 Storage 圖片與文字卡片照常運作。

#### 6.3.4 圖片下載、重新核對與快取的衍生限制

- 每一張卡片每 24 小時最多嘗試保存 2 次照片；同一可寫入者每來源每臺北日最多 12 次實際二進位下載（成功或失敗都計）。這限制不是 API 額度，而是防止 Pixabay 禁止的系統性大量下載及本專案 egress／Storage 成本。
- Pexels 若搜尋快取尚在 24 小時內，不再為保存而額外呼叫單筆 API；使用已核對 metadata，必要時只重新下載選定圖片。快取到期才由使用者明確搜尋觸發新的 API 請求。
- Pixabay 在其 24 小時快取期間不得為同一搜尋重打 API；保存使用快取中有效的候選 metadata 與暫態圖片 URL。URL 過期、下載失敗或 metadata 不完整時停止保存並要求使用者重新明確搜尋，不背景補打。
- 不取得 Pixabay 的 full API access、原圖或向量 URL；候選與保存只使用足以壓縮為 120 KiB WebP 的標準圖片尺寸。

#### 6.3.5 驗收與調整門檻

- 隔離驗證須覆蓋：session 第 5 次換批、Trip 第 24 次、使用者第 40 次、Pexels 第 160 次／hour 與第 16,000 次／month 的邊界，以及 Pixabay 第 60 次／60 sec、24 小時 cache 和 10,000 次自訂月停線。
- 每次來源成功回應都記錄不含 key／query 的來源、cache hit／miss、計數器、官方 remaining／reset（如有）、latency 與錯誤碼；不得記錄 API key、完整搜尋詞、照片 download URL 或 Trip 內容。
- 連續一個完整月的隔離或實際核准流量資料出來前，不提高任何數字。任何提高、申請 Pexels unlimited 或 Pixabay full API access，均需重新說明費用、風險與取得 Product Owner 明確核准。

## 7. 授權、下載保存與展示邊界

### 7.1 共同規則

- 候選只作人工選擇，不寫入 Trip、IndexedDB、localStorage 或 Service Worker；預覽 URL 隨搜尋 session 或來源 TTL 到期失效。
- 選定時以 `source + sourceAssetId` 重新取得或核對來源 metadata；使用未過期的來源快取可以視為核對。來源項目消失、識別不符、授權資料不足或下載失敗時停止保存。
- 只取得規格所需的適當尺寸，不做原圖典藏或批次下載。轉成既有尺寸策略與 `image/webp`，單檔硬上限 120 KiB；失敗則不更新 Trip。
- 卡片照片只可嵌入行程文字、時間與地點脈絡中，不得提供原圖下載、獨立素材庫、桌布、轉售、匯出素材包或可索引的圖庫列表。
- 候選與已保存卡片都顯示來源；Pexels 額外顯示攝影者並連到照片頁，Pixabay 顯示貢獻者與來源頁，Commons 依個別授權顯示作者、來源、授權與修改狀態。
- 縮放、裁切、壓縮與格式轉換的 Commons `CC BY` 封面，一律依《50》3.1.3 的固定變更聲明保存。`CC BY-SA` 一律不接受；不得把它當成可透過相同方式分享而放行的候選。
- 任何來源的 metadata 都不是第三方肖像、商標、建築、財產或隱私權保證；管理者仍須確認照片適合作該地點，申訴／下架時可由保存的 provenance 找回來源。

### 7.2 來源別規則

#### Wikimedia Commons

- 維持 V3.9.0 白名單：Public Domain、CC0、CC BY、CC BY-SA。
- 排除授權不明、缺作者／來源、缺必要 license URL、GFDL-only、NC、ND、限制欄位非空、非 `BITMAP` 或不可顯示 MIME。
- 保存 `fileTitle`、來源頁、作者／credit、授權、license URL、SHA-1、來源 revision 時間與修改狀態。

#### Pexels

- 搜尋候選固定連到 Pexels，並以照片頁連結與攝影者完成 API 指引要求；只顯示「免費」而不提供來源連結不合格。
- 保存前記錄 photo ID、照片頁、攝影者、攝影者頁、`Pexels License`、條款 URL 與查核日期。
- 只保存供行程卡片使用的受控衍生檔；不得建立可瀏覽的 Pexels 素材庫或提供 standalone 檔案散布。
- API 官方文件未提出像 Pixabay 一樣的用戶端強制快取／永久 hotlink 規則；本案仍採 24 小時伺服器搜尋快取與選定後自有 Storage，以節省額度並支援既有離線方向。

#### Pixabay

- 搜尋結果必須明確顯示來源為 Pixabay；雖 Content License 通常不強制署名，本案仍保存並顯示 contributor 與 Pixabay 來源頁。
- 候選只能暫態使用 Pixabay URL；選定後必須先下載並保存受控衍生檔，卡片不得永久引用 `previewURL`、`webformatURL` 或其他 Pixabay CDN URL。
- 保存 image ID、來源頁、contributor、contributor ID、`Pixabay Content License`、條款 URL 與查核日期。
- `safesearch=true`、`image_type=photo`；仍不得把 safesearch 當成地點正確、沒有商標／人物權利風險的保證。

## 8. 資料契約

### 8.1 搜尋請求

```ts
type PhotoSource = "wikimedia-commons" | "pexels" | "pixabay";

interface PhotoSearchRequest {
  action: "itineraryPhotoSearch";
  tripId: string;
  source: PhotoSource;
  query: string;          // trim 後 2～100 字；共同上限採 Pixabay q 的 100 字限制
  pageToken?: string;     // 第一頁省略；opaque，不由前端解析或遞增

```

- `pageToken` 由後端封裝 Commons continuation 或 Pexels／Pixabay page；token 必須綁定 source、正規化 query、filters 與到期時間，來源或搜尋詞改變後不可沿用。
- locale 可由後端依搜尋詞與 App 語系決定，但本子方案不做自動翻譯；Pexels／Pixabay 支援語系不代表改寫使用者查詢。

### 8.2 共同候選回應

  sourceAssetId: string;
  dedupeKey: string;      // `${source}:${sourceAssetId}`

## 9. 無結果與離線降級

| 狀態 | 判定 | 行為語意 |
| --- | --- | --- |
| `empty-first-page` | 第一頁來源回傳 0 筆，或全部因安全／授權契約被排除 | 提示調整搜尋詞或自行切換來源；不得稱為「本批沒有新照片」 |
| `duplicate-page` | 已執行換批、該頁有來源結果但全數已在本 session 看過，且仍有 next token | 表示本批沒有新候選；允許再取下一批 |
| `exhausted` | 沒有 next token，且本頁沒有新候選 | 表示此來源此搜尋已無更多候選 |
| `rate-limited` | remaining=0、429 或來源 cooldown | 顯示來源暫時受限及可重試時機；不自動切換來源 |
| `source-unavailable` | key 未設定、來源停用、401／403、條款閘門未通過或熔斷 | 保持現有封面／文字卡片；可由使用者選別的已啟用來源 |
| `offline` | 發出搜尋前已離線，或連線失敗可明確判定 | 禁止搜尋、換批與保存；不讀過期第三方 preview 充當新候選 |

2026-09-15 Product Owner 已核准可見文案：`empty-first-page` 為「找不到符合條件的照片，請調整搜尋詞後再試。」；`duplicate-page` 為「這一批沒有新的照片；可再換一批或調整搜尋詞。」；`exhausted` 為「已沒有更多照片；可調整搜尋詞或改用其他來源。」三者皆不得自動切換來源；只有 `duplicate-page` 可再取下一批。

- 已保存封面使用自有 Storage／既有受控快取；離線命中時可顯示，未命中或載入失敗就回到現有文字卡片。
- 離線、無結果、來源錯誤與圖片載入失敗都不能阻塞時間、地點、說明、編輯、排序、跨日複製或路線功能。
- 不反覆背景重試，不用舊候選假裝新結果，不因搜尋失敗刪除目前封面。
- 本節只定義狀態與必要訊息，不核准最終可見文案或版面。

單一來源被停用時，既有已合法選定並保存的卡片照片仍依當時保存的 attribution 與 Storage 契約顯示；只有收到具體侵權／下架通知、metadata 證據不足或法務要求時才進入移除流程。來源停用不得造成 Trip 或其他來源不可用。
