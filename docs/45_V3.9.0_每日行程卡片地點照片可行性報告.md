- 狀態：Product Owner 已確認 V3.9.0 同時納入 Google 候選索引照與 Commons 每日卡片選圖；正式 UI 尚待模擬圖核准

## 1. 決策摘要

### 2026-09-12 修正

本報告第一版把「自動照片」過度收斂成 Google Places，沒有重新納入先前討論的免費照片來源。由於 repo 與 Git 文件中沒有留下先前免費方案的正式紀錄，本次依 Product Owner 指正補回 Pexels、Pixabay、Wikimedia Commons／Openverse 與 Unsplash；在命中率 spike 完成前，不再宣稱手動上傳是唯一可行方案。

目前拆成兩條驗證：

1. **地點搜尋候選索引照片**：Google Autocomplete 本身沒有照片，但可依候選 `placeId` 查 Place Details 與 Place Photos。真實 spike 證實 10／10 候選都有可載入照片，包含免費來源找不到的租車點與餐廳；建議立案，但只作管理者搜尋當次的暫態索引照，不保存或延伸到每日卡片。
2. **每日行程卡片照片**：V3.9.0 採 Wikimedia Commons 作知名景點候選，由管理者編輯搜尋詞並人工選圖，不自動採第一張；選定後壓縮為受控檔案並保存完整 attribution。Pexels／Pixabay 不作本版阻擋項目。

下列理由只支持「不以 Google Places 自動照片作為每日卡片永久來源」，不等同排除免費圖庫：

理由如下：

1. Google 允許永久保存 `placeId`，但明確禁止快取照片資源名稱，且照片名稱會失效；這與目前 PWA 的離線優先方向不相容。
2. 顯示 Google 照片時，卡片必須處理 Google Maps 標示及可能存在的作者姓名、頭像與連結；這不是單純加一張背景圖，會直接增加手機卡片的版面與可見文案需求。
3. 每次成功取得照片會觸發 Photos SKU。2026-09-12 官方價目為每月前 1,000 次免費，之後第一級每 1,000 次 US$7；多位使用者重複開啟相同行程時，請求量隨「使用者 × 被看到的卡片 × 冷載入次數」成長。
4. Google 不保證回傳影像格式，也沒有可由本 App 強制的位元組上限。即使限制像素尺寸，仍無法在下載前保證每張照片的傳輸量。
5. 現有 Google Web Service 金鑰安全地留在 Supabase Edge Function；瀏覽器不應直接取得金鑰。若以 Edge Function 代理影像，會增加函式與 egress 成本，且不能藉此規避 Google 的保存／快取限制。
6. 手動上傳或把允許下載保存的免費圖片存入受控 Storage，可在上傳前壓縮、限制格式與容量；但仍須另行設計來源證明、attribution、存取矩陣、刪除與替換流程。

### 2026-09-12 公開 API 命中率 spike

使用 repo 既有公開行程抽取 12 個代表地點：5 個知名景點、2 個交通地點、1 間飯店、4 間餐廳。以英文正式名稱分別查詢 Wikimedia Commons 與 Openverse，各取前 3 筆，共 24 次公開 API 請求；不下載圖片、不寫入 App 或 production。判定只接受標題或描述可確認為同一實體者，不能只因同城市或同類型而算命中。

| 類型 | 樣本數 | Commons hit@3 | Openverse hit@3 | 觀察 |
| --- | ---: | ---: | ---: | --- |
| 知名景點 | 5 | 5／5 | 5／5 | 熊本城、高千穗峽、首里城、美麗海水族館、萬座毛皆有結果。Openverse 首筆可能是歷史照、海底珊瑚等，不一定適合作辨識縮圖。 |
| 交通地點 | 2 | 1／2 | 1／2 | 桃機二航廈命中；OTS 臨空豐崎營業所無結果。 |
| 飯店 | 1 | 1／1 | 1／1 | 日航城市那霸可命中，但 Commons 第一筆是無關 PDF，證明不能自動採第一筆，且必須限制可接受 MIME。 |
| 餐廳 | 4 | 0／4 | 0／4 | 四家在地餐廳皆無結果。 |
| **合計** | **12** | **7／12（58.3%）** | **7／12（58.3%）** | 命中集中在著名地標，無法覆蓋需要確認的長尾商家。 |

回傳結果的 Commons 檔案都有 creator、license 與來源頁資料；Openverse 本輪 20 筆結果也都有 creator、license、license URL 與原始來源。但「metadata 完整」不等於可直接採用：Openverse 多筆 Flickr 結果為 `BY-NC`、`BY-NC-SA` 或 `BY-NC-ND`，若先以可商用且允許必要縮放／裁切的 `CC0／Public Domain／CC BY／CC BY-SA` 白名單過濾，實際可用率會低於表中 hit@3。正式產品仍須逐檔保留授權快照與 attribution。

可重跑治具：`node scripts/spikes/evaluate-v390-free-photo-sources.mjs`。結果不寫檔，避免把第三方縮圖網址或內容當成專案資料保存。

**階段結論：** Commons／Openverse 可作「著名景點的免費封面候選」，不能取代 Google `placeId` 對應的搜尋候選索引照，也不應自動套第一張。Pexels／Pixabay 仍須 API key 才能做同一矩陣；目前 repo 與遠端 secrets 均沒有這兩組憑證，因此未以推測冒充實測。

### Commons 中文／英文、節流、授權與容量補充 spike

針對已命中的 7 個景點／交通／飯店，以中文與英文各查一次 Commons 官方 REST 搜尋，共 14 次請求：12／14 組有可顯示圖片，中文 6／7、英文 6／7，但缺圖對象不同。中文「那霸日航城市飯店」無結果，英文可命中；英文桃機二航廈前 8 筆沒有一般圖片縮圖，中文則可命中。因此選圖器必須允許管理者修改搜尋詞，不能宣稱自動翻譯或單一語言足夠。

一般回應約 463～872 ms，平均受一次 13.4 秒節流長尾拉高到 1.55 秒；先前連續 Action API `extmetadata` 查詢也曾得到 429。正式設計應以 Edge Function 集中 REST 搜尋、少量批次 imageinfo、debounce、節流、`Retry-After` 與短期查詢快取，不能讓每張卡片直接打 Commons API。

搜尋品質仍需人工判斷：熊本城包含 1931 年歷史照與地震損壞照，美麗海水族館大量結果是販賣部飲料罐，萬座毛中文結果集中在商場。這些都有關鍵字關聯，但不一定適合當地標封面。

另選 7 張人工確認圖片，以一次批次 imageinfo 驗證：7／7 均為 `BITMAP` JPEG 縮圖，作者、credit、來源頁與授權資訊完整；包含 Public Domain、CC BY 2.5／4.0、CC BY-SA 3.0／4.0。640px 縮圖為 75,061～408,201 bytes，平均約 239.8 KiB，只有 1／7 符合原 120 KiB 預算。因此不能直接把 Commons 640px 縮圖當最終卡片資產，選定後須縮放／壓縮成受控 WebP，並在 attribution 記錄已修改。

- `node scripts/spikes/verify-v390-commons-license-contract.mjs`

### 2026-09-12 真實 Google Places／Photos spike

經 Product Owner 同意後，在既有 Supabase 專案部署只接受固定五組查詢的暫時性 Edge Function，使用遠端既有 `GOOGLE_MAPS_API_KEY`。每組最多 5 個候選，理論照片請求上限 25 次；實際只有 10 個候選，因此執行 10 次照片請求。函式不接受任意搜尋字、不寫資料庫、不保存圖片或照片 URL，測試完成後立即刪除，刪除後再次請求已確認回傳 `404 NOT_FOUND`。

樣本涵蓋首里城、OTS 臨空豐崎營業所、那霸日航城市飯店、福助玉子燒飯糰與 BANTA CAFE：

| 指標 | 結果 | 判讀 |
| --- | ---: | --- |
| Autocomplete 查詢 | 5／5 成功 | 5 組共回傳 10 個候選；首里城 5 個、BANTA CAFE 2 個，其餘各 1 個。 |
| 有照片候選 | **10／10（100%）** | 每個候選至少 5 張，9 個候選回傳 10 張；包含 Commons／Openverse 無結果的租車點與餐廳。 |
| 實際照片載入 | **10／10（100%）** | 9 張 JPEG、1 張 PNG；未發生 403、404、429 或逾時。 |
| attribution | **10／10** 有 1 筆作者資料 | display name、作者 URI 與作者照片 URI 三種欄位皆存在；正式 UI 必須保留合規入口。 |
| Autocomplete 延遲 | 54～103 ms，平均 73 ms | 文字候選可先快速顯示。 |
| Place Details 延遲 | 67～157 ms，平均 96 ms | 各候選可平行查詢。 |
| Photos API 延遲 | 40～66 ms，平均 51 ms | 不含真正影像下載。 |
| 影像下載延遲 | 62～514 ms，中位數約 86 ms | 3 張出現約 486～514 ms 長尾，應漸進載入，不等待所有圖片才讓候選可操作。 |
| 320×180 傳輸量 | 14,711～52,009 bytes，平均約 24.6 KiB | 10 張合計約 245.9 KiB；本輪雖小，Google 仍不保證固定格式或位元組上限。 |
| 五組完整測試 | 約 4.15 秒 | 這是五組依序跑完；實際使用者一次只搜尋一組。依本輪平行候選估算，單次約 0.24～0.80 秒完成照片。 |

首里城結果同時出現主景點、公園、自行車停車場與 P1／P2 停車場；BANTA CAFE 同時出現咖啡店與停車場。這正是索引照有價值的情境：地址文字相似，但照片可輔助辨識候選類型。Google 結果綁定 `placeId`，對長尾商家覆蓋明顯優於關鍵字免費圖庫。

Supabase changelog 核對結果：2026 年與本評估最相關的異動包括新表預設不再自動暴露至 Data API（2026-10-30 起全面套用）、Edge Function 巢狀呼叫限流，以及 `supabase-js` 未來要求 TypeScript 5+／停止支援 Node.js 20。本專案目前 TypeScript 6.0.2、Node.js 22.23.2，不受後兩項阻擋；若將來新增封面表，migration 必須明確處理 Data API exposure，不能假設建立 `public` table 後前端即可存取。

## 3. 現有架構盤點

| 邊界 | 現況 | 可重用／缺口 |
| --- | --- | --- |
| 地點識別 | `ConfirmedPlace` 只保存 `placeId`；顯示文字仍使用行程資料。 | `placeId` 可重用且符合 Google 永久保存例外；不應擴充為永久照片名稱或 URL。 |
| Google API | `travel-route` Edge Function 使用 `GOOGLE_MAPS_API_KEY` 呼叫 Places Autocomplete 與 Routes，且先驗證 Trip 管理權。 | 金鑰與授權骨架可重用；目前只有管理者可查詢，不能直接滿足所有檢視者看照片。 |
| CSP | production `img-src` 只有 `'self' data: blob:`；`connect-src` 只有同源與 Supabase。 | Google／Googleusercontent 影像目前會被擋。自動照片需調整 CSP，手動私有封面可使用 Supabase 簽名 URL，但仍須核對來源。 |
| PWA 快取 | Workbox precache 本地 `js/css/html/ico/png/svg/json`；沒有遠端照片 runtime cache。 | Google 照片不應加入持久快取；手動且自有權利的封面可另定受控快取與失效策略。 |
| Storage 經驗 | 帳本附件已有私有 bucket、路徑編碼、RLS、簽名 URL、刪除及本機附件流程。 | 可重用壓縮與私有檔案經驗，但附件 policy 只服務 expense ownership，不能複製後直接套用卡片封面。 |
| Trip 資料 | 行程內容存於 Trip payload，卡片有穩定 item id。 | 可在正式規格評估 `cover` metadata；需要 migration／相容性策略與舊版忽略未知欄位驗證。 |
| 公開／離線資料 | App 有 Guest、已登入角色、歷史唯讀、離線與系統保留 Trip。 | 封面必須另定哪些角色可讀、可寫、可刪；Guest 與離線不能靠「管理者查詢照片」臨時補資料。 |

### 自動 Google 照片的最小資料流

1. 瀏覽器把 `tripId`、`itemId`、`placeId` 送至已驗證身分與 Trip 權限的 Edge Function。
2. Edge Function 以固定欄位遮罩向 Place Details 取得當下有效的照片名稱與 attribution。
3. Edge Function 向 Place Photos 要求指定像素尺寸；若只回傳 `photoUri`，瀏覽器再向 Google 圖片主機下載影像。
4. App 不保存照片名稱、URL 或影像本體；下次冷載入重新查詢。
5. App 顯示 Google Maps 與作者 attribution，並處理無照片、403、404、429、逾時與離線。

此資料流若套用到每次每日卡片瀏覽，會有高請求量、無離線照片、attribution UI、CSP 與成本控制問題，所以不建議作每日卡片永久來源；但用於低頻、管理者限定、原本就需要連線的地點搜尋候選，風險與成本可控，建議立案。

### 地點搜尋候選索引照契約 spike

已建立不進入正式 App 的契約治具 `node scripts/spikes/verify-v390-place-photo-contract.mjs`，並驗證：

- 每次搜尋最多讓 5 個唯一 `placeId` 進入照片查詢，理論上最多 5 次成功 Photos SKU 請求。
- 無照片、失敗或逾時只讓該候選沒有縮圖，不能移除候選或阻擋使用者選取。
- 照片資源名稱、Google Maps URI 與作者 attribution 都只存在於當次搜尋暫態；確認地點後仍只永久保存 `placeId`。
- 現有 Edge Function 只有 `placeAutocomplete`／路線查詢，前端 `PlaceCandidate` 沒有照片欄位，production CSP 也未允許外部圖片主機；本次沒有把契約測試誤當產品已實作。

此契約與真實 spike 已共同證明資料邊界、照片命中、回應延遲及 attribution shape 可行。現有 Google 金鑰仍只存在遠端 Supabase secret，CLI 未讀回原值；暫時性函式與本機 token runner 均已移除，正式 `travel-route` 未修改。

### Commons 選定封面的建議資料流

1. 管理者以可編輯搜尋詞查詢 Commons，從通過 MIME 與授權白名單的候選中人工選擇。
2. App 重新核對作者、來源、授權、限制與圖片資訊；瀏覽器把選定圖片縮放／壓縮成 120 KiB 內 WebP，記錄已修改。
3. 新 public bucket 只接受 WebP、固定容量與 Trip scope／item scope／隨機版本路徑；公開讀取與目前匿名可讀的 Trip 一致，寫入／刪除仍只允許可寫入該 Trip 的管理者。
4. Trip payload 保存 storage path、作者、credit、來源頁、授權、來源 SHA-1／revision、修改狀態、版本與圖片尺寸，不保存 Commons hotlink URL 作卡片來源。
5. 替換採先上傳新檔、再更新 Trip、最後刪除舊檔；更新失敗回滾新檔。刪除卡片、Trip、撤銷封面或縮短天數時清理物件並保留 orphan 重試稽核。
6. 歷史唯讀與離線狀態禁止搜尋、選取、替換或移除；讀圖失敗時顯示既有無照片卡片，不阻塞行程文字。

## 5. 降級與錯誤行為

不論未來選哪個照片方案，下列行為應寫入正式規格：

- 圖片不是行程主要資料；時間、類型、地點、說明、路線與管理操作先顯示且不得等待圖片。
- 無照片、未設定封面、離線、逾時、403、404、429、簽名 URL 失效、解碼錯誤時，卡片回到現有無照片版面，不顯示破圖圖示、不反覆重試。
- Day 切換只載入新 Day 的可見卡片；離開 viewport 後不立即取消已接近完成的請求，但同一生命週期不得重複請求同一版本封面。
- 回到前景時，已有有效自有封面快取可直接顯示；已失效簽名 URL 只更新 URL，不重新下載仍有效的 Cache Storage／HTTP cache 內容。
- 圖片載入失敗不顯示阻擋對話框、不影響編輯、排序、跨日複製或路線查詢。
- 自動 Google 方案若遇 attribution 資料不完整，寧可不顯示照片，不可顯示無法合規標示的影像。

### 手動封面的候選預算

正式 spike 建議衍生檔長邊上限 640px、維持原圖比例，壓縮後每張硬上限 120 KiB；卡片以 76×76 方形縮圖和 `object-fit: cover` 顯示，同時下載最多 2 張、`loading=lazy`，且首屏文字先完成 layout。此數值是待實機驗證的效能預算，不是圖片裁切規格。

| 情境 | 手機 390×844 | 桌面 1280×900 |
| --- | ---: | ---: |
| 首屏可見 0 張 | +0 KiB | +0 KiB |
| 首屏可見 1 張 | 最多 +120 KiB | 最多 +120 KiB |
| 首屏可見 2／4 張 | 最多 +240 KiB | 最多 +480 KiB |
| 長 Day 共 12 張、完整捲過 | 最多 +1,440 KiB | 最多 +1,440 KiB |
| 單張解碼 RGBA 參考上限（以 640×640×4 計） | 約 1.56 MiB | 約 1.56 MiB |
| 同時解碼 2／4 張 | 約 3.13 MiB | 約 6.25 MiB |

因此照片可能讓手機首屏傳輸由約 285 kB 增至約 525 kB，桌面四張可見時增至約 765 kB；長 Day 完整捲動可再增加 1.41 MiB。正式開發前應以核准版型、兩組真實且有權使用的測試圖片，在桌面與 390×844 各測冷／暖啟動、Slow 4G、離線重開與 12 張清單。此項尚未完成，不能只以容量模型取代實機量測。

自動 Google 照片只能指定像素尺寸，不能指定檔案大小或格式，因此無法承諾上述 120 KiB 上限；這是拒絕自動方案的主要效能理由之一。

## 7. 請求量與成本模型

### Google 自動照片

每月照片請求量：

`月活躍使用者 × 每位每月查看行程天數 × 每日實際看到的照片卡片數 × 每張卡片冷載入次數`

以 2026-09-12 價目、該 SKU 每月 1,000 次免費用量上限、超額第一級 US$7／1,000 次估算：

| 使用情境 | 算式 | 月請求 | 月費估算 |
| --- | --- | ---: | ---: |
| 小量 | 30 人 × 5 日 × 8 張 × 1 次 | 1,200 | US$1.40 |
| 中量 | 100 人 × 5 日 × 10 張 × 1.5 次 | 7,500 | US$45.50 |
| 高量 | 500 人 × 8 日 × 12 張 × 2 次 | 96,000 | US$665.00 |

試算未含稅、匯率、既有 Google API 使用量及其他 SKU；免費額度由同一 billing account／SKU 的實際用量共同影響。若未來仍重啟自動方案，至少要設定每月 1,000 次 App 端軟上限、Google Cloud quota 與 50%／80%／100% budget alert，超限後直接使用無照片版面。

### 管理者手動封面

以每張 120 KiB 計算：

| 數量 | Storage | 每月每張各下載 1 次 | 每月每張各下載 10 次 |
| --- | ---: | ---: | ---: |
| 100 張 | 約 11.72 MiB | 約 11.72 MiB egress | 約 117.19 MiB egress |

## 9. 本專案建議

採取「用途分流」，不要選一個來源同時解決兩種需求：

1. **地點搜尋候選：採 Google Place Photos。** 它是本輪唯一能以 `placeId` 覆蓋景點、飯店、租車點與長尾餐廳的來源。只讓管理者在搜尋當次看到、最多 5 張候選縮圖；文字先出現、圖片漸進載入，失敗時仍可選地址。照片名稱、URI、影像與 attribution 不寫入 Trip、Storage、IndexedDB 或 Service Worker。
2. **每日行程卡片：V3.9.0 採 Commons 管理者選圖。** 不自動載入 Google；搜尋詞可編輯、最多 8 張、僅白名單授權與圖片格式，管理者人工確認後壓縮保存。找不到適合圖片時維持無照片卡片，不為湊圖而錯配。
3. **成本護欄：** 前端每次搜尋最多 5 個照片候選；Edge Function 同樣截斷為 5，避免繞過前端；只有搜尋字停止輸入且 Autocomplete 成功後才查照片，不預抓、不背景重試。以每月 1,000 次免費額度計算，最壞每次搜尋 5 張約容納 200 次搜尋；建議在 800 次設定內部軟門檻，超過直接退回文字候選，並搭配 Google Cloud quota／budget alert。
4. **安全與合規：** 金鑰只留在 Edge Function；回傳必要暫態欄位；候選容器保留 Google Maps 標示，另提供作者 attribution 的可開啟入口。CSP 只加入實測需要的圖片來源，不開放萬用 `https:`。
5. **版本範圍：** Product Owner 已決定 V3.9.0 同時實作兩軌，但程式、API 與資料邊界保持分離；共同在桌面／390×844 模擬圖核准後進入開發。

此決策把 Google 用在它不可替代且低頻的 `placeId` 辨識，把 Commons 用在管理者已確認、需要重複顯示的知名景點卡片；兩軌同版但不混用資料。
