# 本機測試資料庫同步流程

> 本文件只規範兩台電腦各自的本機 Supabase 測試資料及 Git 版本化合成 fixture。正式 Supabase schema／Migration 與部署請依《[正式 Supabase 資料庫 Migration 與部署流程](81_正式Supabase資料庫Migration流程.md)》辦理。

## 1. 範圍與基準

- Git 管理的 Migration 負責 schema；Git 管理的 Seed／fixture 負責可重現的合成測試資料。兩者不可混為同一同步機制。
- 公司端與家用端的本機 Docker DB 各自獨立；不得複製 Docker volume 或正式 DB dump 作為同步方式。
- fixture 只可含明確挑選的合成／去識別資料，不得含正式資料 dump、secret、token 或 Storage 檔案本體。
- Git pull 只更新版本控制檔案；本機 DB 仍須執行專用同步入口並驗證。

## 2. 對等節點與 revision 規則

家用端與公司端是動態對等節點，任一端都可能產生下一個 fixture revision，也可能接收另一端的 revision。manifest 的 `sourceHost` 僅供來源稽核，不可決定節點角色。

唯一版本判斷依據為本機 applied version／checksum 與 Git current／parent version／checksum：
- applied 等於 Git parent：Git 有新 revision 待接收；只有本機 DB 與 parent 資料相符時才可匯入。
- applied 等於 Git current：基準一致；確認本機有業務資料修改後，才可產生下一 revision。
- applied 與 current／parent 都不符、父鏈斷裂或 baseline 不明：停止並回報，不猜測、不匯出、不覆蓋。

本機 handoff state／檔案 hash 僅供診斷，不可單獨決定角色或判定 peer revision。

## 3. 衝突保護

以下情況一律 fail closed，不採 last-write-wins、不自動合併、不覆蓋：
- 兩端從同一 parent 各自修改；
- 同版不同 checksum、版本回退／缺號、parent checksum 不符；
- 本機 applied baseline 不明；
- 本機 DB 既非已知 parent 也非 current；
- 接收新 revision 時，本機 DB 已有獨立業務資料修改。

資料列基準比較可忽略 DB trigger 自動更新的時間戳差異，但不可忽略業務欄位差異。匯入須在交易內再次核對 parent 資料列及筆數。

## 4. 日常操作

1. 確認主機、工作目錄、分支、upstream、工作樹與遠端差異；不安全時停止，不自動覆寫。
2. 需要取得另一端已提交 revision 時，安全執行 `git pull --ff-only origin develop`。
3. 執行 `npm run db:sync:local`。此入口只操作本機 loopback Supabase；不執行 reset、不清除資料、不自動 pull／commit／push。
4. 依結果判斷已接收、未變更、產生本機下一 revision 或因衝突停止。失敗時保存輸出並停止，不用 reset 作為補救。

## 5. 家用端修正與發布停止線

在家用端完成正式同步邏輯修正、直接測試正式判斷程式、統一 `AGENTS.md` 與相關文件、通過 revision／衝突測試及 fixture 驗證之前，不得執行完整 `commit/push/資料庫` 口令流程，也不得先推送 V6 或未驗證的同步邏輯供另一端測試。

解除停止線前至少驗證：兩端角色互換、接收、未變更、產生下一版、未知 baseline、同版不同 checksum、parent mismatch、雙方獨立修改及時間戳差異；測試必須直接呼叫正式程式邏輯，不能另寫模擬分類函式。

此口令僅啟動已核准範圍的測試 fixture 交接，不授權正式 Supabase 部署、破壞性資料操作或覆寫衝突資料。正式資料庫操作仍依正式 Migration 文件的獨立核准規則。

## 6. 詳細生命週期與驗收

revision manifest、資料列匯入規則、fixture 狀態、歷史驗收與本次問題修正清單，見《[雙電腦測試資料生命週期設計](archive/supabase-sync/82_雙電腦測試資料生命週期設計.md)》。本文件定義日常操作邊界；文件 82 定義 fixture 生命週期及詳細驗收要求。
