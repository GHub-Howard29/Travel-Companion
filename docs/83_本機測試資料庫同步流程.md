# 本機測試資料庫同步流程

> 本文件規範三台以上對等電腦各自的本機 Supabase 合成測試資料同步。Git 只傳遞 fixture 基準檔；正式 Supabase schema／Migration 與部署請依《[正式 Supabase 資料庫 Migration 與部署流程](81_正式Supabase資料庫Migration流程.md)》辦理。

## 1. 範圍與基準

- Git 管理的 Migration 負責 schema；Git 管理的 Seed／fixture 負責可重現的合成測試資料。兩者不可混為同一同步機制。
- 公司端與家用端的本機 Docker DB 各自獨立；不得複製 Docker volume 或正式 DB dump 作為同步方式。
- fixture 只可含明確挑選的合成／去識別資料，不得含正式資料 dump、secret、token 或 Storage 檔案本體。
- **fixture revision 只代表 manifest 明確列出的 fixture 子集合，不代表整個 Supabase DB 快照。** 目前 `tc-test-sync-example` V5 只包含 1 筆 `tc-test-*` Trip、1 筆 shared checklist、6 筆 checklist item、1 筆 expense；不涵蓋其他 `trips`、Excel RPC request registry、其他資訊、Auth／admin profiles、Storage 或其他業務表。`already-applied` 只表示本機已套用該 fixture revision state，不證明全庫與 Git V5 完全相同。
- Git pull 只更新版本控制檔案；本機 DB 仍須由使用者在接收端執行專用同步入口並驗證。

## 2. 對等節點與 revision 規則

家用端與公司端是動態對等節點，任一端都可能產生下一個 fixture revision，也可能接收另一端的 revision。manifest 的 `sourceHost` 僅供來源稽核，不可決定節點角色。

唯一版本判斷依據為本機 applied version／checksum 與 Git current／parent version／checksum；V5、V6 等只是當下 revision 標籤，不是永久基準：
- applied 等於 Git current：兩端基準一致。若本機 DB 相對 current 沒有業務資料變更，維持原版本，不產生新 revision，也不需要上傳；若有業務資料變更，才可由 current 建立下一 revision。
- applied 等於 Git parent：Git 有下一 revision 待接收。只有本機 DB 仍與 parent 資料相符，才可匯入 Git current；接收後 applied state 更新到 current，但不因此再升版或回傳一個空 revision。
- applied 與 current／parent 都不符、父鏈斷裂或 baseline 不明：停止並回報，不猜測、不匯出、不匯入、不覆蓋。

本機 handoff state／檔案 hash 僅供診斷，不可單獨決定角色或判定 peer revision。

## 3. 衝突保護

以下情況一律 fail closed，不採 last-write-wins、不自動合併、不覆蓋：
- 兩端從同一 parent 各自修改；
- 同版不同 checksum、版本回退／缺號、parent checksum 不符；
- 本機 applied baseline 不明；
- 本機 DB 既非已知 parent 也非 current；
- 接收新 revision 時，本機 DB 已有獨立業務資料修改。

資料列基準比較可忽略 DB trigger 自動更新的時間戳差異，但不可忽略業務欄位差異。匯入須在交易內再次核對 parent 資料列及筆數。

## 4. 日常操作

### Git 操作（與資料庫完全分離）

1. `commit`、`push`、`commit/push` 只處理一般程式碼／文件 Git 變更。
2. 完整口令 `commit/push/資料庫` 已整個廢除，不再是有效指令；收到時不執行任何動作，應提示使用者改用一般 Git 口令或獨立資料庫口令。不得將它視為一般 Git 操作，也不得呼叫 `testdata:handoff:publish`、upload、download、export 或 import。
3. Git 操作維持精確 stage、安全分支／upstream／遠端檢查；不可使用 `git add .`，不可順便修改或同步本機資料庫。

### 資料庫上傳（使用者明確輸入 `/上傳資料庫`）

1. 僅執行 `npm run testdata:upload`（`scripts/testdata-upload.mjs`）。
2. 只驗證並上傳本機 loopback Supabase 的合成 fixture manifest/data 白名單至 `origin/develop`；依 baseline、parent、checksum、資料列差異及敏感資料規則 fail closed。
3. 不執行一般程式碼／文件 commit，不 pull、不 download、不 import，也不執行 `db:sync:local` 或舊 `testdata:handoff:publish`。
4. 若分支、upstream、遠端、工作樹或 fixture 安全檢查不符，停止並回報；不得覆寫、reset 或 force-push。

### 資料庫下載（使用者明確輸入 `/下載資料庫`）

1. 使用者先自行確認本機 Git 已取得目標 committed fixture（必要時另行執行安全的 `git pull --ff-only origin develop`）；下載口令本身不得執行 Git pull。
2. 僅執行 `npm run testdata:download`（`scripts/testdata-download.mjs`），只讀取本機 Git 已提交 fixture，並依 baseline／parent／checksum 規則寫入目前主機自己的 loopback Supabase。
3. 不執行 upload、export、一般 Git commit/push/pull 或舊的 `db:sync:local`。
4. 若 fixture 不存在、基準未知、parent 不符或本機資料分歧，停止且不寫入；不可 reset 或覆蓋衝突資料。

**三個動作永遠分開：Git commit/push、資料庫 upload、資料庫 download。** 一個口令只啟動其對應動作；不得由另一個口令、一般工作完成或對話提及自動觸發。所有資料庫動作僅限本機 loopback Supabase，不接觸正式 Supabase。

## 5. 雙機測試啟動與發布停止線

### 5.1 受控雙機測試：已解除啟動限制

**自 2026-11-03 起，允許公司端與家用端開始受控雙機同步驗收。** 不必等到所有真實雙機案例先通過才可開始；雙機驗收本身就是驗證同步流程的必要手段。共同基準不是寫死的 V5，而是兩端以 Git fixture manifest 與本機 applied state／checksum 實際核對後，能證明一致的最新 revision。

目前已知狀態（2026-11-03）：Git fixture 為 V5（checksum `301153c0fa20354522a9d83c1c76f8bb0a7d745e59dbcb48a799a6660b1d15ca`）、家用端 DB 為 V5；公司端 DB V6 是使用者回報，尚未由本機工具在公司端獨立核實，且 V6 尚未上傳 Git。故不得把 V5 寫成永久基準，也不得把公司端 V6 直接視為已驗證的 peer revision。公司端應先確認 applied state = Git V5，且 DB 資料相對 V5 的差異可被限定為允許的合成資料變更；再產生／驗證 V6 fixture，確認 parentVersion=5、parentChecksum 等於上述 Git V5 checksum、資料筆數／checksum／敏感欄位均通過，才可使用安全 publish 發布。若公司端 applied state、父子關係或資料差異無法證明，停止，不可強制上傳。

啟動每一輪前，兩端都必須：
- 確認使用同一個已提交的 fixture revision 與 checksum，且兩端本機 applied state／DB 資料皆可證明基準一致。
- 確認本機 applied revision／checksum 與本機 DB 資料相符；無法證明基準時不得匯入或覆蓋。
- 確認操作目標是各自的本機 loopback Supabase，絕不連線或寫入正式 DB。
- 先完成該端 Git 分支、upstream、工作樹及遠端差異檢查；取得對端 revision 僅使用安全 fast-forward。

一般 A／B 同步流程如下（A、B 可互換，Git current 是共同版本依據）：

1. **A 有資料變更：** A 的本機 applied 必須等於 Git current，且 DB 與 current 的差異可驗證；handoff 產生 current+1，parent 指向 current，執行 fixture 格式／checksum／資料安全驗證後，才可安全 commit／push。不能跳過基準檢查直接上傳。
2. **B 下載並接收：** B 先 `git pull --ff-only origin develop`，再執行 `npm run db:sync:local`。若 B applied 等於 Git current 的 parent，且 B DB 仍與 parent 相符，import 才能將 fixture 所屬資料更新到 Git current，並更新 B 的 applied state；接收本身不建立下一版、不自動回傳空 revision。
3. **B 接收後沒有資料變更：** B 再跑 handoff／標準同步時，若 DB 與 Git current 相符，結果是 unchanged，版本維持 current，不建立新 revision、不需要 commit／push；Git 保持 current。
4. **B 接收後有資料變更：** B 的 applied 已等於 Git current，handoff 比對確認存在業務資料差異，才產生 current+1 並以 current checksum 為 parent；通過驗證後安全 commit／push，Git current 隨之更新。
5. **A 在 B 尚未接收前也有新變更：** 若 A 與 B 分別從同一 current 修改，第一個成功發布者形成 Git current+1；另一端的本機 DB 與 parent 已不一致，接收流程必須停止，不得覆蓋。須由使用者檢視兩邊差異，人工決定保留／合併後形成下一個單一 revision，再讓另一端接收。
6. **同版本不同 checksum、父版不符、baseline 無法證明或版本鏈分歧：** 一律停止，不以時間戳或 `sourceHost` 自動判斷誰應覆蓋誰。人工處理後，建立明確的新共同 revision；不得直接改寫既有 revision 或 force-push。

每一步均核對 manifest revision、parent checksum、applied state 及資料內容；僅同步動作而沒有業務資料變更時，不應無故升版。

**測試期間的衝突停止線仍然有效：** 同版不同 checksum、parent 不符、版本回退／缺號、baseline 不明、兩端從同 parent 各自修改，或接收端存在獨立業務資料修改時，該輪立即停止並保留現況；不得 last-write-wins、自動合併、reset 或覆蓋。停止單一衝突案例不代表禁止其他安全案例繼續驗收。

### 5.2 尚未完成的驗收項目

正式同步決策邏輯已抽為 `scripts/lib/testdata-revision.mjs` 的 `classifyPeerHandoff()`，正式 `handoff()` 已呼叫該函式；`scripts/test-testdata-peer-sync.mjs` 亦直接 import 同一函式。已完成純函式案例包含接收、未變更、產生下一版、未知 baseline、版本／父鏈不符與本機資料分歧保護。2026-11-04 家用端實際 publish 驗證發現並修正一項呼叫端分類錯誤：當 applied version／checksum 已等於 Git HEAD 時，必須以 HEAD 作為 current、incoming=null；只有 applied 等於 Git HEAD 的 parent revision 時，才將 Git HEAD 視為待接收 incoming。修正後本機 `tc-test-sync-example` V5（checksum `301153c0fa20354522a9d83c1c76f8bb0a7d745e59dbcb48a799a6660b1d15ca`）實際 handoff 結果為 `unchanged`，並安全略過空 commit／push，沒有產生 V6。已增加純函式回歸案例，涵蓋 applied=HEAD 時 unchanged，以及 applied=parent 時 receive。仍待補驗兩端角色互換的實際 DB 情境、時間戳差異及真實 A→B→A 端到端流程；這些是驗收待辦，不是禁止開始受控雙機測試的前置條件。

以上是驗收待辦，不再是禁止啟動真實雙機測試的前置條件。測試結果必須如實記錄，全部通過前不得宣稱雙機同步驗收完成。

### 5.3 程式／fixture 發布停止線

受控雙機測試的啟動，不等於授權推送程式或 fixture。一般程式碼／文件 commit、fixture upload 及 fixture download 是三個獨立動作，分別依根目錄 `AGENTS.md` 的 `/上傳資料庫`、`/下載資料庫` 與一般 Git 操作規則執行；歷史完整口令 `commit/push/資料庫` 已廢止其資料庫交接作用，不再觸發 fixture publish。不得把未驗證的同步程式或不合格 fixture 推到另一端。任何口令均不授權正式 Supabase 部署、破壞性資料操作或覆寫衝突資料。正式資料庫操作仍依正式 Migration 文件的獨立核准規則。

## 6. 三方以上對等節點同步（2026-11-04 新規格）

本節為目前生效的方向判斷與程式入口規格；本文件前述雙機步驟屬歷史操作背景，與本節衝突時以本節為準。

### 6.1 節點模型與唯一基準時間

- 公司端、家用端及第三台電腦都是對等節點；不固定 sender／receiver，`sourceHost` 僅作稽核記錄。
- Git `origin/develop` 是測試 fixture 基準檔的傳遞媒介，不代表某台電腦是主機；每台電腦保有自己的本機 Supabase。
- 每份 manifest 使用 `baselineAt`（UTC ISO 8601）代表該 fixture 內容基準建立／更新時間。這不是 row `created_at`、`updated_at`、`exportedAt` 的比較，也不使用資料庫時間欄位判斷方向。
- 舊 manifest 尚未有 `baselineAt` 時，首次相容讀取以既有 `exportedAt` 作為基準時間；之後新版本正式寫入 `baselineAt`。舊版 applied state 若缺少時間，下載程式以 applied version／checksum 回查 Git 歷史 manifest 找回原基準時間，找不到就停止，不以主機目前時間猜測。

### 6.2 時間戳記方向規則

| 本機已套用基準 | Git 目前基準 | 動作 |
|---|---|---|
| 無可證明基準 | 有效基準 | 只有本機 DB 已等於 Git current fixture 才採認；空白或其他內容均停止 |
| 本機較舊 | Git 較新 | 允許下載方向，仍須符合 parent／資料列檢查 |
| 本機較新 | Git 較舊 | 允許上傳方向，須確認本機 applied version/checksum 與 Git current 一致 |
| 時間相同、checksum 相同 | 相同 | unchanged，不傳輸 |
| 時間相同、checksum 不同 | 衝突 | 停止，不覆蓋、不自動合併 |

時間只負責選擇方向；revision parent/checksum、資料列完整性和敏感欄位檢查仍是寫入前必要條件。即使時間較新，只要 parent version/checksum 不連續或本機資料不等於已知 parent，就停止。

### 6.3 獨立程式入口

**上傳端：** `npm run testdata:upload` → `scripts/testdata-upload.mjs`

- 只讀取本機 loopback Supabase 的 `tc-test-*` 合成 fixture；要求 `content.__testFixture=true`、participants 空陣列、欄位白名單與敏感資料檢查通過。
- 只在本機 applied version/checksum 與目前 Git fixture 基準吻合且內容有變更時建立下一基準；內容不變不刷新時間戳、不產生空 revision。
- 只 stage fixture manifest/data 白名單，通過分支、upstream、遠端及工作樹檢查後 commit/push `origin/develop`。
- 不下載、不匯入、不呼叫 `db:sync:local`，不操作正式 Supabase。

**下載端：** `npm run testdata:download` → `scripts/testdata-download.mjs`

- 只讀 Git 已提交的 fixture；不執行 pull、不 commit、不 push。使用者先在該節點安全地 `git pull --ff-only origin develop` 後，才執行下載。
- 只寫入本機 loopback Supabase。方向由 `baselineAt` 比較；同時間 checksum 不同即停止。
- 首次下載只允許空白目標；後續下載須證明本機 DB 等於 Git 目前 manifest 的 parent fixture，並在單一 PostgreSQL transaction 再核對逐列業務欄位與筆數。保留本機 owner／creator／attachment 等不屬 fixture 的欄位。
- 套用成功才更新本機 applied state（version、checksum、baselineAt）；任何 parent 不符、資料分歧或基準未知都不改資料、不更新狀態。

### 6.4 三台電腦的標準循環

1. 任一節點修改自己的本機合成測試資料。
2. 該節點先確認 Git `develop` 已與 `origin/develop` fast-forward 一致，再執行獨立上傳入口；沒有業務資料變更就 unchanged，不發佈。
3. 其他節點各自安全 pull 最新 `origin/develop`，再各自執行獨立下載入口。
4. 下一個節點可再修改並上傳；其餘節點重複下載。第三台與之後加入的節點不需新增角色或修改協定。
5. 同時修改、同 parent 分歧、同時間不同 checksum、缺少 applied baseline、parent 不符或本機有獨立修改，均停止並人工確認；不得 last-write-wins、force-push、reset 或自動合併。
