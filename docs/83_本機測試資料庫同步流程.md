# 本機測試資料庫同步流程

> **本文件規則優先順序：** 第 2 節「對等節點與三方共同基準規則」是同步方向、Base 初始化、格式相容與停止條件的唯一詳細規格；第 4、5 節操作流程均須遵守第 2 節。第 6 節及其他舊紀錄只供追溯，凡與第 2 節不一致均已廢止、不可執行。不得重新提出或套用時間戳新舊判斷。

> 本文件規範公司端（A）與家用端（B）兩台電腦各自的本機 Supabase 測試業務資料同步。Git 只傳遞明確標記的測試 TRIP fixture；不追求整個資料庫完整複製。正式 Supabase schema／Migration 與部署請依《[正式 Supabase 資料庫 Migration 與部署流程](81_正式Supabase資料庫Migration流程.md)》辦理。

> Excel RPC 測試案例是獨立資料集，另見《[Excel RPC 跨電腦測試資料同步定案](106_Excel_RPC跨電腦測試資料同步定案.md)》。RPC 案例是否有變更，不影響一般測試 TRIP fixture 的上傳或下載。Auth、request registry 與 participant Email map 僅在各節點本機使用，禁止跨機複製。

## 1. 範圍與基準

- Git 管理的 Migration 負責 schema；Git 管理的 Seed／fixture 負責可重現的合成測試資料。兩者不可混為同一同步機制。
- 公司端與家用端的本機 Docker DB 各自獨立；不得複製 Docker volume 或正式 DB dump 作為同步方式。
- fixture 只可含明確挑選的合成／去識別資料，不得含正式資料 dump、secret、token 或 Storage 檔案本體。
- **fixture 只代表 manifest 明確列出的合成資料子集合，不代表整個 Supabase DB 快照。** 不同 fixture 的表範圍與資料筆數以各自內容為準；不得將歷史 V5／V6 等標記視為目前同步基準，也不依賴 `already-applied` 等本機狀態判斷資料是否相同。
- Git pull 只更新版本控制檔案；本機 DB 仍須由使用者在接收端執行專用同步入口並驗證。

## 2. 對等節點與三方共同基準規則（現行唯一依據，2026-11-09 定案）

公司端（A）與家用端（B）是對等節點，任一端都可修改、上傳或下載。Git `origin/develop` 只負責傳遞已提交的合成測試資料快照；每台電腦仍只操作自己的本機 loopback Supabase。`sourceHost` 僅作來源紀錄，不決定誰有權同步。

### 2.1 核心原則

**同步方向只依 Local／Git／Base 三方的正規化業務內容比較決定；不得使用 `created_at`、`updated_at`、`baselineAt`、`exportedAt` 或主機時間判斷哪端較新。** 已知資料內容相同但時間戳可能不同，內容不同但時間戳也可能相同；時間戳不具可靠勝負判斷能力。

- **Local**：目前這台電腦本機 loopback Supabase 中，該 fixture 的業務資料。
- **Git**：目前已取得的 `origin/develop`／工作目錄中，該 fixture 的已提交 `data.json` 業務資料。
- **Base**：這台電腦與 Git 上次確認同步成功時的共同業務內容指紋。Base 是比較歷史，不是目前 Git 內容的別名。
- 內容指紋使用 SHA-256 等穩定摘要作為內部相等比較工具；它不是版本號、提交鏈、父版本或同步方向規則。計算前須正規化 JSON 物件鍵順序、白名單資料列順序及各端本機專屬欄位，避免表示順序或應排除欄位造成假差異。
- `created_at`、`updated_at` 是匯入時需要保留的來源資料欄位，但不屬於同步方向的判斷依據；時間戳不同不能單獨構成內容變更，時間戳相同也不能證明內容相同。

### 2.2 唯一三方判斷表

先計算 Local、Git 與 Base 的正規化業務內容指紋，再依下表分類：

| Local 與 Base | Git 與 Base | 判斷 | 允許動作 |
|---|---|---|---|
| 相同 | 相同 | `unchanged` | 不搬動資料；可確認／修復共同基準 |
| 不同 | 相同 | Local 單邊變更 | 僅 `/上傳資料庫` 可將 Local 發布到 Git |
| 相同 | 不同 | Git 單邊變更 | 僅 `/下載資料庫` 可將 Git 匯入 Local |
| 不同 | 不同 | `conflict` | 停止；不得覆蓋任一端，需先人工處理雙邊修改 |

補充：若 Local 與 Git 內容彼此相同，不論舊 Base 是否缺失或已失效，兩端目前內容已一致，可安全以該內容建立／修復 Base。若 Local 與 Git 不同且無有效 Base，無法知道哪端相對共同歷史有變更，必須 `conflict`；不可猜測、不可採信時間戳、不可用目前 Git 內容冒充歷史 Base。

### 2.3 Base 保存與首次初始化（bootstrap）

- 每台節點的本機 Base 檔 `supabase/.temp/testdata-sync-baselines.json` 用來記錄該節點上次成功同步的共同內容指紋；它是本機狀態，不隨 Git 自動覆蓋。每個 fixture 只需要一筆有效 Base 指紋及必要的記錄時間。
- Git manifest 的 `syncBaseChecksum` 只能視為相容舊格式的輔助 metadata，不可在本機 Base 不存在時，直接拿目前 Git 的 checksum 當成該節點的歷史 Base。尤其不能在 Git 已是 C、本機仍是 B 且本機 Base 遺失時，錯把 C 當共同基準而判定 B 可上傳。
- 首次初始化情境：**Local 與 Git 相同**時可自動建立第一筆共同 Base；**Local 不存在且 Git 有有效 fixture**時，依 `/下載資料庫` 的安全資料驗證下載，成功後建立 Base；**Git fixture 不存在且 Local 是明確合成測試資料**時，依 `/上傳資料庫` 的安全檢查建立第一份 fixture 並建立 Base；**兩端都存在但內容不同且沒有共同 Base**時，停止並要求先人工確認哪份內容作為起點，再用明確受控方式建立 Base。
- Base 遺失、格式無效或不相容時，該筆 Base 視為不可採信；若兩端相同可修復，若兩端不同則停止。不得因 Base 格式錯誤而永久阻擋所有 fixture；也不得在沒有共同基準時放寬為單純兩端內容比較後直接覆蓋。
- Base 只能在雙方內容一致或指定方向的資料搬移成功後更新。不得在衝突、驗證失敗、寫入失敗或 Git push 失敗時，提前把 Base 更新成未完成的狀態。

### 2.4 格式相容與簡化界線

- 不依賴 version、revision、parent、applied state、提交數或版本鏈決定方向；不要求建立／維護這些額外同步協定。
- Manifest 的 `schemaVersion`、`counts`、`syncBaseChecksum`、`syncedAt` 等輔助欄位，不應成為舊格式無法進行內容比對的門檻。讀取端應容忍可安全正規化的舊版／缺漏 metadata；需要輸出時再產生目前格式。
- `counts` 是統計資訊，不是內容真偽依據。筆數不同代表內容有差異，應進入三方比較；不能只因 manifest 筆數缺漏或與 JSON 筆數不同就判定同步失敗。必要資料表、欄位型別、關聯、資料範圍及敏感資訊檢查仍須嚴格執行。
- 不因 checksum metadata 缺失或格式版本不同而拒絕比對；應由實際讀取的正規化內容即時計算內容指紋。Base 本身仍需要可靠內容指紋，因為它是三方比較不可缺少的共同歷史。
- 不增加 timestamp fallback、version／parent 鏈、額外 applied registry 或多套重複 baseline。上傳與下載必須共用同一個三方分類函式，避免兩個入口各自判斷。
- `/上傳資料庫` 只執行 Local → Git；若判斷為 Git 單邊變更，安全停止並提示先執行獨立下載。`/下載資料庫` 只執行 Git → Local；若判斷為 Local 單邊變更，安全停止並提示先執行獨立上傳。即使判斷結果顯示另一個方向，也不得在目前口令內偷偷執行另一種寫入。
- 雙方都相對 Base 變更時一律 conflict。這是刻意的資料保護停止線，不是同步故障；在時間戳已證實不可靠的前提下，程式不得自行判定哪端「比較新」。

### 2.5 匯入資料時間欄位處理

下載匯入仍須保留來源資料的 `created_at`／`updated_at`，並於匯入交易期間依既有機制暫停六張白名單表的 touch-updated-at trigger，於同一交易完成前恢復。這只是保留資料欄位原值，不代表以時間戳判斷同步方向。

## 3. 必要安全驗證與寫入界線

不採用不透明的版本鏈、父版或 checksum 門檻；但下列資料安全驗證仍是必要條件，任何一項失敗即停止受影響的寫入：
- 快照／manifest JSON 結構、必要資料表陣列、欄位白名單、必要欄位與資料型別正確。
- 關聯完整、主鍵與業務鍵不衝突，行程範圍一致；測試行程以 `content.testPurpose = "three-way-sync"` 標記識別，不依賴 TRIP 名稱或 ID 的固定格式。每筆 TRIP 保留自己的 ID 與 fixture 目錄；一次上傳／下載可批次處理多筆 fixture。
- **所有使用者帳號及所有參與者資料一律排除，不分測試帳號或真實帳號。** 包含 Auth 使用者、參與者清單、參與者 Email 對照、管理員帳號／身分、登入 session、使用者 ID、token、密碼及任何可識別帳號的資料；不得出現在 fixture、manifest 或任何跨機案例檔。目的端僅使用該節點原有的本機帳號與權限設定。
- 匯出採資料類型白名單：目前允許 `trips`、`checklists`、`checklist_items`、`expenses`、`exchange_purchases`、`other_info_items` 六張業務資料表中的測試資料；不在白名單的資料欄位／關聯一律排除。不得因可安全排除的帳號／參與者欄位存在，就阻擋整筆測試行程。
- 帳戶 Email、管理者／使用者個人資料、Auth users、participants、participant Email map、登入 session、owner／creator 身分欄位、token、密碼、附件中繼資料與 Storage 檔案均不跨機同步；接收端使用自己本機帳號及權限。
- 只有在無法確認行程屬於允許的測試範圍、資料列關聯不完整、主鍵／業務鍵衝突、必要欄位無法成立，或資料白名單內容本身含有敏感資訊時，才阻擋該行程資料集；不得靜默略過必要業務欄位或關聯後產生不完整快照。
- 下載只能寫入確認為 loopback 的本機 Supabase；不得操作 linked／production Supabase。
- DB 匯入在單一 SQL 交易中完成，且只更新 fixture 白名單範圍；保留本機 owner／creator／附件等本機欄位，不刪除其他 Trip、私人 checklist 或非 fixture 資料。
- 同一輪下載先驗證所有 Git 快照及本機比對結果，再套用 DB；Excel RPC 案例 JSON 於 DB 匯入成功後以暫存檔＋rename 更新。若檔案替換失敗，錯誤必須明確回報，重跑下載可依內容差異恢復。
- 不得因資料分歧而盲目覆蓋非合成範圍；只有確認目標本身是該 fixture 的合成範圍，才可依 Git 完整快照反映新增、修改與刪除。

**舊 fixture 相容與往返規則：** 舊資料若具有明確的 `content.__testFixture=true`，可在下載前正規化為現行 `content.testPurpose="three-way-sync"`；正規化時移除 `participants`、participant Email map、舊版 `checklistData`、付款人及白名單以外欄位。此相容只用於辨識已明確標記的舊合成資料，不放寬新格式；下載匯入後會移除舊標記並保存現行標記。上傳端讀取舊 fixture 時使用相同正規化，並將其視為需要更新的快照，確保下一次上傳可發布成現行格式。兩端比較均忽略各節點本機保留的參與者／帳號欄位；一般 TRIP 編輯流程必須保留 `testPurpose`，使下載後修改的測試行程仍可再次上傳。

## 4. 日常操作

### Git 操作（與資料庫完全分離）

1. `commit`、`push`、`commit/push` 只處理一般程式碼／文件 Git 變更。
2. 完整口令 `commit/push/資料庫` 已整個廢除，不再是有效指令；收到時不執行任何動作，應提示使用者改用一般 Git 口令或獨立資料庫口令。不得將它視為一般 Git 操作，也不得呼叫 upload 或 download。
3. Git 操作維持精確 stage、安全分支／upstream／遠端檢查；不可使用 `git add .`，不可順便修改或同步本機資料庫。

### 資料庫上傳（使用者明確輸入 `/上傳資料庫`）

1. 僅執行 `npm run testdata:upload`（`scripts/testdata-upload.mjs`）。
2. 一次搜尋本機 loopback Supabase 中所有 `is_public=false` 且 `content.testPurpose="three-way-sync"` 的 TRIP，逐筆建立／更新自己的 fixture（每筆各有 manifest/data）；不限制 TRIP ID 或名稱格式。依第 2 節 Local／Git／Base 三方共同基準分類：只有 Local 相對 Base 變更才可發布；Git 單邊變更時保留 Git 並提示獨立執行下載；雙邊變更或無 Base 且兩端不同時停止。Excel RPC 案例集獨立比較，未變更時不阻擋 TRIP fixture 上傳。不得以時間戳判斷方向。
3. 不執行一般程式碼／文件 commit，不 pull、不 download、不 import，也不執行 `db:sync:local`。
4. 若分支、upstream、遠端、工作樹或 fixture 安全檢查不符，停止並回報；不得覆寫、reset 或 force-push。

### 資料庫下載（使用者明確輸入 `/下載資料庫`）

1. 使用者先自行確認本機 Git 已取得目標 committed fixture（必要時另行執行安全的 `git pull --ff-only origin develop`）；下載口令本身不得執行 Git pull。
2. 僅執行 `npm run testdata:download`（`scripts/testdata-download.mjs`），掃描本機 Git 已提交的有效 fixture 目錄，不要求資料夾或 TRIP ID 使用固定格式；逐筆與目前主機 loopback Supabase 比較，所有有差異的 fixture 先完成驗證，再以單一 SQL 交易批次套用。不得以時間戳、version／parent／applied state 作為方向判斷；必須依第 2 節 Local／Git／Base 三方共同基準決定是否允許下載。無 Base 且兩端內容不同、或兩端都相對 Base 變更時，停止且不覆蓋。Excel RPC 案例集獨立比較與更新，案例 unchanged 不影響 TRIP fixture 下載。
3. 不執行 upload、export、一般 Git commit/push/pull 或 `db:sync:local`。
4. 若 fixture 缺漏、結構錯誤、資料關聯／業務鍵衝突、敏感資訊檢查失敗或目標不是 loopback 合成資料範圍，停止且不寫入；不可 reset 或觸碰其他資料範圍。

**三個動作永遠分開：Git commit/push、資料庫 upload、資料庫 download。** 一個口令只啟動其對應動作；不得由另一個口令、一般工作完成或對話提及自動觸發。所有資料庫動作僅限本機 loopback Supabase，不接觸正式 Supabase。

## 5. 雙機測試啟動與發布停止線

### 5.1 受控雙機測試：已解除啟動限制

**自 2026-11-03 起，允許公司端與家用端開始受控雙機同步驗收。** 不必等到所有真實雙機案例先通過才可開始；雙機驗收本身就是驗證同步流程的必要手段。現行共同依據一律是第 2 節 Local／Git／Base 三方共同基準；不可只比較兩端後直接覆蓋，也不可使用時間戳、applied state 或 revision 鏈判斷方向。

> **歷史狀態紀錄（2026-11-03，僅供追溯，不可執行）：** 當時曾以 V5／V6、checksum、parentVersion、parentChecksum 與 applied state 討論雙機同步。該版本鏈式流程已廢止；現行唯一方向判斷是第 2 節 Local／Git／Base 三方共同基準，不得依本段舊流程操作或阻擋同步。

啟動每一輪前，兩端都必須：
- 確認操作目標是各自的本機 loopback Supabase，絕不連線或寫入正式 DB。
- 確認 fixture 結構、合成標記、資料關聯、業務鍵與敏感資料檢查可通過。
- 先完成該端 Git 分支、upstream、工作樹及遠端差異檢查；取得對端快照僅使用安全 fast-forward。

日常只需兩個動作，兩端可以互換：

1. **A 上傳：** A 先依第 2 節確認 Local 單邊變更，執行 `/上傳資料庫`；只有該類 fixture 可發布到 Git，Git 單邊變更或衝突項目不得被上傳覆蓋。
2. **B 接收：** B 先執行 `git pull --ff-only origin develop`，再執行 `/下載資料庫`；只有依第 2 節確認 Git 單邊變更的 fixture 才可匯入本機 loopback DB，Local 單邊變更或衝突項目不得被覆蓋。
3. **B 反向上傳、A 接收：** B 修改測試資料後，依第 2 節確認 Local 單邊變更再執行 `/上傳資料庫`；A 安全 pull 最新 develop 後，依第 2 節確認 Git 單邊變更再執行 `/下載資料庫`。若雙端都相對 Base 變更，兩端都停止並先人工處理衝突。
4. **內容未變更：** 對應 fixture 或 RPC 案例各自顯示 unchanged，不產生無意義更新；其中一個資料集 unchanged 不會阻擋另一個資料集。
5. **安全檢查失敗：** 若 TRIP 標記、資料關聯／業務鍵、隱私排除或 loopback 檢查不符，停止受影響的寫入；不得觸碰私人資料或 fixture 以外的 TRIP。

每一步都依第 2 節比較 Local／Git／Base；內容不同不代表可直接同步，只有單邊相對 Base 變更且使用者執行對應入口時才可搬移。雙方變更或缺少 Base 且內容不同時停止。

**必要停止線：** 非 loopback 目標、合成標記不符、欄位／資料結構錯誤、跨行程資料、關聯斷裂、業務鍵衝突、敏感／私人資料外洩，都必須停止。不得刪除或覆蓋 fixture 範圍以外的資料。

### 5.2 驗證狀態

### 5.3 程式／fixture 發布停止線

受控雙機測試的啟動，不等於授權推送程式或 fixture。一般程式碼／文件 commit、fixture upload 及 fixture download 是三個獨立動作，分別依根目錄 `AGENTS.md` 的 `/上傳資料庫`、`/下載資料庫` 與一般 Git 操作規則執行；歷史完整口令 `commit/push/資料庫` 已廢止其資料庫交接作用，不再觸發 fixture publish。不得把未驗證的同步程式或不合格 fixture 推到另一端。任何口令均不授權正式 Supabase 部署、破壞性資料操作或覆寫衝突資料。正式資料庫操作仍依正式 Migration 文件的獨立核准規則。

### 6.3 獨立程式入口

**下載端：** `npm run testdata:download` → `scripts/testdata-download.mjs`

### 6.4 三台電腦的標準循環

1. 任一節點修改自己的本機合成測試資料。
2. 該節點先確認 Git `develop` 已與 `origin/develop` fast-forward 一致，再執行獨立上傳入口；沒有業務資料變更就 unchanged，不發佈。
3. 其他節點各自安全 pull 最新 `origin/develop`，再各自執行獨立下載入口。
4. 下一個節點可再修改並上傳；其餘節點重複下載。第三台與之後加入的節點不需新增角色或修改協定。
5. （歷史流程，已廢止，不可執行）舊版曾以資料時間較新的完整快照覆蓋較舊快照；現行任何節點都必須使用第 2 節 Local／Git／Base 三方共同基準，兩端各自變更時停止，不得以時間戳選勝方。不得 force-push 或 reset。
