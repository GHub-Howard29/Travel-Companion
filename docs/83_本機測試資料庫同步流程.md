# 本機測試資料庫同步流程

> **本文件是 A（公司端）與 B（家用端）本機測試資料庫同步的唯一現行規格。** 本次規格取代舊版 Local／Git／Base 內容指紋、checksum、revision／parent 鏈及 testPurpose 標記門檻。舊文件只保留歷史背景，不得作為操作依據。

## 1. 目標與範圍

- A、B 是平等節點，各自只操作自己的本機 loopback Supabase；Git `origin/develop` 是兩端傳遞測試資料的媒介，不是資料主從權威。
- 同步範圍是六張業務資料表：`trips`（僅 `is_public=false`）、`checklists`（僅 `scope=shared`）、其對應 `checklist_items`，以及私有行程的 `expenses`、`exchange_purchases`、`other_info_items`。不要求 `testPurpose`、`__testFixture` 或固定 TRIP ID／名稱。
- **不再要求 `testPurpose="three-way-sync"`、`__testFixture`、特定 TRIP ID／名稱格式或其他人工標記，作為資料是否可上傳的前置條件。** 本機六張白名單表中有變更的合格業務資料可進入同步判斷；不得只因缺少舊標記而漏掉變更。
- 不同步整個資料庫、Docker volume、正式資料 dump、Auth／登入帳號、密碼、token、session、參與者個人資料／Email、使用者／管理者／owner／creator 身分、裝置專屬設定、Storage 檔案本體及非本次白名單資料。
- 可安全剝除的敏感欄位應在輸出前排除，不得因可剝除欄位存在就拒絕整筆業務資料；若剝除後必要欄位、關聯或資料完整性無法成立，停止該資料集同步。
- Git 必須保留可啟動及驗證的基本測試環境，包括 schema／migrations、必要 seed、基本測試 fixture、測試設定範本及回歸測試所需資產。日常資料同步不得清空、取代或刪除這些基礎環境資產；只更新本次同步範圍內的資料。不得把真實帳號、密碼或個資放入 Git。
- Excel RPC 測試案例定義是獨立案例資料集，依《[Excel RPC 跨電腦測試資料同步定案](106_Excel_RPC跨電腦測試資料同步定案.md)》管理；它不是六張業務表的 DB 變更時間戳替代品，也不得阻擋另一資料集的獨立同步。

## 2. 最後變更時間戳記模型（唯一同步判斷）

同步只使用最後變更時間戳記判斷資料集是否在該節點自己的同步基準之後發生變更。不使用 checksum、hash、內容指紋、遞增版本號、revision、parent version、applied state 或 Git commit 時間判斷一般六表資料集是否需要同步。

本模型有三個時間欄位，A、B 各自保存自己的本機欄位，Git 保存目前已發布資料集的時間：

- `local_last_changed_at`：各電腦本機資料庫中，六張白名單表最近一次 INSERT、UPDATE 或 DELETE 的時間。每台電腦各自保存一筆，不記錄逐筆歷史。
- `last_synced_at`：各電腦本機資料庫中，該台電腦最後一次成功同步的基準時間。A、B 各自保存，不會因另一台電腦上傳而自動改變。
- `git_last_changed_at`：Git 目前已發布的六表資料集最後變更時間，由同步 metadata 保存；不得以 Git commit 時間代替。

### 2.1 本機最後變更時間

- 以資料庫層級 Trigger 監測六張白名單表：`trips`、`checklists`、`checklist_items`、`expenses`、`exchange_purchases`、`other_info_items`。
- INSERT、UPDATE、DELETE 任一操作都更新同一筆 `local_last_changed_at` metadata；永遠只保留最新一次變更時間，不保存事件序列、不新增遞增版本號，也不為每筆資料建立 tombstone。
- Trigger 共用 `tc_testdata.touch_local_last_changed_at()` function。使用資料庫時間（`clock_timestamp()`）記錄實際最後變更時間。實作檔為 `scripts/sql/testdata-sync-clock.sql`，由上／下載入口自動套用；這是本機專用 SQL，不是 Supabase migration，不得部署至正式資料庫。
- 不依賴資料列 `updated_at` 判斷資料集變更，因為部分資料表可能沒有 `updated_at`，而且 DELETE 不會留下被刪資料列供比較。
- Trigger 必須只監測上述六張同步資料表；Excel RPC 案例集與其他資料表不納入這個時間戳。

### 2.2 各節點獨立同步基準

A、B 的 `last_synced_at` 是各自的本機基準，不是 A／B／Git 共用欄位。Git 只保存目前資料集的 `git_last_changed_at`。

一般情況下，該台電腦的判斷方式為：

```text
local_changed = local_last_changed_at > last_synced_at
git_changed   = git_last_changed_at > last_synced_at
```

| 本機是否有變更 | Git 是否有變更 | 判斷 | 對應命令 |
|---|---|---|---|
| 否 | 否 | unchanged，不同步 | 不執行 |
| 是 | 否 | 僅本機有變更 | 只有明確執行 `/上傳資料庫` 才可上傳 |
| 否 | 是 | 僅 Git 有變更 | 只有明確執行 `/下載資料庫` 才可下傳 |
| 是 | 是 | 本機與 Git 都有變更，衝突 | 停止；不覆蓋任一方，交由人工處理 |

**上傳必要條件：本機確實有未同步變更，且 Git 沒有本機基準之後的新變更。**
**下載必要條件：Git 確實有本機基準之後的新變更，且本機沒有未同步變更。**

不得把「對端沒有變更」單獨當成同步觸發條件；不得在 `/上傳資料庫` 中自動改做下載，也不得在 `/下載資料庫` 中自動改做上傳。

### 2.3 上傳與下載後的時間更新

- A 上傳成功後，Git 的 `git_last_changed_at` 設為本次實際發布資料集的 `local_last_changed_at`；A 自己的 `last_synced_at` 更新為該時間。B 的 `last_synced_at` 不變，B 不需要立即下載。
- 若 A 在上傳成功後又修改資料，Trigger 將 A 的 `local_last_changed_at` 推進，而 A 的 `last_synced_at` 保持前次成功發布時間，因此 A 可再次依判斷規則上傳。
- B 之後下載 Git 最新資料且成功後，B 的 `local_last_changed_at` 與 `last_synced_at` 都校正為此次取得的 `git_last_changed_at`。下載套用資料時即使觸發六表 Trigger，也必須在同一下載交易完成後校正，避免把下載動作誤判為 B 的本機新修改。
- 下載成功只更新下載端自己的時間；不會回頭改寫 A 的 `last_synced_at`。
- 上傳資料快照與採用的 `local_last_changed_at` 必須來自同一個資料庫查詢快照。若發布期間本機又有新變更，上傳成功後只把 `last_synced_at` 設為本次已發布快照的時間；較新的 `local_last_changed_at` 保持不變且仍大於基準，因此下一次上傳仍會被允許，不得把未發布的新修改標成已同步。
- 下載資料套用、驗證及本機兩個時間欄位校正應在單一 SQL transaction 內完成；任何失敗都回復資料與時間 metadata，不前移基準。

### 2.4 首次同步與基準缺失

- `last_synced_at` 為 `NULL` 表示該台電腦尚未建立同步基準。NULL 不可直接代入一般四象限公式，也不可自行猜測或從 Git commit 時間重建。
- 首次建立 Git 資料集時，必須明確指定一台電腦作為初始資料來源，執行 `npm run testdata:upload -- --initialize`。成功後以該次發布資料的 `local_last_changed_at` 同時建立 Git `git_last_changed_at` 與初始來源自己的 `last_synced_at`。
- 另一台電腦先自行取得 Git 最新提交，確認本機六表同步範圍為空，再執行 `npm run testdata:download -- --initialize`。成功套用後，將本機 `local_last_changed_at`、`last_synced_at` 設為 Git `git_last_changed_at`，完成該節點基準建立。若本機已有同步範圍資料，程式會停止，不會覆蓋。
- 若兩台電腦都已有資料但都沒有基準，必須先由使用者決定保留哪一端作為初始資料來源；另一端不可直接上傳或覆蓋。首次方向確認前停止同步。
- 基準 metadata 缺失、格式錯誤或無法判斷時停止同步；不得以猜測值、Git commit 時間或資料列時間戳自行補建。

### 2.5 時間戳記原則

- 時間戳使用資料庫時間並保存為固定格式 `YYYY-MM-DDTHH:mm:ss.ffffffZ`（UTC、微秒精度）；比較前驗證格式，再以固定格式時間字串比較，避免 JavaScript 毫秒精度截斷資料庫微秒。
- 此流程以台灣公司端及家用端的正常本機資料庫時間為前提，不額外加入跨國時鐘協調機制。
- 時間戳缺漏、格式錯誤、基準為 NULL（首次同步流程除外）或比較結果無法判斷時，停止同步，不得猜測。
- 時間戳只判斷「同步基準之後是否有變更」，不判斷哪一端的資料內容較新，也不代表可自動合併不同欄位。

## 3. 上傳與下傳操作

### 3.1 上傳（本地 → Git）

1. 使用者明確輸入 `/上傳資料庫`；首次建立 Git 資料集則使用 `npm run testdata:upload -- --initialize` 明確指定初始來源。
2. 檢查目前主機的 loopback Supabase、Git 分支／upstream／遠端及工作樹安全狀態。
3. 讀取本機 `local_last_changed_at`、本機 `last_synced_at` 與 Git `git_last_changed_at`。
4. 若本機沒有基準後變更，回報 unchanged，不得上傳；若 Git 有基準後變更，判定 conflict，停止，不得覆蓋 Git。
5. 本機有變更且 Git 無變更時，完成資料範圍、欄位、關聯與隱私檢查，再只發布本次同步範圍的資料檔及必要 metadata。
6. Git 發布成功並確認後，將 Git `git_last_changed_at` 與本機 `last_synced_at` 設為本次發布資料快照對應的 `local_last_changed_at`。不得更新其他電腦的 `last_synced_at`。
7. 只執行 `npm run testdata:upload`（`scripts/testdata-upload.mjs`）；不得 pull、download、import、執行一般文件 commit，或操作正式 Supabase。

### 3.2 下傳（Git → 本地）

1. 使用者先自行確認本機 Git 已取得目標 committed 資料（必要時另行執行安全的 `git pull --ff-only origin develop`）；`/下載資料庫` 本身不得執行 Git pull。
2. 使用者明確輸入 `/下載資料庫`；首次接收則在本機同步範圍為空時使用 `npm run testdata:download -- --initialize`。
3. 讀取本機 `local_last_changed_at`、本機 `last_synced_at` 與 Git `git_last_changed_at`。
4. 若 Git 沒有本機基準後變更，回報 unchanged，不得下傳；若本機有基準後變更，判定 conflict，停止，不得覆蓋本機。
5. Git 有變更且本機無變更時，先驗證全部待下傳資料及安全邊界，再於單一 SQL transaction 套用至本機 loopback Supabase。
6. DB 寫入與接收驗證成功後，在同一交易將本機 `local_last_changed_at` 與 `last_synced_at` 都設為此次 Git `git_last_changed_at`；任何失敗回復資料與原基準。
7. 只執行 `npm run testdata:download`（`scripts/testdata-download.mjs`）；不得 upload、export、Git pull／commit／push，亦不得連線正式 Supabase。

## 4. 資料安全與環境保護

- 業務資料白名單固定為：`trips`（只同步非公開行程）、`checklists`（只同步 shared）、`checklist_items`（只同步上述 shared checklist 的項目）、`expenses`、`exchange_purchases`、`other_info_items`（後三者只同步非公開行程所屬資料）。
- 不跨機傳輸 Auth users、登入帳號／密碼、使用者或管理者個資、參與者姓名／Email／電話／使用者 ID、participant Email map、session、token、owner／creator 身分、裝置設定、附件中繼資料與 Storage 檔案。
- 保留各節點本機帳號與權限設定；不得因同步資料覆蓋本機 Auth、參與者或權限資料。
- 僅操作目前節點確認為 loopback 的本機 Supabase；禁止 linked／production Supabase、正式資料庫 dump、Docker volume 複製。
- 下傳前先驗證全部資料結構、欄位型別、主鍵、外鍵、業務關聯及敏感欄位；有一項不合格就停止受影響的資料集，不得部分寫入。
- 下載會 upsert 並同步刪除六表範圍內已不存在的資料。若某個待刪除 Trip 仍被六表以外的資料表外鍵或 `trip_id` 欄位參照，交易會停止且回復，不連帶刪除非同步範圍資料；本機參與者、owner／creator、payer、附件及其他非同步欄位不覆蓋。
- Git 必須持續保留可供公司端及家用端啟動與測試的基本環境。同步程序只可更新對應的可變測試資料，不可把基本 seed、必要 fixture、migration、schema、測試設定或測試腳本當成可清空的資料快照。
- Git 一般 commit／push、資料庫上傳、資料庫下傳是三個分離操作。完整口令 `commit/push/資料庫` 已廢止，不得重新啟用。

## 5. Excel RPC 案例集邊界

Excel RPC 案例集是用於目的端重建 RPC 測試的輸入定義，不等同六張業務資料表的已建立資料。其案例檔仍依文件 106 的案例 schema、隱私檢查及案例內容更新規則獨立管理；案例檔的更新不得直接建立／覆蓋 TRIP，也不得複製 Auth、request registry 或 participant Email map。其獨立 unchanged／失敗不得阻擋一般測試資料庫資料集的同步，反之亦然。

## 6. 驗收要求與未完成事項

時間戳同步核心程式與純函式／SQL 產生器測試已實作。目前開發節點的 loopback Supabase 已安裝六個 Trigger，並以回滾交易驗證 UPDATE／INSERT／DELETE 時鐘推進及完整六表匯入 SQL；測試後資料與同步基準均未改變。尚未執行真正首次上傳／下載、另一節點安裝及 A/B 雙機往返人工驗收。不得把舊版 checksum／revision 測試結果描述成新規則已通過。

實作後至少驗證：
- 無變更：本機 `local_last_changed_at` 與 Git `git_last_changed_at` 均未晚於該台電腦自己的 `last_synced_at`，不產生資料上傳／下傳。
- 單邊本機變更：只允許上傳；未明確呼叫上傳時不發布。
- 單邊 Git 變更：只允許下載；未明確呼叫下載時不寫本機 DB。
- 本機與 Git 都在該台電腦同步基準後變更：判定衝突，停止且雙方資料不變。
- INSERT、UPDATE、DELETE 都能推進同一筆本機最後變更時間。
- A 上傳成功後只更新 Git `git_last_changed_at` 與 A 的 `last_synced_at`；B 的 `last_synced_at` 不變。
- B 下載成功後只更新 B 的 `local_last_changed_at` 與 `last_synced_at`；A 的 `last_synced_at` 不變。
- 下載 Trigger 校正、資料套用與驗證在單一 transaction 中成功；任一步失敗時資料與基準回復。
- 上傳發布的資料快照與採用的本機最後變更時間一致；發布期間出現新修改時不得錯誤推進基準。
- 首次同步的 NULL 基準必須走明確指定初始來源的流程；另一節點確認可接收後才建立自己的基準。
- 時間戳缺漏、格式錯誤、基準遺失或比較結果無法判斷時安全停止。
- Git 基本測試環境及必要 seed／fixture 在同步前後均保留。
- 帳號、參與者、secret、token、session、個資及 Storage 檔案均未跨機傳輸。
- 公司端及家用端各自 loopback DB 的真實雙向往返測試。

## 8. 程式實作與操作入口

- 本機 metadata 存放於 `tc_testdata.sync_state`，每台電腦只有一筆 `singleton=true` 記錄，欄位為 `local_last_changed_at`、`last_synced_at`。六張資料表共用 `tc_testdata.touch_local_last_changed_at()` Trigger function。
- `scripts/sql/testdata-sync-clock.sql` 是本機專用初始化 SQL；`testdata:upload`、`testdata:download` 每次執行時會先確保 metadata 與六個 Trigger 存在。不得將它搬進 `supabase/migrations/` 或對 linked／production Supabase 執行。
- Git 資料集固定位於 `supabase/test-fixtures/local-database/manifest.json` 與 `data.json`。manifest 的 `git_last_changed_at` 取自本次資料庫快照的 `local_last_changed_at`，不是 commit timestamp。
- 上傳使用單一 SQL 查詢快照同時讀取六表資料及本機變更時間；Git 僅 stage、commit、push 上述兩個資料集檔案。push 並確認遠端一致後，才更新上傳端自己的 `last_synced_at`。若上傳期間又有本機變更，基準只推進到已發布快照時間，較新的本機變更仍會被下一次判斷偵測。
- 下載在一個 SQL transaction 內鎖定六張表、重新核對 preflight 時間戳、驗證 ID／關聯／刪除影響、upsert 與刪除同步範圍內的舊資料，最後把下載端 `local_last_changed_at`、`last_synced_at` 設為 Git 時間。任一步失敗則整筆 transaction rollback。
- 一般首次來源使用 `npm run testdata:upload -- --initialize`；另一節點先自行 `git pull --ff-only origin develop`，確認本機同步範圍為空後使用 `npm run testdata:download -- --initialize`。日常同步分別使用 `npm run testdata:upload`、`npm run testdata:download`。
