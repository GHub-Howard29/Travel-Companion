# 本機測試資料庫同步流程

> **本文件是 A（公司端）與 B（家用端）本機測試資料庫同步的唯一現行規格。** 本次規格取代舊版 Local／Git／Base 內容指紋、checksum、revision／parent 鏈及 testPurpose 標記門檻。舊文件只保留歷史背景，不得作為操作依據。

## 1. 目標與範圍

- A、B 是平等節點，各自只操作自己的本機 loopback Supabase；Git `origin/develop` 是兩端傳遞測試資料的媒介，不是資料主從權威。
- 同步範圍是六張業務資料表：`trips`、`checklists`、`checklist_items`、`expenses`、`exchange_purchases`、`other_info_items`。依現有資料關聯與安全規則選取可同步的業務資料。
- **不再要求 `testPurpose="three-way-sync"`、`__testFixture`、特定 TRIP ID／名稱格式或其他人工標記，作為資料是否可上傳的前置條件。** 本機六張白名單表中有變更的合格業務資料可進入同步判斷；不得只因缺少舊標記而漏掉變更。
- 不同步整個資料庫、Docker volume、正式資料 dump、Auth／登入帳號、密碼、token、session、參與者個人資料／Email、使用者／管理者／owner／creator 身分、裝置專屬設定、Storage 檔案本體及非本次白名單資料。
- 可安全剝除的敏感欄位應在輸出前排除，不得因可剝除欄位存在就拒絕整筆業務資料；若剝除後必要欄位、關聯或資料完整性無法成立，停止該資料集同步。
- Git 必須保留可啟動及驗證的基本測試環境，包括 schema／migrations、必要 seed、基本測試 fixture、測試設定範本及回歸測試所需資產。日常資料同步不得清空、取代或刪除這些基礎環境資產；只更新本次同步範圍內的資料。不得把真實帳號、密碼或個資放入 Git。
- Excel RPC 測試案例定義是獨立案例資料集，依《[Excel RPC 跨電腦測試資料同步定案](106_Excel_RPC跨電腦測試資料同步定案.md)》管理；它不是六張業務表的 DB 變更時間戳替代品，也不得阻擋另一資料集的獨立同步。

## 2. 時間戳記模型（唯一同步判斷）

同步不使用 checksum、hash、內容指紋、revision、parent version、applied state、Git commit 時間或「哪一端時間比較新」來選擇覆蓋方向。只使用**共同成功同步基準時間**與**兩端各自的最後變更時間**判斷兩端是否在基準後發生變更。

每個同步資料範圍至少記錄：

- `last_synced_at`：A／B／Git 共用的最後一次成功同步基準時間（UTC）。兩端必須持有相同基準。
- `local_last_changed_at`：目前本機六張白名單表中，任何 INSERT、UPDATE、DELETE 發生的最後時間。
- `git_last_changed_at`：Git 端目前同步資料集最後一次被本地端變更並成功發布的變更時間；由資料集 metadata 保存，不得以 Git commit timestamp 代替。
- 時間戳必須涵蓋新增、修改及刪除；不能只看資料列的 `updated_at`，否則刪除無法被偵測。應以資料庫層級的變更紀錄／trigger 或等效可靠機制記錄，且明確限定在六張白名單表及同步範圍。
- 使用 UTC 與一致的時間精度；兩端時鐘須可合理對時。基準缺失、格式錯誤、時間倒退、時鐘偏差導致先後不可信或無法判斷時，停止同步，不得猜測。
- 時間戳記只判斷「基準之後是否有變更」，不判斷哪端內容較新，也不代表可合併不同欄位。

### 2.1 唯一方向判斷表

令 `L_changed = local_last_changed_at > last_synced_at`，`G_changed = git_last_changed_at > last_synced_at`。

| 本地是否有基準後變更 | Git 是否有基準後變更 | 判斷 | 對應命令 |
|---|---|---|---|
| 否 | 否 | unchanged，不同步 | 不執行 |
| 是 | 否 | 僅本地有變更 | 只有明確執行 `/上傳資料庫` 才可上傳 |
| 否 | 是 | 僅 Git 有變更 | 只有明確執行 `/下載資料庫` 才可下傳 |
| 是 | 是 | 雙方都變更，conflict | 停止；不覆蓋任一方，交由人工處理 |

**上傳的必要條件：本地確實有基準後變更，且 Git 沒有基準後變更。**
**下傳的必要條件：Git 確實有基準後變更，且本地沒有基準後變更。**

不得把「對端沒有變更」單獨當成同步觸發條件；也不得因目前命令方向不符合變更方向，就在同一命令內自動改做另一方向。

### 2.2 基準更新

- 首次建立共同基準前，必須確認兩端資料集的起始內容一致，或由使用者明確指定哪一端作為初始基準；若兩端資料不同且沒有共同基準，停止並請人工確認。
- 單邊同步只有在資料寫入／發布成功、接收端驗證成功且兩端狀態確認一致後，才更新共同 `last_synced_at`。不得在上傳 push 失敗、下載交易失敗、驗證失敗或衝突時提前更新。
- 同步成功後，將共同基準設為本次成功確認的 UTC 時間，並同步更新兩端基準 metadata。任何一端未能持久化新基準，必須回報同步未完整完成，不得假裝兩端已同步。
- 基準 metadata 遺失或不一致時停止自動同步；不得以 Git 目前資料、commit 時間或資料列時間戳自行重建歷史基準。
- 雙方都有變更時，即使其中一端時間戳較晚，也必須停止。人工決定保留／整合哪一方後，才可在明確確認兩端一致時建立新的共同基準。

## 3. 上傳與下傳操作

### 3.1 上傳（本地 → Git）

1. 使用者明確輸入 `/上傳資料庫`。
2. 檢查目前主機的 loopback Supabase、Git 分支／upstream／遠端及工作樹安全狀態。
3. 檢查本地六張白名單表是否有基準後變更；若沒有，回報 unchanged，不得上傳。
4. 檢查 Git 端是否有基準後變更；若有，判定 conflict，停止，不得覆蓋 Git。
5. 本地有變更且 Git 無變更時，完成資料範圍、欄位、關聯與隱私檢查，再只發布本次同步範圍的資料檔及必要 metadata。
6. Git 發布成功並確認結果後，更新共同基準；任何失敗保留原資料與原基準。
7. 只執行 `npm run testdata:upload`（`scripts/testdata-upload.mjs`）；不得 pull、download、import、執行一般文件 commit，或操作正式 Supabase。

### 3.2 下傳（Git → 本地）

1. 使用者先自行確認本機 Git 已取得目標 committed 資料（必要時另行執行安全的 `git pull --ff-only origin develop`）；`/下載資料庫` 本身不得執行 Git pull。
2. 使用者明確輸入 `/下載資料庫`。
3. 檢查 Git 端是否有基準後變更；若沒有，回報 unchanged，不得下傳。
4. 檢查本地是否有基準後變更；若有，判定 conflict，停止，不得覆蓋本地。
5. Git 有變更且本地無變更時，先驗證全部待下傳資料及安全邊界，再於單一 SQL transaction 套用至本機 loopback Supabase。
6. DB 寫入與接收驗證成功後更新共同基準；任何失敗保留原基準及可回復的資料狀態。
7. 只執行 `npm run testdata:download`（`scripts/testdata-download.mjs`）；不得 upload、export、Git pull／commit／push，亦不得連線正式 Supabase。

## 4. 資料安全與環境保護

- 業務資料白名單固定為：`trips`、`checklists`、`checklist_items`、`expenses`、`exchange_purchases`、`other_info_items`。
- 不跨機傳輸 Auth users、登入帳號／密碼、使用者或管理者個資、參與者姓名／Email／電話／使用者 ID、participant Email map、session、token、owner／creator 身分、裝置設定、附件中繼資料與 Storage 檔案。
- 保留各節點本機帳號與權限設定；不得因同步資料覆蓋本機 Auth、參與者或權限資料。
- 僅操作目前節點確認為 loopback 的本機 Supabase；禁止 linked／production Supabase、正式資料庫 dump、Docker volume 複製。
- 下傳前先驗證全部資料結構、欄位型別、主鍵、外鍵、業務關聯及敏感欄位；有一項不合格就停止受影響的資料集，不得部分寫入。
- 只更新六張表中明確屬於本同步範圍的資料，不刪除其他 Trip、私人資料或非同步範圍資料。
- Git 必須持續保留可供公司端及家用端啟動與測試的基本環境。同步程序只可更新對應的可變測試資料，不可把基本 seed、必要 fixture、migration、schema、測試設定或測試腳本當成可清空的資料快照。
- Git 一般 commit／push、資料庫上傳、資料庫下傳是三個分離操作。完整口令 `commit/push/資料庫` 已廢止，不得重新啟用。

## 5. Excel RPC 案例集邊界

Excel RPC 案例集是用於目的端重建 RPC 測試的輸入定義，不等同六張業務資料表的已建立資料。其案例檔仍依文件 106 的案例 schema、隱私檢查及案例內容更新規則獨立管理；案例檔的更新不得直接建立／覆蓋 TRIP，也不得複製 Auth、request registry 或 participant Email map。其獨立 unchanged／失敗不得阻擋一般測試資料庫資料集的同步，反之亦然。

## 6. 驗收要求與未完成事項

新時間戳規則屬**已定案、尚未實作**的同步規格。不得把舊版 checksum／revision 測試結果描述成新規則已通過。

實作後至少驗證：
- 無變更：兩端均未晚於共同基準，不產生資料上傳／下傳。
- 單邊本地變更：只允許上傳；未明確呼叫上傳時不發布。
- 單邊 Git 變更：只允許下傳；未明確呼叫下傳時不寫本機 DB。
- 雙邊變更：無論哪端時間較晚，均停止且雙方資料不變。
- INSERT、UPDATE、DELETE 都能推進對應變更時間戳。
- 上傳／下傳成功後兩端基準一致；任一失敗時基準不前移。
- 時鐘偏差、時間戳缺漏／倒退、基準遺失／不一致時安全停止。
- Git 基本測試環境及必要 seed／fixture 在同步前後均保留。
- 帳號、參與者、secret、token、session、個資及 Storage 檔案均未跨機傳輸。
- 公司端及家用端各自 loopback DB 的真實雙向往返測試。
