# 本機測試資料庫同步流程

> 本文件規範三台以上對等電腦各自的本機 Supabase 合成測試資料同步。Git 只傳遞 fixture 基準檔；正式 Supabase schema／Migration 與部署請依《[正式 Supabase 資料庫 Migration 與部署流程](81_正式Supabase資料庫Migration流程.md)》辦理。

> Excel RPC 多案例／多筆 TRIP 測試資料的跨電腦重建規則，另見《[Excel RPC 跨電腦測試資料同步定案](106_Excel_RPC跨電腦測試資料同步定案.md)》。此類資料集與既有單筆 `tc-test-*` fixture 分離版本化；Auth、request registry 與 participant Email map 僅在各節點本機重建，禁止跨機複製。

## 1. 範圍與基準

- Git 管理的 Migration 負責 schema；Git 管理的 Seed／fixture 負責可重現的合成測試資料。兩者不可混為同一同步機制。
- 公司端與家用端的本機 Docker DB 各自獨立；不得複製 Docker volume 或正式 DB dump 作為同步方式。
- fixture 只可含明確挑選的合成／去識別資料，不得含正式資料 dump、secret、token 或 Storage 檔案本體。
- **fixture 只代表 manifest 明確列出的合成資料子集合，不代表整個 Supabase DB 快照。** 不同 fixture 的表範圍與資料筆數以各自內容為準；不得將歷史 V5／V6 等標記視為目前同步基準，也不依賴 `already-applied` 等本機狀態判斷資料是否相同。
- Git pull 只更新版本控制檔案；本機 DB 仍須由使用者在接收端執行專用同步入口並驗證。

## 2. 對等節點與內容同步規則（現行定案）

公司端、家用端及第三台電腦都是對等節點，任一端都可修改、上傳或下載。Git `origin/develop` 只負責傳遞已提交的合成資料快照；`sourceHost` 僅作來源紀錄，不決定誰有權同步。

**唯一同步判斷是實際內容比較，不以 checksum、version、parentVersion、parentChecksum、baselineAt、applied state 或時間戳作為上傳／下載許可門檻。**
- 上傳：將目前本機 loopback DB／案例副本的標準化內容，直接與 Git 目前快照比較；相同就 unchanged，不同就發布內容變更。
- 下載：將目前本機 loopback DB／案例副本的標準化內容，直接與 Git 已提交快照比較；相同就 unchanged，不同就套用 Git 內容。
- manifest 的版本號、checksum、來源及匯出時間若保留，只是人類閱讀或稽核資訊，不得阻止內容合法變更的傳輸。
- DB 比較忽略 trigger 自動維護的 `created_at`／`updated_at` 差異；其他業務欄位、資料列新增與刪除均屬內容差異。

## 3. 必要安全驗證與寫入界線

不採用不透明的版本鏈、父版或 checksum 門檻；但下列資料安全驗證仍是必要條件，任何一項失敗即停止受影響的寫入：
- 快照／manifest JSON 結構、必要資料表陣列、欄位白名單、必要欄位與資料型別正確。
- 關聯完整、主鍵與業務鍵不衝突，行程範圍一致；測試行程以明確的測試資料標記／測試範圍識別，不要求修改或指定由 App／RPC 自動產生的行程 ID。
- **所有使用者帳號及所有參與者資料一律排除，不分測試帳號或真實帳號。** 包含 Auth 使用者、參與者清單、參與者 Email 對照、管理員帳號／身分、登入 session、使用者 ID、token、密碼及任何可識別帳號的資料；不得出現在 fixture、manifest 或任何跨機案例檔。目的端僅使用該節點原有的本機帳號與權限設定。
- 匯出採資料類型白名單：允許的測試行程業務內容、每日卡片、共同清單及其項目、旅費、外幣購買與其他資訊可保留；不在白名單的資料欄位／關聯一律排除，並於檢查報告列出排除類別與筆數。不得因可安全排除的帳號／參與者欄位存在，就阻擋整筆測試行程。
- 只有在無法確認行程屬於允許的測試範圍、資料列關聯不完整、主鍵／業務鍵衝突、必要欄位無法成立，或資料白名單內容本身含有敏感資訊時，才阻擋該行程資料集；不得靜默略過必要業務欄位或關聯後產生不完整快照。
- 下載只能寫入確認為 loopback 的本機 Supabase；不得操作 linked／production Supabase。
- DB 匯入在單一 SQL 交易中完成，且只更新 fixture 白名單範圍；保留本機 owner／creator／附件等本機欄位，不刪除其他 Trip、私人 checklist 或非 fixture 資料。
- 同一輪下載先驗證所有 Git 快照及本機比對結果，再套用 DB；Excel RPC 案例 JSON 於 DB 匯入成功後以暫存檔＋rename 更新。若檔案替換失敗，錯誤必須明確回報，重跑下載可依內容差異恢復。
- 不得因資料分歧而盲目覆蓋非合成範圍；只有確認目標本身是該 fixture 的合成範圍，才可依 Git 完整快照反映新增、修改與刪除。

## 4. 日常操作

### Git 操作（與資料庫完全分離）

1. `commit`、`push`、`commit/push` 只處理一般程式碼／文件 Git 變更。
2. 完整口令 `commit/push/資料庫` 已整個廢除，不再是有效指令；收到時不執行任何動作，應提示使用者改用一般 Git 口令或獨立資料庫口令。不得將它視為一般 Git 操作，也不得呼叫 upload 或 download。
3. Git 操作維持精確 stage、安全分支／upstream／遠端檢查；不可使用 `git add .`，不可順便修改或同步本機資料庫。

### 資料庫上傳（使用者明確輸入 `/上傳資料庫`）

1. 僅執行 `npm run testdata:upload`（`scripts/testdata-upload.mjs`）。
2. 只驗證並上傳本機 loopback Supabase 的合成 fixture manifest/data 白名單至 `origin/develop`；直接比較本機內容與 Git 快照；內容相同為 unchanged，內容不同且通過必要結構、關聯、合成資料與敏感資訊驗證即可發布。version、parent、checksum、baseline 時間與 applied state 不得阻擋內容變更。
3. 不執行一般程式碼／文件 commit，不 pull、不 download、不 import，也不執行 `db:sync:local`。
4. 若分支、upstream、遠端、工作樹或 fixture 安全檢查不符，停止並回報；不得覆寫、reset 或 force-push。

### 資料庫下載（使用者明確輸入 `/下載資料庫`）

1. 使用者先自行確認本機 Git 已取得目標 committed fixture（必要時另行執行安全的 `git pull --ff-only origin develop`）；下載口令本身不得執行 Git pull。
2. 僅執行 `npm run testdata:download`（`scripts/testdata-download.mjs`），只讀取本機 Git 已提交 fixture，直接將 Git 快照與目前主機 loopback Supabase 內容比較；內容不同且必要安全驗證通過才套用，不以 baseline／parent／checksum 作為下載阻擋。
3. 不執行 upload、export、一般 Git commit/push/pull 或 `db:sync:local`。
4. 若 fixture 缺漏、結構錯誤、資料關聯／業務鍵衝突、敏感資訊檢查失敗或目標不是 loopback 合成資料範圍，停止且不寫入；不可 reset 或觸碰其他資料範圍。

**三個動作永遠分開：Git commit/push、資料庫 upload、資料庫 download。** 一個口令只啟動其對應動作；不得由另一個口令、一般工作完成或對話提及自動觸發。所有資料庫動作僅限本機 loopback Supabase，不接觸正式 Supabase。

## 5. 雙機測試啟動與發布停止線

### 5.1 受控雙機測試：已解除啟動限制

**自 2026-11-03 起，允許公司端與家用端開始受控雙機同步驗收。** 不必等到所有真實雙機案例先通過才可開始；雙機驗收本身就是驗證同步流程的必要手段。共同依據是 Git 目前提交的內容快照；每個節點直接比較本機資料內容，不再使用 applied state／checksum／revision 鏈判斷方向。

> **歷史狀態紀錄（2026-11-03，僅供追溯）：** 當時曾以 V5／V6、checksum、parentVersion、parentChecksum 與 applied state 討論雙機同步。該版本鏈式流程已由本節現行內容比較規則取代，不得再依該紀錄操作或阻擋同步。

啟動每一輪前，兩端都必須：
- 確認操作目標是各自的本機 loopback Supabase，絕不連線或寫入正式 DB。
- 確認 fixture 結構、合成標記、資料關聯、業務鍵與敏感資料檢查可通過。
- 先完成該端 Git 分支、upstream、工作樹及遠端差異檢查；取得對端快照僅使用安全 fast-forward。

現行 A／B／C 同步流程如下（節點可互換，Git current 只提供最新內容快照）：

1. **A 有資料變更：** A 將本機 loopback DB／案例副本與 Git current 直接比較；內容不同且必要安全驗證通過，就可發布新快照。
2. **B 下載並接收：** B 先 `git pull --ff-only origin develop`，再執行 `npm run testdata:download`。下載器直接比較 B 本機資料與 Git 快照；內容不同且安全驗證通過，就套用到 B 的 fixture 範圍。
3. **B 接收後沒有資料變更：** 再次比對結果為 unchanged，不產生空提交，也不需維護 applied state。
4. **B 接收後有資料變更：** B 直接比較本機內容與 Git current；有差異且驗證通過即可發布，不需要 parent 或前一版 checksum。
5. **多個節點先後修改：** 每次上傳以當下 Git current 為傳遞快照；下載只更新明確標記的合成 fixture 範圍，私人 checklist、本機擁有者／附件欄位與其他 Trip 不得被刪改。
6. **無法確認目標為合成資料範圍、結構錯誤、關聯／業務鍵衝突或敏感資料檢查失敗：** 停止該資料集寫入，保留現況；不可碰觸不屬於 fixture 的資料。版本、父版本、checksum、時間或 applied state 不構成停止理由。

每一步都直接比較內容；相同為 unchanged，不同且必要安全驗證通過就同步。

**必要停止線：** 非 loopback 目標、合成標記不符、欄位／資料結構錯誤、跨行程資料、關聯斷裂、業務鍵衝突、敏感／私人資料外洩，都必須停止。不得刪除或覆蓋 fixture 範圍以外的資料。

### 5.2 尚未完成的驗收項目

> **以下為 2026-11-04 舊 revision 協定的歷史測試紀錄，不代表目前同步決策規則。** 目前不再以 applied baseline、revision、parent 或 checksum 作為同步門檻。

當時的同步決策邏輯曾抽為 `scripts/lib/testdata-revision.mjs` 的 `classifyPeerHandoff()`，正式 `handoff()` 已呼叫該函式；`scripts/test-testdata-peer-sync.mjs` 亦直接 import 同一函式。已完成純函式案例包含接收、未變更、產生下一版、未知 baseline、版本／父鏈不符與本機資料分歧保護。2026-11-04 家用端實際 publish 驗證發現並修正一項呼叫端分類錯誤：當 applied version／checksum 已等於 Git HEAD 時，必須以 HEAD 作為 current、incoming=null；只有 applied 等於 Git HEAD 的 parent revision 時，才將 Git HEAD 視為待接收 incoming。修正後本機 `tc-test-sync-example` V5（checksum `301153c0fa20354522a9d83c1c76f8bb0a7d745e59dbcb48a799a6660b1d15ca`）實際 handoff 結果為 `unchanged`，並安全略過空 commit／push，沒有產生 V6。已增加純函式回歸案例，涵蓋 applied=HEAD 時 unchanged，以及 applied=parent 時 receive。仍待補驗兩端角色互換的實際 DB 情境、時間戳差異及真實 A→B→A 端到端流程；這些是驗收待辦，不是禁止開始受控雙機測試的前置條件。

以上是驗收待辦，不再是禁止啟動真實雙機測試的前置條件。測試結果必須如實記錄，全部通過前不得宣稱雙機同步驗收完成。

### 5.3 程式／fixture 發布停止線

受控雙機測試的啟動，不等於授權推送程式或 fixture。一般程式碼／文件 commit、fixture upload 及 fixture download 是三個獨立動作，分別依根目錄 `AGENTS.md` 的 `/上傳資料庫`、`/下載資料庫` 與一般 Git 操作規則執行；歷史完整口令 `commit/push/資料庫` 已廢止其資料庫交接作用，不再觸發 fixture publish。不得把未驗證的同步程式或不合格 fixture 推到另一端。任何口令均不授權正式 Supabase 部署、破壞性資料操作或覆寫衝突資料。正式資料庫操作仍依正式 Migration 文件的獨立核准規則。

## 6. 三方以上對等節點同步（2026-11-05 內容比較定案）

本節補充三台以上節點的操作方式；所有節點一律遵循第 2、3 節所定義的內容直接比較與必要安全驗證，不使用時間戳或 revision 鏈決定同步方向。

### 6.1 節點模型

- 公司端、家用端及第三台電腦都是對等節點；不固定 sender／receiver，`sourceHost` 僅作稽核記錄。
- Git `origin/develop` 是合成測試資料快照的傳遞媒介；每台電腦保有自己的本機 Supabase。
- manifest 可保留版本、checksum、來源與時間等資訊作為稽核／閱讀用途，但所有同步程式都必須直接比較內容，不得用這些 metadata 形成額外同步門檻。
- 單筆 fixture 的資料列比較忽略 DB trigger 自動更新的 `created_at`／`updated_at`；其他內容差異（包含新增與刪除）都要被偵測。

### 6.2 節點同步循環

| 操作節點 | 本機內容與 Git 快照 | 結果 |
|---|---|---|
| 上傳 | 相同 | unchanged，不建立新內容提交 |
| 上傳 | 不同且安全驗證通過 | 將本機內容更新到 Git 快照 |
| 下載 | 相同 | unchanged，不寫入 |
| 下載 | 不同且安全驗證通過 | 將 Git 快照套用到本機 loopback DB／案例副本 |

若資料結構、關聯、業務鍵、合成資料標記或敏感資訊檢查失敗，停止受影響的資料集；不以版本號、父版本、checksum、baseline 時間或 applied state 判斷是否允許傳輸。

### 6.3 獨立程式入口

**上傳端：** `npm run testdata:upload` → `scripts/testdata-upload.mjs`

- 單行程測試 fixture：讀取本機 loopback Supabase 中明確屬於測試用途的行程；保留資料庫原始行程 ID，不要求 `tc-test-*` 格式，不要求使用者手動指定 ID。由來源標記／受控測試行程清單確認測試範圍，並只匯出資料欄位白名單；所有使用者帳號及參與者資料無條件排除，參與者存在不構成阻擋。
- Excel RPC 案例資料集：讀取本機忽略目錄 `supabase/.temp/excel-rpc-test-cases.json`（若不存在則使用 Git current 案例），驗證欄位、日期／時間、案例結構及敏感資料，與 Git 目前 `cases.json` 直接比較標準化案例內容；相同為 unchanged，不同且驗證通過就準備發布。不得要求 applied key、revision 或 checksum 才允許發布。
- 兩種資料集均只在標準化內容不同時建立新的 Git 快照；內容不變就 unchanged，不產生空提交。
- 只 stage 各資料集明確白名單：舊 fixture 為 manifest/data，Excel RPC 案例集為 manifest/cases；通過分支、upstream、遠端及工作樹檢查後 commit/push `origin/develop`。
- 不下載、不匯入、不呼叫 `db:sync:local`，不操作正式 Supabase。

**下載端：** `npm run testdata:download` → `scripts/testdata-download.mjs`

- 只讀 Git 已提交的 fixture／案例集；不執行 pull、不 commit、不 push。使用者先在該節點安全地 `git pull --ff-only origin develop` 後，才執行下載。
- 舊 fixture 只寫入本機 loopback Supabase，以標準化資料內容比較後，僅在必要安全驗證通過時執行交易式匯入，不讀取 baselineAt 或 parent 作為匯入門檻。
- Excel RPC 案例集只更新本機忽略目錄中的案例 JSON；不直接寫入任何 TRIP、request registry、Auth 或 Email map。下載前直接比較本機案例副本與 Git 案例內容；內容不同時更新，並保留 request ID 等執行期資料不跨機同步。
- 兩種資料集都不維護或依賴本機 applied state；資料套用成功與否以實際 DB／案例檔內容為準。任何快照結構、關聯、業務鍵、敏感資訊或 loopback 目標檢查失敗才停止寫入。

### 6.4 三台電腦的標準循環

1. 任一節點修改自己的本機合成測試資料。
2. 該節點先確認 Git `develop` 已與 `origin/develop` fast-forward 一致，再執行獨立上傳入口；沒有業務資料變更就 unchanged，不發佈。
3. 其他節點各自安全 pull 最新 `origin/develop`，再各自執行獨立下載入口。
4. 下一個節點可再修改並上傳；其餘節點重複下載。第三台與之後加入的節點不需新增角色或修改協定。
5. 若兩台以上節點各自修改同一份 Git fixture，造成內容分歧，或無法確認寫入範圍僅限合成 fixture，應停止並人工確認；不得以時間戳、版本鏈或 last-write-wins 自動決定覆蓋方向，也不得 force-push 或 reset。

- `npm run test:testdata-download-policy`：通過首次接手只採認 current fixture、空白未知基準停止、非空分歧停止測試。
- `npm run test:testdata-revision`、`npm run test:testdata-peer-sync`：通過。
- 歷史紀錄：當時以 V5 fixture 執行靜態驗證；版本標記與 checksum 僅供追溯，不代表目前同步基準，也不作為同步門檻。
- `npm run verify:docs-links`：通過，130 份 Markdown、273 個本地目標；`git diff --check` 通過。
