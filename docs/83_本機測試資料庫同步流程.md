# 本機測試資料庫同步流程

> 本文件只規範兩台電腦各自的本機 Supabase 測試資料及 Git 版本化合成 fixture。正式 Supabase schema／Migration 與部署請依《[正式 Supabase 資料庫 Migration 與部署流程](81_正式Supabase資料庫Migration流程.md)》辦理。

## 1. 範圍與基準

- Git 管理的 Migration 負責 schema；Git 管理的 Seed／fixture 負責可重現的合成測試資料。兩者不可混為同一同步機制。
- 公司端與家用端的本機 Docker DB 各自獨立；不得複製 Docker volume 或正式 DB dump 作為同步方式。
- fixture 只可含明確挑選的合成／去識別資料，不得含正式資料 dump、secret、token 或 Storage 檔案本體。
- Git pull 只更新版本控制檔案；本機 DB 仍須執行專用同步入口並驗證。

## 2. 對等節點與 revision 規則

家用端與公司端是動態對等節點，任一端都可能產生下一個 fixture revision，也可能接收另一端的 revision。manifest 的 `sourceHost` 僅供來源稽核，不可決定節點角色。

唯一版本判斷依據為本機 applied version／checksum 與 Git current／parent version／checksum；V5、V6 等只是當下 revision 標籤，不是永久基準：
- applied 等於 Git current：兩端基準一致。若本機 DB 相對 current 沒有業務資料變更，維持原版本，不產生新 revision，也不需要上傳；若有業務資料變更，才可由 current 建立下一 revision。
- applied 等於 Git parent：Git 有下一 revision 待接收。只有本機 DB 仍與 parent 資料相符，才可匯入 Git current；接收後 applied state 更新到 current，但不因此再升版或回傳一個空 revision。
- applied 與 current／parent 都不符、父鏈斷裂或 baseline 不明：停止並回報，不猜測、不匯出、不匯入、不覆蓋。

本機 handoff state／檔案 hash 僅供診斷，不可單獨決定角色或判定 peer revision。

## 3. 衝突保護

以下情況一律 fail closed，不採 last-write-wins、不自動合併、不覆蓋：
- 兩端從同一 parent 各自修改；
- 同版不同 checksum、版本回退／缺號、parent checksum 不符；
- 本機 applied baseline 不明；
- 本機 DB 既非已知 parent 也非 current；
- 接收新 revision 時，本機 DB 已有獨立業務資料修改。

資料列基準比較可忽略 DB trigger 自動更新的時間戳差異，但不可忽略業務欄位差異。匯入須在交易內再次核對 parent 資料列及筆數。

## 4. 日常操作

1. 確認主機、工作目錄、分支、upstream、工作樹與遠端差異；不安全時停止，不自動覆寫。
2. 需要取得另一端已提交 revision 時，安全執行 `git pull --ff-only origin develop`。
3. 執行 `npm run db:sync:local`。此入口只操作本機 loopback Supabase；不執行 reset、不清除資料、不自動 pull／commit／push。
4. 依結果判斷已接收、未變更、產生本機下一 revision 或因衝突停止。失敗時保存輸出並停止，不用 reset 作為補救。

## 5. 雙機測試啟動與發布停止線

### 5.1 受控雙機測試：已解除啟動限制

**自 2026-11-03 起，允許公司端與家用端開始受控雙機同步驗收。** 不必等到所有真實雙機案例先通過才可開始；雙機驗收本身就是驗證同步流程的必要手段。共同基準不是寫死的 V5，而是兩端以 Git fixture manifest 與本機 applied state／checksum 實際核對後，能證明一致的最新 revision。

目前已知狀態（2026-11-03）：Git fixture 為 V5（checksum `301153c0fa20354522a9d83c1c76f8bb0a7d745e59dbcb48a799a6660b1d15ca`）、家用端 DB 為 V5；公司端 DB V6 是使用者回報，尚未由本機工具在公司端獨立核實，且 V6 尚未上傳 Git。故不得把 V5 寫成永久基準，也不得把公司端 V6 直接視為已驗證的 peer revision。公司端應先確認 applied state = Git V5，且 DB 資料相對 V5 的差異可被限定為允許的合成資料變更；再產生／驗證 V6 fixture，確認 parentVersion=5、parentChecksum 等於上述 Git V5 checksum、資料筆數／checksum／敏感欄位均通過，才可使用安全 publish 發布。若公司端 applied state、父子關係或資料差異無法證明，停止，不可強制上傳。

啟動每一輪前，兩端都必須：
- 確認使用同一個已提交的 fixture revision 與 checksum，且兩端本機 applied state／DB 資料皆可證明基準一致。
- 確認本機 applied revision／checksum 與本機 DB 資料相符；無法證明基準時不得匯入或覆蓋。
- 確認操作目標是各自的本機 loopback Supabase，絕不連線或寫入正式 DB。
- 先完成該端 Git 分支、upstream、工作樹及遠端差異檢查；取得對端 revision 僅使用安全 fast-forward。

一般 A／B 同步流程如下（A、B 可互換，Git current 是共同版本依據）：

1. **A 有資料變更：** A 的本機 applied 必須等於 Git current，且 DB 與 current 的差異可驗證；handoff 產生 current+1，parent 指向 current，執行 fixture 格式／checksum／資料安全驗證後，才可安全 commit／push。不能跳過基準檢查直接上傳。
2. **B 下載並接收：** B 先 `git pull --ff-only origin develop`，再執行 `npm run db:sync:local`。若 B applied 等於 Git current 的 parent，且 B DB 仍與 parent 相符，import 才能將 fixture 所屬資料更新到 Git current，並更新 B 的 applied state；接收本身不建立下一版、不自動回傳空 revision。
3. **B 接收後沒有資料變更：** B 再跑 handoff／標準同步時，若 DB 與 Git current 相符，結果是 unchanged，版本維持 current，不建立新 revision、不需要 commit／push；Git 保持 current。
4. **B 接收後有資料變更：** B 的 applied 已等於 Git current，handoff 比對確認存在業務資料差異，才產生 current+1 並以 current checksum 為 parent；通過驗證後安全 commit／push，Git current 隨之更新。
5. **A 在 B 尚未接收前也有新變更：** 若 A 與 B 分別從同一 current 修改，第一個成功發布者形成 Git current+1；另一端的本機 DB 與 parent 已不一致，接收流程必須停止，不得覆蓋。須由使用者檢視兩邊差異，人工決定保留／合併後形成下一個單一 revision，再讓另一端接收。
6. **同版本不同 checksum、父版不符、baseline 無法證明或版本鏈分歧：** 一律停止，不以時間戳或 `sourceHost` 自動判斷誰應覆蓋誰。人工處理後，建立明確的新共同 revision；不得直接改寫既有 revision 或 force-push。

每一步均核對 manifest revision、parent checksum、applied state 及資料內容；僅同步動作而沒有業務資料變更時，不應無故升版。

**測試期間的衝突停止線仍然有效：** 同版不同 checksum、parent 不符、版本回退／缺號、baseline 不明、兩端從同 parent 各自修改，或接收端存在獨立業務資料修改時，該輪立即停止並保留現況；不得 last-write-wins、自動合併、reset 或覆蓋。停止單一衝突案例不代表禁止其他安全案例繼續驗收。

### 5.2 尚未完成的驗收項目

正式同步決策邏輯已抽為 `scripts/lib/testdata-revision.mjs` 的 `classifyPeerHandoff()`，正式 `handoff()` 已呼叫該函式；`scripts/test-testdata-peer-sync.mjs` 亦直接 import 同一函式。已完成純函式案例包含接收、未變更、產生下一版、未知 baseline、版本／父鏈不符與本機資料分歧保護。2026-11-04 家用端實際 publish 驗證發現並修正一項呼叫端分類錯誤：當 applied version／checksum 已等於 Git HEAD 時，必須以 HEAD 作為 current、incoming=null；只有 applied 等於 Git HEAD 的 parent revision 時，才將 Git HEAD 視為待接收 incoming。修正後本機 `tc-test-sync-example` V5（checksum `301153c0fa20354522a9d83c1c76f8bb0a7d745e59dbcb48a799a6660b1d15ca`）實際 handoff 結果為 `unchanged`，並安全略過空 commit／push，沒有產生 V6。已增加純函式回歸案例，涵蓋 applied=HEAD 時 unchanged，以及 applied=parent 時 receive。仍待補驗兩端角色互換的實際 DB 情境、時間戳差異及真實 A→B→A 端到端流程；這些是驗收待辦，不是禁止開始受控雙機測試的前置條件。

以上是驗收待辦，不再是禁止啟動真實雙機測試的前置條件。測試結果必須如實記錄，全部通過前不得宣稱雙機同步驗收完成。

### 5.3 程式／fixture 發布停止線

受控雙機測試的啟動，不等於授權推送程式或 fixture。任何一般程式碼／文件 commit、fixture publish 及完整 `commit/push/資料庫` 交接，仍須符合根目錄 `AGENTS.md` 的 Git 安全規則與 fixture 驗證要求；不得把未驗證的同步程式或不合格 fixture 推到另一端。完整交接口令不授權正式 Supabase 部署、破壞性資料操作或覆寫衝突資料。正式資料庫操作仍依正式 Migration 文件的獨立核准規則。
