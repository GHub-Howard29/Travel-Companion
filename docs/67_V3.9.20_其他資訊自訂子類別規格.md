# V3.9.20 其他資訊自訂子類別規格

> 狀態：2026-09-30 Product Owner 已完成 UI 與互動規則定案；本階段只整理文件與編列版本，尚未實作、測試、升版、commit、push、merge、tag 或部署。
>
> 版本決策：本功能插入為 V3.9.20；原 V3.9.20「排序後續時間重算與調整時間整合評估」順延為 V3.9.21。

## 目標

將「其他資訊」目前寫死的固定子類別改為可依每一趟 Trip 需求管理的子類別。使用者可新增、改名、排序與隱藏子類別，例如將本次行程用不到的「簽證」改名為「天氣」，或新增「御朱印」。

本版只處理「其他資訊」子類別管理與顯示排列，不合併 V3.9.21 的排序後續時間重算／調整時間功能。

## 主畫面入口

1. 「其他資訊」上方維持現有子類別按鈕區。
2. 現行提示欄位文字「其他資訊管理」維持不變，直接把這個既有區塊做為子類別管理入口。
3. 不另新增「管理子類別」文案。
4. 「其他資訊管理」入口可加入右箭頭或設定圖示，讓使用者知道可點入，但不改變原本文案。
5. 「新增資訊」表單與一般／敏感資料切換維持現有位置與主要操作流程。

## 其他資訊管理畫面

管理畫面沿用標題「其他資訊管理」，提供：

- 新增子類別。
- 修改子類別名稱。
- 拖曳調整使用者順序。
- 顯示／隱藏子類別。
- 自動排列。
- 恢復預設。
- 排列預覽。
- 完成並返回。

### 子類別列表

每一列至少包含：

- 拖曳把手：手動調整順序。
- 資料夾圖示與子類別名稱。
- 該子類別目前筆數。
- 鉛筆圖示：改名。
- 眼睛圖示：目前顯示。
- 斜線眼睛圖示：目前隱藏。

隱藏只影響「其他資訊」主畫面的子類別按鈕是否顯示，不得刪除該子類別或其既有資料。被隱藏的子類別仍保留在「其他資訊管理」清單內，讓使用者可再次開啟。

### 顯示／隱藏即時回饋

1. 顯示中使用一般眼睛圖示。
2. 點擊後切換成斜線眼睛，表示已隱藏。
3. 隱藏時立即短暫浮現「已隱藏」。
4. 再次點擊後恢復一般眼睛，立即短暫浮現「已顯示」。
5. 狀態提示約 1 秒後自動消失。
6. 圖示必須先立即反映新狀態，不等待提示消失。
7. 提示位置以不遮住目前操作列為原則，建議使用畫面中下方 toast。
8. 顯示／隱藏按鈕需提供可辨識的 aria-label，不能只依圖示讓輔助科技判斷狀態。

## 自動排列

### 操作方式

- 子類別列表提供「自動排列」操作。
- 執行後先更新排列預覽與管理清單順序，實際保存時機依實作階段再確認，但不得在未確認前破壞既有資料。
- 自動排列是協助整理顯示順序，不取代使用者後續拖曳調整。

### 定案排列規則

1. 每列最多顯示 3 個子類別。
2. 短名稱應優先組合在同一列，避免長名稱先佔用剩餘寬度造成不必要空白。
3. 換行後，候選子類別以少字元到多字元優先排列。
4. 若下一個較長名稱無法放進該列剩餘寬度，直接換到下一列，不強制壓縮字寬。
5. 優先維持文字可讀性，不為湊滿三個而縮小字體、壓縮字距或讓文字互相重疊。
6. 子類別按鈕可依內容使用不同寬度；「一列 3 個」是上限，不是固定三等分欄位。
7. 自動排列後仍允許使用者手動拖曳改變順序。

### UI 驗收範例

短名稱可排列為：

- 第 1 列：景點、機票、飯店
- 第 2 列：交通、其他、御朱印
- 第 3 列：天氣與降雨、購票與通關
- 第 4 列：自駕取車／還車

此範例用來驗證「短名稱優先填滿可用列、長名稱放不下才換行」；實際寬度仍以裝置 viewport、字型與按鈕 padding 的量測結果為準。

## 自動排列規則說明

1. 「自動排列規則」在管理畫面預設收合，避免長文案佔用手機畫面。
2. 收合時只顯示簡短標題，例如「ⓘ 自動排列規則」與展開箭頭。
3. 點擊後才展開完整規則，再點一次收合。
4. 展開控制使用真實 button，並提供 aria-expanded 與對應內容區域。
5. 完整文案至少說明：
   - 每列最多 3 個子類別。
   - 換行後優先由少字元排到多字元。
   - 長名稱放不下時直接換行。
   - 不壓縮字寬，優先維持可讀性。

## 新增與改名

- 使用者可新增自訂子類別，例如「御朱印」。
- 使用者可將既有子類別改名，例如「簽證」改為「天氣」。
- 改名不得使既有資料遺失。
- 「其他」保留為可用分類；是否允許改名／隱藏與是否需要至少保留一個可見分類，實作前應由資料契約檢查決定，若現有資料結構有特殊保留值不得直接破壞。
- 名稱空白、重複、過長、特殊字元與最大子類別數量需在實作前依現有資料結構訂出明確驗證規則。

## 資料與同步邊界

- 自訂子類別應屬於目前 Trip，不應無條件影響其他 Trip。
- 本版不得因 UI 改造刪除、重建或重分類既有「其他資訊」資料。
- 若現有分類值同時作為資料識別碼使用，實作時應分離穩定 ID 與顯示名稱，避免「改名」變成資料搬移。
- 需沿用既有其他資訊的 Offline First、同步、權限與敏感資料安全邊界。
- 是否需要 Supabase schema／migration 必須在實作前先檢查現有模型；本文件不預先決定 migration。

## 驗收條件

### 手機 UI

- 390×844 寬度下，短名稱能在同列合理放入最多 3 個。
- 長名稱不重疊、不裁切重要文字、不造成水平捲動。
- 自動排列後可得到上述短名稱優先的驗收範例。
- 「其他資訊管理」入口沿用原文案，不新增重複入口。
- 排列規則預設收合，展開／收合狀態與無障礙屬性正確。

### 管理功能

- 新增子類別後可立即在預覽與清單看到。
- 改名後既有資料仍歸屬原分類。
- 拖曳排序可調整使用者順序。
- 自動排列符合短字元優先與每列最多 3 個規則。
- 隱藏後主畫面不顯示，但管理清單與既有資料仍存在。
- 顯示／隱藏圖示正確切換，並顯示約 1 秒的「已隱藏／已顯示」toast。
- 恢復預設不得無提示刪除使用者既有資料。

### 回歸

- 一般資訊／敏感資料新增與編輯維持。
- 其他資訊既有同步、離線、權限、連結與敏感資料規則不回歸。
- 桌面與手機版均需驗證。
- 完整 build、TypeScript、lint、browser-security、相關 regression 與必要的實機 RC 通過後才可發布。
