# V3.8.1 Trip 刪除墓碑與唯一識別規格

- 狀態：V3.8.1 已完成開發、資料庫驗證、正式發布與 GitHub Pages 部署（2026-09-11）
- 排程版本：V3.8.1
- 發布政策：必要更新；正式 metadata 為 `minimumSupportedVersion: 3.8.1`、`forceUpdate: true`
- 發布日期：2026-09-11
- 資料庫：需要向前新增 Supabase migration；不得修改已發布 migration

## 1. 問題與目標

- V3.8.0 強制更新只替換 App 與 Service Worker，不會清除瀏覽器既有 `localStorage`／IndexedDB。
- 現行 Trip 合併會保留雲端已不存在、但本機仍存在的 Trip，因此另一台裝置刪除 Trip 後，長期未更新或離線裝置仍可能顯示舊資料。
- 現行新 Trip ID 使用「旅遊模式＋出發日期」；重建相同日期及模式的歷史資料會重複 ID，也可能與永久刪除墓碑衝突。
- 本版以永久刪除墓碑阻止舊 Trip 復活，並以不可變 UUID 讓相同日期、模式及名稱可建立為新的 Trip。
- Realtime 只負責快速通知資料失效；墓碑與成功的雲端校正才是清除本機殘留的依據，不要求使用者每次上線手動同步。

## 2. 已定案資料模型

### 新 Trip ID

- 新建 Trip 使用 `trip-${crypto.randomUUID()}`。
- `TripMeta.id` 與 `trips.id` 維持 `string`／`text`，不搬移或改寫既有日期型 ID。
- 旅遊模式、出發日期與名稱只作為業務欄位，不再參與新 Trip 的識別碼。
- 墓碑只封鎖完全相同的舊 `trip_id`；以相同內容重建歷史資料時會取得新 UUID，視為新的資料生命週期。
- 同一天可建立多趟相同模式的 Trip，相關帳本、清單、附件、Other Info、換匯資料與權限均以新 ID 隔離。

### 永久刪除墓碑

新增 `public.trip_deletion_tombstones`：

| 欄位 | 型別 | 規則 |
|---|---|---|
| `trip_id` | `text` | 主鍵；保存被永久刪除的原 Trip ID |
| `deleted_at` | `timestamptz` | 不可為空；由資料庫產生 |
| `deletion_revision` | `bigint` | 不可為空且不得為負；對應同交易產生的全域修訂值 |

- 墓碑永久保留，不保存 Trip 名稱、內容、Email、角色或參與者。
- 新 UUID 不包含日期或其他業務資訊；既有日期型 ID 原本已可由公開 Trip 清單讀取，墓碑不額外加入內容欄位。
- 墓碑 table 啟用 RLS；`anon`／`authenticated` 只具 `SELECT`，沒有 `INSERT`、`UPDATE` 或 `DELETE` grant。
- 讀取 policy 與目前公開 Trip ID 的可見性一致；所有寫入只允許受保護的資料庫 trigger。
- 資料庫在 `trips` INSERT 前檢查墓碑；完全相同的已刪除 ID 必須拒絕建立，前端不得提供解除墓碑或恢復原 ID 的入口。
- `free-travel-2026-01` 與 `group-tour-2026-10` 為固定系統保留 Trip；可編輯但前端、RLS、RPC 與資料庫 trigger 均不得刪除，且不建立墓碑。

## 3. 建立與刪除流程

### 建立

1. 新增 Trip 仍只允許在線狀態及 `super_admin` 執行。
2. 每次建立產生新的 `trip-${UUID}`，依序檢查已載入／本機 Trip、雲端 Trip 與墓碑。
3. 寫入必須使用 `insert`，不得以 `upsert` 覆蓋既有 Trip。
4. 唯一鍵或墓碑若回報 ID 衝突，只針對可確認的 ID 衝突重新產生一次 UUID；其他錯誤不得誤當碰撞重試。
5. 雲端建立成功後才建立正式本機快取及後續子資料 scope。

若未來新增備份匯入，一般匯入必須產生新 Trip ID 並重映射所有子資料的 `trip_id`。保留原 ID 的完整還原屬另一項受控功能；在墓碑不可復原政策下不提供。

### 刪除

1. 整趟 Trip 永久刪除仍只允許 `super_admin`。
2. `trips` DELETE、墓碑建立、`app_data_revision` 遞增及 Broadcast 必須位於同一資料庫交易。
3. 應由既有修訂 trigger 的刪除分支取得新 revision 並寫入墓碑，避免多個同事件 trigger 的執行順序造成 `deletion_revision` 不一致。
4. 前端必須確認實際刪除一列且相同 ID 的墓碑可讀，才回報刪除成功；零列 DELETE 不得視為成功。
5. 關聯資料與附件清理維持既有安全順序，但任一必要清理失敗不得偽裝為完整成功；正式實作需保留可追查錯誤與向前修復方式。

## 4. 啟動、重連與 Realtime 校正

- 冷啟動、登入完成、網路恢復、頁面回到前景及收到 Trip revision 時，各執行一次合併節流的 Trip／墓碑校正。
- 只有 Trip 清單與墓碑查詢都成功時才套用清除；離線、逾時、Session 尚未完成或 Supabase 錯誤不得刪除本機資料。
- 墓碑優先於本機 `updatedAt`、`cloudUpdatedAt`、pending、雲端清單與內建 seed；相同 ID 不得因本機時間較新而復活。
- 墓碑命中的 Trip 會從選單、本機 Trip、權限快取及共用資料移除；私人帳本與私人清單沿用既有保留政策。
- 目前 Trip 被清除時靜默切換至 `findDefaultTrip` 選出的可用 Trip；固定開啟「每日詳細行程」，旅程進行中開啟今天對應 Day，否則 Day 1。非目前 Trip 直接從選單移除。
- 保存最後成功套用的 `deletion_revision` 以避免重複處理，但每次完整啟動及必要一致性檢查仍以伺服器資料為準。
- 不新增固定輪詢，也不要求使用者每次上線按下手動同步。

## 5. V3.8.0 以前的既有殘留修復

- V3.8.1 首次成功取得完整雲端 Trip 清單後執行一次舊快取校正。
- 本機紀錄具有 `cloudUpdatedAt`、但雲端已不存在者，視為曾同步後被遠端刪除的殘留並靜默移除。
- 沒有 `cloudUpdatedAt` 的不明舊資料不得直接刪除，避免誤傷早期只存在本機的資料。
- 墓碑 ID 必須同時排除內建 seed，避免靜態 `trips/list.json` 再次顯示已刪除 Trip。
- 本機資料結構需有獨立版本與一次性 migration 標記；App 版本、Service Worker 版本及資料快取版本不可混為同一狀態。
- 不以清空整個 `localStorage`／IndexedDB 作為升級或殘留修復方式。

- 兩筆固定種子 Trip 確保正常狀態至少有可用 Trip，不新增零 Trip 空狀態；若完整校正資料取得失敗，維持現有本機狀態而非清空。
- 編輯固定種子 Trip 時顯示禁用的「刪除整個旅程」及系統保留說明，仍可編輯其他內容；介面已一併確認。

- 非目前 Trip 的背景移除不新增逐筆提示；既有 V3.6.4 其他遠端變更與撤權提醒不因本版改寫。

## 7. 實作與相容邊界

- 預計調整 Trip ID 產生、雲端建立／刪除服務、Trip repository、啟動／重連校正及本機共用資料清理；不改變既有角色矩陣。
- 新增向前 migration、專項 validation／rollback SQL 與固定領域測試；不得回寫 V3.6.4 或其他已發布 migration。
- 舊日期型 Trip 可繼續讀取、編輯及刪除；只有 V3.8.1 新建 Trip 改用 UUID。
- V3.8.0 不理解墓碑且仍使用日期型 ID，因此 migration 必須先部署並保持伺服器端防復活，前端完成後才發布必要更新 metadata。
- 原 V3.8.1「排序後時間整合」退回未排程候選，不併入本版；若日後需求成立再另行排版號與重新確認介面。

## 8. 驗證與放行

### 程式與資料一致性

- 刪除舊 Trip 後，以相同日期、模式及名稱重建成功，且取得不同 UUID。
- 同一天可建立多趟相同模式 Trip，子資料 scope 完全隔離。
- 舊裝置或錯誤匯入嘗試寫回墓碑 ID 時由資料庫拒絕；新 UUID 不受舊墓碑影響。
- 既有日期型 ID 在升級後仍可正常讀取、編輯及刪除。
- 目前／非目前 Trip、靜態 seed、本機殘留及長期離線裝置都能在成功重連後套用墓碑。
- 網路、Session、Trip 清單或墓碑查詢失敗時不得清除本機資料。
- 共用 pending 依刪除政策清除，私人資料保留，其他 Trip 與其他帳號資料不受影響。

### Supabase 與安全

- 從乾淨資料庫套用 migration，驗證 table、主鍵、constraint、trigger、RLS、GRANT、修訂值與回滾流程。
- 驗證 Guest、User、`trip_editor`、`super_admin` 可讀最小墓碑但都不能直接寫入；只有合法 `super_admin` 刪除 Trip 時能由 trigger 建立墓碑。
- 驗證 DELETE、墓碑與 revision 的交易一致性，以及零列刪除、重複墓碑、原 ID 重建及交易回滾。
- 執行 database advisors；新增物件不得留下未審查的 security／performance finding。若受保護 RPC 因刻意授權產生 SECURITY DEFINER finding，必須逐項核對函式內授權、固定 `search_path`、EXECUTE grant 與直接表格權限並記錄接受理由。

### App 與發布

- 桌面／手機靜默切換與種子保護模擬圖已取得 Product Owner 確認；實作結果必須與核准稿一致。
- 通過專項測試、TypeScript、lint、完整 build、桌面瀏覽器、390×844、即時離線／重連及雙分頁流程；Android／iOS 實體裝置與 PWA 冷啟動離線列為發布前補驗。
- 發布前建立 production logical backup、migration dry-run、回滾演練及舊版相容 smoke；production logical backup、dry-run 與 migration 已於 2026-09-11 完成。
- 部署順序固定為：migration → 資料庫驗證 → V3.8.1 前端 → 正式資產驗證 → `minimumSupportedVersion: 3.8.1` 與 `forceUpdate: true` metadata。
- Product Owner 已於 2026-09-11 放行更新文案與完整發布流程；提交 `da0b87d`、遠端分支、annotated tag `v3.8.1`、GitHub Pages 部署、正式站驗證及正式發布均已完成。

## 9. 明確不做

- 不恢復或刪除永久墓碑。
- 不允許新 Trip 沿用已刪除 ID。
- 不為本版開發備份還原、逐筆刪除歷史、手動同步頁面或固定輪詢。
- 不自動清除來源不明且沒有 `cloudUpdatedAt` 的舊本機 Trip。
- 不改變 Trip 公開瀏覽、角色、歷史行程寫入鎖或 Travel Tool 既有資料模型。
- 不在靜默切換及任何新增 UI 未經模擬圖確認時修改相關前端程式。
