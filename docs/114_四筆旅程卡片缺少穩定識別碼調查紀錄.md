## 2. 已確認的程式證據

### 2.1 UI 直接阻擋點

檔案：`src/components/ItineraryPage.tsx`

函式：`startEditItem()`，先前定位約 lines 947–1048。

當 `event.id` 不存在時，程式設定錯誤訊息並立即 return：

```ts
const cardId = event.id;
if (!cardId) {
  setEditClaimError("此卡片缺少穩定識別碼，為避免覆蓋其他修改，暫時無法編輯。");
  return;
}
```

因此已確認的直接原因是：卡片資料缺少 `event.id`，編輯流程在取得 edit lease、開啟編輯表單前即被 fail-safe 阻擋。

此 helper 可為缺少 ID 或重複 ID 的卡片產生唯一識別碼。

### 2.3 Trip detail 正規化沒有補卡片 ID

檔案：`src/services/tripRepository.ts`

函式：`normalizeTripDetail()`，先前定位約 lines 227–258。

該函式處理 sidebar config、other-info folders/items、mode 等正規化，但沒有呼叫 `ensureItineraryDaysDataIds()`，也沒有自行補正 `daysData` 卡片 ID。

`getTripDetail()` 的兩條路徑先前均已定位：

- Static SEED path：約 lines 470–480，讀取 JSON 後呼叫 `normalizeTripDetail()`。
- Dynamic cloud/local path：約 lines 483–509，取得 cloud/local record 後也呼叫 `normalizeTripDetail()`。

因此目前共同正規化流程不會修復兩類來源中的缺 ID 卡片。

**重要限制：**這只能解釋「已缺 ID 的卡片為何載入後仍缺 ID」，不能單獨解釋正式資料最初如何變成缺 ID，也不能證明日本九州旅程期間曾缺 ID。正式 production history 顯示日本旅程於 2026-10-03 結束時仍有 ID；需另追日本正式 row 與 JSON seed 為何分歧。

### 2.4 Supabase 讀取轉換沒有補 ID

檔案：`src/services/tripCloudService.ts`

函式：`toTripRecord()`，先前定位約 lines 186–234。

`detail.content` 使用：


上述 sanitizer 處理封面照片與過期路線估算，並不負責補卡片 ID。`getCloudTripRecordsStrict()` 約 lines 275–293 透過 `.map(toTripRecord)` 轉換雲端資料；若 Supabase `trips.content.daysData` 原始資料缺 ID，轉換後仍會缺少 ID。

### 2.5 從 detail 建立 Trip record 也沒有補 ID

該函式會 spread `detail.content` 並更新其他欄位，但沒有對 `daysData` 執行 ID 正規化。這代表其他欄位保存時也可能繼續保存缺 ID 的卡片資料。

### 2.6 卡片 ID 型別契約與雲端寫入邊界有缺口（本次程式追查確認）

- `src/types/trip.ts` 的 `ItineraryItem.id` 目前宣告為選填 `id?: string`，註解卻寫明 V3.8.0 起使用穩定卡片識別，舊資料在下一次行程寫入時補齊。型別容許缺 ID，與註解承諾不一致。
- `normalizeTripDetail()`、`toTripRecord()`、`createTripRecordFromDetail()`、`updateTripRecord()`、`createTripRecordFromExisting()` 及 `toCloudTripInsert()` 都沒有在共同資料邊界保證 `daysData` 每張卡片都有非空且唯一的 ID。
- `upsertCloudTripRecord()` 將整個 `TripRecord` 轉成完整 `trips` row 後以 `onConflict: id` upsert；`updateCloudTripRecord()` 雖以 `updated_at` 做樂觀鎖，仍未檢查卡片 ID 完整性。版本鎖只能防止過期 row 覆蓋，不能阻止缺 ID payload 被合法寫入。
- `App.tsx` 的共同清單保存 `handleSaveChecklistData()` 會呼叫 `saveCurrentTripDetail(..., false)`，可走不帶 expected version 的完整 row upsert；`handleSaveOtherInfoFolders()` 也會以完整 Trip detail 保存設定。這些操作本身不是行程卡片編輯，卻會把目前記憶體中的 `content.daysData` 一起寫回。
- `useTripWorkspace.updateTrip()` 會由 `updateTripRecord()`／`createTripRecordFromExisting()` 組裝完整 record，完成 Trip row 保存後再呼叫 `syncTripEditorEmails()`。所以更新標題、日期、參與者或編輯者等設定，也可能連帶保存整份 `daysData`。
- `updateTripRecord()`／`createTripRecordFromExisting()` 會依新天數重新建立 `daysData` 物件，但對保留的日子直接沿用原卡片陣列，沒有補 ID 或檢查唯一性；縮減天數時會依日期 key 過濾，其餘內容原樣保留。
- 手動建立 Trip 表單只建立 Trip metadata／空白日程，沒有卡片產生邏輯；之後手動新增卡片的 `ItineraryPage` 現行保存流程會配置 `createItineraryItemId()`。Excel parser 現行也會為匯入卡片配置 `crypto.randomUUID()`。因此不能概括說所有新建 Trip 都會漏 ID；較精確的風險是舊版／外部來源的卡片 payload 缺 ID 後，載入及一般 Trip 設定保存都沒有共同補正。
- `src/services/itinerarySync.ts` 的 `toLocatedCards()` 對任何缺 ID 卡片會回傳 `legacy-id` 衝突並 fail-closed；這條專用行程同步路徑不會默默把無 ID 卡片濾掉，暫不列為資料被靜默刪除的候選原因。
- Git 歷史顯示 V3.8.0 前的 `ItineraryPage.saveItem()` 在元件內只把 `draft` 原樣合併進 `daysData`，沒有明寫 `id`；但這只是元件層程式，不能單獨證明正式使用者建立的卡片最後沒有 ID。使用者補充實際經驗：目前建立或匯入的卡片 ID 一直有效，因此此舊版片段與實際使用經驗有待以當時正式部署版本、完整父層呼叫鏈及實際卡片來源核對，不列為已證實根因。V3.8.0 commit `93a4df4` 才加入 `createItineraryItemId()`、`ensureItineraryDaysDataIds()`，並在新增卡片及部分既有卡片操作使用；但 helper 沒有進入共同 Trip load／general save 邊界，這個設計缺口仍成立。

**判定：**「缺 ID 資料可經一般 Trip 設定保存／upsert 穿過寫入邊界」是已確認的設計缺口；但它是否就是宜蘭、台中、沖繩當年首次缺 ID 的實際操作，仍須以當時 request payload 或寫入前資料快照證明，不能只憑存在這個漏洞就指認某次操作。

## 4. 根因判斷分級

### 已確認

1. 編輯 UI 將缺少 `event.id` 視為不可安全識別的卡片，並在開啟編輯前阻擋。
2. 專案已有 `ensureItineraryDaysDataIds()`，但它沒有進入共同 Trip detail load／normalization 流程。
3. `normalizeTripDetail()`、`toTripRecord()`、`createTripRecordFromDetail()`、`updateTripRecord()`、`createTripRecordFromExisting()` 與 `toCloudTripInsert()` 均未在共同讀寫邊界保證每張卡片都有非空且唯一 ID。
4. `ItineraryItem.id` 在 `src/types/trip.ts` 被宣告為選填，與其註解「舊資料於下一次行程寫入時補齊」不一致。一般 Trip 設定保存會完整攜帶 `daysData`；`handleSaveChecklistData()` 的 `enforceVersion=false` 路徑會走完整 row upsert，其他 `updateTrip()`／Other Info 設定保存也會寫回完整 Trip record。
5. 正式 production trigger 不會刪除或補正卡片 ID：`trips_guard_visibility_and_email_map` 只移除 `participantEmailMap`、`otherInfoItems`；`trips_capture_itinerary_day_history` 只在 daysData 改變時保存變更前的日程。V3.9.26 migration 未修改 daysData/card ID。

## 6. 修正方案（本階段只制定，不實作）

### 6.1 修正目標與不可破壞的資料契約

1. 每張已儲存的 `ItineraryItem` 必須有非空字串 `id`。
2. 同一 Trip 的所有日期卡片 ID 必須唯一；跨日複製卡片須產生新 ID，不能複用來源卡片 ID。
3. 修改卡片內容、時間、地點、封面、天氣設定、交通估算或排序時，既有卡片 ID 必須保持不變。
4. 新增／匯入卡片建立 ID；載入舊資料時可安全補正；遇到無法安全判定卡片身分的資料，應阻擋寫入並回報，不得靜默丟棄、任意重排或覆蓋其他裝置的新資料。
5. ID 是跨裝置編輯鎖、同步比對、天氣結果關聯、卡片照片等功能共用的持久識別契約，不是 UI 欄位或短期快取值。

### 6.2 A 線：Static SEED JSON（日本九州、沖繩）

**建議作法**

- 先把 JSON 中每張卡片列入逐卡盤點表，以 Trip ID、day key、原始卡片內容及排序作為核對依據。
- 為缺 ID 卡片配置穩定且唯一的 UUID；完成後檢查同一 Trip 全部日期沒有空白或重複 ID。
- 如考慮沿用歷史 Supabase row 的 ID，必須逐卡比對內容（時間、標題、地點、類別、描述及重要屬性），並確認一對一映射；日本歷史 row 31 張與 JSON 20 張數量不同，不得僅用陣列 index、日期或筆數直接搬用 ID。
- JSON 修改前保存原始檔案版本及 checksum；加入資料檢查，防止 Static SEED 再度漏 ID。
- Static SEED 不經一般動態 Trip upsert；不得為修復 JSON 而寫入同 ID 正式 `public.trips` row，也不得以 DB row 覆蓋 JSON。

**風險與防護**

- 最主要風險是錯配 ID，讓 edit lease、天氣資料或封面照片錯誤對應到另一張卡片。
- 無法確認一對一內容對應時，優先配置新且穩定的 ID；但新 ID 對舊有 ID 關聯型資料的影響必須先盤點，不能直接部署。
- 必須驗證正式 PWA 實際取得的 JSON、cache busting／PWA cache 更新行為及回復舊版 JSON 的方式；只改 repository 檔案不等於使用者端已更新。

### 6.3 B 線：動態 TRIP（宜蘭、台中）

**建議作法**

- 建立單一共用的 `daysData` ID integrity validator／normalizer，供讀取、正規化、local storage sanitize、Trip create/update、雲端 insert/upsert/update 及完整 Trip save 共用；不要只依賴 `ItineraryPage` 個別操作。
- 正規化需做到每張卡片 `id` 非空、全 Trip 唯一。已存在且唯一的 ID 必須原樣保留；只有缺少或重複的 ID 才建立替代 ID，並產生可追蹤的修復摘要。
- 在雲端寫入邊界加入 fail-closed 驗證：不接受缺 ID／重複 ID 的 payload；若 normalizer 能安全修復，必須在建立完整保存 record 前完成，再走既有版本檢查及 optimistic concurrency；不得讓 `enforceVersion=false` 變成繞過完整性驗證的後門。
- 將 ID 欄位型別由選填改為必填，並檢查 API、歷史資料、測試 fixture、匯入器、Static SEED 與 recovery code 的兼容性。
- 研究 DB 端 JSONB validation 是否可行，但不把新增 trigger／constraint 當成第一步；先盤點所有寫入者、歷史資料及 migration 回復能力，避免舊版 client 寫入被突然拒絕或觸發非預期資料轉換。
- 動態資料回填先以唯讀 dry-run 產出 Trip／日期／卡片 index／既有 ID／擬新增 ID／重複情形報告；完成備份、跨裝置同步與版本鎖風險審查後，才另案請求正式資料修復授權。

**風險與防護**

- 不得對既有有效 ID 重新產生 ID，否則會破壞 edit lease、同步衝突偵測、weather request ID、cover photo 路徑或其他以 card ID 關聯的資料。
- 不得以陣列 index 作永久識別碼；排序、跨日移動、刪除及新增都可能改變 index。
- 若發現重複 ID，不能任選一張保留原 ID 而不記錄映射；應保留一張明確的 canonical mapping，其餘建立新 ID，並確認相關附屬資料對應。
- 每次雲端寫入仍須保留既有 `updated_at` optimistic concurrency／版本衝突防護，ID 完整性檢查不能取代版本檢查。
