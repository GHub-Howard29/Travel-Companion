# V3.9.22 RC2 實機問題根因分析

> 狀態：2026-10-01 已完成 V3.9.22 RC3、正式 Supabase hotfix 與實機複驗。歷史 Trip 日期修改、Trip 刪除、時間雙欄位檢核，以及排序後交通時間／距離自動更新與保存均通過。Trip 刪除後續追查確認另有資料庫回歸：V3.9.17 Change Journal migration 覆寫 `private.tc_broadcast_trip_data_revision()` 時漏掉 V3.8.1 的 DELETE tombstone 分支，導致 `tc_delete_trip` 以 SQLSTATE `22000` 回滾；修正 commit `0a73149` 與正式 migration `20261001143042_v3922_restore_trip_delete_tombstone` 已套用並驗證刪除成功。本文保留為 V3.9.22 根因與驗收紀錄。

## 1. 歷史行程刪除出現「無法確認旅程已完整刪除」

### 實機現象

super_admin 在歷史行程編輯畫面執行「刪除整個旅程」後，可能出現：

> 無法確認旅程已完整刪除，請保留此畫面並確認網路後再試一次。

### 程式鏈

目前刪除流程為：

1. `handleTripDelete()` 先執行 `checkForRemoteTripChange()`。
2. `deleteTripRecordWithCloudSync()` 呼叫 `deleteCloudTripRecord()`。
3. 先列出費用附件與行程封面，逐筆呼叫 `tc_schedule_storage_deletion` 排入延遲刪除。
4. 呼叫 `tc_delete_trip`；資料庫在同一 transaction 內清理共用資料、刪除 Trip、建立永久 tombstone、增加 revision 並 Broadcast。
5. RPC 已回傳 `deleted_trip_id + deletion_revision` 後，前端又另外查一次 `trip_deletion_tombstones`，確認該 tombstone 存在。
6. 只有上述全部成功後才刪除 localStorage Trip。
7. 任一階段拋錯，App.tsx 最後都顯示同一則「無法確認旅程已完整刪除」。

### 根因

目前可確認的是**刪除成功判定不是單一 transaction 的結果，而是 transaction 完成後又依賴一次額外的網路確認**。

`tc_delete_trip` 本身已把 Trip DELETE、tombstone 建立與 deletion revision 放在同一 transaction，且 RPC 回傳 tombstone revision；但 `deleteCloudTripRecord()` 在 RPC 成功後仍再次 query tombstone。若這個「第二次確認」因瞬時網路／查詢錯誤失敗：

- 雲端 Trip 其實可能已經刪除成功。
- 本機 Trip 因前端丟錯而不會刪除。
- UI 會誤報「刪除失敗」。
- 使用者再次按刪除時，`tc_delete_trip` 會因 Trip 已不存在而回 `Trip does not exist`，形成不可安全重試的 false-negative。

另外，附件 list／延遲刪除排程、RPC、RPC 回傳格式、tombstone 二次查詢目前全部共用同一個最終 alert，因此實機畫面無法辨識是哪一階段失敗，診斷資訊被吃掉。

### 修正方向

下一輪實作應：

- 讓 `tc_delete_trip` 的成功回傳成為刪除 transaction 的 authoritative result，不再以 transaction 後第二次 tombstone query 作為必要成功條件；或把 tombstone 確認設計成可安全重試的 idempotent 流程。
- 刪除 API 必須能處理「Trip 已不存在但對應 tombstone 已存在」的重試情境，視為已完成，而不是再次報錯。
- 把「附件排程失敗」「Trip delete RPC 失敗」「刪除已提交但確認失敗」分成可診斷的 error contract；使用者文案可以維持簡潔，但 console／錯誤代碼必須保留真實階段。
- 新增 regression：RPC 已成功、後續確認失敗時不得讓同一 Trip 進入永久無法重試狀態。

## 2. 歷史行程修改出發日期後跳出遠端版本衝突，重新載入後日期未變

### 實機現象

歷史行程可開啟編輯，修改出發日期後按「儲存旅程」：

- 儲存操作可送出。
- 隨後顯示「行程資料已在其他裝置更新」。
- 按重新載入後，出發日期仍是舊值，表示這次修改沒有成功寫入雲端。

### 程式鏈

目前畫面與儲存使用兩套資料來源：

- TripEditor 畫面主要顯示 React state 的 `currentTrip`／`selectedTripMeta`。
- 真正儲存時，`updateTrip()` 優先呼叫 `updateTripRecord(selectedTripId, input)`。
- `updateTripRecord()` 不使用畫面上的 `currentTrip`，而是重新從 localStorage 的 `readStoredTripRecords()` 取 record，建立新的待儲存內容。
- `saveTripRecordWithCloudSync()` 再使用該 local record 的 `cloudUpdatedAt` 作為 Supabase `updated_at` optimistic-lock 條件。

同時：

- `getTripDetail()` 可以取得較新的 cloud Trip 給 `currentTrip` 顯示，但不保證把那一份最新 record／`cloudUpdatedAt` 寫回 localStorage。
- `isNewerRecord()` 只比較 record 的本機 `updatedAt`，不比較 authoritative `cloudUpdatedAt`；本機-only 寫入可產生較新的 `updatedAt`，使較舊的 Trip 本體在部分 merge 路徑中被保留。
- `saveCurrentTripDetailLocally()` 雖刻意保留既有 `cloudUpdatedAt`，但會建立新的本機 `updatedAt`，因此「本機 updatedAt 很新、cloudUpdatedAt 仍舊」是合法存在的狀態。

### 根因

根因是**Trip 編輯畫面的資料版本與 optimistic-lock 的版本來源沒有單一 owner**。

使用者看到／編輯的是 `currentTrip`，但儲存 payload 與 expected `updated_at` 又回頭讀 localStorage record。當兩者已不同步時：

1. 使用者在看似最新的畫面修改日期。
2. 儲存卻拿另一份 local record 的舊 `cloudUpdatedAt` 去更新雲端。
3. Supabase `.eq("updated_at", expectedUpdatedAt)` 找不到 row，正確拋出 `TripVersionConflictError`。
4. UI 因此顯示「其他裝置已更新」。
5. 實際日期 update 從未 commit，所以重新載入仍是舊日期。

這不是日期欄位本身無法更新，也不是歷史行程 trigger 阻擋 super_admin；資料庫的歷史行程 trigger 對 super_admin 直接放行。問題在 client 的版本基準分裂。

### 修正方向

下一輪實作應：

- Trip 編輯建立 payload 時使用同一個 authoritative record snapshot，不再由 UI state 與 localStorage 各取一半。
- 編輯 modal 開啟或送出前，對需要 optimistic lock 的 Trip 明確取得最新 cloud record／`updated_at`，並把 payload 與 expected version 綁在同一 snapshot。
- `isNewerRecord()` 不應只用 local `updatedAt` 決定雲端／本機哪個 Trip 本體較新；需區分 local mutation time 與 cloud version。
- 保留真正跨裝置衝突阻擋，不能用關閉 optimistic lock 解決。
- 新增 regression：畫面 currentTrip 已是最新雲端內容、local cache 的 `updatedAt` 較新但 `cloudUpdatedAt` 較舊時，修改 Trip master 欄位不得誤判成跨裝置 conflict。
- 歷史 Trip 需至少覆蓋 super_admin 修改出發日期與一般 Trip 相同的版本一致性測試。

## 3. 套用新的順序時間後，交通路徑／交通時間不會自動更新

### 實機現象

RC2 的「新的到達時間＋新的離開時間」與檢核規則正常；排序後建立時間預覽也能計算新的交通時間。但按「套用新時間」後：

- 正式行程卡片的交通路徑／交通時間沒有跟著更新。
- 必須逐段手動點交通方式，才會重新查詢並顯示交通時間。

### 程式鏈

排序儲存時：

- `invalidateChangedTravelDestinations(orderOriginal, orderDraft)` 會把目的地已改變的舊 `travelToNext` 清掉，這部分是正確的。

時間預覽時：

- `calculateTimeAdjustment()` 會透過 resolver 取得每一段有效的 `SavedTravelEstimate`。
- estimate 被放進 `TimeAdjustmentResult.segments[].estimate`，並用來計算下一站到達時間。
- 但計算函式只更新 `items[].time`／`departureTime`，沒有把 segment estimate 寫回 origin item 的 `travelToNext`。

最後套用時：

- `applyTimeAdjustment()` 只把 `timeAdjustmentResult.items` 寫回 `daysData`。
- `TimeAdjustmentResult.segments` 沒有被 materialize 回 `items[].travelToNext`。
- 正式卡片顯示交通資料時只透過 `getSavedTravelEstimate(event, nextTravelEvent)` 讀 origin 的 `travelToNext`。
- 因此正式畫面看不到預覽時已經取得的 estimate。
- 使用者手動點交通方式後，既有單段路線流程才會重新取得 estimate 並寫回 `travelToNext`，所以畫面才恢復。

### 根因

**時間預覽的 route estimate 只存在暫時的 `segments`，套用時沒有寫回正式 itinerary item。**

這是 preview → commit 的資料遺漏，不是 Routes API 沒算出結果，也不是 UI render 沒刷新。

### 修正方向

下一輪實作應：

- 在「套用新時間」前，把 `TimeAdjustmentResult.segments` 的 estimate 依 `originIndex` materialize 到對應 item 的 `travelToNext`。
- 僅保存仍符合 origin/destination place key、travel mode 與 departure-time basis 的 estimate。
- transit estimate 必須使用調整後離開時間作為 `departureTimeBasis`；若預覽中使用的是舊 basis，應重新查詢而不是保存失效 cache。
- 被略過的「餐飲／其他」卡片維持無 `travelToNext`；estimate 應存在前一個有效交通節點上並指向下一個有效交通節點。
- 「套用新時間」完成後，不需再逐段點交通方式，正式卡片應直接顯示與預覽一致的交通時間／距離。
- 新增 regression：排序造成舊 cache invalidation → 預覽取得新 estimate → 套用 → `getSavedTravelEstimate()` 立即可讀到同一 estimate。

## 修正順序建議

三項建議一起進下一個 RC，順序如下：

1. **Trip master 版本一致性**：避免正常修改被誤判 conflict，也避免在錯誤版本上做刪除／更新。
2. **Trip delete idempotency／成功判定**：避免雲端其實已刪除、前端卻保留且無法安全重試。
3. **時間預覽 estimate commit**：把已算出的交通資料完整寫回正式 itinerary。

三項都屬資料一致性，不建議只用 UI workaround 掩蓋。

## 驗收案例

### A. 歷史行程刪除

- super_admin 刪除無附件歷史 Trip：一次完成，Trip 從雲端與本機清單消失。
- super_admin 刪除有費用附件／封面的歷史 Trip：附件成功排入延遲刪除後，Trip 一次完成刪除。
- 模擬 RPC 成功後 client 網路中斷：重新連線後能辨認 tombstone，視為已刪除，不重複報永久失敗。
- 對已 tombstone 的 Trip 再次執行 recovery：結果必須 idempotent。

### B. 歷史行程修改日期

- super_admin 開啟歷史 Trip，修改出發日期後儲存：雲端 `departure_date` 更新，重新載入後保留新日期。
- local `updatedAt` 比 cloud 新、但 `cloudUpdatedAt` 舊：不得因此誤判真正的 Trip 本體版本。
- 另一裝置真的先修改 Trip master：仍必須出現 conflict，不可覆寫遠端新版。

### C. 排序／時間／交通

- A→B→C 改成 A→C→B，舊 route cache 清除。
- 「預覽新時間」取得 A→C、C→B estimates。
- 套用後正式卡片立即顯示 A→C、C→B 的交通時間／距離。
- 關閉再開 App 後仍保留。
- transit、drive、walk 各至少一個案例；另測一張不納入交通計算的中間卡片。
