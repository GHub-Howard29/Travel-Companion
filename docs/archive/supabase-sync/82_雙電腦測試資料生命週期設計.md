# 雙電腦測試資料生命週期與自動同步規則

> **歷史設計原始資料（非現行操作規格）。** 本文件保留測試資料生命週期與雙電腦同步的早期設計思路，包含當時提出、後續已被取代的 testPurpose／fixture 標記門檻、checksum／內容指紋、revision／parent 鏈及自動同步方案。這些內容只作設計沿革參考，不得作為現行操作依據。現行規格、所有實際資料庫交換紀錄及待驗狀態，唯一以《[本機測試資料庫同步流程](../../83_本機測試資料庫同步流程.md)》為準。本文件不再追加後續測試結果、操作紀錄或驗收進度；原有後續測試紀錄已移交至 83，未能在現有主文件找到佐證的項目不擅自補寫。

## 目標

任一台電腦產生的合成測試資料，都要能被另一台電腦取得、套用、驗證及追蹤；資料在回歸測試明確解除前不得清除。解除後，依測試資料的生命週期標記，選擇刪除或封存但不再載入。

## Push／Pull 的自動化界線

- `git push`／`git pull` 只傳輸已提交的版本控制檔案，不會讀取或傳輸本機資料庫中的資料列。
- 版本化測試資料必須先由本機資料庫匯出成 fixture／變更集，經過敏感資料檢查後納入 Git；另一台取得 Git 版本後，再由本機同步入口套用。
- 可將安全的資料套用與驗證掛接到安裝完成的 Git hooks，但 hooks 必須由專案設定明確安裝，且必須允許停用／診斷。不得假設 clone 後 hook 自動存在。
- `push` 前不能盲目自動提交整個本機資料庫；匯出若遇到真實資料、秘密、無法識別的表、衝突或未完成測試資料，必須停止並提示人工處理。
- `pull` 後只允許自動套用已審查、已版本化且標記為可載入的測試資料變更集；不得自動清除本機資料。

## 資料生命週期

每個測試資料集應有穩定的 `fixture_id`、版本、建立來源電腦、狀態與回歸測試紀錄。狀態依序為：

1. `active`：測試資料可使用，必須同步到兩台電腦。
2. `regression_pending`：資料內容已固定，等待指定回歸測試；仍須同步並保留。
3. `released`：回歸測試通過且已明確解除使用；不可再自動載入為活躍測試資料。
4. `archived` 或 `deleted`：解除後依決策封存或刪除。封存資料只作為歷史記錄，不得由日常同步入口重新匯入。

資料集只有在兩台電腦均確認收到同一版本及相同狀態後，才能完成解除／清除。任一台離線或未確認時，另一台不得先刪除唯一可用的測試資料來源。

## 同步安全要求

- 只同步明確標記為合成測試資料的資料集；不得把整個 Supabase dump 當成 fixture。
- 匯入需具冪等性，重複執行不重複新增資料；套用前先驗證 fixture schema、版本、識別碼及相依關係。
- 不可把 Auth session、密碼、token、API key、secret、真實參與者個資、Storage 檔案本體或本機環境設定放入 fixture。
- 跨電腦不得依賴各自不同的 `auth.users.id`。若測試資料需要使用者關聯，應以合成角色映射建立本機關聯，或在匯入時明確重映射；無法安全重映射時停止。
- 不可對兩台獨立修改的資料採用 last-write-wins。只有已提交的 fixture revision 明確指定上一版 parentVersion／parentChecksum，且接收端資料庫逐列、逐筆數符合該父版本時，才允許在單一交易中完整替換該 fixture 的白名單資料範圍；父版本不符、同版 checksum 不同、接收端版本較新或資料存在額外編輯時，一律停止。
- 完整替換只涵蓋 manifest 明列的合成 fixture 範圍（該 Trip、shared checklist、其 checklist items、expenses、exchange purchases、other-info items）；不涵蓋私人 checklist、其他 Trip、一般資料或未列入 fixture 的資料表。
- fixture 內的刪除必須在新 revision 中明確呈現（例如 tombstone 或來源完整快照的列集合差異）；只有父版本完全吻合才可依新版本完整替換，不能把無父版本證明的「來源缺少某列」當成刪除依據。
- 不建立額外備份，除非使用者另行要求。

## 驗收條件

1. 電腦 A 新增合成行程資料，匯出後可在 Git 中看到精確變更集。
2. 電腦 B 取得同一版本並套用後，核心行程資料及關聯資料與 A 一致。
3. 重複套用同一變更集不會重複新增資料，也不會清除其他本機資料。
4. A、B 各自新增資料後，匯出／合併能保留兩邊變更；衝突會明確中止，不會靜默覆蓋。
5. `active`／`regression_pending` 資料不能被清除；只有通過回歸測試且明確標記 `released` 後，才可封存或刪除。
6. `released`／`archived` 資料不會被一般同步入口重新啟用。
7. 兩台電腦都完成實際驗證前，不可宣稱雙電腦同步流程完成。

## 設計沿革：2026-11-03 對等節點同步設計

本節保留當時提出的問題分析與技術設計原始資料；其中流程與狀態定義已由 83 現行規格取代。以下不代表目前實作狀態或測試驗收結果。

### 當時辨識的設計問題

1. `scripts/testdata-sync.mjs` 的 `handoff()` 曾以本機 `testdata-handoff-state.json` 的 fixture 檔案雜湊變化判定 peer revision 是否抵達；此方式無法可靠表達版本因果關係。
2. manifest 的 `sourceHost` 曾被設計為固定區分來源端與接收端，與動態對等節點設計不符。
3. `scripts/test-testdata-peer-sync.mjs` 曾自行重寫分類函式測試，未直接呼叫正式同步路徑使用的決策邏輯。
4. 當時的修正方案曾考慮使用 applied/current/parent version 與 checksum、衝突 fail-closed，以及共用純函式；這些皆為設計沿革，非現行操作依據。

### 當時提出的設計方向

1. 以本機 applied version／checksum 與 Git current／parent version、checksum 判斷資料集因果關係。
2. `sourceHost` 僅供來源稽核，不控制節點角色或匯出權限。
3. 狀態檔與檔案 hash 僅供診斷，不單獨決定同步方向。
4. 本機獨立修改、兩端從相同 parent 各自修改、同版本不同 checksum、版本回退／缺號、parent mismatch、未知 baseline 等情況停止，不自動合併或覆蓋。
5. 比較資料列時可忽略 DB trigger 自動更新的時間戳，但不得忽略業務欄位差異；套用前於單一交易重新核對資料列與筆數。
6. 狀態分類應抽成正式程式可共用的決策邏輯，測試直接呼叫該邏輯。

## 設計沿革：2026-11-04 多節點時間基準方案

本節保留當時的多節點方案草稿，不表示它是現行時間戳模型。現行同步時間戳欄位、方向判斷及操作步驟以 83 為準。

- **節點模型（當時設計）：** 公司端、家用端及其他電腦皆為對等節點；Git `origin/develop` 作為已提交資料傳遞媒介。
- **基準時間（當時設計）：** 曾提議在 fixture manifest 加入 `baselineAt`，並以 `exportedAt` 相容舊資料；這不是現行 metadata 欄位定義。
- **方向分類（當時設計）：** 曾提議以基準時間新舊分類 upload／download，並搭配 checksum、版本鏈驗證；現行流程不以 checksum、revision、parent 或 Git commit 時間決定一般六表同步方向。
- **雙重保護（當時設計）：** 曾提出以 applied/current/parent 與父版資料列比對，並在 PostgreSQL transaction 內重新核對。
- **程式模組（當時設計）：** 曾規劃 `scripts/testdata-upload.mjs`、`scripts/testdata-download.mjs`、`scripts/lib/testdata-clock-sync.mjs` 等模組與相關測試；實際現況請查閱 83 及程式碼。
- **停止條件（當時設計）：** 曾包含 checksum 不一致、時間逆轉、版本鏈不連續、未知 applied state 與雙端修改停止等條件。
