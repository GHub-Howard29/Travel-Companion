# 雙電腦測試資料生命週期與自動同步規則

> **歷史設計文件，已由 2026-11-12 最新定案取代。** 本文件內舊版 testPurpose／fixture 標記門檻、checksum／內容指紋、revision／parent 鏈、時間戳新舊判斷及自動同步規則均不得再作為現行操作依據。現行同步只依共同 `last_synced_at` 與本地／Git `last_changed_at` 判斷基準後變更：本地有變更且 Git 無變更才可上傳；Git 有變更且本地無變更才可下傳；雙方都有變更一律停止，不覆蓋任一端。Git 必須保留基本測試環境與必要 seed／fixture。現行唯一規格為《[本機測試資料庫同步流程](../../83_本機測試資料庫同步流程.md)》及根目錄 `AGENTS.md`；本文件僅供歷史追溯。

## 目標

任一台電腦產生的合成測試資料，都要能被另一台電腦取得、套用、驗證及追蹤；資料在回歸測試明確解除前不得清除。解除後，依測試資料的生命週期標記，選擇刪除或封存但不再載入。

## Push／Pull 的自動化界線

- `git push`／`git pull` 只傳輸已提交的版本控制檔案，不會讀取或傳輸本機資料庫中的資料列。
- 版本化測試資料必須先由本機資料庫匯出成 fixture／變更集，經過敏感資料檢查後納入 Git；另一台取得 Git 版本後，再由本機同步入口套用。
- 可將安全的資料套用與驗證掛接到安裝完成的 Git hooks，但 hooks 必須由專案設定明確安裝，且必須允許停用／診斷。不得假設 clone 後 hook 自動存在。
- `push` 前不能盲目自動提交整個本機資料庫；匯出若遇到真實資料、秘密、無法識別的表、衝突或未完成測試資料，必須停止並提示人工處理。
- `pull` 後只允許自動套用已審查、已版本化且標記為可載入的測試資料變更集；不得自動清除本機資料。

## 資料生命週期

每個測試資料集應有穩定的 `fixture_id`、版本、建立來源電腦、狀態與回歸測試紀錄。狀態依序為：

1. `active`：測試資料可使用，必須同步到兩台電腦。
2. `regression_pending`：資料內容已固定，等待指定回歸測試；仍須同步並保留。
3. `released`：回歸測試通過且已明確解除使用；不可再自動載入為活躍測試資料。
4. `archived` 或 `deleted`：解除後依決策封存或刪除。封存資料只作為歷史記錄，不得由日常同步入口重新匯入。

資料集只有在兩台電腦均確認收到同一版本及相同狀態後，才能完成解除／清除。任一台離線或未確認時，另一台不得先刪除唯一可用的測試資料來源。

## 同步安全要求

- 只同步明確標記為合成測試資料的資料集；不得把整個 Supabase dump 當成 fixture。
- 匯入需具冪等性，重複執行不重複新增資料；套用前先驗證 fixture schema、版本、識別碼及相依關係。
- 不可把 Auth session、密碼、token、API key、secret、真實參與者個資、Storage 檔案本體或本機環境設定放入 fixture。
- 跨電腦不得依賴各自不同的 `auth.users.id`。若測試資料需要使用者關聯，應以合成角色映射建立本機關聯，或在匯入時明確重映射；無法安全重映射時停止。
- 不可對兩台獨立修改的資料採用 last-write-wins。只有已提交的 fixture revision 明確指定上一版 parentVersion／parentChecksum，且接收端資料庫逐列、逐筆數符合該父版本時，才允許在單一交易中完整替換該 fixture 的白名單資料範圍；父版本不符、同版 checksum 不同、接收端版本較新或資料存在額外編輯時，一律停止。
- 完整替換只涵蓋 manifest 明列的合成 fixture 範圍（該 Trip、shared checklist、其 checklist items、expenses、exchange purchases、other-info items）；不涵蓋私人 checklist、其他 Trip、一般資料或未列入 fixture 的資料表。
- fixture 內的刪除必須在新 revision 中明確呈現（例如 tombstone 或來源完整快照的列集合差異）；只有父版本完全吻合才可依新版本完整替換，不能把無父版本證明的「來源缺少某列」當成刪除依據。
- 不建立額外備份，除非使用者另行要求。

## 驗收條件

1. 電腦 A 新增合成行程資料，匯出後可在 Git 中看到精確變更集。
2. 電腦 B 取得同一版本並套用後，核心行程資料及關聯資料與 A 一致。
3. 重複套用同一變更集不會重複新增資料，也不會清除其他本機資料。
4. A、B 各自新增資料後，匯出／合併能保留兩邊變更；衝突會明確中止，不會靜默覆蓋。
5. `active`／`regression_pending` 資料不能被清除；只有通過回歸測試且明確標記 `released` 後，才可封存或刪除。
6. `released`／`archived` 資料不會被一般同步入口重新啟用。
7. 兩台電腦都完成實際驗證前，不可宣稱雙電腦同步流程完成。

## 2026-11-03 對等節點同步問題、修正方案與發布停止線

### 已確認問題

1. `scripts/testdata-sync.mjs` 的 `handoff()` 仍以本機 `testdata-handoff-state.json` 的 fixture 檔案雜湊變化判定是否收到 peer revision；這不是版本因果依據。當本機狀態檔缺失、過期或與 applied revision 不一致時，可能誤判接收／匯出方向。
2. manifest 的 `sourceHost` 原本被設計為固定區分來源端與接收端，與「家用端、公司端為動態對等節點」的定案相衝突。此欄位只能保留來源稽核用途，不得控制同步角色。
3. `scripts/test-testdata-peer-sync.mjs` 目前另行重寫分類函式測試，並未直接呼叫正式同步程式使用的判斷邏輯；該測試通過不能證明正式 handoff 路徑正確。
4. 前一輪只完成部分時間戳比較及 handoff 判斷修改；尚未完成對等節點同步、並行修改衝突保護、測試與權威文件統一。不可將局部測試通過記為完整完成。
5. `AGENTS.md`、本文件及相關同步流程文件仍有舊 sourceHost sender／receiver 敘述，必須一併更新，避免執行規則互相矛盾。

### 必須採用的修正方式

1. 以本機 applied version／checksum 與 Git 已提交 current／parent version、checksum 作唯一狀態判斷：
   - applied 等於 Git parent：Git 有新 revision 待接收；只有本機 DB 與 parent 資料相符時才可匯入。
   - applied 等於 Git current：目前基準一致；只有確認 DB 相對 current 有業務資料修改時，才可從 current 建立下一 revision。
   - applied 與 current／parent 皆不符、parent chain 斷裂或 baseline 不明：停止並回報衝突，不猜測、不匯出、不覆蓋。
2. 移除 `sourceHost` 對節點角色及匯出權限的控制；兩台電腦都必須能在同一規則下產生 revision 或接收 revision。
3. `testdata-handoff-state.json` 與檔案 hash 只可作診斷資訊，不可單獨判斷 peer revision 是否抵達或決定角色。
4. 對本機 DB 既有獨立修改、兩端從相同 parent 各自修改、相同 version 不同 checksum、revision 回退／缺號、parent checksum 不符、未知 applied baseline 等情況，全部採 fail-closed；不採 last-write-wins、不自動合併、不覆蓋。
5. 比較 DB 與 fixture 時可忽略資料庫 trigger 自動改寫的時間戳，但不得忽略任何業務欄位差異；匯入仍須在單一交易內再次核對父版本資料列及筆數。
6. 將 revision／peer 狀態判斷抽成正式程式可共用的純函式或可直接呼叫的邏輯，測試必須 import／呼叫該正式邏輯；不得在測試檔複製另一套模擬分類函式。
7. 更新 `AGENTS.md`、`docs/83_本機測試資料庫同步流程.md`、本文件及相關測試說明，統一採用動態對等節點、applied/current/parent 因果判斷、衝突停止條件及下列發布門檻；正式資料庫流程另依 `docs/81_正式Supabase資料庫Migration流程.md`。

### 雙機測試啟動與程式／fixture 發布停止線（2026-11-03 更新）

**受控雙機測試啟動限制已解除。** 公司端與家用端可依當下已核實的共同 revision 開始真實同步驗收；不得把任何特定版本（例如 V5）寫成永久基準，也不得再以「所有雙機案例尚未驗收」作為禁止開始測試的理由。

啟動條件：兩端確認相同 fixture revision／checksum、本機 applied state 與 DB 資料一致、操作目標為各自本機 loopback Supabase，且 Git 分支／upstream／工作樹／遠端狀態安全。版本標籤只供閱讀；唯一基準是實際 manifest checksum、parent chain 與各端 applied state。

目前紀錄的狀態為 Git V5、家用端 DB V5；公司端 DB V6 為使用者回報，尚未在家用端工具獨立核實且尚未提交 Git。公司端 V6 只有在其 applied state = Git V5、parentVersion = 5、parentChecksum = Git V5 checksum，並通過 fixture 結構、筆數、checksum、敏感欄位及資料差異驗證後，才可作為下一版候選安全發布。條件不符或無法證明時，停止發布，不得覆蓋家用端。

一般同步契約：A 只有在 applied = Git current 且 DB 確有業務資料變更時才建立 current+1，parent 指向 current；安全驗證通過後才發布。B pull 後執行 `npm run db:sync:local`，只有在 applied = incoming parent 且本機 DB 仍與 parent 相符時才匯入 incoming current，並更新 applied state；接收不會再升版。B 若接收後無資料變更，handoff 必須回報 unchanged，不建 revision、不 commit／push，Git 維持 current；B 若有業務資料變更，才建立下一版並安全發布。每一步核對 revision、parent checksum、applied state 與業務資料；無業務資料變更不得無故升版。

以下衝突保護不因解除測試啟動限制而放寬：未知 baseline、同版不同 checksum、parent mismatch、版本回退／缺號、兩端從相同 parent 各自修改、接收端有獨立業務修改，均須 fail-closed，保留現況、不覆蓋、不自動合併、不採 last-write-wins。只停止發生衝突的該輪，不阻止其他符合條件的測試案例。

### 程式／fixture 發布停止線

真實雙機測試可以開始，但這不代表可任意推送尚未驗證的程式或 fixture。程式／文件 commit、fixture upload 與 fixture download 是三個獨立操作，分別使用一般 Git 口令、`/上傳資料庫`、`/下載資料庫`；歷史完整口令 `commit/push/資料庫` 已廢止其資料庫交接作用，不再觸發 fixture publish。所有動作仍須通過根目錄 `AGENTS.md` 的工作樹、分支、upstream、遠端 fast-forward、fixture 格式與安全檢查；不授權正式 DB 部署、破壞性操作或衝突覆寫。

本紀錄只定義驗收及發布界線，不代表雙機驗收已完成。

## 2026-11-04 三方以上時間基準同步規格

本節新增的規格取代本文件前述以雙機 `applied/current/parent` 作為唯一方向判斷的描述；前述內容保留作為歷史設計與既有驗收證據，不應再當作新入口的完整操作說明。

- **節點模型：** 公司端、家用端及第三台以上電腦均為對等節點；沒有固定 sender／receiver。`sourceHost` 僅作稽核欄位。每台節點各自維護本機 loopback Supabase，Git `origin/develop` 傳遞唯一已提交 fixture 基準。
- **基準時間：** fixture manifest 的 `baselineAt` 使用 UTC ISO 8601，代表該 fixture 業務內容基準建立／更新時間；不是任何 row `created_at`／`updated_at`。舊 manifest 尚無 `baselineAt` 時，以 `exportedAt` 相容讀取。舊 applied state 缺基準時間時，依 applied version/checksum 回查 Git 歷史 manifest；查不到即停止。
- **方向分類：** 本機基準時間小於 Git manifest 時間 → download；本機大於 Git → upload；時間相同且 checksum 一致 → unchanged；時間相同但 checksum 不同 → conflict 並停止；本機沒有可證明的基準 → 只有本機 DB 已與 Git current fixture 完全一致時可採認 applied baseline。空白 DB 或其他資料差異一律停止，不根據空白狀態猜測基準或自動 bootstrap 覆寫。
- **雙重保護：** 時間戳只決定方向。實際上傳前仍需證明本機 applied version/checksum 與 Git current fixture 相符；實際下載前仍需證明 Git current 的 parent version/checksum 與本機 applied 相符，並確認本機資料列逐筆等於 parent（忽略 DB trigger 的 created_at／updated_at，但不能忽略業務欄位）。同時在單一 PostgreSQL `DO` transaction 再鎖定／比對 parent rows、筆數及業務鍵，才可套用 fixture 擁有欄位；owner／creator／attachment 等本機欄位保留。
- **獨立上傳程式：** `scripts/testdata-upload.mjs`，npm script `testdata:upload`。只讀本機 loopback DB 的 `tc-test-*` 合成 fixture、驗證敏感欄位與 checksum，限定 stage manifest/data 後 commit/push `origin/develop`；不執行 download/import。
- **獨立下載程式：** `scripts/testdata-download.mjs`，npm script `testdata:download`。只讀 Git 已提交 fixture，使用本機 loopback DB，依 `baselineAt` 分類；實際套用共用 `scripts/lib/testdata-download-apply.mjs` 的交易式匯入器；不執行 pull/commit/push。
- **共用時間協定：** `scripts/lib/testdata-clock-sync.mjs` 提供 `classifyBaselineSync()`、`createBaselineRecord()` 與固定資料列排序後的 checksum。`scripts/test-testdata-clock-sync.mjs` 驗證 download/upload/unchanged/conflict/bootstrap/validation。
- **三方循環：** 任一節點本機資料有變更時可成為上傳節點；其他節點各自 fast-forward pull 後執行下載；下一節點可再次修改並上傳。每台節點使用同一規則，不需配置節點角色。
- **停止條件：** 同時間不同 checksum、時間逆轉／manifest 無效、version/parent/checksum 不連續、本機 applied state 未知、本機資料不等於 parent、不同節點從同一 parent 各自修改，皆停止人工處理；不採 last-write-wins、自動合併、reset、force-push。
- **驗收狀態（2026-11-04 更新）：** Node 22.23.2 語法檢查通過；`test:testdata-clock-sync`、`test:testdata-import-sql`、`test:testdata-download-policy`、原 `test:testdata-revision`／`test:testdata-peer-sync` 均通過；V5 active fixture 靜態驗證、`verify:docs-links`（130 Markdown／273 targets）與 `git diff --check` 通過。此等證據不代表完成三台真實 Supabase DB 驗收；尚需 A→B→C→A、反向輪替、current baseline 採認、parent revision 下載、同時間 checksum 衝突及 parent 不符停止等實際測試。未知 applied baseline 的空白 DB 不自動 bootstrap；必須先建立可證明的共同基準。未完成實機測試前不得宣稱三方同步已驗收完成。

## 目前實作狀態

- `npm run db:sync:local` 已整合成本機標準同步入口：確認 `develop` 與 Supabase loopback、套用 pending migrations、先呼叫 `npm run testdata:handoff` 偵測並驗證本機合成測試資料變更，再匯入已驗證的版本化合成 fixture、準備標準回歸資料並執行本機回歸驗證。不執行 reset、不清除本機資料，也不自動 pull／commit／push。
- `npm run testdata:export -- tc-test-<name>` 僅允許 `tc-test-` 命名且 `content.__testFixture=true` 的行程；只查詢本機 loopback Supabase，匯出限定表與欄位，排除使用者關聯／附件資料，拒絕非空的 `participants`，並檢查疑似 email、token 與敏感欄位。
- `npm run testdata:validate -- supabase/test-fixtures/tc-test-<name>` 會檢查 schema、狀態、表清單、識別碼、依賴關係、每表筆數、敏感資料與 checksum。
- `npm run testdata:validate:active` 會唯讀掃描所有現存 `tc-test-*` fixture，並使用目前版 `readFixture()` 驗證所有 `active`／`regression_pending` fixture 的 manifest 必填欄位、revision parent link、表結構、筆數、敏感資料及 checksum；任一有效使用中的 fixture 不符合要求就回傳失敗。這是提高 Fixture manifest／revision 格式要求時，`commit/push/資料庫` 流程在一般 commit 前的必要相容性檢查，不連線或修改資料庫。
- `npm run testdata:import:all` 只匯入 `active`／`regression_pending` fixture；`released`／`archived`／`deleted` 不會由一般入口重新載入。revision 使用正整數遞增（不使用浮點數），例如 revision 9、10、11 可顯示為 `V0.09`、`V0.10`、`V0.11`。接收端保存本機已套用的 revision／checksum：相同版本同 checksum 驗證後略過；相同版本不同 checksum、收到舊版本或版本鏈不連續皆停止。新版本必須指向前一版 checksum，並在單一 PostgreSQL `DO` transaction 中再次核對父版資料列及數量，完全吻合才會更新 fixture 擁有的欄位、補入新列，並移除父版中存在但新快照明確省略的 fixture 列；資料庫本機 ID、建立者、owner 與附件欄位會保留。本機若已等於新版本，只補記已套用狀態。資料庫不是父版也不是新版本時，視為本機獨立修改或狀態不明，拒絕覆蓋。
- **對等節點規則（取代舊 sourceHost 角色規則）：** 家用端與公司端是同等節點，任一端都可能先產生新 revision，也都可能接收另一端的 revision。manifest 的 `sourceHost` 僅供稽核追蹤，不得用來決定誰可匯出、誰只能接收；不得將電腦名稱寫死為 sender／receiver。
- **唯一版本判斷依據：** 以本機 `testdata-applied-state.json` 記錄的 applied version／checksum，對照 Git 已提交 fixture 的 version／checksum 及其 `parentVersion`／`parentChecksum` 判斷狀態。本機 applied 與 Git parent 完全相符，代表 Git 有下一版待接收；applied 與 Git current 完全相符，代表雙方基準一致，才可檢查本機資料是否有新修改並建立下一版。版本與 checksum 不吻合、父鏈斷裂或狀態無法證明時，一律 fail closed，不猜測、不匯出、不覆蓋。
- **本機 handoff 雜湊狀態的定位（2026-11-03 修正）：** `testdata-handoff-state.json` 及 fixture 檔案雜湊只保留作為診斷／稽核資訊；正式 `handoff()` 不再以 `filesMatchPrevious` 或檔案 hash 決定 peer revision 是否抵達。方向判斷改由 `scripts/lib/testdata-revision.mjs` 的 `classifyPeerHandoff()` 依 applied/current/incoming parent version 與 checksum，以及本機 DB 對父版資料的比對結果決定。`scripts/test-testdata-peer-sync.mjs` 直接 import 並測試同一正式函式。接收後的實際資料套用仍由 `importAllFixtures()` 再次核對 Git parent 的逐列資料與筆數，並在單一 transaction 執行；classifier 通過不代表略過 import 保護。
- **衝突保護：** 只有本機 DB 資料與已知父版本逐列相符（允許資料庫 trigger 自動產生／更新的時間戳差異）時，才可套用 Git 新 revision；若本機 DB 已有獨立修改，即使 applied version 指向父版，也必須停止。兩端從相同父版本各自修改、同版本不同 checksum、舊版回退、revision 缺號／父 checksum 不符、未知 applied baseline、DB 既非 parent 亦非 current 等情況，全部明確報衝突，不採 last-write-wins、不自動合併、不覆蓋。時間戳忽略規則只適用於資料列基準比較，不得忽略業務欄位差異。
- `npm run testdata:handoff` 應依上述 revision 因果關係動態決定接收、保持不變、匯出下一版或停止衝突；一般模式不得自動 stage／commit／push。
- `npm run testdata:handoff:publish` 是同一個 `testdata-sync.mjs` 的安全交接模式：先 fetch 遠端並確認 develop/upstream、本機提交狀態與 fixture 安全；允許保留既有未 staged 的非 fixture 變更，但會比較交接前後狀態，只 stage 本次產生的 fixture manifest/data，然後自動 commit／push `origin/develop`。已有 staged 變更、既有 fixture 變更、非預期差異、衝突、敏感資料或遠端變更都會阻止後續寫入；沒有變更時不建立空 commit。此流程不是正式發布，不 merge `main`、不部署，接收端仍執行 `git pull --ff-only origin develop` 後再跑 `npm run db:sync:local`。
