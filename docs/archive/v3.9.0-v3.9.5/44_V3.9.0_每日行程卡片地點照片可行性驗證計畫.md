# V3.9.0 每日行程卡片地點照片可行性驗證計畫

- 狀態：Product Owner 已確認 V3.9.0 同時納入 Google 搜尋候選暫態索引照與 Commons 每日卡片管理者選圖；正式 UI 尚待模擬圖核准
- 啟動日期：2026-09-12
- 已發布基線：V3.8.2
- 發布：本階段不建立候選版本、不修改 metadata、不部署

## 1. 驗證目標

- 判斷每日行程卡片是否能以合法、穩定、成本可控且不明顯拖慢 PWA 的方式顯示地點照片。
- 比較「自動取得地點照片」、「管理者手動設定封面」與「不新增照片」三種方向。
- 補充比較 Pexels、Pixabay、Wikimedia Commons／Openverse、Unsplash 等免費來源，避免把自動照片等同 Google Places。
- 獨立驗證「地點搜尋候選索引照片」是否能提高 `placeId` 選擇正確率；確認可行後才深入評估 UI、效能與成本。
- 在任何正式 UI、可見文案、資料庫、Storage 或權限變更前，提供足以讓 Product Owner 決策的證據。

## 2. 必查議題

### 照片來源與授權

- 盤點候選照片來源的正式文件、服務條款、可使用情境與禁止事項。
- 確認 attribution 的文字、位置、連結、顯示時機及是否能與現有卡片版面相容。
- 確認照片識別、網址或影像本體能否保存，以及各自的快取與更新期限。
- 不以搜尋引擎結果、非官方轉載或未確認授權的圖片作為正式來源。

### 架構與資料邊界

- 盤點目前 `ItineraryItem.place.placeId`、地點搜尋 Edge Function、CSP、離線快取與 Service Worker 的可重用邊界。
- 比較瀏覽器直接載入、受控後端代理及管理者手動上傳／選擇方案的安全與維運成本。
- 確認是否需要新增資料欄位、Supabase Storage、RLS、刪除流程或資料 migration；本階段只記錄，不套用。
- 不把 API 金鑰、完整照片網址或未授權資料寫入前端 bundle、Git 或測試紀錄。

### 使用體驗與降級

- 定義有照片、無照片、載入中、載入失敗、離線與照片失效時的最低可接受行為。
- 驗證只載入目前可見卡片、快速切換 Day、長行程清單及返回前景時不重複浪費請求。
- 確認照片不影響既有時間、類型、地點、說明、路線資訊及管理操作的可讀性。
- 若進入正式 UI 設計，必須先製作桌面與 390×844 手機模擬圖並取得 Product Owner 確認。

### 效能、離線與成本

- 以無照片基線和候選方案比較首次載入、主要內容可見時間、傳輸量、記憶體與捲動流暢度。
- 測試代表性的 0、1、多張可見照片與長 Day 清單，不得只測單一卡片成功情境。
- 記錄冷啟動、暖啟動、離線重開、弱網路與快取失效行為。
- 建立每趟旅程、每日、每位活躍使用者及每月的請求量與費用估算，列出免費額度及超額風險。

## 3. 可執行的驗證工作

- 閱讀並引用實作當下最新的官方 API、授權、attribution、快取與計價文件。
- 建立不進入正式 App 的最小技術 spike 或量測治具；不得使用 production 寫入或真實使用者敏感資料。
- 使用既有公開／測試行程資料量測桌面與 390×844 viewport；不得提前加入可見於正式 App 的元件或文案。
- 整理候選方案比較表、風險、成本試算、量測結果與明確建議。
