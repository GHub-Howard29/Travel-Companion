# V3.9.3 效能與建置優化設計（由 V3.9.2 延後）

> 因 V3.9.2 改為 BUG031 緊急修正版，本文件內容移至 V3.9.3；驗證聚合與啟動量測已於 V3.9.3 正式發布。

## 1. 測試腳本 (`verify:*`) 瘦身規劃

### 1.1 盤點分析
目前 `package.json` 包含超過 35 個 `verify` 指令，其中多數為舊版專項驗證，導致 `npm run build` 前置驗證時間過長。

### 1.2 已完成策略
- **分級歸檔**：
    - **核心驗證 (保留)**：`update-policy`, `release-history`, `browser-security`, `itinerary-*`。
    - **歸檔驗證 (移出 build 流程)**：`v362-trip-lock`, `v363-front-end`, `v364-*`, `v365-performance` 及 V3.9.1 之前的專項測試。這些驗證改為在需要進行深度回歸時手動執行，而非強綁在 `npm run build`。
- **流程優化**：17 個 V3.9.1 專項由 `npm run verify:v391:all` 統一執行；一般 build 移除 V3.6.2–V3.6.5 重型專項，但完整回歸仍可個別執行。
- **型別閘門**：一般 build 同時執行 `tsc -p tsconfig.app.json --noEmit` 與 Node 設定檢查。

---

## 2. 離線冷啟動與載入效能優化

### 2.1 觀測指標（已建立 Baseline）

- `src/main.tsx` 記錄 `tc_app_bootstrap_start`。
- App 完成既有啟動流程時只量測一次 `tc_app_bootstrap_duration`。
- 本版只建立端到端啟動基線，不宣稱已優化 Service Worker、IndexedDB 或 Trip 載入。

### 2.2 優化方向
- **資料分流**：評估在離線冷啟動時，是否應採用「分頁載入」或「只載入當前 Day」的方式，減少一次性讀取大量歷史行程資料對 IndexedDB 的壓力。
- **快取機制**：檢視 Service Worker 策略，確保關鍵資產在冷啟動時優先獲取。
