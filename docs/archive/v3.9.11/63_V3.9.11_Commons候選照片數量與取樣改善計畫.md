# V3.9.11 Commons 候選照片數量、取樣與選圖體驗改善計畫

> 狀態：V3.9.11 已完成 App／Edge Function、靜態與完整建置、loopback Edge、桌面與 390×844 候選 UI、回歸技能、單次外部 Wikimedia 矩陣、正式部署與發布
>
> 規劃日期：2026-09-25
>
> 類型：Patch／既有照片功能補強

## 1. 問題與目標

V3.9.1 導入 Wikidata／Wikimedia Commons 實體導向精準篩選後，錯誤實體與授權不明照片較不容易混入候選，但目前九州第一天的實際使用顯示：既有五張 Commons 代表照片都不是從此精準流程挑出，部分景點即使在 Commons 網頁可找到多張可用照片，App 仍可能只顯示極少候選，無法讓管理者有效人工選圖。

V3.9.11 的目標是保留授權、來源、尺寸與人工確認安全線，同時把「精準證據」與「可供人工判斷的相關照片」分層，增加可選照片數量，並修正目前選圖流程中的四項可觀察問題。本版照片來源仍只包含 Wikimedia Commons 與自行上傳，不新增第三方圖庫。

## 2. 四項問題與定案方向

| 問題 | 定案方向 |
|---|---|
| 自行上傳照片在行程卡片顯示「自行上傳」備註 | 只移除卡片 76×76 縮圖下方的「自行上傳」文字。Commons 照片仍保留「照片來源」連結；來源選擇、裁切確認與放大檢視中的來源資訊維持。 |
| 照片已載入仍顯示「無法讀取這張照片」 | 視為載入狀態生命週期錯誤，不以隱藏文案處理。後續實作須避免成功 `onload` 後清空暫存 `Image.src` 又觸發既有 `onerror`，成功後解除事件處理並清除舊錯誤；裁切預覽另有明確載入／失敗狀態，未完成或真正失敗時不得儲存。 |
| 候選不足仍可按「換一批」 | 每批預定 6 張。當去重與篩選後少於 6 張時，不提供下一批 token，前端直接隱藏「換一批」，並提示已列出目前可用照片；精準與人工判斷候選均適用。 |
| 同名地點要求使用者判讀搜尋範圍、描述與 QID | 移除公開的地點範圍選擇介面。唯一實體只在背景提供精準證據；多實體或無唯一實體時不得擅自選 QID，直接以原搜尋詞進入 Commons 模糊搜尋，結果標為需人工確認。 |

## 3. 候選取樣與分層

### 3.1 精準候選

- 來源包含 Wikidata `P18`、直接 `P373` Commons Category、直接 `P180` depicts，以及同一實體正式名稱／既有別名的精確描述命中。
- 維持現有授權白名單、作者與來源頁、原圖尺寸、排除明確錯誤實體及人工確認規則。
- 唯一 QID 解析可在背景執行，但不再向使用者顯示技術性的範圍設定。

### 3.2 需人工確認候選

- 使用 Commons MediaSearch、caption／全文、已取得的官方名稱或別名，以及直接分類的一層相關分類擴充候選。
- 多實體或找不到唯一實體時，直接以使用者原始搜尋詞走此層；不得暗中選擇其中一個 QID，也不得把候選標成精準命中。
- 保留授權、來源、作者、尺寸、去重與人工裁切硬性條件；放寬的是實體證據門檻，不是著作權或安全門檻。
- 介面與精準候選分區呈現，明確表示需要管理者自行確認是否適合作為代表照片。

Commons MediaSearch 會綜合結構化資料、caption、Commons 分類、全文與 Wikidata 名稱；`haswbstatement:P180=QID` 可搜尋直接描繪指定實體的檔案。參考：[Commons MediaSearch](https://commons.wikimedia.org/wiki/Commons%3AMedia_search)、[Commons Depicts](https://commons.wikimedia.org/wiki/Commons%3ADepicts/en)。

### 3.3 每批數量與換批

- 一次搜尋先收集精準候選，再以需人工確認候選補足同一批最多 6 張；兩層分區顯示，不混淆證據強度。
- 只有實際回傳 6 張不重複且可顯示的候選、仍有上游 continuation 且 session 預算未耗盡時，才可提供下一批 token。
- 0～5 張時直接視為目前可用候選已全部列出，不顯示「換一批」，也不為可能存在但尚未證實的後續照片繼續耗用流量。
- 跨批與跨層以 canonical `fileTitle`／page ID 去重；修改搜尋詞或關閉後重開會重置 session 與已看過集合。

## 4. 公開契約調整方向

- Commons 搜尋公開契約升版，候選增加 `tier: "precise" | "manual-review"`。
- `entityChoices`、前端 `selectedEntityQid` 與公開 `entity-ambiguous` 選擇流程退出使用者契約；內部仍可記錄解析結果供取樣決策與測試。
- 只有符合第 3.3 節條件時才回傳下一批 token；精準／人工判斷候選若分開續頁，token 必須明確綁定候選層級。
- token 維持不透明，綁定搜尋詞、契約版本與 session；舊契約的快取及 token 不得跨版沿用。
- 專案級 20 次上游請求／分鐘、900 次／日及單一上游鎖維持不變；本規劃不授權提高額度。

## 5. UI 文案與預覽閘門

候選區標題、分層說明、候選不足提示、模糊搜尋提示及錯誤文案已於 2026-09-25 核准；排列須沿用既有設定照片對話框、候選卡片網格、操作列與響應式結構，不另建新版面。核准內容涵蓋：

1. 同時存在精準與需人工確認候選。
2. 只有 1～5 張候選且不顯示「換一批」。
3. 多個同名實體直接顯示模糊候選，不出現 QID／範圍選擇。
4. 自行上傳的裁切預覽載入中、成功及真正失敗狀態。

原始預覽中的並排狀態面板只供文案審核，不是 App 排列規格；程式實作已依核准要求沿用既有畫面。

## 6. 驗證計畫

### 6.1 靜態與本機契約

- 自行上傳成功後不得出現讀取失敗；真正無法解碼時才顯示錯誤，且失敗後可返回重選。
- 行程卡片的自行上傳縮圖下方無來源備註；Commons 照片仍有來源連結。
- 0～5 張不提供下一批 token、不顯示「換一批」；6 張且確有後續資料時才顯示；跨批不得重複。
- 唯一實體可產生精準候選；多實體／無唯一實體直接產生人工判斷候選，前端不得顯示 QID 選擇。
- 桌面與 390×844 驗證鍵盤順序、焦點陷阱與返回、讀屏名稱、水平溢位、裁切、取消及失敗解鎖。

### 6.2 九州第一天人工矩陣

- 以正式站「英鈦日本九州極上五日」第一天為固定案例。
- 五個已有 Commons 封面的項目作正向對照，其他尚未設定照片的項目作長尾案例。
- 比較目前與新版的精準候選數、人工判斷候選數、唯一檔案數、既有代表照片可觸及性、上游請求數、延遲、淘汰原因與人工代表性判斷。
- 若五張既有代表照片仍完全無法由核准搜尋詞觸及，停止發布並確認漏失位於搜尋、分類、metadata、授權、尺寸或預算哪一層。

### 6.3 回歸技能與外部測試邊界

- `travel-companion-regression` 已新增「不足 6 張隱藏換批」與「歧義實體直接模糊搜尋」的 loopback fixture；全部保持零外部流量。
- 自行上傳照片依 2026-09-25 核准邊界，以程式修正及靜態生命週期契約通過為完成條件，不要求實際選檔驗證。
- 真實 Wikimedia 矩陣每次都須取得新的單次授權，事前列明查詢集合、請求上限、逾時、重試與寫入政策；不得寫入 production Trip、Storage、快取或資料庫。
