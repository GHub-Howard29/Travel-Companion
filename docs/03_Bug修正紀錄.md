## 2026/06/30

### BUG001

問題：

離線新增帳目後，Pending（待同步）數量沒有立即更新。

例如：

- P1 → 顯示 1（正常）
- P2（離線新增）→ 應顯示 2，但仍顯示 1。

恢復網路、重新整理或 F5 後，數量才恢復正常。

原因：

資料新增成功、Pending Queue 正常建立，但 Pending Badge 沒有立即重新計算，屬於 UI 更新時機問題。

修正方式：

調整 Pending Badge 更新流程，新增、修改、刪除帳目時立即重新計算 Pending 數量。

狀態：

✅ 已修正（V2.0）

---

### BUG002

問題：

同步完成後，如果修改附件，Pending 數量未立即更新。

原因：

附件修改未同步更新 Pending 狀態。

修正方式：

附件新增、修改、刪除時，同步更新 Pending Queue。

狀態：

✅ 已修正（V2.0）

## 2026/07/06

### BUG003

問題：

手機點選附件時，只出現拍照功能，沒有提供相簿或檔案選擇。

電腦則只有檔案選擇，沒有拍照功能。

2026/07/11 補充：

當時新增記帳本資料時，手機端附件入口需重新確認；預期行為為行動裝置同時支援「使用手機拍照」與「選擇既有照片 / 檔案」。

2026/07/12 補充：

已由 BUG011 的修正取代單一檔案入口做法，新增與編輯帳目都改為「拍照」與「相簿」兩個明確入口。

原因：

不同裝置對 `<input type="file">` 的支援方式不同，目前尚未針對行動裝置進行最佳化。

修正方式：

- 新增帳目與編輯帳目兩個附件入口拆成「拍照」與「相簿」。
- 「拍照」入口使用 `capture="environment"`。
- 「相簿」入口保留一般 `accept="image/*"`，維持既有照片壓縮與同步流程。

狀態：

✅ 已修正（2026/07/12）/ 需手機實機回歸

### BUG004

問題：

Checklist 勾選狀態會影響其他旅程。

例如：

A 行程勾選完成後，B 行程也會顯示相同勾選結果。

原因：

Checklist 尚未依旅程建立獨立資料。

- `guest` / `user` 查看共同清單時顯示乾淨未勾選版本；`trip_editor` / `super_admin` 可同步勾選狀態。

狀態：

✅ 已修正（V3.0）

### BUG005

問題：

Checklist 勾選後，重新整理（F5）會全部消失。

原因：

目前僅使用 React State 保存。

2026/07/13 補充：

共同清單目前已使用 `localStorage` 保存進度，並已接上 Supabase 最小雲端同步；重新整理後會保留可同步角色的雲端狀態與本機 fallback。

修正方式：

- 建立 `checklistStorage`，以 `travel_companion_checklist_{tripId}` 保存共同清單進度。
- `checklistService` 統一讀寫本機進度，UI 不直接操作 storage key。
- `useChecklistState` 讀取 Supabase shared checklist 後，會同步寫回本機進度。

狀態：

✅ 已修正（V3.0）

### BUG009

問題：

iOS 手機使用瀏覽器開啟時，不容易發現可安裝成 App 的入口；Android Chrome 會顯示安裝選項。

- Android 可用原生安裝提示時，點選「立即安裝」觸發瀏覽器安裝流程。
- iOS 顯示「分享 → 加入主畫面」操作提示。
- 提示顯示 3 秒後自動縮回成小按鈕。

狀態：

✅ 已修正（2026/07/12）/ 需 iOS Safari 與 Android Chrome 實機回歸

### BUG010

問題：

記帳本新增帳目並附加照片後，iOS 手機容易出現照片同步失敗。

2026/07/12 補充：

同步失敗後，再次按同步可能顯示同步完成，但清單內仍顯示照片同步失敗，且無法點選開啟照片。

原因：

第一次同步失敗後，雲端狀態會變成 `upload_failed`。重新載入帳本時，程式只會替 `local_pending` 狀態恢復 IndexedDB 裡的本機照片 ID，沒有替 `upload_failed` 恢復，因此失敗項目看起來仍有附件名稱，但實際上失去可重試上傳的本機照片連結。

原始 iOS 同步失敗原因仍需實機追查，可能與 iOS Safari / PWA 在 IndexedDB 暫存照片、Canvas 壓縮、背景切換或 Supabase Storage 上傳期間的網路狀態有關。

修正方式：

- `upload_failed` 與 `local_pending` 一樣會在重新載入時嘗試恢復 IndexedDB 本機照片 ID。
- 再次同步時，`upload_failed` 若仍找得到本機照片，會重新上傳。
- 若找不到本機照片，不再誤顯示同步成功，改提示需重新拍照或選擇照片。
- 同步結果提示改為顯示成功與失敗筆數。

狀態：

✅ 已部分修正（2026/07/12）/ 原始 iOS 上傳失敗原因仍需實機蒐集錯誤訊息

### BUG011

問題：

記帳本照片附件在 Android Chrome 只出現相簿，沒有明確的拍照入口；iOS 會出現拍照或相簿選擇。

不同瀏覽器對單一 `<input type="file" accept="image/*">` 的行動裝置選擇器呈現不同，Android 不一定自動提供相機。

- 「拍照」入口使用 `capture="environment"`，優先開啟後鏡頭。
- 「相簿」入口保留一般 `accept="image/*"`，供使用既有照片。

狀態：

✅ 已修正（2026/07/12）/ 需 iOS 與 Android 實機回歸

### BUG012

問題：

多人共用帳本時，一人新增或刪除單筆帳目，另一人的手機不會即時更新，需重新整理或重新進入才看得到。

原因：

記帳本目前只在進入頁面、指定操作後重新讀取資料，尚未監聽 Supabase 資料變更，也沒有固定時間刷新。

修正方式：

- 共用帳本加入 Supabase Realtime 監聽 `expenses` table 的同旅程變更。
- 若 Realtime 未啟用或網路狀態不穩，保留 30 秒定時刷新備援。
- 視窗重新取得焦點、App 回到前景、恢復連線時立即刷新帳本。

狀態：

✅ 已修正（2026/07/12）/ 若 Supabase Realtime 未開啟，會以 30 秒輪詢更新

### BUG013

問題：

非強制更新時，使用者按「稍後更新」後，App 會把新版標記為已看過；之後使用者重新整理頁面或重新開啟 App，不會再次提醒更新，導致仍需手動清除暫存才容易切到最新版本。

原因：

更新提示的 `dismiss` 流程共用「已讀版本」寫入邏輯，稍後更新與確認已看過版本沒有區分。

修正方式：

- 非強制更新的稍後更新只關閉本次提示，不寫入已讀版本。
- 馬上更新會先清除 App Cache Storage，再 reload 或觸發 Service Worker 更新。
- 更新提示補上未儲存資料警語，提醒使用者先儲存表單內容。
- 強制更新仍維持不可稍後。

狀態：

✅ 已修正（2026/07/13）/ 需安裝版 PWA 實機回歸

### BUG014

問題：

共同帳本分攤狀態在金額不能整除時會出現應收與應補總額不一致。例如 5 元由 2 人分攤時，畫面曾出現代墊者應收 2、未代墊者應補 3，多出 1 元無法解釋。

原因：

畫面直接以 `paid - Math.round(total / 人數)` 計算每個人的狀態，四捨五入後的平均值加總可能大於或小於實際總支出。

修正方式：

- 先計算每位成員的實際應分攤金額，再用已墊金額扣除應分攤金額。
- 分攤狀態顯示「應分攤」金額，摘要文字改為「平均參考」。
- USD / EUR 以分為最小單位分配，避免小數加總不一致。
- TWD / JPY / KRW 採整數進位規格；不能整除時由應分攤者無條件進位負擔，代墊者承接零頭盈餘。

狀態：

✅ 已修正（2026/07/13）/ 需以 TWD、JPY、KRW、USD、EUR 帳本資料回歸

### BUG015

問題：

Android PWA 點擊「馬上更新」後，更新提示可能停在畫面上或沒有自動重新載入；iOS Safari 網頁模式也因先前只允許安裝版 App 顯示更新提示，導致怎麼刷新都不會出現更新提醒。

原因：

馬上更新流程主要依賴 Service Worker 更新函式自行觸發 reload，部分 Android PWA 容器未必會完成重新載入。另一方面，更新提示顯示條件原本只允許 standalone / fullscreen / iOS standalone / Android app referrer，排除了 iOS Safari 網頁模式。

修正方式：

- 馬上更新流程加入 1.5 秒 reload fallback，避免 Service Worker 更新流程沒有自行 reload 時卡住。
- 更新提示顯示條件改為安裝版 App 或 iOS 裝置可顯示，讓 iOS Safari 網頁模式也能收到版本提示。
- 桌面一般瀏覽器仍不主動顯示更新提示，避免日常開發或一般網頁瀏覽干擾。

狀態：

✅ 已修正（2026/07/13）/ 需 Android PWA 與 iOS Safari 實機回歸

## 2026/07/19

### BUG016

問題：

Other Info 與領隊導遊資訊的資料刪除後，在某些舊雲端資料情況下重新整理會再次出現。

原因：

舊雲端列可能沒有 `client_item_id`，既有刪除流程僅以該欄位軟刪除；刪除失敗時，雲端合併資料又會覆蓋目前的卡片清單。

修正方式：

- 雲端讀取排除 `deleted_at` 不為空的資料。
- 支援以 `cloud_<資料列 ID>` 對應舊列並執行軟刪除。
- 在 Trip detail 保存 `isDeleted` 刪除標記，作為雲端舊列無法更新時的同步備援。

狀態：

✅ 已修正並完成重新整理回歸（V3.2.1）

### BUG018

問題：

登入後只預載目前行程，離線切換到尚未載入私人清單的另一行程並新增項目，恢復連線後可能以這份不完整本機快照覆蓋既有雲端私人清單。恢復連線後，該行程的共同清單權限／同步文案也可能要切換行程才更新。

原因：

- 私人清單 pending 只保存 revision，沒有保存第一次離線修改前看得到的項目基準，無法區分「使用者刪除」與「本機根本未載入」。
- 行程權限載入沒有以 React `isOnline` 為依賴，恢復連線時不會主動重新查詢目前行程權限。

修正方式：

- pending 同時保存第一次修改前的項目 ID；重連時先讀取雲端，以基準進行三方合併，保留本機從未載入的雲端項目並疊加離線新增。
- 舊格式 pending 採資料不遺失優先，保留雲端與本機項目的聯集。
- 所有直接寫入也改走相同安全同步流程，避免預載尚未完成時在線新增造成覆蓋。
- 恢復連線時重新載入目前行程權限，讓共同清單同步文案不需切換行程即可更新。

狀態：

🟡 已修正，待多行程離線新增／重連實機回歸（V3.4.1）

## 2026/08/23

### BUG019

問題：

V3.4.5 部署後，Android 手機一般瀏覽器的上方狀態列／網址列與下方系統導覽列會持續顯示明亮藍色；已安裝 PWA 進入 App 後，最上方系統狀態列也會持續顯示同一藍色。原生 Splash 進入 App 時仍可感覺整張畫面跳動；藍色原本只用於啟動銜接，不應在 App 完成載入後持續套用到手機系統介面。

原因：

- `index.html` 的 `<meta name="theme-color">` 設為 `#54B6E7`，Android Chrome 會用它著色一般瀏覽器的上／下系統介面。
- PWA manifest 的 `theme_color` 與 `background_color` 也使用 `#54B6E7`，已安裝 PWA 會將藍色套用到啟動畫面及最上方狀態列。
- `html`、`body`、`#root` 的背景持續為藍色，頁面回彈或 App 內容未完全覆蓋視窗時也可能露出藍底。
- V3.4.1 沒有網頁 Splash 或固定亮藍根背景，manifest 使用深藍主題色與接近 App 內容的米白背景；V3.4.5 則讓亮藍背景、中央原生圖示、綠色 App 頁首與白色內容在極短時間內直接互換，雖然沒有 CSS 動畫，仍會放大視覺重心與整體畫面切換感。

預計修正：

- 將「載入階段藍色背景」與「App 完成載入後的瀏覽器／PWA 系統列顏色」分開管理。
- 保留原生 PWA Splash 所需的藍色啟動背景；React 接管後將 `theme-color` 與頁面底色切換為適合 App 內容的中性淺色。
- 優先以 V3.4.1 動畫前的銜接原理進行模擬：不新增第二層網頁圖示，先讓原生 Splash 背景更接近 App 內容底色，降低中央圖示消失時的跳動感。
- 分別處理一般瀏覽器與 `standalone` PWA 顯示模式，避免修正其中一種模式後影響另一種模式。
- PWA 桌面圖示、網站 favicon、實體圖示檔與 manifest `icons` 不得變動。
- 必測 Android Chrome 一般瀏覽器上／下系統列、Android 已安裝 PWA 最上方狀態列、原生 Splash 藍色銜接與頁面回彈；可用時補測 iOS Safari／PWA。

狀態：

✅ V3.4.6 已完成修正、合併、發布與部署：保留現行 `#54B6E7` 原生 Splash 與專案特製圖示，React 完成掛載後才將 `theme-color`、文件與根節點背景切換為 V3.4.1 動畫前的 `#FFF3E8`。依發布後不可回溯規則，不修改 V3.4.5 既有發布紀錄。

### BUG020

問題：

PWA 顯示更新提示後，按下「馬上更新」可能再次顯示一次更新提示；Android 已安裝 PWA 更新後也可能只顯示純色啟動畫面，必須關閉 App 再重新開啟才能正常使用。

原因：

- `updateServiceWorker(true)` 傳送 `SKIP_WAITING` 後，其 Promise 可能在新版 Service Worker 真正接管目前頁面前就完成。
- 舊流程在 Promise 完成後無條件呼叫 `location.reload()`，同時又在 Workbox 的 `controlling` 事件透過 `onNeedReload` 再次呼叫重載，形成過早與重複重載的競態。
- 過早重載可能再次開啟舊版 App shell，因此同一新版提示會再出現；Android WebView 在連續切換控制器與頁面時，則可能停留在 manifest 的純色啟動背景。
- 原本 1.5 秒備援計時器會在 Promise 完成時被清除，無法可靠處理 Android 偶發漏接 `controlling` 事件的情況。

修正方式：

- 正常流程只在 Workbox 確認新版 Service Worker 已透過 `controlling` 事件接管頁面後才重新載入。

### BUG021

問題：

共同清單在重新整理後第一次勾選，或由私人清單切回共同清單後立即勾選時，偶爾會先顯示新狀態，隨即回復為操作前狀態；後續連續操作通常正常。

- 初始同步記錄本機操作版本；若讀取期間已有新操作，舊快照不得再覆蓋畫面。

- 多次勾選依操作順序排隊，只有最後一次操作更新同步完成或失敗狀態。
- 正式資料庫唯讀檢查確認同一共同清單內沒有重複的 `client_item_id`，排除特定資料列識別衝突。

狀態：

✅ V3.4.9 已完成發布與部署；刷新後立即勾選、由私人清單切回後立即勾選及連續操作順序均已通過實機回歸，重新開啟後狀態與最後一次操作一致。

### BUG025

問題：

使用 `npm run preview` 測試桌面 PWA 更新時，第一次按下強制更新可能沒有完成接管，必須再按一次；重載時若舊版 App shell 仍被重新開啟，頁面可能停在空白畫面。

原因：

- `updateServiceWorker(true)` 的 Promise 只代表已送出 `SKIP_WAITING` 訊息，不代表新版 Service Worker 已接管目前頁面。
- 原流程在按鈕事件中先隱藏更新提示並寫入新版號，接管失敗時會失去可重試的更新入口。
- 頁面若在 `controllerchange` 之前重載，可能取得舊版 `index.html` 與新版快取尚未完成的資源組合，造成空白頁。

修正方式：

- 在送出 `SKIP_WAITING` 前先監聽瀏覽器 `controllerchange`，只有確認新版 Service Worker 接管後才關閉提示並重新載入。
- 若第一次接管事件遺失，自動重送一次更新訊息；使用者不需重複按強制更新。
- 更新未完成或發生例外時保留強制更新提示，不提前寫入已更新版本，避免失去復原入口。
- 保留 Workbox `onNeedReload` 作為非按鈕流程的安全備援，並以單次重載防護避免重複 reload。

狀態：

✅ 已併入 V3.5.0 候選版；`npm run build`、ESLint 與 `git diff --check` 已通過。舊版升級至 V3.5.0 的單次按鈕與更新後非空白實機驗證已於 2026-08-26 通過。

### BUG026

問題：

- V3.5.0 發布後，電腦 PWA（`haw1971.yahoo@gmail.com`，`trip_editor`）與 Android PWA（`haw1971`，`super_admin`）在同一「日本九州」行程中操作。
- 電腦在領隊／導遊聯絡資訊新增資料 1、2 後，畫面顯示已同步且資料建立成功；手機端不會即時更新，切換功能目錄仍看不到，切換行程資料庫後才載入最新資料。
- 刪除資料及「其他資訊」也有相同現象。
- 另發現共同準備清單相同問題：電腦刪除一筆或勾選一筆後顯示已同步，手機端不會自動更新，只有手機 App 重新取得焦點後才會載入雲端結果。

判斷：

- 雲端寫入與既有同步流程正常，問題是另一台裝置缺少目前 Trip 的即時事件訂閱與畫面重新載入；此現象同時涵蓋 `other_info_items`、領隊／導遊資料及共同準備清單。
- 目前 `other_info_items` 沒有針對 `trip_id` 的 `postgres_changes` 訂閱；`currentTrip` 只在行程重新選取等既有生命週期更新，切換功能目錄不會觸發重新查詢。
- 共同準備清單目前只有進入頁面、focus／visibility／online 等時機重新讀取，未訂閱 `checklists`／`checklist_items` 的 Realtime 事件，因此勾選、刪除或管理操作不會即時反映到另一台裝置。

修正方式（V3.5.1）：

- 監聽 `other_info_items` 的 INSERT／UPDATE／DELETE Realtime 事件，限定目前 `trip_id`；收到事件後透過 RLS-safe query 重新載入，不直接信任事件 payload。
- 共同準備清單監聽 shared `checklists`（`trip_id`）及 `checklist_items`（`checklist_id`）的 INSERT／UPDATE／DELETE 事件；收到事件後重新讀取 shared checklist，涵蓋勾選、刪除／軟刪除、排序與新增。
- 軟刪除需處理 UPDATE 事件；保留 focus／visibility／reconnect 重新載入備援。
- 重新載入不得覆蓋尚未送出的本機同步佇列，並補上 Realtime publication／migration 與雙裝置角色回歸。

狀態：

✅ V3.5.1 程式與 Realtime publication migration 已完成並於 2026-08-26 套用正式 Supabase；事件僅作為失效通知並以 RLS-safe query 重新載入，pending order、pending progress、Other Info pending 與本機 cloud write 期間不接受遠端快照覆蓋。`npm run lint`、`npm run build` 與 publication 驗證已通過。2026-08-26 以 Codex 內建瀏覽器與電腦桌面版 PWA 完成雙端實機回歸：任一端同步完成後，另一端均在 1 秒內顯示更新；兩帳號同時編輯共同清單後以最後成功寫入狀態為準，完成同步後不回滾，均通過。

### BUG028
