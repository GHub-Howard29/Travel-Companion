### BUG035：天氣卡片過期且無可用快取時未自動取消顯示天氣

- 問題：行程卡片已超過目的地當地預報資格時間，且沒有可用的快取天氣資料時，畫面仍保留天氣欄位／三個點狀態提示，而不是自動取消「顯示天氣」勾選並隱藏整個天氣欄位。
- 預期：只有同時符合「卡片已過期」及「沒有可用天氣快取」才自動將該卡片 `showWeather` 設為 `false`；卡片尚未過期時仍走既有天氣載入流程。若有可顯示的歷史天氣資料，不得只因停止更新而自動取消勾選。日期、到達時間或地點變更後，應重新評估資格；不應自行重新勾選。
- 程式證據：`src/components/ItineraryPage.tsx` 天氣載入 effect（約第 450–480 行）會依 `showWeather === true` 建立啟用卡片，讀取瀏覽器天氣快取，並將無快取卡片進入等待／請求流程；目前此流程沒有將 `showWeather` 自動設為 `false`。行程卡片渲染區約第 2446 行只以 `event.showWeather === true` 決定天氣欄位是否顯示。
- 遠端唯讀證據：正式 Supabase 中，針對出發日 2026-10-24 的行程，以台灣當地日期／到達時間判斷，查得 16 張已勾選天氣的卡片其日期或到達時間已過；其中 12 張找不到相符的 `weather_daily_forecasts` 遠端快取紀錄。這只能證明遠端缺少相符紀錄，不能證明其瀏覽器 `localStorage` 也沒有可用快取。
- 影響：已過期且無可用快取的卡片仍會保留天氣欄位，重新開啟行程時也可能再次進入天氣請求流程；與使用者已確認的預期不符。
- 建議處理：在不直接於載入 effect 中任意改寫行程快照的前提下，設計可去重且符合既有 Trip 儲存／版本檢查流程的狀態轉換；先以目的地時區判定日期／到達時間，再確認沒有有效本機或遠端快取，才把 `showWeather` 設為 `false` 並透過既有儲存／同步路徑保存。需避免兩台裝置同時寫入時覆蓋其他行程修改、重複保存或形成同步循環。
- 狀態：根因方向已確認；同步安全的持久化方案與跨裝置回歸條件待分析，未實作。

- 問題：正式畫面出現使用者已要求移除的「目前不更新天氣；顯示上次成功取得的資料」；另外，定稿 W15「目前為長期預報，請於出發前再次確認天氣」與前端實際顯示的「長期預報，仍可能變動」不一致。
- 定稿依據：`docs/95_天氣文案校稿與逐項確認紀錄.md` 的 W01–W23 為文案索引；W15 已定稿為「目前為長期預報，請於出發前再次確認天氣」。需遵守文案適用狀態，不得只因文字曾在舊版本出現就沿用。
- 前端證據：`src/components/ItineraryPage.tsx` 約第 2455–2472 行，`statusMessage` 預設取自 `weather.message`，再依狀態覆蓋訊息；若後端回傳不在前端覆蓋條件中的舊 `message`，前端會保留並顯示它。約第 2503 行仍直接渲染「長期預報，仍可能變動」，與 W15 定稿不一致。
- 後端證據（已完成正式部署原始碼比對）：正式 Supabase `weather-forecast` 為 ACTIVE version 14，部署原始碼 SHA-256 為 `d5b7a0115bc69ff0cd2435809a597c880baac172970ab6f983965e238b3fc684`。直接讀取正式 Edge Function 原始碼，確認其回應分支仍是 `eligibilityBlocksRefresh ? (isStale ? 歷史資料文案 : 「目前不更新天氣；顯示上次成功取得的資料」)`。但 `develop` 在 commit `2a88b8a6d00b8b5aa6a117aa8801565dddbfd4d3`（2026-10-21 22:43 +08:00）已將判斷改為 `cachedEligibility === "date_passed" || cachedEligibility === "arrival_passed"` 才回傳歷史資料文案，其他資格阻擋情境不再回傳這句舊訊息。正式部署原始碼仍保留舊判斷，與 Git 已修正版本不一致，直接證實正式 Edge Function 未包含該次修正。正式部署的 `updated_at` 為 Unix 毫秒 `1792574588722`（2026-10-21），晚於該修正提交時間，但部署內容仍舊，顯示更新時間不能當作程式內容已同步的證據。
- 精確觸發條件：正式部署舊分支在 `eligibilityBlocksRefresh` 為真、快取仍可用（`stillUsable` 為真）、且 `isStale` 為假時，會把舊訊息放進 response `message`。其中 `cachedEligibility` 可能是 `long_range` 等非 `date_passed`／`arrival_passed` 的資格阻擋狀態；因此只要仍有未超過 24 小時的可用預報快取，就會走到這句已撤回文案。這是從正式部署函式實際原始碼確認的可達路徑，不是僅由本機原始碼推測。
- 前端證據：`src/components/ItineraryPage.tsx` 約第 2455–2472 行，`statusMessage` 預設取自 `weather.message`，只有特定狀態條件才覆蓋；因此正式 Edge Function 回傳上述 `message` 時，前端會保留並顯示它。前端本身目前未發現另一個直接產生完全相同舊句子的程式分支。
- 發布流程證據：`docs/101_V3.10.8_正式發布紀錄.md` 的 V3.10.9 發布段落明確記載本次「只發布前端及版本 metadata；未執行正式 Supabase migration，未部署 Edge Function，未修改 Secrets」。同文件也記載 V3.10.9 的 W09 修正已修改後端 `weather-forecast/index.ts`，但正式部署仍沿用 V3.10.8 的 Edge Function version 14。GitHub Pages workflow `39626511840` 成功，只能證明前端網站資產發布成功，不能代表 Supabase Edge Function 已更新。
- 根因判定（確定）：**V3.10.9 修正了 Git 中的 Edge Function 原始碼，但發布流程只部署 GitHub Pages 前端，明確沒有部署正式 Edge Function**。因此正式 Supabase 持續執行 V3.10.8 的 version 14，仍可回傳已廢棄文案；前端則把後端 `message` 作為預設顯示內容，將該舊回應呈現在畫面上。正式部署原始碼與 Git 修正內容的直接比對，以及 V3.10.9 發布紀錄對「未部署 Edge Function」的明確記載，兩者共同確定根因。日誌未保存 response body，因此無法事後證明截圖那次 HTTP 回應的每個欄位；但發布遺漏、正式服務可達的舊文案分支、前端顯示路徑均已有直接證據，根因判斷不依賴推測 localStorage 或瀏覽器快取。
- 影響：使用者可能看到已撤回或未依定稿呈現的文案，並誤判預報資料狀態。
- 建議處理：以 W01–W23 作為唯一文案來源，釐清每個後端狀態到文案的映射；移除已撤回訊息的可達分支，校正 W15 前端文字；加入靜態檢查／契約測試，避免舊文案重新進入程式與正式 bundle。部署後以指定卡片情境檢查實際回應與 UI。

### BUG037：長期預報的天氣欄位底色不符合已定案規則

- 問題：長期預報整個天氣欄位使用淺綠底色；需求是所有天氣預報欄位統一淺藍底色，只有點擊三個點後展開的額外狀態訊息使用淺綠底色。
- 前端證據：`src/components/ItineraryPage.tsx` 約第 2447 行的外層天氣容器，會在 `long_range` 或 `isLongRangeForecast(...)` 成立時套用 `border-emerald-100 bg-emerald-50`；約第 2489 行的三點展開訊息本身另有獨立 `border-emerald-100 bg-emerald-50`。因此目前長期預報的綠底是外層容器明確套用的條件結果，不是三點訊息樣式向外繼承。
- 需求：所有具有天氣預報資料的天氣欄位均用淺藍底色；三點展開的額外狀態訊息維持淺綠底色。若歷史資料另有已定案的特殊樣式，需按文案與視覺規格獨立處理，不得將長期預報判斷套用到外層底色。
- 影響：預報類別意外改變整個欄位的視覺語意，且與使用者明確要求不符。
- 建議處理：將外層容器底色規則與三點展開訊息分離；外層天氣預報容器固定淺藍，展開訊息固定淺綠。長期預報提醒文字也應同步核對 BUG036 的 W15 定稿。
- 狀態：外層條件錯置已由程式碼確認；未修改程式，待與 BUG036 一併安排修正及 UI 回歸。
