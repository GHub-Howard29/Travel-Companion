# V3.10.1 天氣功能開發交接

> 更新日期：2026-10-15
> 狀態：產品規則與最小風控方案已定案；2026-10-15 已開始本機實作，前端設定／呈現、天氣服務、Edge Function 與本機 migration 草稿已建立；尚未完成完整後端驗證、排程落地或任何正式環境變更。本文是開發交接摘要，完整產品與資料契約以《79_天氣預報功能規格草案》為準。

## 一、目前定案

1. **Guest／User 只有天氣閱覽權限**：不提供手動更新入口，不允許一般使用者直接寫入地點座標或天氣快取。
2. **天氣更新是後端自動流程**：APP 開啟時的自動檢查只是通知後端檢查目前 Trip；固定每 6 小時的排程負責例行刷新，台灣時間 03:00 是其中一次。首次載入若沒有快取，APP 自動檢查應立即更新符合資格的目標一次。後端必須自行讀取已儲存 Trip／卡片並決定更新目標，不能把前端任意傳入的地點或日期直接當成更新授權。
3. **只處理有效卡片**：卡片已成功儲存、「顯示天氣」已勾選、地點已確認、座標有效、行程日期尚未過去、在 10 天預報範圍內，並符合到達時間／冷卻／重試規則，才可成為更新候選。
4. **沿用既有權限**：沿用 APP 現有角色入口及 Trip 存取規則；後端仍須驗證呼叫者可檢視該 Trip，並從伺服器讀取已儲存內容確認資格。不可只依賴前端隱藏按鈕。
5. **不過度設計風控**：不新增每使用者每分鐘／每小時限流、來源封鎖、錯誤密鑰計數、使用者行為分析或額外風控資料表。只有唯讀檢查證明存在具體、可重現的風險缺口時，才另行評估。
6. **保留必要的快取控制**：座標快取、天氣快取、`(place_id, forecast_date)` 去重、原子租約、成功資料 6 小時冷卻、失敗至少 1 小時冷卻、單筆最多一次重試、每批最多 10 個目標及最多 5 個地點併發。
7. **Cron 基本安全**：排程入口只接受伺服器端 `x-weather-cron-secret`；密鑰只存於後端 Secret／Vault，不傳給前端或寫入日誌。第一版不另做錯誤密鑰來源封鎖系統。
8. **資料邊界**：天氣快取與 Trip JSON、`route_estimate_cache` 分離；天氣更新不修改 Trip、不觸發整份行程同步。第一版只用 Open-Meteo、最多 10 天、不提供官方警報。
9. **手動座標功能暫緩**：依 2026-10-15 決策，目前沒有實際需求，V3.10.1 不新增地點手動輸入／覆寫經緯度的 UI 或資料欄位。仍需實作可靠的座標取得與快取；未來若出現景點搜尋不到或定位不準的實際問題，再評估選填座標覆寫，並定義驗證、優先順序與座標變更後的快取失效規則。

## 二、本次 repository 唯讀盤點結果

本機檢查範圍包括 APP 原始碼、現有 Edge Functions、Supabase 設定與 migration 清單。2026-10-15 另透過 Supabase 管理連線對正式專案執行唯讀 metadata／catalog 查詢，以確認已套用 migration、資料表與 RLS policies；未執行寫入 SQL、migration、部署或任何遠端設定變更，未讀取秘密值。

### 已確認

- 在 `src` 原始碼搜尋天氣函式名稱、Open-Meteo、`weather_code` 與「顯示天氣」等關鍵字，沒有找到天氣功能實作。
- `supabase/functions` 目前只有 `travel-route` 與 `taiwan-bank-exchange-rate` 兩個 Edge Function；沒有天氣 Edge Function。
- 現有 `supabase/migrations` 清單沒有天氣座標快取、天氣快取或天氣排程 migration。
- `src/types/trip.ts` 的確認地點型別只保存 `placeId`；`src/services/travelRouteService.ts` 的 `getConfirmedPlace()` 也只回傳 `{ placeId }`。APP 目前沒有在確認地點物件內保存經緯度。
- 現有地點搜尋經由 `travel-route` 後端，Google Maps API 金鑰由後端環境讀取。其 `getAuthorizedClients()` 會驗證登入 token，並只允許 `super_admin` 或該 Trip 的 `trip_editor`；因此不可直接沿用這個管理者專用授權函式來實作天氣閱覽／自動更新。
- `supabase/config.toml` 將現有兩個 Edge Function 設為 `verify_jwt = false`。若天氣函式沿用此專案模式，必須在函式內自行驗證 APP 請求的 Trip 存取權限；Cron 路徑另以伺服器密鑰驗證，兩者不能混用。
- **正式 Supabase migration 已確認**：正式專案 `travel-companion-db`（project ref `omnnmpcbcicpltkkobae`）的 migration 清單包含 `20261009133523 / v3926_visibility_and_private_participants`，因此此 migration 已記錄為正式環境已套用；本機較早的候選檔名／版本與正式 migration 版本不同，後續判斷以遠端實際 migration 清單及 catalog 為準。
- **正式 Trip RLS 已唯讀確認**：`public.trips` 已啟用 RLS。實際 SELECT policy `trips_select_policy` 允許 `is_public = true`，或 `super_admin`，或該 Trip 的 `trip_editor` 讀取；UPDATE policy 使用 `tc_can_write_shared_trip`。正式 helper `tc_is_trip_editor` 以 `admin_users` 的 email、`trip_editor` role 與指定 `trip_id` 判斷；`tc_can_write_shared_trip` 則限制為 super admin，或對尚未結束行程的 trip editor。不能把「有登入」直接視為可讀取任意 Trip，天氣後端仍須對目標 Trip 執行明確授權判斷。
- **正式 Edge Function 狀態**：目前部署的函式只有 `travel-route`（version 19）與 `taiwan-bank-exchange-rate`（version 8），兩者 `verify_jwt = false`；若天氣函式沿用此設定，APP 請求必須在函式內自行驗證 JWT 與 Trip 讀取權限，Cron 必須使用獨立伺服器密鑰驗證。

### 尚未確認

- **Cron Secret 尚未進入配置階段**：天氣功能尚未實作，因此目前不需要確認或建立 Cron Secret。待實作時先定案 Secret 名稱與驗證流程，再於正式部署前確認是否已配置；只確認存在狀態，不讀取或分享秘密值。
- 新天氣函式仍需根據已確認的正式 Trip RLS／公開可見性政策實作獨立的 Trip read authorization。
- 天氣功能需要的資料表、RLS、原子租約、Edge Function、Cron 與前端天氣呈現都尚未建立。

## 三、建議實作順序（仍須依既有核准流程）

1. **實作前設計已整理**：直接依下節「最小實作變更清單」逐項拆解工作。開始實作時再定案 Cron Secret 名稱與驗證流程；正式部署前才確認是否已配置，現在不需進 Dashboard 核對或建立。
2. **建立最小資料層**：依《79》建立座標快取與每日天氣快取所需 migration、索引、RLS／grant 及原子租約機制；不建立限流／來源封鎖資料表。
3. **建立天氣後端流程**：APP 自動檢查與 Cron 共用快取、資格判斷、去重、冷卻、租約、逾時及重試。後端先驗證 Trip 存取權，再從已儲存內容挑選卡片；不得接受任意 `place_id`／日期直接觸發上游請求。
4. **接上座標與預報**：只有符合資格且沒有有效座標快取時，才使用已確認的 Place ID 取得座標；只有座標有效後才呼叫 Open-Meteo。有效座標與有效天氣快取都應重用。
5. **最後才接前端顯示**：沿用既有卡片編輯權限新增天氣勾選欄位；Guest／User 只讀取與顯示，不提供手動更新或快取寫入操作。來源署名、舊資料狀態、失效日期與離線行為依《79》。
6. **驗收後再議發布**：在本機／測試環境驗證角色、快取命中、重複請求、座標變更、併發、失敗重試與 Cron 授權；正式 migration／部署仍須另行取得明確核准。

## 四、最小實作變更清單（本機實作中；正式環境變更未核准）

以下是依《79》及本次唯讀盤點整理的最小工作清單。2026-10-15 已獲使用者明確指示開始本機實作，因此可在本機新增／修改程式、migration 草稿及測試；這不代表已核准正式資料庫 migration、排程設定或部署。

### A. APP／前端

- [x] **卡片設定（本機已完成）**：在可設定地點的卡片編輯介面新增「顯示天氣」欄位；新卡片預設未勾選，舊卡片缺值一律視為 false，保留已有明確設定。
- [x] **儲存語意（本機已接線，待整合驗收）**：勾選狀態只存在編輯草稿；成功儲存後才生效。儲存卡片時不直接呼叫天氣 API，先顯示等候訊息；下一次 APP 開啟／恢復連線／切換行程時才檢查，且只有天氣已勾選、進入 10 天預報範圍並確實需要更新時，後端才依座標快取規則重用或取得 Google Places 座標。取消勾選後立即停止顯示該卡片天氣，但不主動刪除共享快取。
- [ ] **座標流程**：目前地點型別只有 placeId，getConfirmedPlace() 也只回傳 { placeId }。不要為預留彈性新增手動經緯度欄位；由後端在確實有符合資格的天氣需求時取得／重用座標，APP 不直接寫入座標快取。
- [ ] **讀取與顯示**：接入天氣後端的唯讀結果；卡片頂端顯示天氣描述／內建圖示、最低／最高溫、有效的降雨機率、必要提醒、來源連結與更新狀態。實作《79》規定的 1–7 天、8–10 天、超過 10 天、失敗舊資料、48 小時失效、離線與到達時間後停止更新等呈現。
- [ ] **不擴大同步範圍**：天氣資料不得寫入 Trip JSON，也不得觸發整份 Trip 同步；不提供手動更新按鈕或前端快取寫入操作。

### B. Migration／資料庫

- [ ] **座標快取表**：以 place_id 為唯一鍵，保存有效座標、取得時間與到期時間；座標需驗證緯度／經度範圍，最多連續保存 30 日。到期後清除座標值但保留 Place ID；未勾選或超過預報範圍時，不為天氣目的重新查詢。
- [ ] **每日天氣快取表**：以 (place_id, forecast_date) 去重；依《79》保存天氣欄位、景點時區、fetched_at、最後嘗試／失敗時間、穩定錯誤碼、排程刷新時間，以及 refresh_lease_token／refresh_lease_until。首次更新可用不含天氣資料的占位列承載租約，但不得回傳給前端當作有效天氣。
- [ ] **索引與權限**：新增必要唯一鍵／查詢索引、RLS／GRANT；一般 APP 使用者不可直接寫入兩張快取表，前端也不可讀取整張座標快取。以受控後端路徑提供符合 Trip 權限的天氣結果。
- [ ] **原子租約與失效清理**：使用快取列上的 30 秒租約，寫入結果時再次驗證 token、租約仍有效及座標仍相符，阻止過期工作覆蓋新資料。48 小時失效及景點當地預報日期已過的資料，服務端先拒絕回傳，再依清理規則移除。
- [ ] 不新增額外的使用者限流、封鎖、錯誤密鑰計數或卡片—快取關聯表；除非後續檢查發現具體必要性，否則不擴充 schema。

### C. Edge Function／後端

- [ ] **新增天氣後端入口與服務**：APP 自動檢查及排程共用資格判斷、快取、租約、冷卻、重試與去重邏輯；前端只能通知檢查目前 Trip，不可用任意傳入的 Place ID／日期決定上游請求。
- [ ] **獨立 Trip 讀取授權**：APP 入口必須驗證登入身分及該呼叫者是否可檢視指定 Trip，再由伺服器讀取已儲存卡片確認資格。不能直接沿用 travel-route 的 getAuthorizedClients()，因其只授權 super_admin／該 Trip 的 trip_editor，會錯誤排除可閱覽天氣的 Guest／User。若沿用 verify_jwt = false 專案模式，必須在函式內明確驗證 JWT 與 Trip 讀取權限。
- [ ] **資格判斷**：只處理已成功儲存、天氣已勾選、地點已確認、座標有效、日期在 10 天範圍內且尚未過去的卡片；套用景點當地時區／到達時間排除。共用同一地點／日期時，只要仍有一張有效且啟用天氣的卡片未到達時間，即可保留該共用需求。
- [ ] **供應商請求**：只有符合資格且沒有有效座標快取時，才以已確認 Place ID 呼叫 Google Places Place Details (New) 的 location 欄位；座標有效後才呼叫 Open-Meteo，使用 timezone=auto 取得並保存景點時區。未知／無效座標不得猜測。
- [ ] **冷卻與錯誤處理**：遵守一般成功資料 6 小時冷卻、APP 開啟檢查在 6–24 小時區間的嘗試間隔、滿 24 小時更新、失敗後至少 1 小時冷卻、單筆最多一次重試、單次 HTTP 8 秒及單筆工作總期限 20 秒。每批最多 10 個去重目標、最多 5 個地點併發；失敗不得覆蓋舊成功資料或重設 fetched_at。
- [ ] **Cron 專用授權**：排程入口只接受伺服器端 x-weather-cron-secret，與 APP 路徑分開；缺少／錯誤密鑰立即拒絕，秘密不傳前端、不寫日誌。現在不檢查或建立 Secret；實作時定案名稱與驗證流程，正式部署前才核對配置狀態。
- [ ] **來源與資料契約**：第一版只用 Open-Meteo，落實每張卡片旁的來源連結；實作前再核實 CC BY 4.0 的署名、修改說明及可見性要求。不要加入官方警報、手動更新、手動座標覆寫或付費服務。

### D. 排程落地

- [ ] 以現有 pg_cron／pg_net 為優先方案；固定每 6 小時執行一次，台灣時間為 03:00、09:00、15:00、21:00；若 Cron 使用 UTC，對應 19:00、01:00、07:00、13:00 UTC。03:00 是其中一次每日固定刷新，不另加每日排程，也不得改成每 5 分鐘 sweep。每次排程最多 10 個去重目標、最多 5 個併發；首次 APP 載入若沒有快取，APP 自動檢查應立即為符合資格的目標發起一次更新，透過唯一鍵／原子租約避免與排程重複。
- [ ] 每 6 小時排程須遵守卡片資格、景點當地到達時間排除、失敗至少 1 小時冷卻及原子租約；若 APP 已在該排程時段前成功更新，排程應跳過不需更新的同一目標，不得無條件刷新所有快取。
- [ ] Cron 使用的秘密透過 Supabase Vault／後端 Secret 注入，只供內部請求使用；不得把服務角色金鑰寫進 SQL 原始碼或日誌。
- [ ] 驗證 cron.job_run_details、net._http_response 及 Edge Function logs 能區分排程是否啟動、HTTP dispatch 是否成功與實際更新結果；確認台灣時間換算、專案暫停／HTTP 失敗時可由下一次固定每 6 小時排程或 APP 開啟時自動檢查恢復。Free 方案短期日誌保留限制下，不新增獨立監控表或外部告警。
- [ ] 排程 migration／設定只先在本機或測試環境驗證；正式環境新增排程前另行取得明確核准。

### E. 測試與驗收

- [ ] 單元測試：預報日期／景點時區、到達時間邊界、天氣代碼映射、提醒優先順序、缺少或無效欄位、24／48 小時快取期限及狀態文案。
- [ ] 權限測試：Guest／User／trip_editor／super_admin 對公開與私人 Trip 的讀取結果；未授權 Trip、無效 JWT、偽造 Place ID／日期、缺少或錯誤 Cron Secret 都應被拒絕，且不觸發上游 API。
- [ ] 快取／併發測試：座標命中、30 日到期、同一 (place_id, forecast_date) 去重、APP 與 Cron 同時觸發只取得一個有效租約、租約到期後恢復、舊 token 不得覆蓋新結果。
- [ ] 失敗測試：Google Places／Open-Meteo 逾時、限流及錯誤回應；單次重試與 Retry-After、1 小時失敗冷卻、舊資料備援及 48 小時失效。
- [ ] APP 整合測試：勾選草稿／取消草稿／儲存失敗不觸發更新；成功儲存後才套用；天氣更新不修改 Trip JSON、不觸發 Trip 同步；窄螢幕與離線顯示符合《79》。
- [ ] 排程測試：確認每 6 小時執行一次（台灣時間 03:00、09:00、15:00、21:00）、UTC 換算、批次上限、APP 首次載入無快取時立即更新一次、APP 已更新後的排除條件、診斷紀錄及失敗恢復。
