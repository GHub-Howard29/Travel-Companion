## 使用規則

1. 每次開始 Travel-Companion 的設計討論、除錯、程式修改、測試或審查前，先讀取本索引。
2. 依本次工作範圍讀取對應的有效決策文件，以及原本已指定的產品規格／資料契約；不得只讀本索引就推測細節。
3. **定案觸發：** 使用者明確表示「定案、確定、核准、就照這個做」或同等明確批准某項持續性規格／架構／資料契約／行為／工作邊界時，該表述本身就是記錄授權，不需再問是否要記錄。若批准對象明確，AI 必須在同一工作階段立即建立 Accepted 決策文件並更新本索引；不得只回覆「已記錄」而未寫檔。
4. **定案內容不完整：** 若無法從對話明確判定決策文字、適用範圍或核准對象，先用最短文字整理理解並只詢問缺少的關鍵點；未釐清前標示 Proposed，不得當成 Accepted 或開始依此擴大實作。定案紀錄至少包含 ID、標題、狀態、核准日期、決策內容、適用範圍、限制／不可做事項、依據／理由、驗收或解除條件、權威規格連結。
5. **記錄回報：** 寫檔後重新讀取決策文件及索引，確認內容與連結正確，再回報 ID、檔案路徑及記錄摘要。若寫檔或驗證失敗，必須明確回報未完成，不得宣稱已記錄。
6. 新增持續性決策時，建立一份決策文件並在本索引登記 ID、標題、狀態、適用範圍及權威文件連結。一般一次性修 Bug、暫時除錯細節不建立決策。
7. 修改若違反現行 Accepted 決策或超出其核准範圍，停止受影響的修改，指出衝突及影響，取得使用者核准後才能變更決策與實作。
8. **移入歷史的時機：** AI 不得因程式完成、功能發布、版本更新、文件變舊或主觀認為不再需要，就自行解除決策。只有以下情況可移入 history：(a) 使用者明確核准解除；(b) 使用者核准新的決策取代舊決策；(c) 舊決策原文已明定客觀解除條件，且 AI 已取得可驗證證據確認條件成立。若條件成立與否、是否仍適用有疑義，保持 Accepted 並詢問使用者。
9. **移轉程序：** 先記錄解除／取代日期、原因、證據、取代決策 ID（如有），更新舊決策狀態為 Retired／Superseded，再將完整文件移至 history，最後更新索引；完成後重新讀取並驗證舊檔新位置及索引連結。不得刪除或只覆寫舊內容。
10. 跨對話交接只需指出本索引與本次相關決策 ID；接續工作必須重新讀取檔案並核對實際 Git 狀態。

## 目錄

- `active/`：目前有效且必須遵守的 Accepted 決策。
- `history/`：已解除、已取代或已失效的決策，供除錯及追溯。

## 狀態定義

- `Proposed`：提案／待確認，不構成實作授權。
- `Accepted`：使用者已核准，於適用範圍內具約束力。
- `Superseded`：已被另一項核准決策取代，保留於 history。
- `Retired`：已核准解除或依明定條件失效，保留於 history。
- `Rejected`：已拒絕，不得作為實作依據；保留於 history。

## 單一權威來源

本目錄不取代既有領域規格、API／資料契約、資料庫設計及驗收文件。每個決策只指定一份完整權威內容；其他文件僅連結，不複製另一份可能漂移的規格。
