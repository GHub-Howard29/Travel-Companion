## 2026-11-27 瀏覽器隔離測試

### 環境與真實程式模組

- 建立兩個 Chrome 分頁，均位於獨立測試 origin http://127.0.0.1:8765/；頁面是無應用程式程式碼的靜態 HTML（0 scripts）。測試完成後兩個 harness 分頁已關閉，臨時 HttpListener 已停止。
- 從本機 Vite dev server 載入實際來源模組：tripStorage.ts、itinerarySyncStorage.ts、itinerarySync.ts、tripReconciliation.ts、itinerarySaveGate.ts。
- 使用實際 upsertStoredTripRecord、read/writeItinerarySyncState、createPendingItinerarySyncState、reconcilePendingItinerarySyncState、decideTripReconciliation、shouldSkipDuplicateItinerarySave 與 saveItineraryWithRevisionNotice。
- Lease、cloud snapshot、RPC 均由測試 origin 的 synthetic localStorage stub 模擬；隔離 harness 本身未建立 Supabase client、未呼叫 Supabase RPC，未寫入 repository 或資料庫。

### Case A：跨 context 的 Lease 前覆寫

1. Context A 以 D2／D3 含既有卡片及新增卡片的 snapshot 寫入 local Trip 與 Pending，取得 stub Lease。
2. Context B 使用 stale snapshot（D2、D3 為空）執行相同的 Lease 前 local Trip／Pending 寫入；隨後 Lease claim 因 A 持有而失敗。
3. A 收到 travel_companion_custom_trips storage event；測試 listener 按 useTripWorkspace.ts 的實際判斷條件檢查 cache，因 selected Trip 仍存在而 return，不更新 A 的 currentTrip。
4. 結果：A 的記憶體 currentTrip 仍有 D2／D3 卡片，但共享 local Trip 與 Pending 已變成 B 的空 D2／D3 snapshot。
5. A 檢查 Pending revision 時發現已由 B 改變，保存中止；stub RPC 呼叫數為 0，cloud snapshot 保持原資料。

**結果：PASS（競態重現）。** 證明 Lease claim 失敗不會回滾其之前的 local Trip／Pending 寫入；也證明 storage listener 不會因 Trip 仍存在就刷新目前 context 的 currentTrip。

### Case B：Workspace reconciliation 與 Pending revision

1. 使用第二組 synthetic Trip 重播 A 先持有 Lease、B 先覆寫 stale local Trip／Pending 的順序。
2. 在 A context 呼叫實際 decideTripReconciliation()，以原始 cloud record 與目前 local/Pending 執行 workspace reconciliation，再用實際 replaceStoredTripRecords() 寫回 cache。
3. reconciliation 將 B 的 stale deletion 合併為 pending（無 conflict），更新 Pending revision，並將 local Trip D2／D3 保持為空。
4. selected Trip 仍存在；原始碼核對 reconcileTripWorkspaceWithResult() 在此情況只更新 tripOptions，不會呼叫 setCurrentTrip()。因此測試中的 A 記憶體 currentTrip 仍保留 A snapshot。
5. A 後續讀取 Pending revision 時，與原保存開始時的 revision 不同，會中止保存；cloud snapshot 未變，stub RPC 呼叫數為 0。

**結果：PASS（workspace reconciliation 保留 stale Pending，並使原保存 revision check 中止）。**

### Case C：後續 hydration 觸發 Pending auto-sync

1. 在 Case A 的 B context，模擬 currentTrip 重新 hydration；確認 isSessionReady、online、selected writable Trip 與 Pending 條件均成立。
2. 依 useTripWorkspace.ts 的 Pending auto-sync effect 建立 pendingTrip，使用實際 createPendingItinerarySyncState() 與 reconcilePendingItinerarySyncState()。實際 shouldSkipDuplicateItinerarySave() 對相同 Pending snapshot 在 prior save in-flight 時回傳 true；prior save settled 後回傳 false，因此只阻擋同頁即時重入，不阻止後續 hydration retry。
3. A 已釋放 Lease 後，B 的 retry 取得 stub Lease；reconciliation 將 B 的 D2／D3 deletion 合併到原 cloud baseline，結果無 conflict。
4. stub RPC 將 D2／D3 空 snapshot 寫入 cloud version 2，Pending 轉為 synced。

**結果：PASS（條件式重試可將 stale empty snapshot 寫入 cloud）。** 這證明後續 hydration 若觸發 Pending auto-sync，stale Pending 不只影響 local cache，也可能成為雲端最終資料。React useEffect 本身及真實 Lease／RPC 未在此測試中啟動；測試是依實際 effect 條件與 helper 執行的隔離瀏覽器流程。

### Case D：Weather ineligible writeback

依 ItineraryPage.tsx 實際轉換條件，以 synthetic ineligible result 執行相同的 card mapping：只將符合條件卡片的 showWeather 設為 false。前後所有 card ID 與總卡片數一致。

**結果：PASS（排除 Weather ineligible mapping 單獨刪除卡片）。** 但此 effect 仍以完整 daysData snapshot 呼叫保存，因此若 weatherTripRef.current 本身是 stale snapshot，仍可能把 stale 全量資料送入保存流程。

### Case E：revision notice 與 access reconciliation 重疊

- 載入實際 saveItineraryWithRevisionNotice() helper，使用 deferred stub 模擬 checkForRemoteTripChange() 內的 acceptRevision() 已啟動但未等待的 inspectAccess()。
- 實際 gate 只等待 checkForRemoteTripChange()；inspectAccess() 尚未完成時，save 已開始並完成。
- 原始碼確認 acceptRevision() 使用 void inspectAccess()；inspectAccess() 再呼叫 onReconcileTrips()。
- reconcileTripWorkspaceWithResult() 若 selected Trip 仍存在，只更新 Trip options，不會直接 reload selected currentTrip。先前「revision reconciliation 直接觸發 selected Trip reload」的描述應修正為：它可與保存重疊並改寫 shared local/Pending；selected currentTrip 仍可能維持舊快照，必須等後續 hydration 才會重新觸發 Pending auto-sync。

**結果：PASS（確認 gate 不等待 access reconciliation 完成）。**

## 觸發條件與限制

- **初始 workspace hydration 已確認會直接接上 Pending auto-sync：** online 時 loadInitialWorkspace() 先 await reconcileTripWorkspace()；selected Trip 載入 effect 再呼叫 getTripDetail()。若 Pending／Conflict 存在，effect 會以 pendingDaysData 覆蓋 tripData.content.daysData，再 setCurrentTrip(resolvedTrip)。這個 currentTrip 更新會觸發 Pending auto-sync effect；effect 條件為 session ready、online、selected writable Trip、sync state pending，且依賴 currentTrip。故只要頁面重新載入／重新選取 Trip，stale Pending 就可能被重新套回 UI 並進入保存。
- **App update／restart 路徑：** App.tsx 的 runAppUpdate() 在 session ready、online、具管理角色時，依序執行 reconcileTripWorkspace() 與 reloadCurrentTrip()。此 reload 不設 preferCloud；getTripDetail() 會按 updatedAt 在 local／cloud record 中選較新者，之後同樣 setCurrentTrip 並觸發 Pending auto-sync。
- **Trip editor 路徑：** openEditTrip() 先取得 __trip__ Lease，再呼叫 reloadCurrentTrip(true) 從 cloud 重新載入並 setCurrentTrip。Pending auto-sync effect 沒有檢查 locally-held Trip editor Lease；同一分頁的 ITINERARY_EDIT_CLIENT_ID 存於 sessionStorage，SQL claim 允許相同 user/client 重新 claim，因此此 effect 仍可能在 editor Lease 持有期間執行保存。這些是已確認的程式觸發路徑，不代表正式事件當時一定發生。
- Weather ineligible mapping 只改 showWeather，並非 D2／D3 卡片清空的單獨原因。
- 本測試沒有重播完整 React hook mount、實際 Supabase Lease、真實 RPC 或正式資料；不能據此宣稱已定位正式事件的發送 context。
- 測試建立初期，兩個新分頁曾短暫導向本機 Vite SPA fallback；發現載入應用程式模組後立即切換至獨立 8765 測試 origin。沒有進行 UI 操作或下達資料庫寫入命令；該短暫啟動期間的自動初始化網路請求未另行擷取，因此不將整個 setup 過程描述為可證明的零應用程式請求。正式 harness 的所有執行均在 8765 靜態頁，沒有 Supabase client／RPC。

## 目前判斷

**強力支持的候選根因：** stale full daysData snapshot 在 Lease claim 前覆寫共享 local Trip／Pending；另一 context 的保存因 Pending revision 改變而中止，但 local stale state 不回滾。Workspace reconciliation 可再次以 stale Pending 更新 local cache／revision。初始 workspace hydration 會將 pendingDaysData 套回 currentTrip 並觸發 Pending auto-sync；App update/restart 與 openEditTrip 也會改變 currentTrip。故 stale snapshot 具備在後續 hydration 被再次保存至 cloud 的完整程式路徑。

**仍未證實：** V3.11.7 正式事件是否走過上述完整時序、哪個 page／client 發出空 D2／D3 snapshot，以及該時間窗是否真的發生 initial hydration、App update/restart 或 openEditTrip。

## 既有 Lease 契約核對與最小修正（2026-11-27）

### 已確認的實作偏差

- 原 S3 保存流程採用 save-scoped temporary Lease（保存函式自行 claim／save／release）；2026-11-24 ADR-001 擴充為編輯入口先取得 Trip Lease、整段編輯期間續約、離開時才釋放後，saveItineraryTripDetail() 未同步改為沿用 isManagedItineraryTripLeaseActive()／isLocallyHeldTripEditorLease()，形成新舊 lifecycle 契約不一致。
- 同一分頁因共用 ITINERARY_EDIT_CLIENT_ID，資料庫 Claim RPC 允許同一 user/client 重新 claim；因此重複 claim 本身通常不會拒絕同一持有者。真正的偏差是保存流程未辨識目前 Lease owner，並在 finally 可能釋放由 Trip editor 持有的 Lease（原先只排除 managed mode）。
- 對沒有本地 Lease marker 的第二個 context，Claim 可能因另一 context 持有 Lease 而拒絕；舊流程卻先寫 shared Trip／Pending，再 Claim，造成被拒絕的 stale snapshot 已覆寫共享資料。
- applyItineraryResolution() 也曾無條件 claim，並在 finally 無條件 release，可能提前釋放正在使用中的 managed／Trip editor Lease。

### 已實作的最小修正

- saveItineraryTripDetail()：若目前 context 已持有 managed Trip Lease 或 Trip editor Lease，直接沿用，不重新 claim，也不由保存流程釋放。
- 無既有 Lease 的線上背景保存（包含 Weather ineligible mapping 與 Pending auto-sync）可取得暫時 Lease，但 Claim 必須先於 shared Trip／Pending 寫入。Claim 被拒絕時不重寫 shared state；既有 Pending 保留，沒有 Pending 時拒絕保存。
- 暫時 Claim 成功後，保存完成才釋放；若執行期間轉為 managed／Trip editor 持有狀態，finally 會保留該 Lease。
- applyItineraryResolution() 採相同的 Lease reuse／temporary claim／conditional release 原則。
- 不新增鎖定種類、Lease RPC、revision 欄位、Web Locks、IndexedDB、draft/conflict 持久化或新的同步協定；不修改 ADR-001／ADR-002 Accepted 決策。

### 回歸條件

- 同一 context 已持有 managed Lease 時，卡片保存不再 claim，保存完成後 Lease 仍有效。
- 同一 context 已持有 Trip editor Lease 時，Pending auto-sync／保存不再 claim，完成後 Lease 仍有效。
- 無既有 Lease 的線上背景保存（Weather ineligible mapping／Pending auto-sync）必須先 Claim 再寫 shared Trip／Pending；Claim 被拒絕時 shared Trip／Pending 不變，既有 Pending 保留，沒有 Pending 時保存失敗。
- 暫時 Lease 只在由本次流程取得時釋放；managed／Trip editor Lease 由其入口 lifecycle 釋放，不得被保存流程提前釋放。
- 失網或本機保存失敗時，若本次流程曾取得暫時 Lease，需嘗試釋放；釋放失敗以既有 Lease TTL 作為回收機制。
- Save RPC、itinerary version CAS、Pending／Recovery、Conflict resolution 與既有 cloud readback 行為維持原狀。

## 2026-11-27 Pending auto-sync stale queued snapshot 局部修正

### 根因證據

- `saveItineraryTripDetail()` 以 Trip ID 維護單一 save Promise。新呼叫若遇到既有 Promise，會先 `await existingSave`，但原始呼叫當下的 `nextTrip` snapshot 仍被閉包保留；等待結束後原流程可能以舊 snapshot 重建 Pending。
- 使用真實 `createPendingItinerarySyncState()` 與 `reconcilePendingItinerarySyncState()` 進行純記憶體時序重播：第一筆 Pending 修改 card A；較新的 Pending 再修改 card B；較舊 queued invocation 在前一筆完成後，以其 captured snapshot 重建 Pending。reconciliation 結果將 card B 的較新修改退回 baseline，結果仍為 `pending`，而非 conflict，故單靠既有三方合併不會保護此類 stale replay。

## 2026-11-27 BUG 3 後端同一路線併發查詢保護（Accepted）

### 定案

- 相同 route `cache_key` 的 cache miss 採用資料庫持久化 keyed reservation：同一 key 同一時間只允許一個有效持有者呼叫 Google Routes provider；其他請求不另佔每日額度，等待後重讀既有 cache。
- Reservation 使用唯一 owner token 與到期時間；成功／失敗路徑以 owner token 條件式釋放，避免舊處理者釋放新處理者的 reservation。持有者逾時後允許新請求原子接手，避免永久卡住。Google Routes 單次呼叫設 20 秒 timeout，reservation TTL 為 90 秒；`tc_store_route_estimate_if_owner` 在同一 DB statement 內核對未過期 owner 並條件式 upsert cache，過期舊 owner 不得寫入或覆蓋結果。
- 先檢查快取；有效 cache hit 不必取得 reservation，也不增加等待。
- 取得 reservation 後才呼叫既有 `tc_claim_route_query_slot`，每日 100 次額度仍只計真正開始的 provider 查詢；若 quota 不足則釋放 reservation。
- 保留既有 cache key 算法、30 天 cache TTL、route payload／回應格式、Google 路線計算及 transit fallback；不修改 Trip 編輯 Lease、天氣契約、路線 UI 或 caller 範圍。
- 範圍限本機程式、migration、隔離資料庫／Edge regression、ADR 文件與必要文件索引；不包含正式 Supabase 操作、部署或 Git commit／push。

### 實作與驗收要求

1. 同 key 併發 claim 只有一個取得成功；不同 key 可同時取得。
2. 第二個同 key 請求在第一個完成後讀到 cache，且不消耗每日 quota、不呼叫 provider。
3. 第一個處理者 provider 失敗或無有效結果時，reservation 會釋放，等待者可接手。
4. 處理者異常終止後，reservation 到期可被新請求接手；舊 owner 的延遲 release 不得刪除新 owner 的 reservation。
5. cache hit 不進 reservation／quota； quota 已滿時釋放 reservation，回傳既有 429。
6. Cache write 失敗仍須釋放 reservation；後續請求可以重新查詢，不可永久阻塞。
7. 保留每日額度上限及現有路線輸出行為；以隔離 DB 驗證 RPC 原子性，並以 Edge stub 測試驗證整體呼叫順序及錯誤路徑。

## 2026-11-27 Realtime invalid filter：Lease subscription 權限衝突根因確認

### 正式環境唯讀證據

- 固定查詢正式 Supabase `travel-companion-db`；只讀 schema catalog、function definition、migration source 與 unified logs，未讀取行程卡片內容，未修改正式資料／權限／RLS／migration／Secrets。
- 10:20–10:30 UTC 的 10 筆 `invalid column for filter trip_id` 均來自 Postgres `realtime_subscription_manager_pub`，`command_tag=INSERT`，context 為 `PL/pgSQL function realtime.subscription_check_filters() line 26 at RAISE`。因此錯誤發生在新增 `realtime.subscription` row 的註冊驗證階段，不是 DELETE／WAL event filter 執行階段。
- 正式 `realtime.subscription_check_filters()` function definition 的 `col_names` 是透過 `pg_catalog.has_column_privilege((new.claims ->> 'role'), a.attrelid, a.attnum, 'SELECT')` 篩選；filter 欄位不在該清單時就會 `raise exception 'invalid column for filter %'`。所以錯誤訊息中的「invalid column」代表該 subscription role 無可用 SELECT 欄位，不必然代表資料表 schema 沒有該欄位。
- 正式 `itinerary_trip_edit_leases`：`supabase_realtime` publication membership=true；RLS enabled；對 anon／authenticated／service_role 的 table SELECT 與 `trip_id` column SELECT 均為 false；`pg_policies` 沒有任何該表 policy。Migration `20261101103000_v31012_itinerary_card_edit_leases.sql` 建表後明確 `REVOKE ALL ... FROM public, anon, authenticated, service_role`；`20261120120000_adr001_stage1_trip_itinerary_edit_enforcement.sql` 將舊表 rename 為 `itinerary_trip_edit_leases`，保留該 ACL，並未重新授予 client SELECT。
- 同一正式 DB 中，`checklists`、`other_info_items`、`exchange_purchases` 的 authenticated table／`trip_id` SELECT privilege 均為 true；四表 schema 都有 `trip_id`，也都在 publication。這排除「現行 source 的四個 filter table 全都缺少 trip_id」的說法，並將權限不相容鎖定到 Lease table。
- 正式 `tc_list_itinerary_trip_edit_leases` 在 10:20–10:26:19 有 28 次 HTTP 200；這是 SECURITY DEFINER RPC，能讀取 Lease row 不代表 browser client 有直接 table SELECT 權限。正式同窗另有 `tc_claim` 5 次、`tc_renew` 13 次、`tc_release` 4 次 HTTP 200，說明 Lease 功能路徑確實活躍。
- `ItineraryPage.tsx`（tag `v3.11.8` 與目前 HEAD 相同）在 `canUseEditLeases` scope 啟動時，會直接註冊 `table: "itinerary_trip_edit_leases"`、`event: "*"`、`filter: trip_id=eq.${trip.id}` 的 Postgres Changes subscription；註冊失敗不會阻止同 effect 透過 SECURITY DEFINER `tc_list_itinerary_trip_edit_leases` RPC 讀取初始 Lease 清單。

### Save 403：Lease release 緊鄰 Save 的競態線索

- 正式 Gateway 同一 authenticated session 的請求順序：10:25:06.043 `tc_renew_itinerary_trip_edit_lease` HTTP 200、response content-length=4（boolean `true`）；10:25:08.831 `tc_release_itinerary_trip_edit_lease` HTTP 200、content-length=4（boolean `true`）；10:25:08.892 `tc_save_itinerary_days` HTTP 403，兩個最後請求相隔 61 ms。10:26:00.256 同 session 再次 `tc_claim_itinerary_trip_edit_lease` HTTP 200，10:26:01.462 `tc_save_itinerary_days` HTTP 200。
- 正式 `tc_release_itinerary_trip_edit_lease` 只在 `trip_id`、`owner_user_id`、`owner_client_id` 相符時刪除 Lease row；`tc_save_itinerary_days` 隨後要求同一 Trip 的 Lease row 存在、owner user/client 相符且未過期，否則拋出 `ADR001_EDIT_LEASE_REQUIRED`。因此若上述 Release 與 403 Save 是同一 Trip/client，這個時間序列足以直接解釋 403；前一筆 Renew `true` 也不支持「自然過期」是當次直接原因。
- 正式 Gateway logs 沒有 `p_trip_id`／`p_client_id`，故目前只能確認同一 authenticated session 中有成功 Release 緊接失敗 Save，不能證明兩筆是同一 Trip/client，也不能宣稱已逐筆確認 403 根因。
- Source-level race path：`useTripWorkspace.ts` 的 pending-sync `useEffect` 可在背景直接呼叫 `saveItineraryTripDetail()`，不會設定 `ItineraryPage` 的 `isItemSaving`／`isOrderSaving`／`isTimeAdjustmentSaving`／`isCopySaving` UI flags。`saveItineraryTripDetail()` 開始時只計算一次 `ownsExistingLease`；若當時為 true，後續會經過版本／雲端讀取後直接呼叫 Save RPC，不會在 Save 前重新 claim／renew／確認 Lease 仍存在。相對地，`ItineraryPage.closeManageMode()` 只檢查上述 UI flags，`cleanupManagementSession()` 隨後會 release managed Trip Lease，但不等待 `waitForPendingItinerarySaves()`；component unmount cleanup 也會直接 release。`waitForPendingItinerarySaves()` 目前只在 App logout 流程呼叫。
- **判斷：** 已找到可造成「背景 Save 已認定沿用 managed Lease → UI cleanup 先 release → 背景 Save 隨後 403」的具體競態程式路徑，且正式請求時間序列高度吻合；但缺少正式 Trip/client IDs，仍列為高可信根因候選，不升格為已逐筆確認。

### 本機同機制重現

- 本機 Supabase catalog 與正式一致：`itinerary_trip_edit_leases` 的 replica identity=`d`、PK=`trip_id`、publication membership=true；對照三張一般資料表的 PK=`id`。本輪沒有把 replica identity／DELETE 行為當成錯誤原因。
- 直接在本機 `realtime.subscription` 以 `claims.role=authenticated`、entity=`public.itinerary_trip_edit_leases`、filter=`trip_id=eq.trip-synthetic-realtime-test` 執行註冊測試，trigger 回傳完全相同的 `invalid column for filter trip_id`。
- 以相同方式測試 `checklists`、`other_info_items`、`exchange_purchases`，三者的 `trip_id` filter 均被接受；測試使用 DO block 子交易回滾，沒有留下 subscription row 或 fixture data。

### 根因判斷與影響界線

- **已確認的程式缺陷：** `ItineraryPage` 直接訂閱一張對 browser roles 完全 REVOKE、刻意透過 SECURITY DEFINER RPC 存取的 Lease table。Realtime 註冊 trigger 需要 `trip_id` 的 SELECT column privilege，與 RPC-only 權限設計直接衝突，因此這條 subscription 在目前 V3.11.8 source／正式 ACL 下必然註冊失敗。
- **正式錯誤歸因限制：** 10 筆正式 error log 沒有保留 subscription table／filter bind parameters；現行 source 中上述 Lease subscription 是已證實的失敗路徑，但不能把每筆正式錯誤逐一映射到它，也不能排除另有舊 client／其他 subscription。
- **可能的產品影響：** Lease row 變更無法透過這條 Realtime subscription 即時觸發 `refresh()`；目前仍有初始 RPC 讀取及 focus／visibility refresh fallback。此問題可能使跨 client Lease 狀態更新延遲，但尚未證明它就是 10:25:08 Save 403 的直接原因。
- **未授權變更：** 本輪只做唯讀正式查證及本機 trigger reproduction；沒有 grant SELECT、建立 RLS policy、移除／替換 Realtime subscription、修改程式、部署或 commit／push。修正方向涉及 Lease 權限與事件傳遞契約，須在既有 ADR-001／ADR-002 邊界內另行確認，不在本輪自行改動。
