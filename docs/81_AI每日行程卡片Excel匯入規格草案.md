## 已確認決策紀錄（2026-10-19）

1. **使用情境與最小化原則**：使用者先手動建立並儲存一筆 Trip；初始日期可先填暫定日期，天數預設為 1 天。再用標準 `.xlsx` 範本人工整理或由 AI 依規則產生每日行程，匯入後由系統建立基本每日卡片，避免逐張手動新增。
2. **Excel 資料交換範圍**：匯出與匯入都只處理每日行程卡片、Trip 出發日期及旅程天數。其他功能資料一律不匯出也不匯入，包含 Trip 名稱、`guided`／`selfGuided` 旅程性質、帳本、其他資訊及所有不屬於每日卡片的模組資料。Excel 出發日期可與目標 Trip 不同，差異需在匯入預覽顯示並由使用者二次確認，不是阻擋條件。
3. **天數與卡片**：Excel 天數為準；增加天數時建立相應日期資料，縮短時移除超出範圍的舊天數與卡片；匯入範圍內原有卡片全部取代。新卡片 ID 由系統產生。
4. **系統管理欄位排除**：不從 Excel 匯入 Place ID、座標、天氣、照片／Storage 路徑、路線估算、移動方式或其他系統管理欄位。天氣預設不勾選，完全不列入 V1 匯入欄位或匯入觸發流程。
5. **地點資料處理與配對積分（已定案）**：Excel 必填「地點名稱＋完整地址」，Plus Code V1 不填。匯入時以名稱與完整地址交叉搜尋／確認 Google Maps 店點，採簡單的 3／2／1／0 分規則，不開發名稱相似度評分、多階段候選排序或其他複雜配對機制。3 分代表名稱與地址都符合同一店點；2 分代表名稱唯一符合且沒有地址衝突；1 分代表地址唯一符合；0 分代表無可靠候選、最高分候選不唯一或名稱／地址資料互相衝突。3 分與 2 分成功配對時保存 Maps 店點識別資料，卡片主要顯示名稱沿用 Excel 原始名稱；1 分時以地址作為地點顯示／地圖搜尋值，避免把不確定的名稱當成已確認店點；0 分時仍允許匯入其他卡片資料，保留 Excel 原始地點名稱與地址資料，但地圖搜尋欄位留白並提示使用者手動更新地圖，不得盲選排名第一的候選。0 分項目不得被當成已確認的 Google Place，不得依未確認地點觸發需要已確認地點的天氣或路線功能。
6. **嚴格雲端保護**：完整檔案先驗證並在記憶體組裝新資料，再顯示差異預覽及二次確認。匯入前必須能確認在線與雲端版本；離線、版本衝突或無法確認雲端版本時停止，不得只寫本機或宣稱成功。寫入失敗保留舊資料；只有整批雲端提交成功後才能更新 UI 並安排舊照片清理。
7. **復原策略（使用者選擇 D／自訂）**：遵守不過度開發原則，V1 不新增每次匯入的持久化快照子系統，也不承諾匯入成功後可一鍵還原上一版。V1 重點是匯入失敗時不破壞舊資料；若日後明確需要成功後復原，再另行評估最小單筆 Trip 備份。
8. **離開時間（使用者選擇 B）**：`arrival_time` 必填；`departure_time` 可空白，空白時系統以抵達時間作為離開時間，不阻止匯入。
9. **實作邊界**：現有一般儲存入口可能在雲端同步失敗時仍更新本機 UI 或排程照片清理，因此不能未經調整就直接作為嚴格匯入入口；須設計具雲端成功閘門的專用整批流程。以上為規格決策，尚未授權開始程式實作或資料庫變更。

## 1. 目標與範圍

讓使用者能將 AI 產生的每日行程資料整理成固定格式的 Excel 檔，再匯入 Travel-Companion 既有旅程。

- 正式匯入格式：Excel .xlsx。
- Markdown 可用於需求整理及人工審閱，但不是 V1 正式匯入格式。
- 匯入目標必須是已建立並儲存的既有旅程；確認覆蓋後更新該 Trip 的起始日期與旅程天數，並取代全部每日行程卡片，不建立新旅程。
- 跟團／自駕是目標旅程既有的旅程性質，不是每日卡片類別，也不需要匯入。
- 共用一份範本，不為跟團與自駕製作兩份不相容的範本。
- 不匯入移動方式、路線距離／時間、Google Place ID、座標、天氣資料、照片、卡片 ID 或其他系統計算欄位。
- 自駕／跟團專屬資訊及額外備註不納入匯入；本功能只處理每日行程卡片所需資料。

## 2. Excel 範本

工作簿包含兩張工作表：

1. 使用說明：範本版本、欄位定義、格式規則、現有卡片類別允許值、出發日期、旅程天數及注意事項。不得將 Trip 名稱或其他功能資料放入匯出檔；目標 Trip 名稱如需顯示，只能由 APP 在匯入預覽畫面讀取目前選定的 Trip 顯示，不屬於 Excel 資料。
2. 每日行程：第一列固定欄位標題，每列代表一張行程卡片。每日卡片總數與每日分布由系統依資料列計算，不由 AI 提供的摘要數字決定。

匯出功能應產生相同格式的 `.xlsx`，只輸出目前已儲存旅程的出發日期、天數與每日行程卡片，讓檔案可供後續編輯並重新匯入。不得輸出 Trip 名稱、旅程性質、帳本、其他資訊或其他功能模組資料。匯入目標仍以 APP 當下選定的既有 Trip 為準；Excel 不攜帶目標 Trip 名稱或識別資料，也不依檔案內其他文字自動切換目標。

不得以合併儲存格、空白分隔列、顏色或額外小標題承載資料。欄位標題固定，不允許 AI 任意改名或新增欄位。

## 3. V1 標準欄位

| 標準欄位 | 中文名稱 | 必填 | 規則 |
|---|---|---:|---|
| day_number | 第幾天 | 是 | 正整數，須在 Excel「使用說明」所定義的匯入旅程天數範圍內 |
| arrival_time | 抵達／開始時間 | 是 | 使用 24 小時制時間；匯入時依現有時間驗證與正規化規則處理 |
| departure_time | 離開／結束時間 | 否 | 空白時使用抵達時間，與目前卡片儲存行為一致 |
| title | 行程名稱 | 是 | 去除前後空白後不得為空 |
| category | 行程卡片類別 | 是 | 必須是專案目前支援的類別之一 |
| location | 地點名稱 | 是 | 填寫卡片應顯示的地點名稱；匯入後保留並直接顯示此原始名稱，不以 Google Maps 回傳名稱覆蓋 |
| location_address | 完整地址 | 是 | 提供完整地址，匯入時以此搜尋 Google Maps 店點；地址本身不是已確認地點或 Place ID |
| description | 行程描述 | 否 | 卡片內容說明；不作為跟團／自駕專屬備註的獨立匯入管道 |

### 現有卡片類別

依目前 src/components/ItineraryPage.tsx 的 ITINERARY_TYPE_OPTIONS，已核對的類別為：

- 交通
- 住宿
- 景點
- 餐飲
- 自駕
- 其他

範本正式版應以程式中的選項清單作為允許值來源，避免文件與程式日後不一致。Excel 可顯示使用者看得懂的中文名稱；匯入端須以明確對照映射到程式內部值，不得讓 AI 自創類別。

## 4. 時間與日期規則

- 使用 day_number 表示旅程中的第幾天；不要求 AI 在每張卡片填寫實際日期或星期。
- 工作簿「使用說明」中的起始日期與旅程天數是整趟旅程匯入資料的一部分，必須提供有效值；確認覆蓋後以 Excel 值更新 APP 旅程起始日期與天數。
- day_number 必須是正整數，且不得大於 Excel 中的旅程天數；有效旅程天數至少涵蓋所有行程資料列所需的天數。若天數與卡片資料互相矛盾，視為驗證錯誤，不執行覆蓋。
- arrival_time 必填，依現有程式的時間驗證與正規化規則處理。
- departure_time 可空白；空白時離開時間等於抵達時間。
- 第一版不另外定義跨午夜時間區間的匯入支援；遇到跨午夜行程時，先由使用者在匯入前調整資料。

## 5. 地點、交通與系統欄位

- Excel 必須提供 `location`（原始地點名稱）與 `location_address`（完整地址）。匯入時使用名稱與地址交叉搜尋／確認 Google Maps 店點，採簡單的積分規則，不使用名稱相似度模型或多階段候選排序。Plus Code V1 不填，也不列入匯入欄位。
- 配對積分：**3 分**＝名稱與地址都符合同一店點；**2 分**＝名稱唯一符合，且沒有地址衝突；**1 分**＝地址唯一符合；**0 分**＝沒有可靠候選、最高分候選不唯一，或名稱與地址互相衝突。依最高分結果判斷，但若最高分仍有多個候選，不可任意選第一筆。
- 3 分與 2 分：保存可靠確認的 Maps 店點識別資料，卡片主要顯示名稱保留 Excel 的原始 `location`，不以 Maps 回傳名稱取代。
- 1 分：以地址作為地點顯示／地圖搜尋值，避免把未充分確認的名稱當成確定店點。
- 0 分：不阻擋整份 Excel 匯入，其他卡片資料照常匯入；保留 Excel 原始地點名稱與地址資料，但地圖搜尋欄位留白，並提示使用者進入編輯時手動更新地圖。不可盲選排名第一的候選。
- 0 分項目不得被誤認為已確認 Google Place，也不得使用未確認地點的 Place ID／座標觸發天氣或路線計算。使用者不需要在匯入時逐筆挑選候選。
- V1 不要求填寫移動方式。地點尚未確認時，要求 AI 指定交通方式沒有必要。
- 匯入不得觸發自動路線估算，也不得寫入或捏造交通模式、交通時間、距離或路線快取。
- 卡片 ID 由系統產生。
- 類別顏色沿用現有類別設定，不由 AI 或 Excel 指定。
- 不匯入座標、天氣快取、照片或 Storage 路徑等系統管理欄位。

## 6. 匯入流程

1. 使用者先建立並儲存目標 Trip，再從功能表「匯率換算」下方的「其他功能」進入「匯入 Excel 行程」；同一處提供「匯出 Excel 行程」。入口操作的目標固定為 APP 目前選定且已儲存的 Trip，避免跨日批次操作被誤認為單日行程管理。
2. 使用者上傳 `.xlsx`。系統檢查工作表、範本版本、必要欄位、起始日期、旅程天數、欄位值與時間格式；驗證失敗時不修改任何資料。
3. 系統計算並顯示覆蓋前差異摘要，至少包含目標 Trip 名稱、起始日期變化、旅程天數變化、原有與匯入卡片總數，以及每日卡片數量變化；同時列出錯誤與警告。
4. 系統明確警告這是整趟旅程覆蓋操作。使用者須在差異預覽後再次按下「確認覆蓋並匯入」；取消則不修改資料。
5. 使用者確認後，重新確認在線狀態與最新雲端版本；若離線、版本衝突或無法確認雲端版本，立即停止且不做本機單獨寫入。通過檢查後，以 Excel 的起始日期與旅程天數更新目標 Trip，並以 Excel「每日行程」工作表中的全部卡片取代原有每日行程卡片。無論天數增加或縮短、日期不同、原有卡片與匯入卡片相似，均不再分別詢問或逐張保留；這是使用者已明確確認的全覆蓋操作。
6. 只覆蓋本規格明確列出的旅程欄位與每日行程卡片；旅程名稱、旅程性質及其他不在匯入範圍的設定維持 APP 原值。系統管理欄位不由 Excel 寫入，必要識別資料由系統重新產生或依現有安全規則處理。
7. 只有整批雲端提交成功後才回報成功結果，包括實際更新的日期、天數與卡片數量。失敗時保留原資料，不得把部分成功回報為整批成功；若底層儲存無法保證整批提交，實作前必須先補足必要的原子性或安全補償設計。

## 7. 全覆蓋、錯誤處理與安全邊界

- **整趟旅程全覆蓋**：使用者完成二次確認後，起始日期、旅程天數與匯入範圍內的全部每日行程卡片，一律依 Excel 內容更新／取代。天數增加或縮短、起始日期不同、既有卡片位於縮短後的日期範圍等情況，不再設計不同的分支詢問。
- **不做逐張重複判斷**：全覆蓋後不保留原有卡片，也不需要為疑似重複卡片另外警告；差異摘要中的原有／匯入卡片數量已足以讓使用者判斷影響。
- **必要資料錯誤**：例如缺標題、無效起始日期、無效旅程天數、卡片天數超出 Excel 旅程範圍、無效時間或不支援的類別，阻止覆蓋並指出工作表、列號與欄位。
- **地點資料處理**：`location`（Excel 原始地點名稱）與 `location_address`（完整地址）為必填；以名稱＋地址交叉搜尋 Google Maps，依 3／2／1／0 分規則選擇可靠候選。3 分（名稱＋地址同一店點）及 2 分（名稱唯一符合且地址無衝突）保存 Maps 店點識別資料，卡片主要顯示名稱保留 Excel 原始名稱；1 分（地址唯一符合）以地址作為地點顯示／地圖搜尋值；0 分（無可靠候選、最高分不唯一或資料衝突）仍匯入其他卡片資料，但地圖搜尋欄留白，保留原始名稱／地址資料並提示使用者手動更新地圖。不得盲選第一筆候選；0 分項目不得被當成已確認 Google Place，亦不得以未確認地點啟動依賴已確認地點的天氣或路線功能。
- **空白離開時間**：以抵達時間補入。
- **缺少描述或地點不明確**：依欄位規則允許或警告；不得自行補造地點事實。
- **覆蓋範圍限制**：不因 Excel 內容而改寫 Trip 名稱、`guided`／`selfGuided` 旅程性質、Place ID、座標、天氣快取、照片／Storage 路徑、類別顏色、路線估算、移動方式或其他未列入匯入範圍的系統管理資料。被取代的舊卡片不會自動把照片附掛到新卡片；舊照片資產是否清理須遵守 APP 既有安全規則，不可因匯入而盲目刪除。新卡片 ID 由 APP 依既有規則產生。
- **完整性與雲端保護**：寫入前先完整驗證工作簿，並在記憶體建構完整的新 Trip 資料。二次確認後，若離線、雲端版本衝突或無法確認雲端版本，立即停止，不得退回本機單獨寫入。必須保留樂觀鎖／版本衝突保護；只有整批雲端寫入成功後才能更新 UI 與排程清理舊照片。失敗時舊資料與舊照片均須保留，不可將部分成功回報為整批成功。
- **復原範圍（V1）**：不新增每次匯入的持久化快照子系統，不承諾匯入成功後一鍵還原；這是控制複雜度的明確取捨。既有每日卡片歷程與全應用程式快照是不同用途的復原機制，不可宣稱等同於單次匯入交易回滾。

## 8. 實作時的架構要求

目前每日行程儲存資料使用 daysData，卡片型別為 ItineraryItem；既有 UI 儲存入口會進行時間驗證、產生 ID、排序及可能的路線估算。因此未來匯入應設計專用的解析／驗證／整批取代流程，沿用合適的型別與儲存入口，但不得直接逐張模擬 UI 新增而意外觸發路線估算。

已核對：
- 每日卡片類別選項目前為「交通、住宿、景點、餐飲、自駕、其他」。
- 空白離開時間在現有儲存邏輯中會回退為抵達時間。
- 專案已有 ExcelJS 用於其他模組的 Excel 功能，但目前尚未找到每日行程卡片的 XLSX 匯入流程。

實作前仍須核對：
- category 中文顯示值與內部 type 值的完整對照，以及 typeColor 的權威來源。
- daysData 的日期鍵值、卡片排序與 ID 正規化規則。
- 專用匯入流程如何在雲端版本驗證及整批提交成功後才更新 UI，並確保同步失敗時不更新本機畫面、不清理舊照片；不可直接沿用行為不符合此條件的一般儲存入口。
- `arrival_time` 必填；`departure_time` 可空白，空白時等於 `arrival_time`（已定案，選項 B）。
