>
> 開發狀態：尚未實作程式。本文只記錄規劃，不代表已核准開始開發。
>
> 範圍限制：只處理已儲存 Trip 的起始日期、旅程天數與每日行程卡片全覆蓋，不建立新旅程、不擴充其他旅程設定或模組。
>
> 決策紀錄更新：2026-10-19。已定案的產品規則以本文「已確認決策紀錄」及後續流程／驗收矩陣為準；剩餘項目主要是實作前的程式結構與安全性核對，不代表重新開放已定案的產品決策。

## 已確認決策紀錄（2026-10-19）

1. **使用情境與最小化原則**：使用者先手動建立並儲存一筆 Trip；初始日期可先填暫定日期，天數預設為 1 天。再用標準 `.xlsx` 範本人工整理或由 AI 依規則產生每日行程，匯入後由系統建立基本每日卡片，避免逐張手動新增。
2. **Excel 資料交換範圍**：匯出與匯入都只處理每日行程卡片、Trip 出發日期及旅程天數。其他功能資料一律不匯出也不匯入，包含 Trip 名稱、`guided`／`selfGuided` 旅程性質、帳本、其他資訊及所有不屬於每日卡片的模組資料。Excel 出發日期可與目標 Trip 不同，差異需在匯入預覽顯示並由使用者二次確認，不是阻擋條件。
3. **天數與卡片**：Excel 天數為準；增加天數時建立相應日期資料，縮短時移除超出範圍的舊天數與卡片；匯入範圍內原有卡片全部取代。新卡片 ID 由系統產生。
4. **系統管理欄位排除**：不從 Excel 匯入 Place ID、座標、天氣、照片／Storage 路徑、路線估算、移動方式或其他系統管理欄位。天氣預設不勾選，完全不列入 V1 匯入欄位或匯入觸發流程。
5. **地點資料處理與確認規則（2026-10-19 定案）**：V1 不採用 3／2／1／0 自動配對評分。匯入解析時保留 Excel 的原始地點文字，允許空白；若範本有 `location_address`，只可作為當次地圖搜尋的輔助文字，不保存到卡片或資料庫，也不新增資料欄位／資料表。一般情況下，每張卡片的地點確認都必須明確選擇以下其中一項，才能完成該地點確認步驟並繼續儲存確認結果：①選擇一個地圖候選地點，取得有效 `placeId`；②選擇「不帶入地圖地點，保留原始地點欄位（可空白）」，保留 Excel 原始地點文字且不設定 Place ID。例外：若 `location` 與 `location_address` 兩欄都空白，允許直接跳過該卡片的地點確認，視為不帶入地圖地點、不設定 Place ID，且不觸發該地點的天氣或路線功能。其他未操作／未選擇的地點仍不可視為已確認或自動當成不帶入地圖地點。不得自動採用排名第一的候選。卡片顯示名稱保留 Excel 原始地點文字（包含空白）；選定的 Google 地點只用於確認 Place ID，不把地址額外存入卡片。選擇不帶入地圖地點時，卡片仍可隨整份匯入儲存，但不得被當成已確認 Google Place，也不得以該地點觸發天氣或路線功能。V1 不增加逐筆 Place Details 呼叫，除非後續確認現有搜尋介面無法提供選取所需的基本資訊。
6. **雲端保護與空白單日旅程限定強制匯入（2026-10-19 定案）**：完整檔案先驗證並在記憶體組裝新資料，再顯示差異預覽及二次確認。一般情況沿用雲端版本衝突保護；但使用者在確認匯入當下，若最新雲端狀態明確符合「目標 Trip 恰為 1 天，且該日沒有任何行程卡片」，允許限定強制匯入覆蓋，不要求使用者為這個空白初始 Trip 反覆處理一般預覽版本差異。此例外不是無條件忽略競態：提交仍須以剛確認的雲端版本／updated_at 作條件，若確認與提交之間資料又變更，則不得覆蓋新資料，重新讀取並按最新狀態處理。離線或無法讀取／確認最新雲端狀態時不允許強制匯入，也不得只寫本機或宣稱成功。只有整批雲端提交成功後才能更新 UI；匯入成功後優先透過既有同步機制讓其他設備取得新資料，不另建同步子系統。由於強制匯入前目標必須是無卡片的單日 Trip，不應存在由現有卡片引用的舊封面照片；不得因這項例外額外執行無法證明安全的照片刪除。
7. **復原策略（使用者選擇 D／自訂）**：遵守不過度開發原則，V1 不新增每次匯入的持久化快照子系統，也不承諾匯入成功後可一鍵還原上一版。V1 重點是匯入失敗時不破壞舊資料；若日後明確需要成功後復原，再另行評估最小單筆 Trip 備份。
8. **離開時間（使用者選擇 B）**：`arrival_time` 必填；`departure_time` 可空白，空白時系統以抵達時間作為離開時間，不阻止匯入。
9. **實作邊界**：現有一般儲存入口可能在雲端同步失敗時仍更新本機 UI 或排程照片清理，因此不能未經調整就直接作為嚴格匯入入口；須設計具雲端成功閘門的專用整批流程。以上為規格決策，尚未授權開始程式實作或資料庫變更。
10. **地點確認摘要與三個操作選項（2026-10-19 定案）**：完成逐張地點選擇後，在匯入前簡單顯示三項數量：「已選擇地圖地點」、「未確認地點」、「不設定地點」。第三項「不設定地點」專門計算 `location` 與 `location_address` 兩欄都空白、因而自動略過確認的卡片；不把這類卡片併入「未確認地點」，也不併入使用者主動選擇不帶入地圖地點的數量。摘要不必逐一列出所有卡片名稱。摘要畫面必須同時提供三個選項：①「回去確認全部地點」；②「再次確認尚未完成的地點」；③「完成並儲存」。選擇①時，重新逐張顯示全部需要使用者確認的地點；每張卡片預先帶入上次選擇的候選作為提示，但該候選只屬於「預先選取、尚未確認」，不可直接視為已確認或自動提交。兩欄都空白、已自動略過的卡片不要求重新確認。使用者可明確再次選擇該候選、改選其他候選，或選擇「不帶入地圖地點，保留原始地點欄位（可空白）」。選擇②只重新顯示尚未完成選擇的地點；完成每筆選擇後自動返回摘要並重新計算三項數量及三個選項。若任何需要確認的地點未選擇上述兩項之一，禁止完成／儲存地點確認流程；不得將未操作視為已選擇不帶入地圖地點。選擇③表示完成並保存目前匯入流程中的地點選擇結果，繼續至匯入預覽／最終覆蓋確認；不代表跳過原有的最終匯入二次確認。選擇不帶入地圖地點的卡片仍可匯入，原始地點文字允許為空白且不設定 Place ID。
11. **地點文字允許空白（2026-10-19 定案）**：`location` 欄位可以是空白；適用於不需要指定地點的行程。若 `location` 與 `location_address` 兩欄都空白，依 2026-10-19 決策允許直接跳過該卡片的地點確認，視為不帶入地圖地點、不設定 Place ID，且不觸發該地點的天氣或路線功能。若只有 `location` 空白但 `location_address` 有值，仍以地址作初始搜尋文字，須依一般規則明確選擇地圖候選或不帶入地圖地點。不得要求為了儲存卡片而填入虛構地點。若選擇地圖候選，則仍須選擇有效候選並保存 Place ID。行程名稱等其他必要欄位仍依原規則驗證。
12. **地圖搜尋次數依現有設計，不另設新限制（2026-10-19 定案）**：沿用目前 PWA 地點搜尋規則，使用者可在結果不理想時調整關鍵字重新搜尋；V1 不新增人工設定的重搜次數上限。沿用既有旅程管理權限驗證及輸入驗證（搜尋文字 2–120 字元）。本次檢視的 `travel-route` Edge Function 未發現獨立的 Place Autocomplete 搜尋次數上限；Google Cloud 專案本身的 API 配額／限制仍照常生效。地點照片查詢有獨立既有額度限制，不應誤認為 Autocomplete 搜尋次數限制。若服務拒絕或暫時不可用，顯示既有錯誤，不以無限自動重試或額外自動重送繞過限制。
13. **`location_address` 的搜尋輔助方式（2026-10-19 定案，選項 A）**：若 Excel 的 `location` 有值，先以原始地點名稱作為初始搜尋文字；若搜尋結果不理想，使用者可自行在搜尋輸入中加入地址或調整關鍵字後重新搜尋。若 `location` 空白但 `location_address` 有值，則以 `location_address` 作為初始搜尋文字；這只影響搜尋輸入，不會把地址填入卡片顯示名稱。若 `location` 與 `location_address` 都空白，允許直接跳過該卡片地點確認；視為不帶入地圖地點、不設定 Place ID，也不觸發該地點的天氣或路線功能。`location_address` 不自動與非空白地點名稱合併、不直接取代非空白地點名稱，也不保存到卡片或資料庫；卡片顯示名稱仍保留 Excel 原始 `location` 文字（可以空白）。搜尋輸入沿用現有 PWA 的單一文字欄位、2–120 字元驗證與手動重搜流程，不新增重搜次數限制。

## 1. 目標與範圍

讓使用者能將 AI 產生的每日行程資料整理成固定格式的 Excel 檔，再匯入 Travel-Companion 既有旅程。

- 正式匯入格式：Excel .xlsx。
- Markdown 可用於需求整理及人工審閱，但不是 V1 正式匯入格式。
- 匯入目標必須是已建立並儲存的既有旅程；確認覆蓋後更新該 Trip 的起始日期與旅程天數，並取代全部每日行程卡片，不建立新旅程。
- 跟團／自駕是目標旅程既有的旅程性質，不是每日卡片類別，也不需要匯入。
- 共用一份範本，不為跟團與自駕製作兩份不相容的範本。
- 不匯入移動方式、路線距離／時間、Google Place ID、座標、天氣資料、照片、卡片 ID 或其他系統計算欄位。
- 自駕／跟團專屬資訊及額外備註不納入匯入；本功能只處理每日行程卡片所需資料。

## 2. Excel 範本

工作簿包含兩張工作表：

1. 使用說明：範本版本、欄位定義、格式規則、現有卡片類別允許值、出發日期、旅程天數及注意事項。不得將 Trip 名稱或其他功能資料放入匯出檔；目標 Trip 名稱如需顯示，只能由 APP 在匯入預覽畫面讀取目前選定的 Trip 顯示，不屬於 Excel 資料。
2. 每日行程：第一列固定欄位標題，每列代表一張行程卡片。每日卡片總數與每日分布由系統依資料列計算，不由 AI 提供的摘要數字決定。

匯出功能應產生相同格式的 `.xlsx`，只輸出目前已儲存旅程的出發日期、天數與每日行程卡片，讓檔案可供後續編輯並重新匯入。不得輸出 Trip 名稱、旅程性質、帳本、其他資訊或其他功能模組資料。匯入目標仍以 APP 當下選定的既有 Trip 為準；Excel 不攜帶目標 Trip 名稱或識別資料，也不依檔案內其他文字自動切換目標。

不得以合併儲存格、空白分隔列、顏色或額外小標題承載資料。欄位標題固定，不允許 AI 任意改名或新增欄位。

## 3. V1 標準欄位

| 標準欄位 | 中文名稱 | 必填 | 規則 |
|---|---|---:|---|
| day_number | 第幾天 | 是 | 正整數，須在 Excel「使用說明」所定義的匯入旅程天數範圍內 |
| arrival_time | 抵達／開始時間 | 是 | 使用 24 小時制時間；匯入時依現有時間驗證與正規化規則處理 |
| departure_time | 離開／結束時間 | 否 | 空白時使用抵達時間，與目前卡片儲存行為一致 |
| title | 行程名稱 | 是 | 去除前後空白後不得為空 |
| category | 行程卡片類別 | 是 | 必須是專案目前支援的類別之一 |
| location | 地點名稱 | 否 | 可填寫卡片應顯示的地點名稱，也允許空白（例如不需要指定地點的行程）；匯入後保留此原始文字，不以 Google Maps 回傳名稱覆蓋。若此欄與 `location_address` 都空白，可直接略過地點確認；若只有此欄空白但 `location_address` 有值，仍須依一般規則明確選擇地圖候選或「不帶入地圖地點，保留原始地點欄位（可空白）」 |
| location_address | 完整地址 | 否 | 可提供作為地圖搜尋輔助文字；可空白，不代表地點已確認；匯入時不保存到卡片或資料庫 |
| description | 行程描述 | 否 | 卡片內容說明；不作為跟團／自駕專屬備註的獨立匯入管道 |

## 4. 時間與日期規則

- 使用 day_number 表示旅程中的第幾天；不要求 AI 在每張卡片填寫實際日期或星期。
- 工作簿「使用說明」中的起始日期與旅程天數是整趟旅程匯入資料的一部分，必須提供有效值；確認覆蓋後以 Excel 值更新 APP 旅程起始日期與天數。
- day_number 必須是正整數，且不得大於 Excel 中的旅程天數；有效旅程天數至少涵蓋所有行程資料列所需的天數。若天數與卡片資料互相矛盾，視為驗證錯誤，不執行覆蓋。
- arrival_time 必填，依現有程式的時間驗證與正規化規則處理。
- departure_time 可空白；空白時離開時間等於抵達時間。
- 第一版不另外定義跨午夜時間區間的匯入支援；遇到跨午夜行程時，先由使用者在匯入前調整資料。

## 5. 地點、交通與系統欄位

- Excel 範本必須保留 `location` 欄位，但欄位值允許空白；空白代表行程不需要指定地點，不視為匯入錯誤。`location_address`（完整地址）為選填，只作為匯入當下地圖搜尋的暫存輔助文字，不保存到卡片或資料庫，也不新增資料欄位／資料表。若 `location` 有值，先以原始地點名稱搜尋，結果不理想時由使用者自行把地址加入搜尋輸入並重搜；若 `location` 空白但 `location_address` 有值，則以地址作為初始搜尋文字，但不把地址填入卡片顯示名稱；若兩欄都空白，依定案允許直接跳過該卡片地點確認，視為不帶入地圖地點、不設定 Place ID，且不觸發該地點的天氣或路線功能。Plus Code V1 不填，也不列入匯入欄位。
- 一般情況下，使用者逐張卡片確認地點時，必須明確選擇以下其中一項：①選擇地圖候選以設定 `place.placeId`；②選擇「不帶入地圖地點，保留原始地點欄位（可空白）」，保留 Excel 原始地點文字（允許空白）且不設定 Place ID。例外：若 `location` 與 `location_address` 兩欄都空白，允許直接跳過該卡片地點確認，視為不帶入地圖地點、不設定 Place ID，也不觸發該地點的天氣或路線功能。除此以外，兩項都未選擇時不可完成／儲存地點確認流程；不得把其他未操作情況視為已選擇不帶入地圖地點。不得自動採用排名第一的候選。
- 卡片 `location` 一律保留 Excel 原始地點文字（包含空白），不以 Google Maps 回傳名稱或地址覆蓋；Google 地點名稱只在確認介面中協助辨識。
- 已選定有效 Place ID 的卡片才算地圖地點已確認；若使用者選擇「不帶入地圖地點，保留原始地點欄位（可空白）」，該卡片不設定 Place ID，也不得被誤認為已確認 Google Place 或觸發天氣／路線計算。使用者可在匯入後再手動設定地圖地點。
- **地點候選顯示規則沿用目前 PWA 地圖地點搜尋介面**：候選卡片顯示地點照片縮圖（目前先查前 5 筆候選的照片；無照片時顯示地圖圖釘佔位圖，載入中顯示骨架佔位）、地點名稱（`displayName`）、有提供時顯示次要地址文字（`address`）、有照片作者資料時顯示照片署名，以及「在 Google Maps 查看地點資訊」外部連結；保留 Google Maps 標示。此處沿用現有搜尋回傳與照片服務，不要求完整地址，也不新增逐筆 Place Details 請求。
- V1 不要求填寫移動方式。地點尚未確認時，要求 AI 指定交通方式沒有必要。
- 匯入不得觸發自動路線估算，也不得寫入或捏造交通模式、交通時間、距離或路線快取。
- 卡片 ID 由系統產生。
- 類別顏色沿用現有類別設定，不由 AI 或 Excel 指定。
- 不匯入座標、天氣快取、照片或 Storage 路徑等系統管理欄位。

## 6. 匯入流程

1. 使用者先建立並儲存目標 Trip，再從功能表「匯率換算」下方的「其他功能」進入「匯入 Excel 行程」；同一處提供「匯出 Excel 行程」。入口操作的目標固定為 APP 目前選定且已儲存的 Trip，避免跨日批次操作被誤認為單日行程管理。
2. 使用者上傳 `.xlsx`。系統檢查工作表、範本版本、必要欄位、起始日期、旅程天數、欄位值與時間格式；驗證失敗時不修改任何資料。
3. 系統計算並顯示覆蓋前差異摘要，至少包含目標 Trip 名稱、起始日期變化、旅程天數變化、原有與匯入卡片總數，以及每日卡片數量變化；同時列出錯誤與警告。地點確認摘要簡單顯示三項數量：「已選擇地圖地點」、「未確認地點」、「不設定地點」。其中「不設定地點」專門計算 `location` 與 `location_address` 兩欄都空白、已自動略過確認的卡片；不併入未確認數量，也不併入使用者主動選擇不帶入地圖地點的數量。摘要同時提供三個選擇：①「回去確認全部地點」；②「再次確認尚未完成的地點」；③「完成並儲存」。選擇①會重新逐張顯示全部需要使用者確認的地點，並預先帶入上次選擇的候選作為提示；使用者必須明確再次選擇該候選、改選其他候選或選擇「不帶入地圖地點，保留原始地點欄位（可空白）」，不得將預先選取自動當成已確認。兩欄都空白且已自動略過的卡片不要求重新確認。若需要確認的地點兩項都未選擇，不可完成地點確認流程。地點候選資訊顯示沿用目前 PWA 地圖搜尋介面；搜尋文字沿用現有 2–120 字元驗證，無新增重搜次數上限。選擇②只顯示尚未完成選擇的地點；完成後自動返回此摘要並重新顯示三項數量與三個選項。
4. 選擇③「完成並儲存」後，保存本次匯入流程的地點選擇結果並繼續至最終匯入預覽／覆蓋確認；仍須由使用者再次按下「確認覆蓋並匯入」，取消則不修改旅程資料。每張卡片都必須已明確選擇地圖候選或「不帶入地圖地點，保留原始地點欄位（可空白）」；若任一筆既未選擇地圖候選、也未選擇不帶入地圖地點，且該筆 `location` 或 `location_address` 至少一欄有值，禁止完成此步驟並提示尚未處理的地點；兩欄都空白的卡片可直接跳過。選擇或視為不帶入地圖地點的卡片不設定 Place ID，也不觸發天氣／路線功能。
5. 使用者確認後，重新確認在線狀態與最新雲端資料。若最新雲端 Trip 恰為 1 天且當天沒有任何卡片，套用限定強制匯入規則；否則依一般版本衝突規則處理，預覽後若雲端版本已變更，重新載入最新資料、重算差異並要求再次確認，不可直接用新版本號重試覆蓋。即使符合限定強制匯入條件，也必須以剛讀取的雲端版本／updated_at 作條件提交，防止檢查與提交之間發生競態；若條件更新失敗，重新讀取狀態，不可無條件重試。離線或無法確認最新雲端狀態時停止，不做本機單獨寫入。通過檢查後，以 Excel 的起始日期與旅程天數更新目標 Trip，並以 Excel「每日行程」工作表中的全部卡片取代原有每日行程卡片。無論天數增加或縮短、日期不同、原有卡片與匯入卡片相似，均不再分別詢問或逐張保留；這是使用者已明確確認的全覆蓋操作。
6. 只覆蓋本規格明確列出的旅程欄位與每日行程卡片；旅程名稱、旅程性質及其他不在匯入範圍的設定維持 APP 原值。系統管理欄位不由 Excel 寫入，必要識別資料由系統重新產生或依現有安全規則處理。
7. 只有整批雲端提交成功後才回報成功結果，包括實際更新的日期、天數與卡片數量。失敗時保留原資料，不得把部分成功回報為整批成功；若底層儲存無法保證整批提交，實作前必須先補足必要的原子性或安全補償設計。

## 7. 全覆蓋、錯誤處理與安全邊界

- **整趟旅程全覆蓋**：使用者完成二次確認後，起始日期、旅程天數與匯入範圍內的全部每日行程卡片，一律依 Excel 內容更新／取代。天數增加或縮短、起始日期不同、既有卡片位於縮短後的日期範圍等情況，不再設計不同的分支詢問。
- **不做逐張重複判斷**：全覆蓋後不保留原有卡片，也不需要為疑似重複卡片另外警告；差異摘要中的原有／匯入卡片數量已足以讓使用者判斷影響。
- **必要資料錯誤**：例如缺標題、無效起始日期、無效旅程天數、卡片天數超出 Excel 旅程範圍、無效時間或不支援的類別，阻止覆蓋並指出工作表、列號與欄位。
- **地點資料處理**：`location`（Excel 原始地點文字）欄位必須存在，但值可空白；`location_address` 選填，只作當次地圖搜尋的輔助文字，不保存到卡片或資料庫。一般情況下，逐張卡片確認時，使用者必須選定地圖候選以保存 `placeId`，或明確選擇「不帶入地圖地點，保留原始地點欄位（可空白）」。若 `location` 與 `location_address` 兩欄都空白，允許直接跳過該筆地點確認，視為不帶入地圖地點；不設定 Place ID，也不觸發該地點的天氣或路線功能。除這項例外外，未選擇其中一項時不可完成地點確認流程；不可把其他未操作情況視為已選擇不帶入地圖地點。不得盲選第一筆候選。卡片顯示名稱保留 Excel 原始地點文字（包含空白），Google 地點名稱只在確認介面中供辨識。選擇或視為不帶入地圖地點的卡片仍可匯入，但不得被當成已確認 Google Place，也不得以該地點啟動天氣或路線功能；使用者可在匯入後再手動設定地圖地點。V1 不增加額外 Place Details 呼叫。
- **空白離開時間**：以抵達時間補入。
- **缺少描述或地點不明確**：依欄位規則允許或警告；不得自行補造地點事實。
- **覆蓋範圍限制**：不因 Excel 內容而改寫 Trip 名稱、`guided`／`selfGuided` 旅程性質、Place ID、座標、天氣快取、照片／Storage 路徑、類別顏色、路線估算、移動方式或其他未列入匯入範圍的系統管理資料。被取代的舊卡片不會自動把照片附掛到新卡片；舊照片資產是否清理須遵守 APP 既有安全規則，不可因匯入而盲目刪除。新卡片 ID 由 APP 依既有規則產生。
- **完整性與雲端保護**：寫入前先完整驗證工作簿，並在記憶體建構完整的新 Trip 資料。確認時重新讀取雲端最新資料；僅當最新資料恰為 1 天且 0 張卡片時，才適用限定強制匯入。所有匯入提交都須使用剛讀取的 `updated_at` 做條件更新；提交前再次發生變更即中止，不得無條件重試，也不得沿用一般儲存流程的自動版本復原。其他預覽版本衝突則重新載入、重算差異並要求再次確認。離線或無法確認雲端狀態時停止，不得退回本機單獨寫入。只有整批雲端寫入成功後才能更新 UI 與排程清理經確認未再引用的舊照片；明確失敗時保留原資料，結果不明時核對雲端，仍不明則提示待確認且不得清理照片。
- **復原範圍（V1）**：不新增每次匯入的持久化快照子系統，不承諾匯入成功後一鍵還原；這是控制複雜度的明確取捨。既有每日卡片歷程與全應用程式快照是不同用途的復原機制，不可宣稱等同於單次匯入交易回滾。

## 8. 實作時的架構要求

## 10. 範本版本相容性與提交結果

- 範本「使用說明」工作表必須包含固定欄位 `template_version`，V1 標準範本版本值為 `1`。匯入端只接受明確支援的版本；缺少版本欄位、版本值空白、格式錯誤或不支援的版本一律拒絕匯入，不以欄位猜測版本，也不自動改寫使用者檔案。
- 匯入端仍須驗證工作表名稱、固定欄位標題、必要欄位與資料格式；即使 `template_version=1`，若必要欄位缺少、標題重複／改名或工作表結構不符，也要拒絕匯入並指出位置。
- 雲端提交若明確失敗且確認沒有提交，保留原資料且不清理照片。若請求逾時或連線中斷，無法判斷雲端是否已提交，須重新讀取雲端核對；若仍無法確認，顯示「匯入結果待確認」，不可宣稱成功、失敗或保證舊資料未變，也不得清理照片。此處不新增持久化快照或匯入交易子系統。
- 雲端提交成功後，立即以雲端回傳的權威資料更新本機快取與 UI，並讓其他設備透過現有 Trip workspace reconciliation 取得最新資料。目前查證到的 Trip 主資料刷新觸發點是啟動／重新協調、網路恢復、視窗 focus 與頁面回到 visible；目前未找到 `trips` 主資料表的 Realtime 訂閱，因此不能承諾其他設備在仍停留於前景時立即收到事件。**已選方案 A（2026-10-19）：V1 沿用既有刷新機制，不增加 `trips` Realtime 訂閱，也不另建同步子系統。** 匯入端在雲端提交成功後立即更新本機權威快取／UI；其他設備透過啟動／重新協調、網路恢復、視窗 focus、頁面回到 visible 等既有觸發點取得最新資料。其他設備若一直停留在前景，可能不會立即刷新；此為 V1 接受的同步時效限制，不列為本次阻擋項。成功訊息只在確認雲端資料已提交後顯示。限定強制匯入的基礎是單日空白 Trip，因此不應有由舊卡片引用的封面照片；不得因「優先同步」而提早刪除照片或繞過既有安全檢查。
