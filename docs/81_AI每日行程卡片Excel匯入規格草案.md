## 新增 TRIP 匯入／建立欄位決策紀錄（2026-11-02）

> 本節只記錄新增 TRIP 的 Excel 建立流程決策；每日行程卡片 Excel 匯入欄位規則仍見後續章節。逐項討論使用固定編號 P01、P02…；後續回覆沿用相同編號。

1. **P01｜權限安全（已同意，技術核對待完成）**：只有 Super Admin 可使用新增 TRIP Excel 匯入；不得因輸入方式為 Excel 而限制 Super Admin。必須同時在 UI、非 UI 服務／資料庫寫入邊界驗證實際登入者角色，阻擋非 UI 直接呼叫、偽造前端狀態或直接 API 請求繞過權限。現有資料庫 INSERT RLS 是否符合此要求尚待技術核對，不可先宣稱現況安全。
2. **P02｜可由 Excel 控制的資料範圍（已同意）**：系統背景產生、自動計算，或由資料庫／安全規則保護的資料不得由 Excel 指定或覆寫，例如 TRIP ID、卡片 ID、建立／更新時間、預設 Super Admin 帳號與角色及其他系統識別資料。手動新增 UI 可修改或選填的欄位原則上納入 Excel；個別欄位仍須核對實際資料來源、權限及格式。
3. **P03｜中文欄位及備註（部分定案）**：Excel 欄位標題必須使用手動新增 UI 實際顯示的繁體中文，不使用英文程式／資料庫欄位代碼作為使用者欄名。備註、允許值、範例及輸入方式須逐項提出討論；不得自行定稿或使用可能造成不固定輸入格式的開放式說明。
4. **P04-01｜標準範本與嚴格驗證（已同意）**：系統提供含標準初始值的固定格式 Excel 範本，使用者可保留初始值或按固定規則修改資料欄位。匯入時區分允許空白與格式錯誤；允許空白依各欄位專屬規則處理，任何非空白但不符合格式／允許值的資料一律拒絕整份匯入，不猜測、不自動轉換、不靜默忽略。範本版本／格式識別由系統管理，使用者不得任意修改。
5. **P04-02｜記帳參與者（已同意）**：手動新增 TRIP 時系統依資料庫 `admin_profiles` 與 `admin_users` 權威設定，預設帶入兩筆管理者參與者（目前 UI 名稱 Howard、Carol；Email 以資料庫即時設定為準）。Excel 匯入不得建立、覆寫或變更系統預設管理者身分／名單。參與者欄位規則：①整個欄位空白時，匯入自動沿用系統預設參與者，確保不會建立零參與者 TRIP；②新增參與者符合手動新增的名稱／Email 格式及驗證規則時允許匯入；③輸入系統管理者 Email 的參與者資料若符合手動新增規則，依手動新增允許方式處理；④非空白資料若不符合格式、Email 或名稱唯一性規則，拒絕整份匯入。匯入時必須重新讀取資料庫權威管理者名單並驗證最終參與者至少保留一筆 Email 符合現行 Super Admin 名單的參與者；不得只相信 Excel 自填內容。手動新增允許管理者參與者資料調整，此既有規則不可由匯入另行禁止。
6. **P04-03｜可編輯者（已同意）**：可編輯者是 `trip_editor` 授權名單，與記帳參與者及系統預設 Super Admin 不同。Excel 可提供一位或多位可編輯者 Google Email；欄位允許空白，代表不額外授予任何 `trip_editor`。目前手動新增程式沒有至少一位可編輯者的要求。僅經實際 Super Admin 權限驗證者可透過匯入新增授權。
7. **P04-04｜幣別與符號（最新定案，取代先前版本）**：Excel V1 不提供幣別代碼、幣別名稱或幣別符號輸入欄。匯入建立 TRIP 時由系統固定使用 TWD，並依 TWD 自動帶入對應符號；不得由 Excel 資料覆寫。匯入完成後須提醒使用者目前預設幣別為 TWD，請依實際旅行地重新設定。手動新增 UI 原有幣別選擇與符號編輯行為不變。此決策刻意減少欄位及輸入錯誤。
8. **P05-01｜正式範本保存（已同意）**：完成欄位契約與內容定義後，產生一份正式 `.xlsx` 範本，固定放在專案資料夾，供日後提取及修改；不建立多份不相容範本。建議路徑 `docs/templates/AI新增TRIP標準範本_V1.xlsx`，配套欄位契約文件 `docs/templates/AI新增TRIP標準範本_V1_欄位契約.md`。兩份檔案尚未建立，待 P05 欄位契約完成後產生。
9. **P05-01-01｜TRIP 名稱（已定案）**：欄位名稱採手動新增 UI 實際顯示的「TRIP 名稱」；必填。沿用手動新增現行驗證：去除前後空白後不可為空；目前未設定長度上限或字元白名單，Excel V1 不另增限制。
10. **P05-01-02｜出發日期與旅程天數（已定案）**：「出發日期」必填；「結束日期」不列入 Excel 欄位，由系統依出發日期與天數計算；「旅程天數」必填，僅接受整數 1–30。
11. **P05-01-03｜結束日期計算（已定案）**：旅程天數包含出發當日。系統以出發日期加上「旅程天數減 1」計算結束日期。例如出發日期為 2027-02-09、旅程天數為 7，結束日期為 2027-02-15。
12. **P05-01-04｜TRIP 名稱重複規則（已定案）**：TRIP 名稱可以重複；系統會自動將出發日期帶入正式名稱。若計算後的「正式名稱＋出發日期」已與資料庫既有 TRIP 重複，拒絕本次匯入，不覆蓋既有 TRIP。
13. **P05-01-05｜預設幣別（已定案）**：Excel 匯入建立 TRIP 時不提供幣別代碼或幣別符號輸入欄，系統固定以 TWD 作為預設幣別，並依 TWD 帶入符號。匯入完成後提醒使用者：目前預設幣別為 TWD，請依實際旅行地重新設定。此規則刻意減少範本欄位與輸入錯誤；不得因匯入資料而覆寫預設幣別。
14. **P05-01-06｜記帳參與者（已定案，2026-11-02 更新輸入版面）**：採單一工作表，欄位表以「備註｜TRIP欄位｜輸入1｜輸入2｜輸入3｜輸入4｜輸入5」呈現。參與者名稱與 Email 分別使用「參與者名稱」及「參與者 Email」兩列，最多各輸入五位；同一輸入位置的名稱與 Email 配對，例如輸入1名稱對應輸入1 Email。每一對允許同時空白；若填寫，必須從輸入1開始連續填寫，不得跳格。名稱與 Email 只填其中一項即拒絕整份匯入。兩列全部空白時，依 P04-02 沿用系統預設參與者。任何非空白資料仍須符合手動新增的名稱、Email 與名稱唯一性驗證，否則拒絕整份匯入。
15. **P05-01-07｜TRIP 編輯者（已定案，2026-11-02 更新輸入版面）**：使用「TRIP 編輯者 Email」一列，橫向提供「輸入1」至「輸入5」，最多五位。整列可留空，代表不額外指派 `trip_editor`；若有填寫，必須從輸入1開始連續填寫，不得跳格；每個非空白值須符合 Email 驗證規則。不得以逗號或其他分隔符在單一儲存格合併多個 Email。
16. **P05-01-08｜TRIP 備註（已定案：不納入）**：Excel V1 不新增 TRIP 備註欄位。
17. **P05-05｜公開行程（已定案）**：Excel 欄位使用數值 `0`／`1`，不使用「是／否」文字；`0` 代表不公開，僅管理員及本行程受邀編輯者可閱覽；`1` 代表公開，所有使用者及訪客可閱覽。正式範本欄位備註必須明確標示 `0＝不公開`、`1＝公開` 及各自的閱覽範圍，使用者依此對應填寫；不符合 `0` 或 `1` 的非空白值拒絕整份匯入。
18. **P05-06｜顯示農曆日期（已定案）**：Excel 欄位使用數值 `0`／`1`；`0` 代表關閉，不顯示農曆日期；`1` 代表開啟，在西洋月日後顯示農曆月日。此欄位範本預設值為 `1`；正式範本備註須明確列出數值對應與顯示效果。非空白值只接受 `0` 或 `1`，其他值拒絕整份匯入。
19. **P05-07｜旅程型態（已定案）**：對照手動新增 UI 的 `guided`／`selfGuided` 選項，Excel 使用數值 `0`／`1`；`0` 代表「跟團」，`1` 代表「自助 / 自駕」。範本預設值為 `0`（跟團）；非空白值只接受 `0` 或 `1`，其他值拒絕整份匯入。範本欄位備註須明確標示數值對應。

**預設值補充（2026-11-02）**：P05-05「公開行程」預設值為 `0`（不公開）；P05-06「顯示農曆日期」預設值為 `1`（開啟）；P05-07「旅程型態」預設值為 `0`（跟團）。

## 2. Excel 範本

工作簿包含兩張工作表：

1. **TRIP 基本資料**：提供建立新 TRIP 所需的手動新增欄位契約資料，欄位、必填／選填及驗證依本文前段 P01–P05 決策紀錄；不包含系統產生的 TRIP ID、建立時間等欄位。

不得以合併儲存格、空白分隔列、顏色或額外小標題承載資料。欄位標題固定，不允許 AI 任意改名或新增欄位。

## 4. 時間與日期規則

- `day_number` 表示新 TRIP 中的第幾天，必須是正整數，且不得大於 TRIP 基本資料所設定的旅程天數；所有卡片資料列均須落在旅程天數範圍內。
- TRIP 出發日期由「TRIP 基本資料」提供；實際卡片日期由系統依出發日期及 `day_number` 建立，不要求 Excel 每張卡片另填實際日期或星期。
- `arrival_time` 必填，只接受四位數字 `HHMM`，例如 `0930`、`1845`；不接受 `9:30`、`930`、`24:00` 等格式。此為 Excel V1 契約，不改變 App 現有手動編輯欄位的時間輸入行為。
- `departure_time` 可空白；空白時系統以抵達／開始時間補入，與目前卡片儲存行為一致。非空白時採相同 `HHMM` 格式與有效時間檢查。
- 第一版不另外定義跨午夜時間區間的匯入支援；遇到跨午夜行程時，須在匯入前調整資料。

## 5. 地點、交通與系統欄位

- 「行程名稱」對應卡片 `title`，是每日行程卡片的顯示名稱，也是 Excel 必填欄位；去除前後空白後不得為空。
- Excel V1 完全不提供地點名稱、完整地址、`location` 或 `location_address` 欄位；匯入不寫入地點文字，也不執行地點搜尋或確認。
- 卡片建立後，如需地圖地點，使用者可在 App 內編輯卡片，透過現有地圖搜尋／確認功能自行設定。此限制僅適用 Excel 匯入，不改變 App 既有 `location`、Place ID、地圖、天氣及路線功能。
- V1 不匯入移動方式、交通估算、路線距離／時間或路線快取；匯入不得觸發自動路線估算。
- 卡片 ID 由系統產生；類別顏色沿用現有類別設定，不由 Excel 指定。
- 不匯入 Place ID、座標、天氣快取、照片或 Storage 路徑等系統管理欄位。天氣不列入 Excel 欄位，也不得因匯入而觸發天氣更新。

## 6. 匯入流程

1. 使用者在「新增 TRIP」流程中選擇「匯入 Excel」或「手動原始新增」。選擇匯入時直接進入新 TRIP Excel 建立流程，不先建立空白 TRIP，也不從既有 TRIP 功能選單啟動。匯入建立所需的 TRIP 欄位必填／選填規則與手動新增完全一致；每日卡片依本文件第 3～5 節契約驗證。**此流程僅在網路連線可用且雲端服務可正常連線時開放；離線狀態直接禁止開始。**
2. 開始匯入前先檢查網路狀態，再以實際雲端請求確認服務可達，並確認使用者具備新增 TRIP 的權限。`navigator.onLine` 只能作為初步訊號，不可單獨視為雲端可用證明。若離線、雲端請求失敗、逾時或無法確認，停止匯入，不進入會修改資料的流程，也不得改成本機暫存建立。
3. 使用者上傳 `.xlsx`。系統檢查工作表、範本版本、固定欄位、TRIP 基本資料欄位契約、卡片必要欄位、旅程天數、欄位值與時間格式；任何驗證失敗均不得建立 TRIP 或寫入部分卡片，並指出工作表、列號及欄位。
4. 驗證成功後顯示建立預覽，至少包含 TRIP 名稱、出發日期、結束日期、旅程天數、預設幣別 TWD 提醒、參與者／編輯者摘要，以及每日卡片總數與每日分布；列出所有錯誤與警告。此預覽不包含地點確認摘要、Google 地圖候選或地點確認操作。
5. 使用者按下「確認建立」後，依新 TRIP 雲端建立流程提交 TRIP 主資料及每日卡片；提交前再次確認連線、Super Admin 身分及建立欄位共同契約。TRIP ID、卡片 ID、日期資料及其他系統初始結構由系統產生。若建立提交失敗或結果不明，依雲端建立結果核對流程處理；不得本機單獨建立或誤報成功。
6. 只有整批雲端建立成功後才回報成功，並以雲端回傳的權威資料更新本機快取／UI。失敗時不得留下部分建立的 TRIP 或卡片；若底層儲存無法保證整批完整性，實作前必須補足原子性或安全補償設計。

## 7. 匯入初始化、錯誤處理與安全邊界

- **新增 TRIP 匯入建立**：從新增 TRIP 流程選擇匯入，依與手動原始新增相同的 TRIP 欄位契約建立旅程；不得要求先建立已儲存、單日、零卡片的空白 TRIP。若規格其他段落仍出現此限制，均屬舊版錯誤前提，應依本條及本文開頭的 2026-11-02 更正解讀。
- **新增 TRIP 建立不做既有卡片覆蓋／合併**：目標 TRIP 尚未建立，因此匯入流程只建立新旅程及其每日卡片；不執行既有 TRIP 每日卡片的逐張比對、合併或刪除。
- **必要資料錯誤**：例如缺少 TRIP 名稱、出發日期或旅程天數，卡片缺少行程名稱／類別／抵達時間，旅程天數不合法、卡片天數超出旅程範圍、時間格式錯誤或類別不支援，均阻止整份建立並指出工作表、列號與欄位。
- **地點欄位排除**：Excel V1 不提供地點名稱、完整地址、`location` 或 `location_address` 欄位，也不匯入地點文字。匯入過程不搜尋／確認地點、不設定 Place ID 或座標；如需設定地圖地點，使用者於建立完成後在 App 卡片編輯功能自行設定。
- **空白離開時間**：以抵達／開始時間補入。
- **雲端連線與完整性保護**：建立流程只允許在線使用。預檢時以實際雲端請求確認服務可達及操作者有權限；提交前再次確認連線與 Super Admin 身分。只有雲端整批建立成功後才更新本機權威快取／UI。預檢失敗、逾時或建立結果不明時停止或核對雲端，不允許本機暫存／離線建立，不得誤報成功。
- **復原範圍（V1）**：不新增每次匯入的持久化快照子系統，也不承諾匯入成功後一鍵還原；重點是匯入失敗時不得留下部分 TRIP 或卡片。

## 8. 實作時的架構要求

新 TRIP Excel 建立應設計專用的解析／驗證／整批建立流程，重用現有 TRIP 建立資料模型及 ItineraryItem 型別。建立每日卡片時沿用必要的時間驗證、ID 產生、排序及類別設定，但不得呼叫地圖搜尋、路線估算或天氣更新。整份 TRIP 主資料與每日卡片需具備整批建立完整性；不得模擬逐張 UI 新增而意外觸發其他副作用。

已核對：
- 每日卡片類別選項目前為「交通、住宿、景點、餐飲、自駕、其他」。
- 空白離開時間在現有儲存邏輯中會回退為抵達時間。
- 專案已有 ExcelJS 用於其他模組的 Excel 功能，但目前尚未找到每日行程卡片的 XLSX 匯入流程。

實作前待審查清單（僅技術核對，不重新開放產品決策）：
- 核對 `category` 中文顯示值與內部 `type` 的完整對照，以及 `typeColor` 的權威來源。
- 核對 TRIP 建立資料模型、日期鍵值、卡片排序與 ID 正規化規則。
- 設計並驗證 TRIP 主資料與每日卡片的整批建立流程：入口確認網路及雲端服務可用、驗證 Super Admin 權限；提交成功前不更新 UI／本機快取。驗證離線、雲端不可達、預覽期間斷線、欄位／權限不符、提交逾時或連線中斷導致的結果不明，以及既有跨裝置刷新機制。
- 以測試確認匯入過程不呼叫地圖搜尋、不設定 Place ID、不觸發天氣更新或交通估算。

## 9. 明確不在 V1 範圍內

- 新 TRIP Excel 建立不匯入系統產生的 TRIP ID、卡片 ID、建立／更新時間、Place ID、座標、天氣快取、照片／Storage 路徑、路線估算結果或其他系統管理欄位。

- 依卡片內容自動比對重複項目並個別保留／略過。
- 正式資料庫 schema／migration 變更。

## 10. 範本版本相容性與提交結果

- 範本「使用說明」工作表必須包含固定欄位 `template_version`，V1 標準範本版本值為 `1`。匯入端只接受明確支援的版本；缺少版本欄位、版本值空白、格式錯誤或不支援的版本一律拒絕匯入，不以欄位猜測版本，也不自動改寫使用者檔案。
- 匯入端仍須驗證工作表名稱、固定欄位標題、必要欄位與資料格式；即使 `template_version=1`，若必要欄位缺少、標題重複／改名或工作表結構不符，也要拒絕匯入並指出位置。
- 雲端提交若明確失敗且確認沒有提交，保持原有雲端資料且不清理照片。若請求逾時或連線中斷，無法判斷雲端是否已提交，須重新讀取雲端核對；若仍無法確認，顯示「建立結果待確認」，不可宣稱成功或失敗，也不得清理其他既有照片資產。此處不新增持久化快照或匯入交易子系統。
- 雲端建立成功後，立即以雲端回傳的權威資料更新本機快取與 UI；其他設備沿用既有 Trip workspace reconciliation 取得最新資料。目前查證到的 Trip 主資料刷新觸發點是啟動／重新協調、網路恢復、視窗 focus 與頁面回到 visible；目前未找到 `trips` 主資料表的 Realtime 訂閱，因此不能承諾其他設備在仍停留於前景時立即收到事件。**已選方案 A（2026-10-19）：V1 沿用既有刷新機制，不增加 `trips` Realtime 訂閱，也不另建同步子系統。** 其他設備若一直停留在前景，可能不會立即刷新；此為 V1 接受的同步時效限制，不列為本次阻擋項。成功訊息只在確認雲端資料已建立後顯示。

| IM07 | 雲端建立失敗、拒絕及逾時結果不明 | 明確失敗時不更新 UI／本機快取；逾時或斷線時重新核對雲端，仍不明則顯示「建立結果待確認」，不得誤報成功／失敗 | 階段 3 的建立與錯誤處理設計 |
| IM08 | 成功建立後雲端與本機資料完整性 | 核對 TRIP 基本資料、旅程天數與日期、每日卡片、唯一新 ID、時間／類別／排序及系統預設資料；只有雲端整批建立成功後才更新本機權威快取／UI，不得出現部分成功 | IM01–IM07；本機隔離測試環境 |
| IM09 | 地點欄位排除與既有功能隔離 | 驗證範本不含任何地點名稱／地址欄位，不匯入 `location`、`location_address`、Place ID 或座標；匯入不觸發地圖、天氣、照片或路線副作用；建立後仍可在 App 手動設定地點 | 階段 0、1、2 |
| IM10 | 建立後其他裝置透過既有刷新機制取得新 TRIP | 雲端新 TRIP 建立成功後，另一裝置透過啟動／重新協調／網路恢復／focus／visible 等既有觸發取得最新資料；不要求前景即時推送，不新增 Realtime 訂閱或同步子系統 | IM08；既有 reconciliation 契約 |

1. 每次只處理目前階段尚未定案的項目；完成後記錄決策與證據，再進入下一個依賴階段。

3. 若實作過程發現規格矛盾，先回到本文件相應階段修訂並取得 Product Owner 確認；不得私下改變已定案產品規則。
4. 本機 Supabase 測試只能使用明確標記、可識別及可清理的專用測試 Trip；不得 reset 資料庫、修改正式環境或碰觸既有資料。
5. 每項測試記錄：狀態（未開始／待定案／可測試／通過／失敗／阻塞）、前置條件、環境、操作、預期結果、實際結果及證據。未執行不得標記通過。
6. 本計畫不納入 V3.10.12 的 TC01–TC14 舊版同步驗收重測；除非 V3.11.0 實作實際修改相關程式路徑，且能指出具體受影響行為，才新增最小範圍的回歸項目。
7. 本文件的產品決策及範圍限制優先於測試便利性；不得為了通過測試而擴大 V1 範圍。
