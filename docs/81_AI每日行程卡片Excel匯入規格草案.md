## 已確認決策紀錄（2026-10-19）

1. **使用情境與最小化原則**：使用者先手動建立並儲存一筆 Trip；初始日期可先填暫定日期，天數預設為 1 天。再用標準 `.xlsx` 範本人工整理或由 AI 依規則產生每日行程，匯入後由系統建立基本每日卡片，避免逐張手動新增。
2. **Excel 資料交換範圍**：匯出與匯入只處理旅程天數與每日行程卡片。出發日期不放入 Excel，匯入時沿用目標 Trip 原有出發日期，不修改日期。其他功能資料一律不匯出也不匯入，包含 Trip 名稱、`guided`／`selfGuided` 旅程性質、帳本、其他資訊及所有不屬於每日卡片的模組資料。
3. **天數與卡片**：Excel 天數為準；增加天數時建立相應日期資料，縮短時移除超出範圍的舊天數與卡片；匯入範圍內原有卡片全部取代。新卡片 ID 由系統產生。
4. **系統管理欄位排除**：不從 Excel 匯入 Place ID、座標、天氣、照片／Storage 路徑、路線估算、移動方式或其他系統管理欄位。天氣預設不勾選，完全不列入 V1 匯入欄位或匯入觸發流程。
5. **地點資料處理與確認規則（2026-10-19 定案）**：V1 不採用 3／2／1／0 自動配對評分。匯入解析時保留 Excel 的原始地點文字，允許空白；若範本有 `location_address`，只可作為當次地圖搜尋的輔助文字，不保存到卡片或資料庫，也不新增資料欄位／資料表。一般情況下，每張卡片的地點確認都必須明確選擇以下其中一項，才能完成該地點確認步驟並繼續儲存確認結果：①選擇一個地圖候選地點，取得有效 `placeId`；②選擇「不帶入地圖地點，保留原始地點欄位（可空白）」，保留 Excel 原始地點文字且不設定 Place ID。例外：若 `location` 與 `location_address` 兩欄都空白，允許直接跳過該卡片的地點確認，視為不帶入地圖地點、不設定 Place ID，且不觸發該地點的天氣或路線功能。其他未操作／未選擇的地點仍不可視為已確認或自動當成不帶入地圖地點。不得自動採用排名第一的候選。卡片顯示名稱保留 Excel 原始地點文字（包含空白）；選定的 Google 地點只用於確認 Place ID，不把地址額外存入卡片。選擇不帶入地圖地點時，卡片仍可隨整份匯入儲存，但不得被當成已確認 Google Place，也不得以該地點觸發天氣或路線功能。V1 不增加逐筆 Place Details 呼叫，除非後續確認現有搜尋介面無法提供選取所需的基本資訊。
6. **新建空白 Trip 限定與雲端保護（2026-11-02 修訂）**：匯入只允許目標 Trip 在最新雲端狀態符合「恰為 1 天，且整個 Trip 的所有日期均沒有任何行程卡片」時執行；「新建」以此即時雲端資格判斷，不額外設定 Trip 建立時間門檻。這項資格是功能前置條件，不是一般既有旅程覆蓋的例外。匯入前須重新讀取雲端狀態並檢查資格，離線或無法確認最新狀態時停止。提交仍須以剛讀取的 `updated_at` 作條件更新；若檢查與提交之間資料又變更，條件更新失敗即中止，不得無條件重試或覆蓋新資料。匯入只更新旅程天數與每日行程卡片，出發日期及其他 Trip／模組資料均保留原值。只有整批雲端提交成功後才能更新 UI／本機權威快取；其他設備沿用既有同步機制，不另建同步子系統。新建空白 Trip 不應存在由卡片引用的舊封面照片；不得因匯入額外執行無法證明安全的照片刪除。
7. **復原策略（使用者選擇 D／自訂）**：遵守不過度開發原則，V1 不新增每次匯入的持久化快照子系統，也不承諾匯入成功後可一鍵還原上一版。V1 重點是匯入失敗時不破壞舊資料；若日後明確需要成功後復原，再另行評估最小單筆 Trip 備份。
8. **離開時間（使用者選擇 B）**：`arrival_time` 必填；`departure_time` 可空白，空白時系統以抵達時間作為離開時間，不阻止匯入。
9. **實作邊界**：現有一般儲存入口可能在雲端同步失敗時仍更新本機 UI 或排程照片清理，因此不能未經調整就直接作為嚴格匯入入口；須設計具雲端成功閘門的專用整批流程。以上為規格決策，尚未授權開始程式實作或資料庫變更。
10. **地點確認摘要與三個操作選項（2026-10-19 定案）**：完成逐張地點選擇後，在匯入前簡單顯示三項數量：「已選擇地圖地點」、「未確認地點」、「不設定地點」。第三項「不設定地點」專門計算 `location` 與 `location_address` 兩欄都空白、因而自動略過確認的卡片；不把這類卡片併入「未確認地點」，也不併入使用者主動選擇不帶入地圖地點的數量。摘要不必逐一列出所有卡片名稱。摘要畫面必須同時提供三個選項：①「回去確認全部地點」；②「再次確認尚未完成的地點」；③「完成並儲存」。選擇①時，重新逐張顯示全部需要使用者確認的地點；每張卡片預先帶入上次選擇的候選作為提示，但該候選只屬於「預先選取、尚未確認」，不可直接視為已確認或自動提交。兩欄都空白、已自動略過的卡片不要求重新確認。使用者可明確再次選擇該候選、改選其他候選，或選擇「不帶入地圖地點，保留原始地點欄位（可空白）」。選擇②只重新顯示尚未完成選擇的地點；完成每筆選擇後自動返回摘要並重新計算三項數量及三個選項。若任何需要確認的地點未選擇上述兩項之一，禁止完成／儲存地點確認流程；不得將未操作視為已選擇不帶入地圖地點。選擇③表示完成並保存目前匯入流程中的地點選擇結果，繼續至匯入預覽／最終確認；不代表跳過原有的最終匯入二次確認。選擇不帶入地圖地點的卡片仍可匯入，原始地點文字允許為空白且不設定 Place ID。
11. **地點文字允許空白（2026-10-19 定案）**：`location` 欄位可以是空白；適用於不需要指定地點的行程。若 `location` 與 `location_address` 兩欄都空白，依 2026-10-19 決策允許直接跳過該卡片的地點確認，視為不帶入地圖地點、不設定 Place ID，且不觸發該地點的天氣或路線功能。若只有 `location` 空白但 `location_address` 有值，仍以地址作初始搜尋文字，須依一般規則明確選擇地圖候選或不帶入地圖地點。不得要求為了儲存卡片而填入虛構地點。若選擇地圖候選，則仍須選擇有效候選並保存 Place ID。行程名稱等其他必要欄位仍依原規則驗證。
12. **地圖搜尋次數依現有設計，不另設新限制（2026-10-19 定案）**：沿用目前 PWA 地點搜尋規則，使用者可在結果不理想時調整關鍵字重新搜尋；V1 不新增人工設定的重搜次數上限。沿用既有旅程管理權限驗證及輸入驗證（搜尋文字 2–120 字元）。本次檢視的 `travel-route` Edge Function 未發現獨立的 Place Autocomplete 搜尋次數上限；Google Cloud 專案本身的 API 配額／限制仍照常生效。地點照片查詢有獨立既有額度限制，不應誤認為 Autocomplete 搜尋次數限制。若服務拒絕或暫時不可用，顯示既有錯誤，不以無限自動重試或額外自動重送繞過限制。
13. **`location_address` 的搜尋輔助方式（2026-10-19 定案，選項 A）**：若 Excel 的 `location` 有值，先以原始地點名稱作為初始搜尋文字；若搜尋結果不理想，使用者可自行在搜尋輸入中加入地址或調整關鍵字後重新搜尋。若 `location` 空白但 `location_address` 有值，則以 `location_address` 作為初始搜尋文字；這只影響搜尋輸入，不會把地址填入卡片顯示名稱。若 `location` 與 `location_address` 都空白，允許直接跳過該卡片地點確認；視為不帶入地圖地點、不設定 Place ID，也不觸發該地點的天氣或路線功能。`location_address` 不自動與非空白地點名稱合併、不直接取代非空白地點名稱，也不保存到卡片或資料庫；卡片顯示名稱仍保留 Excel 原始 `location` 文字（可以空白）。搜尋輸入沿用現有 PWA 的單一文字欄位、2–120 字元驗證與手動重搜流程，不新增重搜次數限制。

## 1. 目標與範圍

讓使用者能將 AI 產生的每日行程資料整理成固定格式的 Excel 檔，再匯入 Travel-Companion 既有旅程。

- 正式匯入格式：Excel .xlsx。
- Markdown 可用於需求整理及人工審閱，但不是 V1 正式匯入格式。
- 匯入目標必須是新建立並儲存的空白 Trip，且匯入前雲端資格為恰好 1 天、整個 Trip 零張卡片。匯入成功後只更新旅程天數與每日行程卡片；保留目標 Trip 原有出發日期，不建立新旅程，也不允許用此功能覆蓋已使用的既有旅程。
- 跟團／自駕是目標旅程既有的旅程性質，不是每日卡片類別，也不需要匯入。
- 共用一份範本，不為跟團與自駕製作兩份不相容的範本。
- 不匯入移動方式、路線距離／時間、Google Place ID、座標、天氣資料、照片、卡片 ID 或其他系統計算欄位。
- 自駕／跟團專屬資訊及額外備註不納入匯入；本功能只處理每日行程卡片所需資料。

## 2. Excel 範本

工作簿包含兩張工作表：

1. 使用說明：範本版本、欄位定義、格式規則、現有卡片類別允許值、旅程天數及注意事項。不得放入出發日期、Trip 名稱或其他功能資料；目標 Trip 名稱如需顯示，只能由 APP 在匯入預覽畫面讀取目前選定的 Trip 顯示，不屬於 Excel 資料。
2. 每日行程：第一列固定欄位標題，每列代表一張行程卡片。每日卡片總數與每日分布由系統依資料列計算，不由 AI 提供的摘要數字決定。

匯出功能應產生相同格式的 `.xlsx`，只輸出目前已儲存旅程的天數與每日行程卡片，讓檔案可供後續編輯；匯入則僅接受符合「新建、單日、零卡片」資格的目標 Trip。不得輸出出發日期、Trip 名稱、旅程性質、帳本、其他資訊或其他功能模組資料。匯入目標以 APP 當下選定且通過資格檢查的 Trip 為準；Excel 不攜帶目標 Trip 名稱或識別資料，也不依檔案內其他文字自動切換目標。

不得以合併儲存格、空白分隔列、顏色或額外小標題承載資料。欄位標題固定，不允許 AI 任意改名或新增欄位。

## 3. V1 標準欄位

| 標準欄位 | 中文名稱 | 必填 | 規則 |
|---|---|---:|---|
| day_number | 第幾天 | 是 | 正整數，須在 Excel「使用說明」所定義的匯入旅程天數範圍內 |
| arrival_time | 抵達／開始時間 | 是 | 使用 24 小時制時間；匯入時依現有時間驗證與正規化規則處理 |
| departure_time | 離開／結束時間 | 否 | 空白時使用抵達時間，與目前卡片儲存行為一致 |
| title | 行程名稱 | 是 | 去除前後空白後不得為空 |
| category | 行程卡片類別 | 是 | 必須是專案目前支援的類別之一 |
| location | 地點名稱 | 否 | 可填寫卡片應顯示的地點名稱，也允許空白（例如不需要指定地點的行程）；匯入後保留此原始文字，不以 Google Maps 回傳名稱覆蓋。若此欄與 `location_address` 都空白，可直接略過地點確認；若只有此欄空白但 `location_address` 有值，仍須依一般規則明確選擇地圖候選或「不帶入地圖地點，保留原始地點欄位（可空白）」 |

## 4. 時間與日期規則

- 使用 day_number 表示旅程中的第幾天；不要求 AI 在每張卡片填寫實際日期或星期。
- 工作簿「使用說明」只提供旅程天數，不包含出發日期。匯入不得變更 APP 目前 Trip 的出發日期。
- day_number 必須是正整數，且不得大於 Excel 中的旅程天數；有效旅程天數至少涵蓋所有行程資料列所需的天數。若天數與卡片資料互相矛盾，視為驗證錯誤，不執行覆蓋。
- arrival_time 必填，依現有程式的時間驗證與正規化規則處理。
- departure_time 可空白；空白時離開時間等於抵達時間。
- 第一版不另外定義跨午夜時間區間的匯入支援；遇到跨午夜行程時，先由使用者在匯入前調整資料。

## 5. 地點、交通與系統欄位

- Excel 範本必須保留 `location` 欄位，但欄位值允許空白；空白代表行程不需要指定地點，不視為匯入錯誤。`location_address`（完整地址）為選填，只作為匯入當下地圖搜尋的暫存輔助文字，不保存到卡片或資料庫，也不新增資料欄位／資料表。若 `location` 有值，先以原始地點名稱搜尋，結果不理想時由使用者自行把地址加入搜尋輸入並重搜；若 `location` 空白但 `location_address` 有值，則以地址作為初始搜尋文字，但不把地址填入卡片顯示名稱；若兩欄都空白，依定案允許直接跳過該卡片地點確認，視為不帶入地圖地點、不設定 Place ID，且不觸發該地點的天氣或路線功能。Plus Code V1 不填，也不列入匯入欄位。
- 一般情況下，使用者逐張卡片確認地點時，必須明確選擇以下其中一項：①選擇地圖候選以設定 `place.placeId`；②選擇「不帶入地圖地點，保留原始地點欄位（可空白）」，保留 Excel 原始地點文字（允許空白）且不設定 Place ID。例外：若 `location` 與 `location_address` 兩欄都空白，允許直接跳過該卡片地點確認，視為不帶入地圖地點、不設定 Place ID，也不觸發該地點的天氣或路線功能。除此以外，兩項都未選擇時不可完成／儲存地點確認流程；不得把其他未操作情況視為已選擇不帶入地圖地點。不得自動採用排名第一的候選。
- 卡片 `location` 一律保留 Excel 原始地點文字（包含空白），不以 Google Maps 回傳名稱或地址覆蓋；Google 地點名稱只在確認介面中協助辨識。
- 已選定有效 Place ID 的卡片才算地圖地點已確認；若使用者選擇「不帶入地圖地點，保留原始地點欄位（可空白）」，該卡片不設定 Place ID，也不得被誤認為已確認 Google Place 或觸發天氣／路線計算。使用者可在匯入後再手動設定地圖地點。
- **地點候選顯示規則沿用目前 PWA 地圖地點搜尋介面**：候選卡片顯示地點照片縮圖（目前先查前 5 筆候選的照片；無照片時顯示地圖圖釘佔位圖，載入中顯示骨架佔位）、地點名稱（`displayName`）、有提供時顯示次要地址文字（`address`）、有照片作者資料時顯示照片署名，以及「在 Google Maps 查看地點資訊」外部連結；保留 Google Maps 標示。此處沿用現有搜尋回傳與照片服務，不要求完整地址，也不新增逐筆 Place Details 請求。
- V1 不要求填寫移動方式。地點尚未確認時，要求 AI 指定交通方式沒有必要。
- 匯入不得觸發自動路線估算，也不得寫入或捏造交通模式、交通時間、距離或路線快取。
- 卡片 ID 由系統產生。
- 類別顏色沿用現有類別設定，不由 AI 或 Excel 指定。
- 不匯入座標、天氣快取、照片或 Storage 路徑等系統管理欄位。

## 6. 匯入流程

1. 使用者先建立並儲存目標 Trip，再從功能表「匯率換算」下方的「其他功能」進入「匯入 Excel 行程」；同一處提供「匯出 Excel 行程」。入口操作的目標固定為 APP 目前選定且已儲存的 Trip，避免跨日批次操作被誤認為單日行程管理。**匯入入口僅在網路連線可用且雲端服務可正常連線時開放；離線狀態直接禁止開始匯入。**
2. 開始匯入前先執行連線預檢：先檢查瀏覽器網路狀態，再以實際雲端讀取請求確認服務可達且使用者具備讀取目標 Trip 的權限。`navigator.onLine` 只能作為初步訊號，不可單獨視為網路品質良好或雲端可用的證明。若離線、雲端請求失敗、逾時或無法確認讀取結果，停止匯入並提示檢查連線；不得進入會修改資料的流程，也不得改成本機暫存匯入。
3. 使用者上傳 `.xlsx`。系統檢查工作表、範本版本、必要欄位、旅程天數、欄位值與時間格式；驗證失敗時不修改任何資料。
4. 系統計算並顯示匯入摘要，至少包含目標 Trip 名稱、出發日期保留提示、匯入前 0 張卡片、匯入後旅程天數與卡片總數，以及每日卡片數量分布；同時列出錯誤與警告。地點確認摘要簡單顯示三項數量：「已選擇地圖地點」、「未確認地點」、「不設定地點」。其中「不設定地點」專門計算 `location` 與 `location_address` 兩欄都空白、已自動略過確認的卡片；不併入未確認數量，也不併入使用者主動選擇不帶入地圖地點的數量。摘要同時提供三個選擇：①「回去確認全部地點」；②「再次確認尚未完成的地點」；③「完成並儲存」。選擇①會重新逐張顯示全部需要使用者確認的地點，並預先帶入上次選擇的候選作為提示；使用者必須明確再次選擇該候選、改選其他候選或選擇「不帶入地圖地點，保留原始地點欄位（可空白）」，不得將預先選取自動當成已確認。兩欄都空白且已自動略過的卡片不要求重新確認。若需要確認的地點兩項都未選擇，不可完成地點確認流程。地點候選資訊顯示沿用目前 PWA 地圖搜尋介面；搜尋文字沿用現有 2–120 字元驗證，無新增重搜次數上限。選擇②只顯示尚未完成選擇的地點；完成後自動返回此摘要並重新顯示三項數量與三個選項。
4. 選擇③「完成並儲存」後，保存本次匯入流程的地點選擇結果並繼續至最終匯入預覽／確認；仍須由使用者再次按下「確認匯入」，取消則不修改旅程資料。每張卡片都必須已明確選擇地圖候選或「不帶入地圖地點，保留原始地點欄位（可空白）」；若任一筆既未選擇地圖候選、也未選擇不帶入地圖地點，且該筆 `location` 或 `location_address` 至少一欄有值，禁止完成此步驟並提示尚未處理的地點；兩欄都空白的卡片可直接跳過。選擇或視為不帶入地圖地點的卡片不設定 Place ID，也不觸發天氣／路線功能。
5. 使用者確認後，重新確認在線狀態與最新雲端資料。僅當最新雲端 Trip 恰為 1 天且整個 Trip 的所有日期均為 0 張卡片時，才符合匯入資格；不符合即阻止匯入，不提供一般既有旅程覆蓋路徑。通過資格檢查後，以剛讀取的 `updated_at` 作條件更新，防止檢查與提交之間發生競態；若條件更新失敗即中止並提示重新整理／確認，不可無條件重試。離線或無法確認最新雲端狀態時停止，不做本機單獨寫入。匯入依 Excel 的旅程天數建立日期資料（可維持 1 天或增加天數），並以 Excel「每日行程」工作表中的卡片建立每日行程；目標 Trip 出發日期及其他既有資料維持不變。
6. 只更新本規格明確列出的旅程天數與每日行程卡片；出發日期、旅程名稱、旅程性質及其他不在匯入範圍的設定維持 APP 原值。系統管理欄位不由 Excel 寫入，必要識別資料由系統重新產生或依現有安全規則處理。
7. 只有整批雲端提交成功後才回報成功結果，包括實際更新的日期、天數與卡片數量。失敗時保留原資料，不得把部分成功回報為整批成功；若底層儲存無法保證整批提交，實作前必須先補足必要的原子性或安全補償設計。

## 7. 匯入初始化、錯誤處理與安全邊界

- **空白 Trip 初始化**：僅對新建、已儲存、恰為 1 天且整個 Trip 零卡片的目標匯入。匯入後建立 Excel 指定天數及每日卡片；出發日期與其他 Trip／模組資料均保留。既有非空白 Trip 不得使用此匯入功能。
- **不做逐張重複判斷**：匯入前已要求整個 Trip 零卡片，因此不需要進行既有卡片比對、合併或刪除。匯入只建立新卡片。
- **必要資料錯誤**：例如缺標題、無效旅程天數、卡片天數超出 Excel 旅程範圍、無效時間或不支援的類別，阻止匯入並指出工作表、列號與欄位。
- **地點資料處理**：`location`（Excel 原始地點文字）欄位必須存在，但值可空白；`location_address` 選填，只作當次地圖搜尋的輔助文字，不保存到卡片或資料庫。一般情況下，逐張卡片確認時，使用者必須選定地圖候選以保存 `placeId`，或明確選擇「不帶入地圖地點，保留原始地點欄位（可空白）」。若 `location` 與 `location_address` 兩欄都空白，允許直接跳過該筆地點確認，視為不帶入地圖地點；不設定 Place ID，也不觸發該地點的天氣或路線功能。除這項例外外，未選擇其中一項時不可完成地點確認流程；不可把其他未操作情況視為已選擇不帶入地圖地點。不得盲選第一筆候選。卡片顯示名稱保留 Excel 原始地點文字（包含空白），Google 地點名稱只在確認介面中供辨識。選擇或視為不帶入地圖地點的卡片仍可匯入，但不得被當成已確認 Google Place，也不得以該地點啟動天氣或路線功能；使用者可在匯入後再手動設定地圖地點。V1 不增加額外 Place Details 呼叫。
- **空白離開時間**：以抵達時間補入。
- **缺少描述或地點不明確**：依欄位規則允許或警告；不得自行補造地點事實。
- **資料修改範圍限制**：只更新 Trip 天數與每日卡片；出發日期、Trip 名稱、`guided`／`selfGuided` 旅程性質、帳本、其他資訊、Place ID、座標、天氣快取、照片／Storage 路徑、類別顏色、路線估算、移動方式及其他未列入匯入範圍的資料均保留原值。匯入前已要求整個 Trip 零卡片，因此不會刪除或取代舊卡片，也不涉及既有卡片照片資產清理。新卡片 ID 由 APP 依既有規則產生。
- **連線前置條件與完整性保護**：匯入功能只允許在線使用。使用者進入匯入流程前，先檢查瀏覽器網路狀態，再執行實際雲端讀取以確認服務可達及目標 Trip 可讀；`navigator.onLine` 不足以單獨證明雲端連線正常。預檢離線、請求失敗、逾時或結果不明時立即停止，不開放上傳後的匯入操作，也不允許本機暫存／離線匯入。最終確認提交前仍須再次檢查連線並讀取雲端最新資料；僅當最新資料恰為 1 天且整個 Trip 零卡片時才允許匯入。所有匯入提交都須使用剛讀取的 `updated_at` 做條件更新；提交前再次發生變更即中止，不得無條件重試，也不得沿用一般儲存流程的自動版本復原。只要連線中斷、雲端不可用或無法確認最新狀態，即停止，不得退回本機單獨寫入。只更新天數與每日卡片；出發日期和其他資料保留。只有整批雲端寫入成功後才能更新 UI／本機快取；結果不明時核對雲端，仍不明則提示待確認。
- **復原範圍（V1）**：不新增每次匯入的持久化快照子系統，不承諾匯入成功後一鍵還原；這是控制複雜度的明確取捨。既有每日卡片歷程與全應用程式快照是不同用途的復原機制，不可宣稱等同於單次匯入交易回滾。

## 8. 實作時的架構要求

目前每日行程儲存資料使用 daysData，卡片型別為 ItineraryItem；既有 UI 儲存入口會進行時間驗證、產生 ID、排序及可能的路線估算。因此未來匯入應設計專用的解析／驗證／整批取代流程，沿用合適的型別與儲存入口，但不得直接逐張模擬 UI 新增而意外觸發路線估算。

已核對：
- 每日卡片類別選項目前為「交通、住宿、景點、餐飲、自駕、其他」。
- 空白離開時間在現有儲存邏輯中會回退為抵達時間。
- 專案已有 ExcelJS 用於其他模組的 Excel 功能，但目前尚未找到每日行程卡片的 XLSX 匯入流程。

實作前待審查清單（僅技術核對，不重新開放產品決策）：
- 核對 `category` 中文顯示值與內部 `type` 的完整對照，以及 `typeColor` 的權威來源。
- 核對 `daysData` 的日期鍵值、卡片排序與 ID 正規化規則。
- 設計並驗證專用整批匯入提交流程：入口先做網路狀態與實際雲端讀取預檢；最終提交前再次確認連線、讀取最新雲端資格並使用 `updated_at` 條件更新；提交成功前不更新 UI／本機快取。驗證入口離線、雲端不可達、預覽期間斷線、資格不符、條件更新競態、提交逾時／連線中斷導致的結果不明，以及既有跨裝置刷新機制。
- 以測試確認匯入地點搜尋不會觸發天氣更新或交通估算；天氣資料不屬於 V1 匯入範圍。

## 9. 明確不在 V1 範圍內

- 匯入跟團／自駕旅程性質或專屬備註。
- 移動方式、交通估算、路線距離與時間。
- 不允許 Excel 直接指定或匯入 Google Place ID／座標；地點由使用者在匯入時逐張明確選擇地圖候選，或選擇不帶入地圖地點；原始地點文字可空白。天氣資料不在 V1 範圍內。
- 照片與其他資訊模組。
- 依卡片內容自動比對重複項目並個別保留／略過。
- 正式資料庫 schema／migration 變更。

## 10. 範本版本相容性與提交結果

- 範本「使用說明」工作表必須包含固定欄位 `template_version`，V1 標準範本版本值為 `1`。匯入端只接受明確支援的版本；缺少版本欄位、版本值空白、格式錯誤或不支援的版本一律拒絕匯入，不以欄位猜測版本，也不自動改寫使用者檔案。
- 匯入端仍須驗證工作表名稱、固定欄位標題、必要欄位與資料格式；即使 `template_version=1`，若必要欄位缺少、標題重複／改名或工作表結構不符，也要拒絕匯入並指出位置。
- 雲端提交若明確失敗且確認沒有提交，保留原資料且不清理照片。若請求逾時或連線中斷，無法判斷雲端是否已提交，須重新讀取雲端核對；若仍無法確認，顯示「匯入結果待確認」，不可宣稱成功、失敗或保證舊資料未變，也不得清理照片。此處不新增持久化快照或匯入交易子系統。
- 雲端提交成功後，立即以雲端回傳的權威資料更新本機快取與 UI，並讓其他設備透過現有 Trip workspace reconciliation 取得最新資料。目前查證到的 Trip 主資料刷新觸發點是啟動／重新協調、網路恢復、視窗 focus 與頁面回到 visible；目前未找到 `trips` 主資料表的 Realtime 訂閱，因此不能承諾其他設備在仍停留於前景時立即收到事件。**已選方案 A（2026-10-19）：V1 沿用既有刷新機制，不增加 `trips` Realtime 訂閱，也不另建同步子系統。** 匯入端在雲端提交成功後立即更新本機權威快取／UI；其他設備透過啟動／重新協調、網路恢復、視窗 focus、頁面回到 visible 等既有觸發點取得最新資料。其他設備若一直停留在前景，可能不會立即刷新；此為 V1 接受的同步時效限制，不列為本次阻擋項。成功訊息只在確認雲端資料已提交後顯示。匯入前整個 Trip 必須零卡片，因此本功能不處理舊卡片封面照片；不得因匯入流程而清理其他模組或未被匯入資料引用的照片資產。

| 使用者選擇不帶入地圖地點 | 仍匯入卡片其他欄位；保留 Excel 原始地點文字（允許空白）、不設定 Place ID、不觸發天氣／路線；使用者日後可手動設定地圖地點 |
| Excel `location` 欄位值空白 | 不視為驗證錯誤；若 `location_address` 有值，以地址作初始搜尋文字並依一般規則明確確認；若兩欄都空白，可直接跳過地點確認，視為不帶入地圖地點、不設定 Place ID、不觸發該地點天氣／路線 |
| 地圖搜尋結果不理想 | 先以 Excel `location` 搜尋；必要時由使用者自行加入 `location_address` 或調整關鍵字重搜。沿用現有 2–120 字元輸入驗證，不新增重搜次數限制，既有權限驗證與 Google API 配額照常生效 |
| 地點確認摘要 | 顯示「已選擇地圖地點」、「未確認地點」、「不設定地點」三項數量；「不設定地點」只計算 `location` 與 `location_address` 兩欄都空白、已自動略過確認的卡片，不併入未確認或主動選擇不帶入地圖地點的數量。並同時提供「回去確認全部地點」、「再次確認尚未完成的地點」、「完成並儲存」三個選項；回去確認全部時重新逐張顯示所有需要確認的地點，預先帶入上次候選但標示為尚未確認，使用者須明確再次選擇候選或選擇不帶入地圖地點；兩欄都空白的卡片不要求重新確認；再次確認只顯示未完成選擇的地點並在完成後自動返回摘要；任何需要確認的地點兩項都未選擇時不可儲存確認結果；完成並儲存後仍須經過最終覆蓋二次確認 |
| 使用者選定地圖地點 | 保存所選地點的 Place ID；卡片仍顯示 Excel 原始地點名稱 |
| 地點候選資訊顯示 | 沿用目前 PWA 地圖搜尋介面：顯示候選照片／佔位圖、地點名稱、可用的次要地址、照片署名及 Google Maps 查看連結；不額外呼叫 Place Details。若照片額度達上限或照片查詢失敗，沿用目前行為顯示圖釘佔位圖，地點候選仍可選擇 |
| 回去確認全部時的上次選擇 | 上次候選作為預先選取提示但未確認；使用者必須明確再次選擇該候選、改選其他候選或選擇不帶入地圖地點（原始文字可空白） |
| 天氣欄位未勾選／V1 匯入 | 不匯入天氣資料，不因匯入觸發天氣更新 |

## 12. V3.11.0 審查與定案工作流程

> 本節是 V3.11.0 Excel 匯出／匯入功能的唯一逐項審查與定案工作清單。後續討論、產品決策、技術核對、測試及實作均沿用本節，不另行建立平行流程或重複規劃。
>
> **執行原則：先確認前置定義，再確認後續設計；前一階段未定案或未通過，不得把依賴它的後續項目標記為可執行／通過。** 可以預先整理測試案例，但不得以尚未定案的規格作為測試通過依據。
>
> 本流程目前是規劃與審查階段，不代表已授權開始程式實作、正式資料庫變更或發布。逐項定案完成後，再由 Product Owner 明確決定進入實作。

### 12.1 階段與依賴關係

| 階段 | 工作內容 | 進入條件 | 完成條件／交付物 | 未完成時禁止進行 |
|---|---|---|---|---|
| 0. 產品契約定案 | Excel 範本版本、工作表名稱、欄位名稱、型別、必填／選填、允許值、欄位語意與匯出／匯入範圍 | 依本文已確認決策整理，不重新開放既有產品決策 | 形成唯一且完整的 Excel V1 欄位契約與標準範本定義；未明確項目逐一標示待確認 | 不得開始正式解析驗收，也不得自行猜測欄位語意 |
| 1. 程式資料契約核對 | Excel 欄位到 `ItineraryItem` 的映射、中文 category 到內部 `type`、`typeColor` 權威來源、`daysData` 日期鍵、排序、時間正規化、ID 產生規則 | 階段 0 完成 | 產生可供解析器、預覽、資料庫寫入及測試共用的明確資料映射表 | 不得宣稱解析結果正確，不得進行正式整批寫入 |
| 2. Excel 解析與資料驗證（IM01–IM03） | 有效範本解析、範本／工作表／標題錯誤、資料列／時間／天數／類別驗證 | 階段 0、1 完成 | 有效檔案輸出符合資料契約；錯誤檔案拒絕且無任何 Trip／本機權威資料變更；錯誤定位可辨識 | 不得進行 Supabase 整批寫入測試 |
| 3. 匯入資格與提交安全設計（IM04–IM06） | 目標 Trip 資格、最新雲端重讀、`updated_at` 條件更新、競態保護及整批寫入原子性／安全補償策略 | 階段 0、1 完成；階段 2 的有效解析輸出及差異預覽契約確認 | 匯入資格與寫入流程的狀態轉移、條件、失敗結果及防競態方式均明確；確認整批寫入安全性可被測試 | 不得執行正式資料庫競態／寫入驗收 |
| 4. 本機 Supabase 整批寫入與失敗處理（IM07–IM08） | 使用隔離的本機測試 Trip 驗證成功提交、明確失敗、逾時結果不明、雲端權威資料與本機快取更新順序、匯入前後資料差異 | 階段 2、3 均完成；已確認僅連線本機 Supabase，且具備本次專用測試資料及清理方案 | 整批提交成功才更新本機 UI／快取；失敗不部分更新；結果不明能重新核對；匯入範圍內外資料均符合規格 | 不得宣稱匯入資料完整性通過或進入整體驗收 |
| 5. 地點及既有功能相容性（IM09–IM10） | 地點選擇／不帶入／兩欄空白案例；確認不觸發天氣、路線、照片副作用；其他裝置沿用已定案 workspace reconciliation | 階段 0、1、2 完成；IM08 成功匯入路徑可供驗證 | 確認匯入只影響天數與每日卡片，其他模組及既有同步規則不被改動；不新增 Realtime／同步子系統 | 不得宣稱整體功能驗收完成 |
| 6. 最終審查與實作授權 | 彙整所有定案、測試證據、未解問題與不在 V1 範圍的項目 | 階段 0–5 完成，所有必測項目有結果 | 提交完整審查摘要，由 Product Owner 決定是否進入實作 | 未取得明確實作授權，不得開始程式實作或資料庫變更 |

### 12.2 固定測試清單（IM01–IM10）

| ID | 測試項目 | 測試目的與通過條件 | 前置依賴 |

| IM02 | 範本版本、工作表及欄位結構錯誤 | 缺少／空白／未知 `template_version`、工作表錯誤、標題缺少／改名／重複時拒絕；指出具體位置；資料完全不變 | 階段 0 |
| IM03 | 資料列、型別、時間、天數與類別驗證 | 必填欄位、時間格式、天數範圍、category 允許值等依定案契約驗證；錯誤檔案不得進入可提交狀態 | 階段 0、1 |

### 12.4 固定停止規則與執行紀錄

1. 每次只處理目前階段尚未定案的項目；完成後記錄決策與證據，再進入下一個依賴階段。
2. 前置定義不完整時，可以整理問題與測試案例，但不得自行補猜規格，也不得將依賴後續階段的測試標記為通過。
3. 若實作過程發現規格矛盾，先回到本文件相應階段修訂並取得 Product Owner 確認；不得私下改變已定案產品規則。
4. 本機 Supabase 測試只能使用明確標記、可識別及可清理的專用測試 Trip；不得 reset 資料庫、修改正式環境或碰觸既有資料。
5. 每項測試記錄：狀態（未開始／待定案／可測試／通過／失敗／阻塞）、前置條件、環境、操作、預期結果、實際結果及證據。未執行不得標記通過。
6. 本計畫不納入 V3.10.12 的 TC01–TC14 舊版同步驗收重測；除非 V3.11.0 實作實際修改相關程式路徑，且能指出具體受影響行為，才新增最小範圍的回歸項目。
7. 本文件的產品決策及範圍限制優先於測試便利性；不得為了通過測試而擴大 V1 範圍。
