# V3.10.0 使用紀錄重新評估草案

- 狀態：尚未定案，不得直接實作
- 前身：原 V3.9.0「使用者使用紀錄與開發者二次驗證」已確認設計
- 變更：2026-09-10 過度開發盤點後，原設計與預覽改列先前方案草案，不再代表目前核准範圍
- 排程：V3.9.0 卡片照片可行性確認之後再決定是否立案

## 1. 最小目標

- 僅在確實需要了解登入使用頻率時，保存已登入使用者的首次使用時間、最近使用時間及累計有效工作階段數。
- 同一工作階段 30 分鐘內的重新整理、重新連線、多分頁、重試與併發只計一次。
- 純離線開啟不記錄，紀錄失敗不得阻擋登入、行程載入或離線功能。
- 不收集 IP、User-Agent、裝置指紋、位置、語系、行程內容、頁面路徑或按鈕操作。

## 2. 目前建議的 MVP

- 只保存每位使用者的彙總資料，不保存逐次工作階段明細，因此不需要 180 天清除 Cron。
- 不建立 App 內「使用紀錄」頁，維護者直接透過 Supabase Dashboard 或受控管理查詢查看。
- 不新增 `system_developer` App 角色、QR Code、TOTP 設定、每次開頁驗證或五分鐘 `aal2` 視窗。
- 若未來出現多人維運或必須在 App 內查閱的需求，再重新設計獨立授權、RPC 與 MFA；不得直接沿用先前預覽當作已核准介面。

## 3. 立案前決策

- 說明彙總使用次數將解決的具體維運問題，以及 Supabase 既有 Auth／Log 能力為何不足。
- 確認保存 Email 是否必要；若 Auth user ID 足以完成目的，應避免重複保存 Email。
- 確認資料保存期限、刪除流程、查閱者與隱私告知方式。
- 重新查閱實作當時的 Supabase Auth、Database、MFA 與權限文件。
- 重新製作任何需要的介面模擬圖並取得 Product Owner 確認。

## 4. 先前方案狀態

- 逐次 180 天明細、Cron、永久摘要加明細雙表、App 查詢頁、獨立 `system_developer`、每次開頁 TOTP 與短效 `amr` 驗證，全部保留為歷史設計參考。
- 上述內容目前均為「尚未定案」，不得據此建立 migration、修改 UI、調整版本 metadata 或部署。
