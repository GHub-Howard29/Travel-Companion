# V3.9.22 排序後續時間重算與調整時間整合規格

> 狀態：2026-10-01 已完成 V3.9.22 第一版實作與本機驗證。排序與時間重算已分離，「預覽新時間」、人工延後到達時間、餐飲／其他「納入交通計算」與略過節點跨接均已落地；ESLint、TypeScript、V3.9.22 專屬 regression、完整 production build、PWA 與 browser-security 均通過。尚未 commit／push／部署 RC；RC 階段仍須完成 Android 實機功能驗收，以及 V3.9.21 → V3.9.22 的 PWA 更新補驗。

## 版本目標

V3.9.22 將「調整順序」與「後續時間重算」拆成兩個明確階段：排序可以獨立儲存；時間只在使用者要求預覽後計算，經人工審核與必要微調後，最後一次性套用。

核心原則：

- 排序不自動改時間。
- 預覽不直接寫入正式行程。
- 自動計算結果維持旅遊規劃用途的 30 分鐘刻度。
- 不建立「固定時間活動」等低使用率專屬功能。
- 人工判斷集中在預覽流程，避免過度開發。
- 優先沿用有效路線快取，只查詢真正需要的新相鄰路線。
- 缺資料或刻意留白的卡片不得無條件讓整日預覽失敗。

## 1. 調整順序與時間計算分離

### 排序模式

使用者進入「管理 → 調整順序」後：

- 可使用拖曳、上移／下移及既有鍵盤操作調整卡片順序。
- 排序過程不重新計算到達／離開時間。
- 排序過程不查 Google Routes。
- 原本交通方式偏好與時間資料保持不變。
- 「儲存順序」只寫入新的卡片順序。

排序模式提示文案應明確表示：

> 移動行程卡片只會改變排列順序，不會修改原本時間。儲存後可再預覽依新順序重新計算的時間。

### 排序完成 UI

儲存順序後顯示：

- 「順序已儲存」
- 「原本時間尚未變更，可先預覽依新順序計算的時間」
- 按鈕：
  - 完成
  - 預覽新時間

「預覽新時間」取代原本語意較模糊的「接著調整時間」。

允許排序已改、時間暫時看起來不合理；這是刻意的非破壞性中間狀態，不視為錯誤。

## 2. 新時間預覽

### 入口與寫入邊界

使用者按「預覽新時間」後才開始：

- 讀取有效路線快取。
- 判斷排序後新產生或失效的相鄰路線。
- 必要時查詢新的交通時間。
- 依已定案規則計算新的建議到達／離開時間。

預覽階段不修改正式 Trip。

只有最後按「套用新時間」才一次性寫入。

按「取消預覽」時：

- 保留已儲存的新排序。
- 放棄本次時間預覽與人工微調。
- 正式行程原時間保持不變。

### 預覽資訊

預覽區沿用目前「行程管理」區塊展開，不另開獨立頁面。

頂部應顯示：

- 新時間預覽
- 尚未修改正式行程
- 簡短說明可逐項接受或調整建議時間。

每個有變更的活動顯示：

- 活動名稱。
- 原時間。
- 建議新時間。
- 必要的前一段交通時間。
- 接受
- 調整到達時間

時間沒有變更的活動只顯示「時間不變」，不增加多餘按鈕。

路線顯示位於兩個有效交通節點之間，例如：

> 🚗 約 25 分鐘

一般使用者不顯示快取命中或 API 技術來源。

## 3. 半小時進位規則

維持原本半小時進位設計。

- 路線查詢與內部運算可保留分鐘精度。
- 正式建議到達／離開時間採 30 分鐘刻度。
- 自動計算結果一律向後進位到最近的整點或半點，不做四捨五入。
- 剛好位於整點或半點時保持不變。

例：

- 10:00 → 10:00
- 10:01 → 10:30
- 10:30 → 10:30
- 10:31 → 11:00

理由：旅遊行程不是精密交通時刻表，應保留可讀性與合理緩衝，且自動時間不可早於實際可到達時間。

## 4. 預覽階段人工審核與手動微調

V3.9.22 不新增永久性的「固定時間活動」功能，不新增 fixed-time 欄位、Checkbox、卡片標記或專屬 migration。

固定時間／想晚一點抵達等少數情境，統一由預覽階段人工處理。

### 逐項審核

有變更的活動提供：

- 接受
- 調整到達時間

「接受」只代表使用者接受該項預覽建議，仍不寫入正式 Trip。

不要求每張卡片都必須按「接受」才能套用；這只是長行程中的輕量審核標記。

### 手動調整到達時間

按「調整到達時間」後，在原位置展開簡單編輯：

- 系統建議到達時間。
- 使用者調整後的到達時間。
- 原本停留時間。
- 取消。
- 確認調整。

規則：

- 手動時間不得早於系統計算出的最早可到達時間。
- 可以往後延，例如想慢慢移動、休息或不急著趕路。
- 手動調整後保留原本停留時間。
- 從該活動之後重新計算後續建議時間。
- 若相鄰地點沒有改變，優先沿用已取得的路線時間，不重查 API。
- 最終仍須按「套用新時間」才正式寫入。

## 5. 卡片是否參與交通計算

### 基本原則

「有地點」不等於「一定參與交通計算」。

地點可以只作為：

- Map 定位。
- 導航參考。
- 地址顯示。
- 集合點或附近位置備註。

### 類型規則

只有以下兩類卡片顯示「納入交通計算」：

- 餐飲
- 其他

預設：

- 餐飲：預設勾選。
- 其他：預設不勾選。

其餘卡片類型：

- 不顯示此選項。
- 預設都納入交通計算。

### 被略過的卡片

若 B 卡片不納入交通計算：

A 景點 → B 備註／其他 → C 景點

交通節點鏈應壓縮為：

A 景點 → C 景點

B 仍保留在行程畫面，也可保留地點供 Map 使用，但：

- B 本身不成為交通節點。
- B 不應中斷 A → C 的路徑計算。
- 系統必須計算 A → C 的交通時間，才能正確推算 C 的到達時間。

若連續多張卡片都不參與交通計算，應跨過它們，尋找前後最近的有效交通節點。

### 後續新增／修改地點

若時間已經套用後，原本被略過的 B 後來：

- 補上地點，或
- 將「納入交通計算」改為勾選，

APP 不得自動改寫既有路線與時間。

應標記受影響區段需要重新確認，並提示：

- 稍後處理
- 預覽更新

若使用者選擇「預覽更新」，只重新處理受影響的相鄰路線與後續時間。

## 6. 缺資料、離線與失敗行為

### 可略過卡片不是錯誤

卡片沒有地點或沒有時間，不一定代表資料錯誤。

若本來就是備註／提醒／資訊用途，且未納入交通計算：

- 可直接略過交通節點。
- 不阻斷整日預覽。

若卡片看起來是實際活動，但資料不足而無法計算交通：

- 在預覽中就地提示。
- 允許使用者補地點。
- 若該類型支援「納入交通計算」選項，可取消勾選以略過。
- 不應只因一張刻意留白卡片就讓整日直接失敗。

### 路線與 API

- 有有效路線快取：直接使用。
- 無快取但有完整資料且在線：才查 Google Routes。
- 無網路：只能使用有效快取；缺快取區段無法自動計算。
- Google Routes 查詢失敗：不猜測交通時間。
- API 額度／限制已達：停止新查詢，既有快取仍可使用。
- 航班維持現有特殊處理，不建立機場到機場的地面路線。
- 跨午夜不在 V3.9.22 做跨日自動排程；若時間超過 24:00，提示使用者調整或移至下一天。

### 套用限制

若存在關鍵阻斷錯誤，不能部分套用一部分新時間。

只有整個可套用範圍的預覽結果完整且一致時，才允許「套用新時間」。

## 7. 既有「調整時間」功能

既有「調整時間」入口保留，不改名。

用途區分：

### 排序後預覽新時間

用途：使用者重新排列整天行程後，檢查並重算時間。

入口：

調整順序 → 儲存順序 → 預覽新時間

### 既有調整時間

用途：旅途中臨時延誤，或某活動晚離開，需要從某一點重新計算後續。

入口：

調整時間

兩個入口盡量共用同一套底層時間預覽能力：

- 30 分鐘向後進位。
- 路線快取。
- 卡片是否參與交通計算。
- 缺資料／可略過卡片規則。
- 預覽。
- 人工微調。
- 最後確認才寫入。
- API／離線／跨午夜停止規則。

V3.9.22 不開發兩套不同的時間重算引擎。

## 8. 預覽完整 UI 流程

完整流程：

1. 調整順序。
2. 調整卡片位置。
3. 儲存順序。
4. 顯示「順序已儲存，原時間尚未變更」。
5. 使用者選擇：
   - 完成
   - 預覽新時間
6. 進入新時間預覽。
7. 系統顯示原時間／新時間／必要路線資訊。
8. 有變更的活動可：
   - 接受
   - 調整到達時間
9. 不參與交通計算的卡片保持在畫面，但交通節點鏈跨過它。
10. 若人工延後某活動，重新計算該點之後的建議時間。
11. 底部提供：
   - 取消預覽
   - 套用新時間
12. 只有按「套用新時間」才一次性寫回正式 Trip。

## 不可過度開發邊界

V3.9.22 明確不做：

- 永久性的固定時間活動功能。
- fixed-time 欄位、專屬卡片狀態或固定時間 migration。
- 每張卡片都增加交通計算設定。
- 拖曳排序期間即時查 API。
- 自動猜測使用者刻意留白的卡片用途。
- 部分成功就部分寫入時間。
- 另做第二套時間重算引擎。
- 跨日自動排程。
- 為一般使用者顯示快取命中、API 來源等技術細節。

## 實作前仍需確認

產品規則已定案，但實作前仍需依現有資料模型確認：

- 「餐飲／其他」的現有 activity type 值與相容性。
- 「納入交通計算」狀態最小可行的持久化位置與同步方式。
- 既有舊 Trip／舊卡片的預設相容策略。
- 路線快取失效條件是否已足以支援排序後相鄰節點變化。
- 哪些既有測試需擴充，確保 Offline First、同步與權限不回歸。

以上屬實作技術確認，不重新開放已定案的產品流程，除非發現與現有資料契約有明確衝突。
